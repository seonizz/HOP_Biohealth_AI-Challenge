## 먼저 해결할 API 형식 호환성

현재 로컬 `server.py`의 요청 검사에 실제 94건을 대입하면 **60건 허용·34건 거부**다. 이 검사는 네트워크 호출·토큰화·모델 생성 없이 수행했으며 배포 서버의 코드 일치는 실행 전에 확인한다. 결과와 사례별 사유는 [31B 수집 전 API 형식 검사](평가양식/31B_수집전_API형식검사.json)에 있다.

거부 사례는 기존 검증용 상담 29건과 공개 합성 상담 5건이다. 원문 대화 중 `assistant`로 시작하는 이력과 연속 `user` 발화가 현재 API의 엄격한 교대 규칙과 맞지 않는다. 행동 분류 31건은 형식 검사에 모두 통과했다.

**전체 94건 수집의 선행 조건**은 원본 `messages`의 역할·순서·내용을 보존할 수 있는 수집 경로다. 담당 에이전트는 기존 tokenizer·backend가 해당 대화를 처리할 수 있는지 확인하고, 수집용 요청 검사에서 필요한 형식만 허용하도록 호환 경로를 설계·검증한다. 운영 API 변경·재배포가 필요한 경우 해당 API 담당 작업과 조율하며, 이 문서만으로 기존 서비스의 변경이나 재시작을 실행하지 않는다. 별도 수집 경로도 기존 모델과 체크포인트·템플릿·decoding 조건의 일치를 검증해야 한다.

빈 user 발화 삽입, 초기 assistant 삭제, 연속 user 병합, 역할 변경으로 기존 결과와 같다고 취급하지 않는다. API를 그대로 쓰는 60건 수집은 별도의 부분 실행으로만 표시한다. 그 경우 원래 배정 94건과 형식 미지원 34건을 보고하고 12B도 같은 60건으로 다시 집계한다. 전체 94건 수집 목표를 부분 실행 완료로 표시하지 않는다.

## 생성 전에 고정할 조건

| 항목 | 수집 조건 |
|---|---|
| 상담 출력 예약 | `max_tokens=512` |
| 행동 분류 출력 예약 | `max_tokens=32` |
| 비교용 전체 문맥 예산 | 실제 31B 입력 토큰 + 출력 예약 ≤ 4,096 |
| temperature | 0 |
| 사고 모드 | 현재 서버 구현의 `enable_thinking=False` |
| 동시성 | 1 |
| 시도 정책 | 과제·사례별 첫 시도 1회 |
| streaming | false |
| 입력 자르기 | 허용하지 않음 |

서버의 최대 문맥 설정과 이번 비교 예산은 별개다. 현재 로컬 `config.json`의 `max_context_tokens`는 131,072지만 실제 서버 설정은 수집 시점의 `/healthz`와 서버 설정 사본으로 확인한다. 이번 비교에서는 4,096 예산을 적용한다.

31B 서버에서 사용하는 실제 tokenizer·채팅 템플릿으로 **94건 모두를 생성 전에** 토큰화한다. `backend.py`와 같은 `apply_chat_template(messages, tokenize=False, add_generation_prompt=True, enable_thinking=False)`와 `tokenizer(prompt, add_special_tokens=False, truncation=False)` 경로를 사용한다. 모델을 추가로 로드하지 않고 기존 서버 환경의 tokenizer를 사용하며 파일 해시·템플릿 해시·코드·라이브러리 버전을 남긴다.

API에는 별도 토큰화 엔드포인트가 없으므로 기존 서버 환경에서 사전 계산을 수행한다. 12B 토큰 수를 31B 토큰 수로 복사하지 않는다. 사전 토큰화를 수행할 수 없으면 생성 전에 이 항목을 해결한다.

초과 사례가 있으면 `preflight.json`에 ID·과제·토큰 수·제외 사유를 고정한다. 원래 배정 94건과 실행 가능 N을 함께 보고하고, 비교표는 양쪽이 같은 조건을 만족하는 과제·사례 교집합으로 다시 집계한다. 12B의 기존 94건 전체 집계도 그대로 보존한다. 초과가 없으면 상담 63건·분류 31건을 모두 실행한다.

12B의 `seed=3407`, `top_k=64`, `top_p=0.95`, `repeat_penalty=1.0`은 12B 설정으로 보존한다. 현재 31B API는 `seed`, `top_k`, `repeat_penalty`, `think`, `num_ctx` 필드를 받지 않는다. 해당 값을 요청에 넣거나 31B에 적용됐다고 표시하지 않는다. 31B는 temperature 0일 때 서버의 결정적 생성 설정을 사용하며 실제 설정과 차이를 manifest에 기록한다.

## API 연결과 요청

기존 SSH 연결을 이용해 터널과 인증 키를 준비한다. 연결 명령은 추론용 연결만 준비한다.

```sh
python3 /Volumes/Dev/HOP_Projet/말씨/ai/trained_model_api/connect.py
```

수집 시작·종료에 인증된 `/healthz`와 `/v1/models` 응답을 저장한다. `status=ready`, 모델 ID, checkpoint step과 전체 체크포인트 SHA-256을 확인한다. 키는 HTTP 인증 헤더에서만 사용하고 문서·로그·ZIP에 넣지 않는다.

다음은 첫 실제 사례의 `messages`를 사용하는 호출 예다. 이 예제는 전체 수집기가 아니며, 호출하면 모델 생성 1건이 실행된다. 담당 에이전트는 아래 저장·검증 계약을 구현한 수집기로 전체 run을 실행한다.

```python
import json
import sys
from pathlib import Path

sys.path.insert(0, "/Volumes/Dev/HOP_Projet/말씨/ai")
from trained_model_api.client import chat

source = Path("/Volumes/Dev/HOP_Projet/말씨/ai/outputs/base12_local_20261009")
cases = [json.loads(line) for line in (source / "case_manifest.jsonl").read_text().splitlines()]
case = next(c for c in cases if c["task"] == "action")
input_record = json.loads((source / case["input_file"]).read_text())
result = chat(
    input_record["messages"],
    model="malssi-gemma4-31b-step100",
    max_tokens=32 if case["task"] == "action" else 512,
    temperature=0,
    timeout=1800,
)
print(json.dumps(result, ensure_ascii=False, indent=2))
```

HTTP 429는 별도 오류 시도로 남기고 본 실행을 중지해 API가 한가한 시점에 이어간다. timeout·연결 단절은 서버가 이미 생성했을 수 있으므로 자동 재요청하지 않는다. 요청 ID·서버 로그를 대조해 상태를 확정하며, 확인할 수 없으면 `unknown_completion`으로 남긴다. 재시도 run은 첫 시도 결과와 분리한다.

## 자동 집계와 검증

상담 정상 종료는 HTTP 성공, 예상 모델·지문, `finish_reason=stop`, 비어 있지 않은 답변, 사전 입력 토큰 수와 실측 일치로 확인한다. 분류는 이 조건과 함께 앞뒤 공백만 제거한 답변이 `ASK_CFI`, `CLARIFY`, `SUPPORT`, `SUPPORT_LIMITED`, `SAFETY_SUPPORT`, `END` 중 하나와 정확히 일치해야 형식 유효로 센다.

| 지표 | 계산과 보고 |
|---|---|
| 상담 정상 종료율 | 정상 종료 상담 수 ÷ 사전 실행 가능 상담 N × 100 |
| 분류 형식 유효율 | 정상 종료한 단일 허용 코드 수 ÷ 사전 실행 가능 분류 N × 100 |
| 종료와 실패 상태 | stop·length·HTTP 오류·timeout·지문 오류·형식 오류·미실행 각각의 건수 |
| 실제 토큰 | 과제·split별 입력과 출력 합계·최소·최대, 관측 가능한 건수와 미측정 건수 |
| 행동 코드 분포 | 허용 코드 6개 각각의 관측 건수, 0건 포함 |
| 12B와의 차이 | 동일 과제·case ID·입력·출력 예산의 교집합에서 비율 차이, 단위 %p |

오류·길이 소진·미실행은 사전 실행 가능 N에 남긴다. 결과를 본 뒤 분모를 줄이지 않는다. 시간·처리속도·메모리는 환경이 다른 원시 관측으로만 남기며 기존 발표용 CSV의 지표에 추가하지 않는다. 형식·종료·토큰 지표를 상담 품질이나 안전성 점수로 표현하지 않는다. 12B와 31B의 차이에는 모델 크기·배포 방식·학습 상태가 함께 반영되므로 순수 학습 효과로 해석하지 않는다.

31B용 검증기는 저장 파일만 읽고 집계값을 다시 계산한다. 사례-입력-요청-응답 해시, 첫 시도 고유성, 과제별 분모, 토큰 합계, 종료 상태, 허용 코드, 모델 지문과 누락을 검사한다. 12B용 `verify_measurements.py`는 Ollama 응답 형식·12B blob을 검사하므로 31B에 그대로 적용하지 않는다. 파일 변조·중복·누락·잘못된 모델 지문을 거부하는 검사도 수행한다.

정상 전체 수집이면 94건의 입력·요청·원시 응답 연결을 확인한다. 오류나 사전 제외가 있으면 이를 포함한 상태 분해표와 실제 확인 건수를 보고한다. API 오류는 기록될 수 있지만 해시·사례 연결·집계 불일치는 검증 실패다. `COLLECTION_COMPLETE.json`에는 배정·제외·시도·응답·미실행 건수와 완료 상태를 명시한다.

## Excel 데이터 시트 자동 생성

준비된 [데이터 시트 양식](outputs/ft31_datasheet_setup_20261010/31B_데이터시트_수집양식.xlsx)에는 12B의 실제 기록 94건과 답변 원문이 들어 있다. 31B 측정칸은 아직 빈칸이다. 실행 API의 형식 지원 여부는 별도 열이며 31B 생성 결과로 집계하지 않는다.

| 시트 | 필수 내용 |
|---|---|
| `요약` | 원래 배정·사전 실행 가능·시도·유효·출력 소진 건수, 입력·생성 토큰 합계와 관측 건수, 동일 사례 상담·분류 비율과 차이 `%p`, 행동 코드별 관측 건수 |
| `사례별결과` | 과제·사례 ID·split·원천 그룹, 12B와 31B의 상태·입력 토큰·생성 토큰·행동 코드, 31B 사전 실행 가능·종료 사유, 현재 API 형식 지원, 입력 해시, 양쪽 답변 원문, 31B 원시 응답 파일·체크포인트 해시·시도 기록 여부 |

사례별 시트는 **원래 94건을 한 행씩 모두 보존**한다. 제외·미실행·오류의 행을 삭제하지 않는다. FT31의 빈 측정값은 Excel에서도 빈칸으로 두며 0으로 채우지 않는다. 정상 실행에서 실제 관측한 0은 숫자 0으로 보존한다. 비율 차이는 같은 사례의 사전 분모가 확정되고 해당 과제의 첫 시도 기록이 전부 있을 때 표시한다. 수집 도중에는 관측 건수와 관측 토큰 합계를 표시하고 최종 비율은 비워 둔다.

`preflight.json`은 다음 구조로 94건 전체를 포함한다. 아래 값은 **형식 설명용 예시**이며 실제 토큰 수와 사유로 채운다.

```json
{
  "cases": [
    {
      "task": "response",
      "case_id": "DEV001",
      "eligible": true,
      "input_tokens_preflight": 100,
      "exclusion_reason": null
    }
  ]
}
```

`run_manifest.json`에는 `run_id`, `condition: "FT31_STEP100"`, 위 `checkpoint_sha256`이 있어야 한다. 수집 완료 후 다음 명령으로 `.xlsx`를 자동 생성한다. 경로 예시의 `<실제수집폴더>`와 `<결과폴더>`를 해당 run의 절대경로로 바꾼다.

```sh
/Users/chihun/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node \
  /Volumes/Dev/HOP_Projet/말씨/presentation/outputs/ft31_datasheet_setup_20261010/build_datasheet.mjs \
  --ft31 '<실제수집폴더>' \
  --output '<결과폴더>/FT31_STEP100_데이터시트.xlsx'
```

[데이터 시트 생성기](outputs/ft31_datasheet_setup_20261010/build_datasheet.mjs)는 기존 12B 원자료와 새 31B 원장을 `task + case_id`로 결합한다. 입력·체크포인트·원시 응답·답변 해시, 실제 응답의 모델 지문·토큰·종료·행동 코드를 확인한 뒤 시트를 만든다. 다른 컴퓨터에서 실행하면 번들 Node와 `@oai/artifact-tool` 경로를 그 환경에 맞춘다.

완성 시트의 요약과 원자료 집계값을 대조하고 수식 오류·미측정 값의 0 치환·분모 불일치를 검사한다. `datasheet_verification.json`과 `datasheet_formula_scan.json`을 원자료 검증 결과와 함께 보존한다. 생성기의 검증은 데이터 시트에 반영한 기록을 확인하며 전체 원자료 검증기를 대신하지 않는다.

## 전달 자료와 완료 기준

원자료와 검증된 발표 산출물을 모두 보존한다. 공개 산출물은 `HOP_pptdata/outputs/presentation_collection_FT31_STEP100_<UTC수집시각>/`에 새로 저장한다. 12B 파일과 기존 완료된 FT31을 위한 지침은 덮어쓰지 않는다.

ZIP에는 **실제 수집값이 채워진 `FT31_STEP100_데이터시트.xlsx`**, 결과 요약, CSV·JSON, 공개 합성 실제 답변, 생성 원장, 수집·검증·시트 생성 코드, 실행 조건, 검증 결과, 파일 SHA-256 목록과 먼저읽기를 넣는다. 기존 검증용 상담 입력·답변과 이를 담은 데이터 시트는 내부 전달 자료로 표시한다. 공개 발표에는 공개 합성 자료만 별도로 내보낸다. 인증 키·가중치·optimizer 상태는 포함하지 않는다.

완료 보고에는 모델과 체크포인트, 배정과 실행 건수, 정상 종료·형식 유효·실패 건수, 검증 결과, **Excel 데이터 시트 경로**와 ZIP 경로를 적는다. `.md` 보고서나 CSV만으로 데이터 시트 생성 완료를 표시하지 않는다. API 접속이나 토큰화가 불가능하면 준비된 파일과 부족한 조건을 보고하고 결과값은 미측정으로 남긴다. 빈 양식은 실제 31B 결과 시트와 구분한다.

## 수집 담당 에이전트에게 전달할 요청

> 이 문서를 기준으로 Gemma 4 31B의 step100 체크포인트에서 12B와 같은 데이터를 수집하고 **실제 값이 채워진 Excel 데이터 시트**를 만들어라. 먼저 현재 API가 원본 34건을 거부하는 형식 문제를 확인하고 역할·순서·내용을 보존하는 호환 수집 경로를 마련하라. 기존 12B 입력 94건을 고정하고 실제 31B tokenizer로 사전 예산을 확인한 후, 새 run과 별도 수집기를 구현해 동시성 1로 호출하라. 상담 512·분류 32토큰, temperature 0, 서버의 사고 비활성 조건을 사용하라. 요청·원시 응답·답변·해시·종료·실제 토큰·오류를 저장하고 검증 가능한 JSON·CSV·답변 문서를 만들어라. 제공된 build_datasheet.mjs로 요약과 사례별 94행의 FT31_STEP100_데이터시트.xlsx를 생성·검증하고 ZIP에 포함하라. 미측정 값은 빈칸으로 보존하고 Excel이 없는 상태를 완료로 표시하지 말라. 모델은 FT31_STEP100으로 표기하라. 기존 학습은 재개하지 말고 모델 변경·API 재배포·기존 기록 덮어쓰기를 하지 말라. 호환성 해결에 운영 API 변경이 필요하면 API 담당 작업과 조율하고, 해결 전 부분 결과를 전체 완료로 표시하지 말라. 접속·토큰화·모델 식별을 확인할 수 없으면 해당 조건을 해결하거나 구체적인 차단 원인을 보고하라.
