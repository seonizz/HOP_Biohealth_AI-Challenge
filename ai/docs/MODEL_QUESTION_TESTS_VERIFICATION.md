# AI 테스트 도구의 실제 워크플로우 연결 검증

검증일: 2026-11-01(KST). 테스트 도구는 실제 앱 모듈을 import해 실행하며, 모델 호출 수·단계 순서·병렬 스케줄을 자체 구현하지 않는다.

## 실사용 코드 재검토와 수정

후속 코드 검토에서 아래 문제를 확인하고 수정했다. 입력·진행 상태 문제는 수정 전 실패하는 회귀 검사를 먼저 추가해 재현했다.

| 문제 | 수정·검증 |
|---|---|
| workflow에서 문항 ID 오타·중복 답변을 미사용 입력으로 무시하고 기대값 통과 가능 | 실제 질문 은행과 앱의 후속·보충·명확화 질문에서 허용 조합을 구성하고, 알 수 없는 조합과 중복을 요청 전에 거부. 정상 모델 생략은 유지 |
| 두 번째 턴이나 최종 생성 실패 시 완료 답변 수가 0, workflow 정보 누락 | 각 턴 시작·적용 후·최종 생성 전에 마지막 적용 상태를 유지. 실패 턴은 `applied:false`, 이전 승인 결과는 `result_scope:last_applied_turn`으로 표시 |
| 에이전트가 보고서 갱신 중 잘린 JSON을 읽거나, 보조 파일 저장 실패 전에 완료 JSON이 노출될 수 있음 | 파일별 원자 교체, 기준 JSON을 마지막에 게시. 파일 저장 실패를 주입해 이전 JSON 보존·임시 파일 정리를 확인 |
| 취소 직후 반환된 스냅샷 결과가 상태 반영 완료로 표시될 수 있음 | 모델 반환 직후 취소 확인을 상태 반영보다 먼저 수행 |
| `--describe`의 validate 명령은 snapshot인데 run 명령은 workflow | 검증·실행 모드를 일치시키고 snapshot 검증 명령을 별도로 제공 |

수정 후 관련 검사 **56개 통과, 실패·건너뜀 0개**. `65f9705`의 앱 코드에 이번 수정만 적용한 임시 검증본에서도 동일하게 통과했다. 새 CLI 통합 검사는 실제 `ModelGateway`의 JSON-schema 프로토콜을 임시 loopback HTTP 서버에 연결해 **답변 2개 → 이전 기억의 실제 요청 전송 → 최종 가이드 → 앱 상태 반영 → 보고서 → 종료 코드 0**까지 확인한다. 모의 HTTP 응답을 사용한 코드 경로 검증이며, 아래 실제 로컬 모델 검증과 구분한다.

지정된 LAN Ollama 검토 API는 연결 오류로 추가 검토 결과를 제공하지 못했다. 판단 근거는 직접 코드 대조, 오류 재현과 회귀·통합 검사다. 이번 후속 검토에서 장시간 실제 모델 생성을 다시 실행하거나, 이전의 최종 카드 생성 미완료를 성공으로 바꾸지는 않았다.

## 확인한 차이와 보완

초기 도구의 `final/state`는 `createTestIntake`로 완료된 입력 스냅샷을 만들었다. 실제 모델 생성 코드는 사용했지만, 답변별 기억 갱신과 다음 질문 선택은 재현하지 않았다. 특히 완료 스냅샷에는 활성 질문 후보가 없어 `state`를 다음 질문 선택 검증으로 설명하면 부정확했다.

이번 보완에서 `workflow` 모드를 추가하고 아래 앱 함수를 그대로 사용했다.

| 경계 | 실제 서비스와 공유하는 코드 |
|---|---|
| 대화 시작·현재 질문 | `createIntake`, `currentView` |
| 답변 반영 대기·문맥 | `prepareModelAnswer`, `buildContext` |
| 상태·질문·독립 검토 | `configuredModelGateway`가 만든 `gateway.updateState` |
| 승인된 기억·질문 선택 반영 | `completeModelAnswer` |
| 기억을 전달한 최종 생성 | `gateway.respond` |
| 최종 상태 반영 검증 | `applyModelUpdate` |

모델이 질문을 생략하면 해당 답변을 강제로 제출하지 않고 미사용 입력으로 남긴다. 다음 질문에 대한 명시적인 답변이 없으면 `awaiting_input`으로 멈춘다. 후속 답변도 별도 입력이 있어야 한다. 앱과 같은 재시도 설정을 사용하고, 모델이 전달한 카드 이벤트도 보존한다.

실제 HTTP 호출은 writer/reviewer의 기존 전송 함수를 감싸 관측한다. 새 진단 이벤트나 기존 검증기의 재시도 한도를 넘는 기록이 생겨도 HTTP 집계와 생성 결과 검사는 계속 동작한다. 응답 헤더 전 동시 요청 수를 측정하며, 스트림 전체 또는 물리 GPU 동시 추론 수로 해석하지 않는다.

## 실제 Mac 모델 실행

Mac의 `ollama` 프로세스가 `127.0.0.1:11434`를 사용하고 `/api/tags`에 `gemma4:12b`가 등록된 것을 확인했다. `app/.env`의 실제 설정은 `relationship_agent`, `combined_blocks`, 독립 reviewer, JSON 스트리밍, 기본 재시도 활성이다. GPU 서버는 사용하지 않았다. 모델 입력은 직접 작성한 합성 사례만 사용했다.

최종 스냅샷 검증에서는 다음 실제 실행을 관측했다.

- HTTP 요청 7회: 모델 생성 5회, 설정 조회 2회.
- `state_observations` 성공 → `relationship_memory`의 `agent_memory_name_only` 검증 거절 → 관계 기억 재생성 성공 → `state_review` 성공 → `relationship_analysis` 진행.
- 전체 300,000ms 제한에서 취소되어 `CASE_TIMEOUT`, 종료 코드 1을 기록했다. 카드 생성은 완료되지 않았다.
- 취소 후 관측 중인 HTTP 요청은 0개였고, 최종 JSON·CSV·요약 파일이 생성됐다. 기대값 통과로 집계하지 않았다.

이 실행은 호출 경로와 실제 검증·재시도가 연결됨을 확인하지만 **최종 카드 생성 성공의 증거는 아니다**. 모델의 실패를 테스트 코드에서 숨기거나 성공으로 바꾸지 않았다. 시간은 실행 경계를 위한 기록이며 대회 점수에 반영하지 않는다.

로컬 원본 보고서: `ai/outputs/model-tests/private/run-3C4VN0/report.json`. 원문 포함 보고서는 Git에서 제외한다. 라이브 실행은 당시 Mac 작업 폴더의 앱 소스를 사용했으며 앱 소스 해시는 보고서의 `identity.source`에 남겼다. 미커밋 앱 변경을 원격에 함께 올리지 않았다.

workflow의 첫 180,000ms 검증에서는 실제 질문 블록과 환자 상태 블록이 겹쳐 요청됐고, 두 블록 및 이름 블록이 생성에 성공했다. 관계 기억 블록 진행 중 제한 시간으로 취소됐다. HTTP 5회 중 생성 4회·설정 조회 1회, 응답 헤더 전 최대 미완료 요청 2개, 취소 후 미완료 요청 0개였다. 보고서는 `ai/outputs/model-tests/private/run-o7IkKO/report.json`에 있다. 이 중단 실행을 승인된 첫 턴 또는 전체 workflow 성공으로 계산하지 않는다.

기본 제한 시간인 600,000ms로 다시 실행한 workflow는 **첫 턴 작성·독립 검토·앱 상태 반영을 완료**했다.

- 실제 앱의 `latest_answer`는 `name`, 활성 다음 질문 후보는 22개였다. 최초 스냅샷 모드의 후보 0개와 구분된다.
- 환자 상태·질문·이름·관계 기억 작성과 `turn_review`, `safety_review`가 모두 성공했고 `state_agent.reviewed:true`, `turns[0].applied:true`를 확인했다.
- 모델 생성 6회, 설정 조회 3회로 HTTP 총 9회가 관측됐다. 설정 조회의 404는 앱의 조회 경로에서 관측한 응답이며, 생성 6회는 모두 정상 완료됐다. 응답 헤더 전 최대 미완료 요청은 2개였다. 이것은 이번 사례의 관측값이며 고정 합격 기준이 아니다.
- 앱이 반환한 다음 질문은 `want`였다. 해당 답변을 제공하지 않았으므로 `awaiting_input`, 종료 코드 3, `errors:0`으로 종료했다. 답변을 만들어 넣거나 미완료 대화를 기대값 통과로 계산하지 않았다.
- 실행 시간은 442,742ms였고 종료 후 미완료 HTTP 요청은 0개였다. 보고서의 토큰 수는 제공·검증할 수 없어 `null`로 유지했다.

이 완료된 첫 턴의 원본은 `ai/outputs/model-tests/private/run-8FZJI9/report.json`이다. 세 라이브 실행의 앱 소스 SHA-256은 모두 `c3c5e0c978a60ce1c55c354ad1af19a865a6ef0005942ec1568a81ace72e7f5f`이며 검증 종료 시 작업 폴더와 같음을 확인했다. **첫 턴 승인은 확인했지만 전체 문답 및 최종 카드까지 완료한 라이브 성공 사례는 이번 검증에 없다.**

## 적용 범위

이 도구로 실제 앱의 메모리 내 문답·AI 생성·검토·상태 적용을 검사할 수 있다. DB에서 바꾼 질문 은행은 `--questions`로 명시해야 한다. HTTP 인증·CSRF·revision 충돌·DB 저장·기록 조회·화면 렌더링까지 확인하는 전체 서비스 E2E 테스트는 별도다. 이번 검증만으로 실제 모델의 모든 입력에서 최종 생성 성공이나 서비스 운영 준비 완료를 선언하지 않는다.
