## 확인된 현상과 범위

엄격한 스키마 채점 기준이다. 잘못된 형식·누락·출력 제한은 실패로 유지한다. 한 쌍은 같은 사건의 정상 초안과 필드 하나가 틀린 초안이며, 두 판단이 모두 맞아야 쌍 성공이다.

| 평가 | 정상 승인 전→후 | 오류 거절 전→후 | 쌍 성공 전→후 |
|---|---:|---:|---:|
| 12B 사건 | 0/80 → 80/80 | 66/80 → 0/80 | 0/80 → 0/80 |
| 31B 사건 | 28/72 → 72/72 | 49/72 → 36/72 | 14/72 → 36/72 |

12B의 **사건 검토 160/160개가 승인으로 붕괴**했다. 답변·기억 검토까지 모두 승인한 것은 아니다. 앱 개발 평가에서는 답변 오류 거절이 36/80→73/80, 기억 오류 거절이 9/80→80/80으로 개선됐지만, 정상 오거절은 각각 1→4개, 0→1개로 늘었다. 앱 쌍 성공은 44/160→148/160이며 기존 모델 대비 정상 판단 퇴행 때문에 전체 통과로 판단하지 않는다.

사건 `time` 정확도는 12B 397/704→405/704, 31B 613/666→626/666으로 일부 개선됐다. 이 수치는 검토의 오류 거절 실패를 상쇄하지 않는다. 원천을 공유하는 형식·오류 변형은 독립 표본이 아니다.

## 실제 자료와 설정에서 확인한 원인 후보

### 1. 행 수는 균형이지만 판정 토큰의 손실 계수는 불균형

두 모델의 기존 사건 학습은 정상 240행, 오류 240행으로 1:1이다. 각 모델의 사건 원천은 120개다. 따라서 승인 사례가 행 수로 더 많아서 생긴 문제는 아니다.

실제 12B `training_core.py`의 `target_ce`와 31B 실행이 고정한 `reference_train_cards_31b.py`는 정답 토큰 CE를 **행마다 토큰 수로 나눈 뒤 행을 평균**한다. 정상 사건 답변은 모두 같은 10토큰이고, 오류 답변은 평균 12B 41.32토큰, 31B 39.82토큰이다. 승인 여부의 불리언은 양쪽 모두 한 토큰이므로, 그 토큰의 계수는 행마다 `1 / 정답 토큰 수`가 된다.

실제 토큰을 다시 계산한 승인/거절 판정 토큰의 **누적 CE 계수 비율**:

| 학습 범위 | 기존 승인:거절 계수 |
|---|---:|
| 12B 사건 검토 | 3.9907:1 |
| 31B 사건 검토 | 3.8237:1 |
| 12B 답변 검토 | 4.3956:1 |
| 12B 기억 검토 | 1.5265:1 |

정상 사건 정답은 고정 문자열 하나이고 오류 정답은 내용이 다양하다. 짧은 승인 응답을 반복하는 학습 신호와 위 계수 비대칭이 함께 존재한다. **계수 비대칭은 확인된 사실이지만, 실제 파라미터 기울기 크기나 붕괴의 단독 원인이 증명된 것은 아니다.** 답변·기억 과제의 결과가 서로 다른 점도 단일 원인 단정을 막는다.

근거: `runtime/approval-bias-audit-20261113/audit.json`, `notes.json`, `compute_audit.py`. 기존 3,496행을 재토큰화했고, 31B 기준 코드 SHA-256을 실제 실행 바인딩과 대조했다.

### 2. 12B는 사건 학습 뒤 앱 학습만 계속했다

실행된 12B는 사건 720행/90업데이트 뒤 앱 1,280행/160업데이트를 순서대로 학습했다. 뒤의 160업데이트에는 사건 복습이 없다. 섞기는 각 단계 내부에서만 수행했다. 후반 과제 간섭·망각은 가능한 설명이지만, 단계 경계의 생성 평가가 없어 붕괴가 정확히 언제 시작됐는지는 아직 알 수 없다.

두 실행 모두 학습률 `1e-5`, 누적 8행, 1 epoch, AdamW·weight decay 0.01이었다. 31B는 step4723에서 90업데이트했다. 학습률이 높아서 생겼다고 단정할 비교 실험은 없다. 이번에는 학습률이나 epoch를 임의로 바꾸지 않았다.

12B 실제 실행은 NF4 double quant/BF16, LoRA rank8/alpha16/dropout0이다. 로컬 `plan.json`의 오래된 NVFP4 설명보다 `gpu_worker.py`의 검증과 실제 로더·실행 결과를 우선했다. 전후 모델은 같은 NF4 기반이므로 이 오래된 설명을 전후 성능 변화의 원인으로 취급하지 않는다.

### 3. `time`의 오류 종류와 평가 단위가 충분하지 않았다

`time`은 날짜 내용이 아니라 **해당 person/attribute의 최신 사건 순서값**이다. 기존 31B의 잘못된 time 40행은 모두 다른 실제 사건의 순서값으로 치환한 사례였다. 날짜 내용·사람 ID·`none`을 time으로 복사하는 오류와 같은 값이 다시 나온 뒤 최신 순서만 달라지는 경우를 직접 포괄하지 못했다.

12B는 이미 위 네 가지를 각각 30행씩 포함했다. 따라서 12B에 time 사례가 없었다고 설명할 수 없다. 다만 같은 원천은 한 종류의 오류만 배정받았고, 긴 상태 JSON에서 time은 다른 토큰과 같은 단위의 손실을 받았다. 새 설계는 같은 원천에서 모든 오류 유형을 비교하고 time 필드 손실을 분리한다. 이 설계 선택의 실제 모델 효과는 후속 실험 대상이다.

### 4. 손실 감소·부분 개선과 전체 성공이 분리되지 않은 요약

31B 검증 CE는 약 0.16577→0.03188로 감소했지만 오류 거절은 49/72→36/72로 나빠졌다. CE만으로 검토 판단이 개선됐다고 볼 수 없다.

기존 평가의 절대 기준과 퇴행 검사는 이미 두 후보를 탈락시켰다. 문제는 12B 보고서 첫머리가 정상 거절 감소·time 감소를 각각 ‘확인’으로 보여 전체 성공처럼 읽힐 수 있다는 점이다. 기존 증거는 보존하고, 새 평가의 최상위 판정은 양쪽 판단·근거·time·기존 대비 퇴행을 함께 반영한다.

## 반영한 자료와 목적함수 설계

생성 코드: `ai/scripts/review_bias_curriculum.py`.
실제 자료: `training_data/paired_review_objective_20261113_v1/` — Git 제외 경로다.

- 기존 두 사건 자료의 모든 분할과 구조 중복을 제거한 새 원천을 train60/validation20/test20으로 분리했다. 원천마다 두 표현 형식 × 9종 오류 × 상태/정상/오류로 54행을 만든다. 전체 사건 자료는 5,400행이다.
- 9종은 time의 날짜값·사람·none·동일값의 과거 순서 4종, person/attribute/value/negated/certainty 5종이다. 정상·오류 쌍은 사건 문맥과 초안 순서가 같고 필드 하나만 다르다. pair ID는 모델 입력에 넣지 않는다.
- 12B 학습 4,520행·검증 1,400행, 31B 학습 3,240행·검증 1,080행을 생성했다. 12B 앱 원천과 기존 train/validation 분할은 보존했다. 사건 test 1,080행은 학습 토큰 파일과 일정에 포함하지 않는다.
- 승인 불리언에 행 손실의 0.5, 나머지 정답 토큰에 합계 0.5를 배정한 float32 가중치 파일을 만들었다. 정상/오류 판정 토큰 계수는 모든 검토 과제에서 정확히 1:1이다. 메모리의 중첩 `state.approved`도 확인한다.
- 상태 추출은 모든 time 숫자 필드에 합계 0.5를 균등 분배하고 나머지 정답에 0.5를 준다. 프롬프트 손실은 0이다. 0.5는 사전 설계값이며 최적값이 검증된 것은 아니다.
- 12B는 사건·답변·기억 과제를 전체 과정에 섞는다. 정상·오류 쌍을 같은 8행 누적 창에 배치하고, 각 행을 한 번씩 사용한다. 565개 창 모두 승인·거절 균형이며 마지막 구간에도 사건 과제가 남는다. 31B도 쌍을 같은 창에 둔다.
- 두 실제 토크나이저로 10,240개 학습·검증 행의 원문 왕복, 생성 접두부, 타깃 경계, 마스킹, 의미 토큰 위치와 저장된 가중치를 검증한다. 인덱스 ID와 실제 행도 연결한다. 최장 입력은 12B 8,675토큰, 31B 2,369토큰이며 잘라내기 없이 인코딩했다.

행 수를 늘린 것이 독립 자료의 다양성 증가를 뜻하지는 않는다. 새 사건 train은 60개 원천이며 기존 120개보다 적다. 이번 자료는 동일 원천의 대조 범위를 넓힌 연구용 수정본이다. 다양한 원천과 자연어 실제 계약으로 일반화되는지는 별도 검증이 필요하다. 다중 오류·누락/추가 사실 전체를 포괄하는 자료라고 주장하지 않는다.

## 반영한 평가 설계

`ai/scripts/review_pair_evaluation.py`는 기존 엄격한 사건·앱 scorer를 그대로 호출하고 다음을 추가한다.

- 정상 승인과 오류 거절, 쌍의 두 결정, 오류 위치·actual·expected 근거까지 함께 평가한다.
- 각 오류 필드와 세부 challenge를 별도 채점한다. time 네 종류 중 하나의 실패를 평균으로 가릴 수 없다.
- ‘모두 승인’, ‘모두 거절’ 및 쌍 성공률 0%를 드러낸다. 쌍·근거 지표는 95% 이상이어야 하며 기존 스키마·사실·time 기준을 유지한다.
- 기준 모델과 동일한 입력·정답 집단인지 해시로 확인한다. 정상 거절/time 일부가 좋아져도 핵심 지표 하나가 퇴행하면 `regression_detected`이다.
- 원천 수와 원천별 평균을 별도 표시한다. 원천을 공유하는 변형 수를 독립 표본 수로 해석하지 않는다.
- 과거 노출된 test 재채점은 `diagnostic`으로 표시한다. 새 test는 후보 선택에 사용하지 않고, 선택은 validation에서 한다. 앱 validation은 재사용 개발 평가이며 새로운 독립 앱 test가 아니다.
- 모든 통과 판정은 연구 기준이다. 자동 배포 승인으로 바뀌지 않는다.

## 검증 결과와 다음 실행 경계

의미 정답은 생성 함수와 별도의 역방향 사건 탐색·튜플 차집합 oracle로 5,400행 전체를 대조했다. 저장된 토큰/가중치도 실제 원문에서 재계산했다. 해시만 다시 맞춘 결정 토큰 위치 변조, 잘못된 행 ID, NaN/음수 가중치, 손상 토큰, 과대 누적 창, 앱 전용 후반 구간은 회귀 테스트에서 거부한다.

새 validation에서 정답 출력은 사건 360/360쌍·앱 160/160쌍으로 통과한다. 모두 승인/거절, time 손상, 앱 근거 위조 출력은 탈락한다. 이는 **평가 코드의 대조군 검증**이며 모델 생성 결과가 아니다. 과거 실제 출력 재채점에서도 두 모델의 사건 후보를 퇴행으로 판정했다.

실행 증거: `runtime/review-bias-repair-20261113/VERIFICATION.json`, `verify-final.log`, `tests.log`, `eval_checks/SUMMARY.json`, `eval_checks/SOURCE_INTEGRITY.json`.

`COURSE_PROPOSAL.json`은 `design_ready=true`, **`training_ready=false`, `execution_ready=false`, `training_started=false`**다. 기존 학습기는 새 토큰 가중치를 읽지 않으므로 이번 자료를 기존 명령에 바로 넣으면 수정한 목적함수가 적용되지 않는다. 기존 평균 CE로 실행하는 것을 금지하는 명시적 계약을 넣었다. 실행 코드까지 연결됐다는 뜻은 아니다.

다음에 학습을 명시적으로 요청하면 먼저 두 학습기에 가중 손실을 연결하고, label shift 1회·누적 창 정규화·CPU 기준 손실/기울기 일치 canary를 확인해야 한다. 늘어난 자료에 맞는 토큰·업데이트 예산과 validation 중단 규칙을 고정한 뒤 시작한다. 기존 분할의 목적함수만 변경 / 과제 혼합 추가 / 새 대조 자료 추가를 분리하는 절제 실험과 단계 경계 평가가 필요하다. 기존 후보의 test 결과를 보고 반복 선택하는 방식은 사용하지 않는다.

이 작업으로 자료·목적함수 명세·평가의 결함을 수정하고 검증했다. 수정 후 모델의 과승인과 time 오류가 실제로 감소했는지는 아직 확인하지 않았다.
