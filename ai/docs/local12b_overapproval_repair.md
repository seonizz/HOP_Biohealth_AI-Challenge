# 12B 오승인 원인 분석과 자료·평가 수정

작성: 2026-11-15. 대상은 완료된 12B 추가 학습의 로컬 회수본이다. **자료와 평가 코드 검증을 완료했으며, 새 학습·모델 추론·서버 접속은 하지 않았다. 31B 코드·자료·작업은 변경하지 않았다.**

## 실제 결과와 원인 판단

기존 `A_original`과 565업데이트 후보의 동일 사건 test 1,080개 출력을 다시 대조했다.

| 지표 | 기존 | 후보 |
|---|---:|---:|
| 정상 초안 거절 | 325/360 | 45/360 |
| 잘못된 초안 승인 | 0/360 | 97/360 |
| 상태 추출 time 오류 | 1,480/3,330 | 830/3,330 |

정상 초안 무효 출력은 35→0개, 잘못된 초안 무효 출력은 24→4개다. 무효 출력을 승인·거절로 간주하거나 분모에서 빼지 않았다. 정상 승인이 늘었지만 정상·오류 초안을 모두 승인한 쌍도 94개다. 기존 모델의 오승인 0건은 정상 초안까지 대부분 거절하던 성향과 함께 해석해야 한다.

### 확인된 사실

1. **실패가 부정·확실성 구분에 집중됐다.** 오승인 97건 중 `certainty` 31건, `negated` 26건으로 합계 57건이다. 나머지는 person 15, time 12, value 7, attribute 6건이다. object 형식은 61/180, pipe 형식은 36/180을 잘못 승인했다. 모든 test 원천 20개에서 오승인이 발생했다.
2. **승인·거절 결정 가중치가 잘못 적용된 문제는 재현되지 않았다.** 실제 학습 토큰·가중치 4,520행을 독립적으로 읽어 prompt 가중치 0, 행 합계 1, 결정 토큰 비중 0.5를 확인했다. 사건 정상·오류 각 1,080행의 결정 누적 가중치는 각각 540이다. 실행 코드도 causal shift 1회와 배치 정규화를 적용했다. 사건 학습 정답 3,240행은 독립 oracle과 일치했다.
3. **행 수에 비해 원천 다양성이 작았다.** 사건 학습 원천은 60개였다. 정상 초안과 상태 입력은 순서를 제외하면 각각 120개 내용(60원천×2형식)을 반복했다. 정상 승인 정답이 하나인 것은 출력 계약상 정상이며 라벨 오류가 아니다. 다만 반복된 쉬운 승인과 다양한 오류 근거 생성 사이의 학습 난도 차이는 남는다.
4. **오류 종류와 방향이 불균형했다.** time 오류 예시는 480행, negated와 certainty는 각각 120행이었다. 학습의 실제 오류값→정답 방향은 negated false→true 37 대 true→false 83, certainty unknown→reported 82 대 reported→unknown 38이었다. 실제 실패는 양방향에서 발생했으므로 드문 방향만의 문제로 단정할 수 없다.
5. **학습 중 검증이 핵심 실패를 관찰하지 못했다.** 실제 probe는 전체 과제 합계 7행이고 사건은 원천 하나의 상태·정상·오류 3행뿐이었다. 오류 유형도 `value_as_time` 하나여서 부정·확실성·형식별 일반화를 검사하지 못했다. 업데이트 300·400에서는 이 한 쌍조차 모두 승인했지만 probe는 관찰용이었고 고정 565업데이트 일정은 계속됐다. 최종에는 그 오류 한 건을 다시 거절했지만 전체 test 오승인은 97건이었다. 이는 당시 고정 실행 정책 위반이 아니라 검증·중단 설계의 한계다.

오승인 97건 중 88건은 **별도의 상태 추출 호출**에서 해당 변경 필드가 정답이었다. 따라서 상태 추출 성공만으로 초안 검토 성공을 보장할 수 없다. 서로 다른 호출의 연관성이므로 “모델이 정답을 알고 일부러 승인했다”는 인과 해석은 하지 않는다.

가장 강한 개선 근거는 **좁은 검증 범위**다. 그다음은 **반복이 많은 자료와 필드·방향 불균형**, 그리고 검토 지시에서 여섯 필드의 동일성 조건을 충분히 명시하지 않은 점이다. 이 요인들이 승인 성향 증가에 기여했을 가능성은 있지만, 기존 실험에서 자료·목적함수·혼합 순서를 함께 바꿨으므로 단일 원인을 증명한 것은 아니다.

근거: [재현 감사 결과](../../runtime/12b-overapproval-repair-20261115/audit.json), [감사 코드](../../runtime/12b-overapproval-repair-20261115/audit.py), [기존 최종 비교](../../runtime/ubuntu12b-evalresume-20261115-1269/FINAL_SUMMARY.json). 로컬 증거는 Git 제외 대상이며 실제 학습 원문을 이 문서에 복사하지 않았다.

- 새 원천마다 오류 대조 하나를 배정하고, 두 입력 형식 각각 상태·정상·오류를 만든다. 같은 정상 내용을 오류 종류마다 반복하는 구조를 줄였다.
- person·attribute·value·time·negated·certainty에 학습 원천을 각각 96개, validation/test에는 각각 32개 배정했다. 두 flag의 양방향과 두 형식을 균등하게 만들고 오류 위치도 앞·중간·뒤로 분산했다.
- 정상·오류 입력에 동일한 공개 규칙을 적용했다. 여섯 필드를 모두 비교하고 부정·확실성의 양방향 변화도 오류로 판단하도록 명시했다. 정답·오류 유형·방향 메타데이터는 모델 메시지에 넣지 않았다.
- 승인·거절 결정 가중치 0.5와 상태 time 가중치 정책은 유지했다. 근거 없이 거절 가중치를 높이지 않았다. 쌍을 같은 누적 창에 유지하고 네 과제가 학습의 각 구간에 섞이도록 했다.
- 기존 12B 자료에 노출된 원천 구조와 새 train/validation/test 간 구조·입력 중복을 검사했다. 과거 test는 진단용으로 격리했다. 새 test는 학습 토큰으로 인코딩하지 않았다.
- 앱 학습 1,280행과 validation 320행은 기존 회수본을 보존했다. 현재 앱 코드 변경을 이용해 자료를 재생성하지 않았다.

**절충:** 필드 균형을 맞추면서 time 오류 초안은 480→192행(세부 유형당 48행)으로 줄었고, negated·certainty는 각각 120→192행으로 늘었다. 상태 추출은 1,080→1,152행이다. time 성능 개선이 보장되는 구성은 아니므로 기존 time 기준과 유형별 검사를 유지한다. 전체 행·업데이트도 약 4.8% 늘어났으므로 이전 실행과 동일 예산의 인과 비교로 해석할 수 없다.

## 평가·선택 설계 수정

[12B 전용 평가 코드](../scripts/local12b_repair_evaluation.py)를 추가했으며 기존 공용·31B 평가 코드는 수정하지 않았다.

- 오승인을 `1 - 오류 거절률`로 추정하지 않고 유효한 `approved=true`로 직접 센다. 정상 거절·무효 출력·time 오류를 별도로 보고하며 고정 분모를 사용한다.
- 전체 사건 validation 1,152행의 ID·원천·입력/정답 해시·오류 종류·형식·방향 구성을 고정한다. 일부 행만 평가하거나 기존 7행 probe만 제출하면 후보 선택이 불가능하다.
- 평균뿐 아니라 **오류 종류×입력 형식×변경 방향**별 오승인·정상 거절·무효 출력·근거 정확도와 기존 모델 대비 퇴행을 검사한다. 기존 쌍 판단·필드·time 기준도 유지한다. 오승인/정상 거절 최대 5%, time 오류 최대 2%, 각 세부 집단 무효 출력 0 및 오류 근거 일치 95% 이상을 요구한다. 작은 집단에서는 한 건의 오류도 기준을 넘을 수 있다.
- 기준 모델의 동일한 전체 validation 결과가 없으면 `checkpoint_selection_allowed=false`다. 사건 기준 통과도 `event_validation_only`이며 별도 앱 320행 기준을 통과해야 한다. 평가기는 최종 모델 승인으로 오해되지 않도록 항상 `model_selection_ready=false`를 반환한다.
- 새 test와 과거 출력 재채점(`diagnostic`)은 후보 선택에 쓸 수 없다. 원천별 평균은 기술 통계이며 변형 행을 독립 표본으로 간주하지 않는다.

[CHECKPOINT_POLICY](../../training_data/12b_review_contrast_repair_20261115_v2/CHECKPOINT_POLICY.json)는 0·25·50·100·200·300·400·500·592업데이트에서 전체 사건/앱 validation을 요구한다. 오승인이 5%를 넘거나 기준 모델보다 악화되면 후속 업데이트를 멈추고 검토하도록 명시했다. **이는 정책 파일이며 실제 학습기의 중단 hook 연결은 아직 하지 않았다.**

## 검증 결과와 실행 경계

- 독립 역방향 사건 탐색·튜플 차집합 oracle로 새 사건 **5,760행**의 의미 정답을 확인했다.
- 실제 tokenizer/template로 train+validation **6,208행**의 토큰·가중치를 생성하고 원문에서 재계산했다. 학습 최대 8,675토큰, validation 최대 8,601토큰이며 임의 절단하지 않았다. 원본 자료·앱 자료 보존 및 구조·입력 누출 0건을 확인했다.
- 생성·평가 회귀 테스트 **16개 통과**. 평균이 같아도 방향별 오류가 옮겨간 사례, 불완전한 baseline, 메타데이터 오염 등을 검사한다.
- 전체 validation/test를 이용한 **대조군 12종 통과**. 정답 출력은 통과하고 모두 승인/거절, flag 무시, time 손상, 근거 위조, 누락, 잘못된 JSON, 길이 제한 종료, 7행 축소는 거부했다. 정답 test도 후보 선택에는 쓰이지 않는다.
- 과거 실제 before/after 결과 2개를 새 평가기로 재채점해 **오승인 97건 및 퇴행을 다시 검출**했다. 이 결과 외의 정답 대조군은 모델 추론 결과가 아니다.

## 2026-11-16 후속: 학습기 연결과 자동 실행 시작

사용자의 추가 학습 요청에 따라 **새 12B 전용 실행 묶음**에 전체 validation·중단·후보 선택·비교 코드를 연결했다. 자료·평가 테스트 16개와 실제 학습기·정책·보고서 통합 테스트 30개를 통과했다. 25업데이트에서의 실제 CPU 학습 루프 중단과 평가 후 RNG 복원도 검증했다. 기존 준비 자료의 명세는 보존하고 별도 실행 COURSE·사전 검증·고정 plan으로 학습을 허용한다.

`chihun@chihun-ubuntu`에서 SSH와 독립된 자동 작업을 시작했다. 시작 확인 시 CUDA canary 단계에서 모델을 로드 중이었으며, **CUDA 검증 통과와 모델 개선 여부는 아직 미확정**이다. 검증 통과 시 직전 565업데이트 후보에서 최대 592업데이트 추가 학습하고 동일 입력으로 비교한다. 후보가 전체 validation 기준을 통과하지 못하면 새 test를 사용하지 않고 validation 진단 비교만 남긴다. 31B와 서비스 모델은 변경하지 않았다.

첫 중단 판단·진단 완료까지 약 10–14시간, 중단 없이 전체 학습·검증·test를 수행하면 약 55–75시간으로 예상한다. GPU 대기·충돌은 별도다. 실행 경계·근거·로그 위치는 [12B 실행 기록](../../runtime/ubuntu12b-contrast-20261116/RUN.md)에 정리했다.

### 모델·프로젝트 시간과 품질 계측 연결

별도 백그라운드 작업으로 기존 평가의 시간·품질을 1분 간격으로 집계하고, 원래 12B 작업이 완료되고 GPU가 반환된 뒤 실제 프로젝트 최종 생성·검토 흐름의 6개 사례를 두 모델에서 측정하도록 연결했다. 원래 학습·평가 코드는 수정하지 않았다. 평균·p95·TTFT·처리량과 정상 거절·오승인·time 오류·프로젝트 완료 성공률을 함께 기록한다. UI·HTTP 네트워크·DB 저장 시간은 포함하지 않으며 기존 프로젝트 채점의 시간·모델 제외 규칙도 유지한다. 범위·검증·결과 위치는 [시간·품질 측정 기록](../../runtime/12b-project-timing-20261116/RUN.md)을 따른다.

### 25업데이트 결과와 후처리 복구

전체 validation 1,472개씩의 비교에서 사건 정상 거절은 32/384→31/384, 오승인은 162/384→149/384로 줄었지만 time 오류는 708/3,406→756/3,406으로 늘었다. 오류 초안 무효 출력도 20→26개로 증가했다. 일부 유형별·앱 근거 지표의 퇴행도 발견돼 25업데이트(200행)에서 정책에 따라 학습을 중단했다. 최종 판정은 **regression_detected**, 선택된 후보는 없으며 새 test를 사용하지 않았다. 이전 20개 원천 test 수치와 이번 새 validation 수치를 직접 같은 분모로 비교하지 않는다.

같은 입력의 요청 시간은 전체 1,472건 기준 평균 10.954→11.303초, p95 32.061→32.588초였다. 실제 학습 계산은 약 20분 29초였고, 학습 전·후 전체 validation을 포함한 작업은 후처리 오류까지 약 9시간 31분이 걸렸다. 생성 길이와 prefill을 포함한 관측값이며 인과적인 순수 decode 속도 변화로 해석하지 않는다.

정책 중단 후 `shutil.copytree`가 파일 내용 복사를 마친 뒤 속성 복사에서 격리 정책에 막히는 결함이 있었다. 각 파일 해시와 25개 누적 창·두 전체 validation을 재검증해 추가 학습·추론 없이 최종 보고서를 복구했고 실패 기록도 보존했다. 권한 제한은 완화하지 않았다. 복구 검증 테스트 3개가 통과했다.

프로젝트 측정은 별도 r2 작업으로 재시작했으며 결과는 아직 미완료다. [복구된 모델 보고서](../../runtime/12b-postprocess-recovery-20261116/final/REPORT.md), [프로젝트 측정 재시작 기록](../../runtime/12b-project-timing-20261116-r2/RUN.md)을 참고한다. 31B는 변경하지 않았다.

### 2026-11-16 추가 검증: 상태 중복과 프로젝트 생성 규격

프로젝트 r2 측정은 완료됐으며 A_step565와 추가25 후보 모두 최종 출력 성공 0/6이다. 실제 52개 모델 응답을 고정 ModelGateway에 CPU 재생해 12개 실패를 동일하게 재현했고, 모든 재생 요청과 모델·코드·설정 연결을 검증했다. `patient_state.facts` 최대3개 요청에 7~9개를 내는 규격 위반이 주된 장애였다. 이는 재시도를 포함한 요청 진단이며 통신·토큰 한도 실패가 아니다.

사건 validation 재채점은 기존 집계와 일치했다. time 오류708→756의 내부를 분리하면 무효 상태출력으로 인한 슬롯 벌점405→465가 증가의 큰 원인이다. 상태 출력의 중복 `(person, attribute)` 원인은37→43행이며, 유효 출력의 time/슬롯 오류는303/3001→291/2941로 분모가 달라 개선을 단정할 수 없다. 부정·확실성 변경 오류의 오승인도47/64→50/64, 45/64→48/64로 악화했다.

최근 실제 학습200행에는 사건 상태/검토와 답변/메모리 검토만 있으며 앱 생성 단계와 직접 대응하는 과제는 없다. 다음 보완은 상태 유일성, 부정·확실성 대조, 실제 앱 생성 규격과 재시도 수정 과제를 우선한다. 이번에는 새 학습·추론·배포·31B 변경 없이 검증만 수행했다. [추가 검증 보고서](../../runtime/12b-additional-validation-20261116/REPORT.md)에 범위·재현 근거·한계를 기록했다.
