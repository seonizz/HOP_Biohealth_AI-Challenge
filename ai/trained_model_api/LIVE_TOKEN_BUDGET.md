# v11 실행 경로 입출력 한도 수정 — 2026-10-17

사용자가 입출력 토큰 문서를 확인하고 문서대로 적용하도록 지정했다. 서비스 화면에는 이 개발 상세를 추가하지 않는다.

## 적용 기준

| 항목 | 한도 |
| --- | ---: |
| 채팅 템플릿·이력·JSON 스키마를 포함한 입력 | 65,536토큰 |
| 요청한 출력 예약 `max_tokens` | 8,192토큰 |
| 입력 + 요청한 출력 예약 | 69,632토큰 |
| 출력 8,192 예약 시 유효 입력 | 61,440토큰 |
| 출력 1,800 예약 시 유효 입력 | 65,536토큰 |

입력은 자르거나 요약하지 않는다. 합산 검사는 전체 출력 상한을 무조건 빼지 않고 해당 요청의 `max_tokens`를 사용한다. 예약량은 실제 생성량을 뜻하지 않는다.

근거는 [v11 데이터 이관 검증](../../docs/archive/2026-10/GPU_서버_데이터이관_아카이브_검증_2026-10-17.md)의 입력 65,536·출력 8,192·합산 69,632 계약이다. [로컬 이용 안내](LOCAL_USAGE_REFERENCE.md)와 [10월 10일 추론 최적화 기록](INFERENCE_OPTIMIZATION.md)은 앞선 step100 운영 당시 출력 4,096을 기록한다. [128K 용량 보고서](CAPACITY_REPORT.md)와 기존 `config.json`은 다른 step100 실행의 과거 검증 기록이며, 이후 운영 정책 및 현재 v11 worker의 한도로 혼용하지 않는다.

[v11 본학습·서비스 검증](../../docs/archive/2026-10/GPU_서버_v11_본학습_재개_서비스검증_2026-10-17.md)의 입력 4,096·출력 8,192·합산 12,288은 해당 검증용 프로필이다. 학습 시퀀스 4,096이나 prefill 조각 4,096도 서비스 전체 입력 한도가 아니다. 각 과거 문서와 검증 결과는 보존한다.

## 재현한 결함과 수정

- 관계 질문의 `relationship_memory` 요청이 HTTP 400으로 거절되고 앱에는 `MODEL_UPSTREAM_ERROR`가 전달됐다. 동일 tokenizer로 실패한 저장 대화를 다시 구성하면, 관찰 결과를 비워도 입력이 4,606토큰이었다. 기존 live worker의 입력 4,096 제한을 넘는다.
- worker가 입력과 **전역 출력 상한 8,192**의 합을 검사했다. 이를 위 문서 계약 및 **요청한 출력 예약** 기준으로 수정했다.
- relay가 worker 오류를 일반 `invalid_request`로 바꾸면서 문맥 초과 원인이 사라졌다. 숫자와 고정 문구만 포함하는 알려진 예산 오류만 통과시키고, 앱에서 `MODEL_CONTEXT_TOO_LONG`으로 구분한다. 임의 오류 원문은 전달하지 않는다.
- 기존 구현을 재사용해 prefill 1,024 분할·요청별 DynamicCache·global attention KV 그룹 처리를 활성화했다. 분할 처리는 입력 삭제가 아니다. 모델·tokenizer·checkpoint 고정 해시는 유지한다.

실행 변경은 [예산 검사](inference_budget.py), [회귀 검사](test_inference_budget.py), [live worker·relay·회귀 패치](live_input_budget.patch)에 보관했다. 패치는 기존 `live_worker.py`, `local_live.py`, `test_live_worker.py`에 적용하는 차이이며, `inference_budget.py`와 기존 `grouped_attention.py`를 worker 폴더에 함께 두고 코드 manifest의 SHA-256을 갱신해야 한다. 원격 적용은 해당 요청의 지정 작업 폴더에 한정했다.

## 검증

CPU 검사: 앱 모델·복구 59개, 예산·오류 whitelist 13개, live worker 22개 통과. 합산 경계 61,440+8,192 허용 / 61,441+8,192 거부, 입력 경계 65,536 허용 / 65,537 거부, 요청한 출력만 예약, 원문 비절단을 검사했다.

최종 prefill 1,024 설정에서 실패했던 저장 대화를 별도 소유자의 테스트 복제본으로 재시도했다. `relationship_memory`는 입력 **4,714**·생성 **271**토큰으로 HTTP 200이었다. 이어 `state_review`·`question_plan`까지 통과해 앱 `/answers`가 HTTP 200을 반환하고 `rel → contact`로 진행했다. pending 상태는 해제되고 복제 대화의 revision은 0→1로 증가했다. 원래 세 대화의 암호문 SHA-256과 revision은 모두 일치했고, 테스트 복제본과 테스트 소유자는 삭제했다.

이 검증은 해당 관계 질문의 실패 복구를 확인한다. 남은 모든 질문과 최종 결과 전체 여정은 이번 검사 범위에 포함하지 않았다. 최대 입력과 출력 예약의 실제 검증 결과는 다음과 같다.

최대 입력 첫 시도에서는 prefill 4,096에서 HTTP 400 `generation_failed`가 발생했다. 그 시점의 GPU 0 점유는 23,969 MiB였으나 오류 종류를 보존하지 않아 OOM으로 확정하지 않는다. 전체 입력 한도는 유지하고 prefill 조각만 1,024로 낮춰 재검증했다. 새 worker는 예외 원문 대신 `out_of_memory` 또는 `generation_failed` 분류만 원문 없는 상태 기록에 남긴다.

| 실제 HTTP 검사 | 결과 |
| --- | --- |
| 입력 65,536 + 출력 예약 1 | 200, 실제 입력 65,536·생성 1토큰 |
| 입력 65,537 + 출력 예약 1 | 400, 입력 한도 초과 정확히 전달 |
| 입력 61,441 + 출력 예약 8,192 | 400, 합산 한도 초과 정확히 전달 |
| 짧은 입력 + 출력 예약 8,192 | 200, 실제 생성은 2토큰에서 종료 |
| 긴 입력 뒤 짧은 후속 요청 | 200 |

65,536토큰 실행 용량과 8,192 출력 **예약**을 확인했다. 8,192토큰 전체 생성이나 장문 이해 품질을 검증한 결과는 아니다.

검증 후 이번 작업의 GPU worker만 정상 종료했다. GPU 계산 프로세스는 0개이고 메모리는 실행 전과 동일한 GPU 0 **11 MiB**, GPU 1 **30 MiB**로 복귀했다. 로컬 웹과 API 상태 확인은 HTTP 200이며, 다음 생성 요청에서 지정 worker를 다시 로드한다. 서버 전역 변경이나 GPU reset은 하지 않았다. 검증용 임시 인증 키와 원문 복사본은 제거했다.

원문 없는 [검증 근거 JSON](LIVE_TOKEN_BUDGET_verification.json)에 코드·실행 파일 해시, 단계별 토큰 사용량, 최초 최대 입력 실패와 최종 성공, 원래 대화 보존 및 GPU 반환을 기록했다.
