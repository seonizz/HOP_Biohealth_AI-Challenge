# 말씨 모델 학습과 비교 평가 데이터 수집 지침

학습 전에 비교 조건과 기록 형식을 고정하고, 학습 중에는 실제 optimizer 업데이트·손실·자원 사용을, 학습 후에는 같은 사례에 대한 기반 모델과 학습 모델의 응답을 남긴다. 이 기록으로 학습 곡선, 토큰 처리량, 메모리, 데이터 선별률, 응답 품질 차이를 다시 계산할 수 있어야 한다.

아래 지침은 이번 학습부터 적용할 수집 계약이다. 기존 45,974행·4,096 후보 17,236행·LoRA r=8 등의 숫자는 이전 실행의 기준값이다. 이번 실제 데이터와 설정을 다시 기록하며, 이전 숫자를 새 실험의 측정값으로 복사하지 않는다. 이 키트는 학습 실행기가 아니다.

## 1. 시작 전에 반드시 남길 것

1. **run ID와 실험 목적:** 예비 검증, 원본 상담사 응답 SFT, 주변인 지원 SFT를 구분한다. 설정·데이터가 바뀐 재실험에는 새 run ID를 쓴다. 단순 checkpoint 재개는 같은 run ID와 새 segment ID를 쓴다.
2. **모델과 코드:** 모델 ID·실제 revision·로컬 파일 SHA-256, tokenizer 파일 SHA-256, 채팅 템플릿 SHA-256, 실행 코드 commit과 미커밋 diff를 저장한다. 모르는 값은 `null`로 남기고 이유를 적는다.
3. **실행 환경:** 실행 프로세스가 사용한 Python, Torch, CUDA runtime, driver, Transformers, Unsloth, PEFT, bitsandbytes, GPU 종류·개수·VRAM을 저장한다. 설치 목록과 `nvidia-smi` 출력은 증거 파일로 남긴다.
4. **데이터 동결:** 데이터 버전·manifest·split·파일 SHA-256과 Train/Dev/Test별 행·상담·관측 그룹 수를 기록한다. 같은 상담·파생 시나리오의 계보를 분할 전에 연결한다.
5. **기반 모델 비교 준비:** 학습하지 않은 기반 모델을 다시 로드할 수 있도록 fingerprint와 프롬프트를 보존한다. 고정 Dev 사례의 기반 응답을 학습 전 수집하면 데이터·설정 누락을 일찍 발견할 수 있다.
6. **평가 설계:** 비교할 checkpoint 선택 규칙, 지표의 분모, 평가 주기, generation 조건, 검토 기준, Test 사용 규칙을 학습 전에 고정한다.

최종 Test는 정책·프롬프트·하이퍼파라미터·checkpoint 선택에 사용하지 않는다. 최종 Test에서 B0와 학습 모델의 응답은 선택 완료 후 같은 조건으로 수집한다. Test를 이미 개발에 사용했다면 Dev로 표시하고 미사용 Test를 새로 확보한다. 임의의 8:1:1 비율보다 원천 그룹의 독립성과 행동 범위가 우선이다.

  preflight.json             학습 연결과 손실 검증 결과
  evaluation_plan.json       동결 비교 조건·평가 분모

  events.jsonl               시작·종료·OOM·저장·재개·실패
  generations.jsonl          모든 모델 생성 시도
  reviews.jsonl              응답에 연결된 독립 검토
  artifacts/                설정·환경·체크포인트 지문·검증 증거

`python3 collection_tools.py init --run-id malssi_sft_001 --output /경로/malssi_sft_001`로 빈 기록 폴더를 만든다. 예시 run ID는 실제 모델 성능을 뜻하지 않는다. 기존 폴더를 덮어쓰지 않는다. [필드 양식](templates/record_templates.json)의 각 record를 실제 값으로 채워 해당 JSONL에 추가한다. `null`은 미측정이고 `0`은 실제 관측 0이다. 빈 파일도 그대로 보존한다.

## 3. 데이터셋과 토크나이징

### 데이터 선별 원장

원본 → 형식 검사 → 내용/출처 보류 → 길이 선별 → 최종 학습 입력의 각 단계마다 다음을 기록한다.

| 항목 | 저장할 값 | 계산할 수치 |
|---|---|---|
| 규모 | split별 행·상담·관측 그룹·합성 계보 수 | 원본 대비 유지율, 단계별 보류율 |
| 선별 사유 | 각 사유 행 수, 사유 합집합, 사유 간 중복 수 | 중복을 뺀 고유 보류량 |
| 중복·누출 | 정확 일치·근사 검사 방법, 교차 그룹 수와 보류 결정 | 검사 범위별 노출 건수 |
| 사례 범위 | 주변인 관계, 목표 행동, 안전 여부, 원문 대화 위치 | 행동/관계별 비중과 평가 공백 |
| 검토 상태 | 원본 관측 응답·AI 초안·사람 검토·전문가 검토의 건수 | 실제 승인 감독량 |

단어 등장 건·고유 어휘·모델 token·응답 행·독립 상담·사람 수를 다른 단위로 기록한다. 사유별 보류량은 겹칠 수 있으므로 합집합을 별도로 구한다. 관측 그룹은 확인된 사람 수와 같지 않다.

### 실제 토큰 원장

실제로 Trainer에 전달할 serializer와 tokenizer로 각 사례의 `sample_id`, `split`, `conversation_id`, `source_group_id`, `full_tokens`, `prefix_tokens`, `target_tokens`, `supervised_tokens`, 포함 여부, 보류 사유를 비공개 원장에 저장한다. 원문 내용 대신 hash와 내부 ID를 분석표에 사용한다.

분할·선별 단계별로 합계, 평균, p50, p95, p99, 최대, 길이 상한 초과 건수를 집계한다. 기존 자료와 비교할 때 백분위는 nearest-rank(`ceil(n×p)`)로 맞춘다. 실제 loss에서 제외되는 shifted label 위치와 padding을 확인하고 `supervised_tokens`를 센다. 단순 문자열 길이를 token 수로 환산하지 않는다.

`감독 비중 = 감독 토큰 합 / 전체 non-padding 입력 토큰 합`이다. 감독 대상이 적어도 앞선 문맥의 계산 비용은 발생하므로 비용 절감률로 바꾸지 않는다. packing·truncation·특수 토큰·종료 경계·패딩 방향이 변경되면 새 데이터/입력 계약 버전을 기록한다.

## 4. 본학습 전에 실행할 연결 검증

짧은 사례, 긴 사례, 다중 턴, padding이 있는 배치, 경계 길이 사례를 실제 Trainer/collator에 넣고 결과를 보존한다. 과거 코드 검사만 통과한 것으로 대체하지 않는다.

| 검사 | 반드시 보존할 근거 |
|---|---|
| 입력·목표 경계 | 실제 input_ids/labels/attention_mask의 비공개 배열·SHA, 최초/마지막 감독 위치 |
| 손실 마스크 | system/user/과거 assistant/padding의 제외, 마지막 목표와 종료 직렬화 경계의 포함 |
| 손실 비교 | 기준 CE의 정의, dtype, reduction, atol/rtol, 실제 값·오차·통과 여부 |
| 손실 세부 | 첫 목표·본문·종료별 token CE, 유효 label 수가 다른 chunk의 집계, 필요한 gradient 비교 |
| 실제 업데이트 | 첫 optimizer 상태 할당, 업데이트 성공 여부, 전후 adapter SHA·파라미터 변화 |
| 지속 실행 | 연속 업데이트의 finite loss/gradient, OOM·overflow·skip 여부 |
| 저장·재개 | model/adapter뿐 아니라 optimizer·scheduler·RNG·Trainer 상태와 재개 전후 step |

이전 엄격 손실 gate는 실패로 남아 있다. 이번 실행에서는 기준식을 먼저 고정하고 실제 Trainer 경로에서 재검증한다. 원인 분석을 위해 허용 오차를 바꾸었다면 변경 전후 값과 이유를 보존한다. 실패 상태에서 진행한 탐색 실행은 `pilot`으로 표시하고, 전체 학습 동등성 통과로 보고하지 않는다.

처음에는 별도 pilot run에서 짧은 연속 업데이트와 저장·재개를 검증한다. 업데이트 수는 실행 계획에 명시하며 작은 pilot 결과를 전체 학습 완료로 집계하지 않는다. 재개 성공은 파일 존재뿐 아니라 이어지는 step·scheduler·optimizer 상태와 가능한 범위의 출력/파라미터 대조로 확인한다.

## 5. 학습 중 기록할 값과 주기

### 모든 optimizer 시도

각 시도마다 `attempt_id`, `segment_id`, `optimizer_attempt`, 누적 성공 업데이트 수, 결과(`updated/skipped/oom/failed`), 시각, epoch 진행도, microbatch 수, samples, non-padding 입력 token, 실제 감독 token, LR, loss, gradient norm/finite 여부를 기록한다. gradient accumulation의 microstep과 optimizer update를 같은 step으로 세지 않는다. overflow나 skipped step은 성공 업데이트에 더하지 않는다.

`optimizer_attempt`는 1부터 시작해 재개 segment를 포함하여 연속으로 증가한다. `successful_update_count`는 0에서 시작해 실제 `updated`일 때만 1 증가한다. 재개 시 이전 로그를 포함하고 카운터를 이어간다.

loss는 다음 두 값을 구분한다.

- `loss_reported`: Trainer가 보고한 scalar와 `loss_reduction` 설명. accumulation·여러 rank의 평균·logging window 영향을 함께 기록한다.
- `token_ce_sum`과 `supervised_tokens`: 정확한 비교가 가능한 CE 합과 유효 token 수. 직접 얻지 못하면 CE 합은 `null`로 남긴다. 이미 평균·스케일링된 loss에 임의의 token 수를 곱해 복원하지 않는다.

`token-weighted CE = Σ token_ce_sum / Σ supervised_tokens`다. `exp(CE)`는 동일 label mask·tokenizer·평가집합에서 해석할 수 있는 perplexity이며, overflow 시 수치를 억지로 만들지 않는다. train loss 감소를 곧바로 실제 지원 품질 향상이라고 표현하지 않는다.

### Dev 평가와 checkpoint

실용적인 시작안은 **매 100 성공 업데이트 또는 매 epoch 중 먼저 도달한 시점**에 고정 Dev를 평가하는 것이다. 비용에 따라 시작 전에 간격을 바꾸고, 실제 실행 간격을 기록한다. Trainer가 두 조건을 자동 결합한다고 가정하지 말고 실행 코드에서 한 가지 명확한 규칙으로 구현한다. 첫 pilot은 더 짧은 간격을 써도 별도 run으로 기록한다.

각 평가에서 checkpoint 지문, 실제 평가한 행·상담·그룹 수, 제외·오류 수, CE 합과 token 분모를 기록한다. checkpoint 선택 기준은 고정 Dev의 사전 지표로 정하고 최종 Test 점수로 바꾸지 않는다. 마지막 checkpoint와 선택된 best checkpoint를 모두 식별할 수 있어야 한다.

### 시간과 GPU 자원

| 구간 | 필수 수치 | 수집 방법 |
|---|---|---|
| 모델 로드·optimizer 최초 생성 | 소요시간, GPU별 할당/예약 peak | 최초 step 전후를 구분 |
| 학습 step | dataload+forward+backward+optimizer wall time, 입력/감독 tokens/s | 같은 시간 창의 실제 token 합 사용 |
| 정밀 성능 표본 | warmup 구분, 측정 창, 동기화 여부, GPU별 peak byte | 처음 pilot과 정해진 표본 구간에 집중 |
| Dev·저장 | 각각 소요시간과 메모리 | 학습 계산 시간과 별도 event |
| epoch·전체 run | 실제 시작/종료/중단/재개·총 wall time | 평가·저장·재시도 포함 여부 명시 |

기본 step 시간은 매 시도 남기고, 정밀 CUDA 동기화·peak 측정은 예를 들어 **warmup 후 10개 연속 업데이트와 이후 매 100번째 업데이트**에서 수행한다. 표본 정책을 기록하고 계측 overhead가 큰 구간과 일반 학습 시간을 구분한다. 매 step 전체 tensor·gradient를 파일로 복사하지 않는다.

CUDA는 비동기이므로 정밀 wall-clock 측정은 구간 시작·종료에서 동기화한다. peak 측정은 구간 시작 전 `reset_peak_memory_stats()`와 종료 후 `max_memory_allocated()`·`max_memory_reserved()`를 사용한다. 메모리는 byte로 저장하고 GiB 변환은 `/1024**3`로 한다. GPU별 값을 보존하며 최대 GPU 값과 합계를 구분한다. 전역 tokens/s와 rank별 시간을 혼합하지 않는다. [PyTorch CUDA 의미](https://docs.pytorch.org/docs/2.14/notes/cuda.html), [peak 통계 초기화](https://docs.pytorch.org/docs/2.14/generated/torch.cuda.memory.reset_peak_memory_stats.html).

epoch 예상시간과 실제시간은 별도 필드다. 실패/OOM을 제외하고 계산한 빠른 처리율만 대표값으로 제시하지 않는다. 입력 token 처리율과 감독 token 처리율은 이름과 분모를 각각 표시한다.

## 6. 학습 전후 모델 비교

최소 비교는 **같은 기반 모델 + 같은 말씨 프롬프트**의 미학습 상태와 선택된 학습 checkpoint다. 동일 과제에서 입력과 프롬프트까지 바꾼 결과를 순수 학습 효과라고 해석하지 않는다.

| 조건 | 역할 | 필요한 경우 |
|---|---|---|
| B0 기반 모델 + 최소 과제 지시 | 기본 기준점 | 기본 성능을 보여줄 때 |
| B1 기반 모델 + 말씨 정책 프롬프트 | 프롬프트 적용 기준점 | 학습 효과의 직접 비교 기준 |
| B2 원본 상담 응답 SFT + 같은 정책 | 원본 응답 학습 효과 | 이번 학습이 원본 SFT일 때 |
| B3 주변인 목표 SFT + 같은 정책 | 목표 데이터 학습 효과 | 해당 검토 데이터로 실제 학습했을 때 |

실제로 존재하지 않는 B2/B3는 빈칸으로 남긴다. 비교 조건이 추가될 때마다 같은 `case_id`·split·원천 그룹·input hash를 사용한다. 모델 상태 외에 tokenizer/template/precision/양자화/context/max_new_tokens/temperature/top_p/top_k/seed/batch/stopping 설정을 맞추거나 차이를 기록한다. 최소한 하나의 고정 decoding 조건을 모든 모델에 적용한다. 무작위 decoding을 비교하면 동일 seed 목록과 반복 수를 사전에 정한다.

원본 응답 SFT 평가와 주변인 지원 과제 평가는 각각 보고한다. 기존 예약 조건의 공통 Validation 1,335행은 **원본 응답 재현의 개발 비교**에 재사용할 수 있다. 주변인 지원의 미사용 최종 Test를 대신하지 않는다.

### 모든 생성 시도에 저장할 것

`generation_id`, 모델 조건·checkpoint 지문, case/session/turn/group ID, split, 프롬프트·입력 hash, 실제 입력 token 수, 예약 token 수, 실제 생성 token 수, 상태, 종료 분류, 전체 지연, 가능하면 TTFT, GPU 메모리를 저장한다. 요청 실패·timeout·OOM도 행을 남긴다.

별도 비공개 파일에는 **후처리 전 생성 suffix token IDs, 실제 response text, 실제 prefill IDs/해시, 최종 적용 generation config, 호출 override와 추가 stopping criteria**를 보존한다. batched decoder-only 생성은 attention mask 합과 padded input width를 구분하고 실제 반환 계약에 따라 suffix를 자른다. `input_ids.shape[-1]` 등의 의미를 확인 없이 샘플별 prompt 길이로 바꿔 쓰지 않는다.

종료는 `eos_observed`, `length_limit`, `tool_handoff`, `custom_stop`, `error`, `unknown`을 구분하고 `forced_eos_at_limit`은 별도 boolean/null로 남긴다. 마지막 token이 EOS라는 이유만으로 자연스럽게 답을 마쳤다고 판정하지 않는다. `forced_eos_token_id`는 길이 한계에서 EOS를 넣을 수 있고 직접 호출 인자가 설정을 덮어쓸 수 있다. [Transformers 생성 설정](https://huggingface.co/docs/transformers/main_classes/text_generation).

TTFT는 첫 token이 실제로 관측되는 계측에서만 기록한다. 전체 generate 시간에서 나누어 추정한 값을 TTFT라고 쓰지 않는다. 비스트리밍에서 측정하지 못하면 `null`이다.

## 7. 응답 품질과 다중 턴 평가

검토자는 모델 이름을 가린 응답을 같은 rubric으로 평가한다. 검토자 ID, 사람/전문가/AI 구분, rubric 버전·hash, 응답 hash, 검토 시각, 판단 이유를 기록한다. 사람의 실제 검토가 없으면 `human`으로 표시하지 않는다. 가능하면 독립 검토자 2명을 배치하고 합의·불일치·미확정을 보존한다. 최종 판정 규칙과 안전 사례의 전문 검토 범위는 사전에 정한다.

항목 결과는 `pass/fail/uncertain/not_applicable`로 기록한다. not_applicable은 rubric상 해당하지 않는 경우에만 사용하고, 단순 미검토는 별도 상태로 남긴다.

Case manifest의 `criterion_applicability`에 각 기준의 적용 여부를 응답 생성 전에 고정한다. 예를 들어 거절·정정이 없는 사례는 해당 기준의 대상에서 사전에 제외한다. 모든 모델에 같은 적용 대상을 쓰며, 응답이 좋지 않다는 이유로 나중에 N/A로 바꾸지 않는다. 템플릿의 `supporting_records.case_manifest.jsonl`을 사용할 수 있다.

| 항목 | 판단 기준 |
|---|---|
| request_resolution | 현재 요청에 실제로 답했는가 |
| actionable_support | 사용할 말·실행 가능한 행동이 구체적인가 |
| subject_evidence | 사용자/당사자/제3자와 관찰/해석/전언을 보존했는가 |
| question_necessity | 질문이 필요하고 반복·불필요 질문이 없는가 |
| refusal_correction | 모름·거절·정정을 적절히 반영했는가 |
| safety | 해당 사례의 사전 안전 기준을 충족했는가 |
| completion | 응답 내용이 의미적으로 완결됐는가 |

다중 턴은 `teacher_forced_history`와 `model_accumulated_history`를 분리한다. 후자는 모델이 생성한 응답을 실제 다음 턴 이력에 넣는다. session ID, turn index, 각 모델별 이력 hash, 사용자/simulator 버전·seed, 요청 전환·거절·정정 이벤트, 종료 결과를 남긴다. 모델별로 이력이 달라지는 다중 턴에서는 같은 session 시나리오를 맞추되 중간 input hash의 동일성을 강제하지 않는다. simulator의 숨은 정답을 모델 입력에 넣지 않는다.

## 8. 최종 계산식과 분모

| 지표 | 계산 |
|---|---|
| 요청 해결·구체성·근거·안전 통과율 | 확정 pass / 사전 applicability=true인 전체 배정 사례; 미검토·실패·불일치 수 함께 표시 |
| 검토 완료율 | 확정 검토 사례 / 전체 배정 사례 |
| 불필요 질문률 | 불필요 질문으로 확정된 사례 / 사전 질문 필요성 평가 대상; 미확정 별도 |
| 거절·정정 성공률 | 처리 pass / 사전 해당 상황 사례 전체 |
| 다중 턴 해결률 | 해결 pass session / 전체 배정 session |
| 생성 시스템 실패율 | error·timeout·OOM / 모든 생성 시도 |
| 길이 소진률 | length_limit / 모든 생성 시도; 성공 생성만의 비율은 추가 지표로 별도 표시 |
| CE·perplexity | 정확한 token CE 합 / 실제 유효 감독 token 수; 필요시 exp(CE) |
| 모델 차이 | 100 × (학습 모델 비율 − 기반 모델 비율), 단위 pp |

배정 사례와 재시도 횟수를 구분한다. 사례 단위 품질 점수는 사전에 정한 첫 시도 또는 재시도 정책의 결과 한 개로 계산하고, 모든 시도는 시스템 실패율에 포함한다. 결과가 좋은 재시도를 임의로 골라 점수를 계산하지 않는다.

미검토가 있는 통과율은 확정 pass의 전체 대비 비율로 표시하며, 모델 실패율로 해석하지 않는다. 확정 fail·uncertain·검토 대기·생성 오류의 분해표를 함께 낸다. 검토 완료 사례만의 조건부 통과율을 추가하면 그 분모를 따로 쓴다. 모델별 검토 완료 비중이 다른 상태에서 우열을 확정하지 않는다.

사전 비적용 사례는 기준별 분모에서 제외하고 그 수를 별도로 표시한다. 사전 적용 사례가 검토 시 N/A로 표시되면 자동으로 분모에서 빼지 않고 applicability 충돌로 재검토한다.

행 평균 외에 상담·관측 그룹 평균도 계산한다. 점수 차이의 신뢰구간을 계산할 때 같은 사례/그룹을 묶어 paired 재표집하고 재표집 단위·반복 수·seed·신뢰수준을 기록한다. 새로운 모델 훈련을 한 번만 했다면 학습 seed 간 변동성을 측정했다고 주장하지 않는다.

## 9. 학습 담당 에이전트에 전달할 실행 순서

1. 수집 폴더를 초기화하고 모든 설정·데이터·모델·환경 지문을 채운다.
2. 데이터/토큰 profile과 실제 Trainer preflight를 기록한다. 해결되지 않은 검사와 실행 목적을 명시한다.
3. 고정 Dev에서 B1 기반 모델 응답을 수집하고 생성 종료·비공개 원장 저장을 확인한다.
4. pilot에서 실제 optimizer 업데이트·자원·저장/재개가 기록되는지 확인한다.
5. main run의 모든 update·실패·Dev 평가·checkpoint를 기록한다. 선정 규칙에 따라 best checkpoint를 지정한다.
6. B1과 선택된 학습 모델을 같은 Dev/Test 평가 조건으로 실행하고 독립 검토한다. Test는 선정 완료 후 사용한다.
7. 다중 턴 평가·실패 사례·미확정 사례를 남긴다.
8. `collection_tools.py check --run <폴더> --phase after_eval`로 구조와 필수 기록을 확인한다. 이 검사는 모델 품질·안전 통과를 판정하지 않는다.

Trainer의 logging/eval/save 전략과 update 간격, accumulation, resume 인자 및 실제 선택된 checkpoint 경로를 저장한다. `save_only_model=True`만으로는 학습 재개에 필요한 optimizer/scheduler 상태가 보존되지 않는다. [Transformers Trainer](https://huggingface.co/docs/transformers/main_classes/trainer). 공식 문서 링크와 실행 중인 설치 버전이 같다는 보장은 없으므로 실제 환경 값과 해당 버전 API를 우선 확인한다.

## 10. 수집 완료 후 다시 전달할 자료

**필수:** 네 JSON 설정 파일, 다섯 JSONL 로그, 실제 학습 설정, 환경 버전, checkpoint 파일 목록·SHA, 손실 검증·저장/재개 결과를 전달한다. 중단·실패 실행도 run ID를 유지해 함께 포함한다. 실행하지 않은 항목은 `null` 또는 빈 로그와 미실행 이유를 남긴다.

발표용 집계에는 원문 상담, 원시 token ID, 가중치, 접속 정보가 필요하지 않다. 원문·응답·token ID의 비공개 원장은 별도 보관하고 hash로 연결한다. 의미 평가를 다시 검토하려면 비식별 입력·응답·검토 이유를 별도 전달한다. 토큰 ID도 tokenizer로 원문을 복원할 수 있으므로 공개 발표자료에 넣지 않는다.

이 자료를 받으면 데이터 funnel·토큰 분포·train/dev loss 곡선·실제 시간/VRAM·B1 대비 성능 차이·행동별 실패율·다중 턴 결과를 같은 분모로 다시 산출할 수 있다.
