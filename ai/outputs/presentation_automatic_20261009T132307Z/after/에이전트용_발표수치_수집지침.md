# 에이전트용 말씨 발표 수치 수집 지침

**목표:** [발표 문서](발표용_데이터_추출_활용안.md)에 원시기록으로부터 기계적으로 재계산할 수 있는 수치만 반영한다. **원자료 고정 → 해시·건수 검증 → 계산 → 발표표 반영** 순서로 진행한다. 응답의 의미·적절성에 대한 판정 점수는 수집·발표하지 않는다.

여기서 검증 가능하다는 것은 **같은 원시파일과 계산식으로 동일한 집계값을 재현할 수 있음**을 뜻한다. 새로운 생성 실행의 출력이나 수치가 불변이라는 뜻은 아니다. 응답 시간·처리속도·메모리는 환경 의존 측정이므로 발표 지표에서 제외하고 기존 원시기록만 보존한다.

**비교 조건**

| 조건 | 모델 |
|---|---|
| `BASE31` | Gemma 4 31B IT · 학습 adapter 없음 |
| `BASE12` | Gemma 4 12B IT · Ollama MLX NVFP4 · 학습 adapter 없음 |
| `FT31` | Gemma 4 31B IT + 본학습 완료 adapter |

12B 설치·생성은 확인했다. 모델은 `google/gemma-4-12B-it`의 Ollama `gemma4:12b` 배포본(MLX NVFP4), digest는 `c7597fc90b86aff6965317f37dd5465402284e26382d9b4bf2dfe3ef1491f4b6`이다. Google 원본 revision 연결은 미확인이다. 상담 63건·행동 분류 31건을 수집했다. [최신 결과](outputs/presentation_automatic_20261009T132307Z/comparison.md) · [CSV](outputs/presentation_automatic_20261009T132307Z/local_measurements.csv).

Δ학습은 FT31−BASE31, Δ소형은 FT31−BASE12다. Δ소형에는 크기·배포 정밀도·학습 차이가 함께 반영되므로 순수 파인튜닝 효과로 표현하지 않는다.

**작업 순서**

1. 원자료 사본과 `run_id`, 관측시각, 사례·모델·adapter·프롬프트·설정 SHA-256을 기록한다. 진행 중인 기록은 부분 결과로 표시한다.
2. 기존 생성·사례·학습 기록에서 먼저 추출한다. 계획 파일의 예정값을 실측값으로 쓰지 않는다. 이전 원자료를 덮어쓰지 않는다.
3. 사례별 배정·실행·종료·형식·실제 토큰을 자동 집계한다. 사례 ID 중복, 누락, 사례-생성 연결, 원문 해시를 확인한다.
4. 비교는 같은 사례·의미상 동일 프롬프트·출력 예산을 사용하고 두 조건이 모두 완료됐을 때만 계산한다. FT31은 본학습 완료 증거와 adapter 해시가 있어야 한다.
5. [검증 코드](outputs/presentation_automatic_20261009T132307Z/verify_measurements.py)로 집계값을 재계산해 [검증 결과](outputs/presentation_automatic_20261009T132307Z/verification.json)를 남긴다. 없는 원자료는 `null` / `[미측정]`으로 남기고 추정하지 않는다.

| 항목 | 원자료 | 계산·해석 |

분모가 0인 비율은 0%가 아니라 미측정이다. 토큰 수는 해당 런타임·tokenizer의 관측값이며 다른 tokenizer와 의미상 처리량을 직접 비교하지 않는다.

**사례·분모·비교 규칙**

- 현재 상담은 기존 검증용 32건과 공개 합성 31건, 행동 분류는 공개 합성 31건이다. 공개 합성 31개 실행 단위는 28개 상황 그룹이며 독립 표본 31개로 표현하지 않는다. 현재 자료를 독립 test·서비스 대표 분포로 승격하지 않는다.
- 생성 전 사례 ID·입력·프롬프트·배정 N과 제외 사유를 고정한다. 입력에는 현재 시점까지의 대화만 넣는다. 실제 train/dev 중복 점검과 자료 범위를 기록한다.
- 기본은 조건·사례별 첫 시도 1회다. 오류·timeout·형식 오류·길이 소진·미실행을 N에서 빼지 않는다. 중복 실행은 집계 정책과 함께 분리한다.
- 허용 코드 파서는 앞뒤 공백만 제거한다. 설명에서 코드를 추출하거나 여러 라벨을 하나로 고치지 않는다. 정상 종료와 형식 유효는 각각 검증한다.
- BASE31/FT31은 같은 기반 가중치·tokenizer·템플릿·양자화 조건을 사용한다. BASE12는 배포 digest·tokenizer·템플릿·실제 설정을 별도로 남기며 31B adapter를 적용하지 않는다.
- 모든 비교 조건의 tokenizer 길이를 실행 전에 검사한다. 공통 예산 초과 사례는 전 조건에서 사전 제외하며 건수·사유를 기록한다. 결과를 본 뒤 사례를 제외하지 않는다.
- NLL은 BASE31/FT31만 비교한다. 사례 수가 같아도 ID·해시가 다르면 B0/B1을 비교하지 않는다. BASE12 NLL은 이번 비교에서 비적용이다.
- BASE31·FT31 출력이 없으면 차이를 계산하지 않는다. 형식·종료·토큰 지표로 상담 품질·모델의 의미상 대응 능력·안전성·우위를 주장하지 않는다.

**저장과 완료 기준**

새 결과는 `HOP_pptdata/outputs/presentation_automatic_<수집시각>/`에 저장한다.

| 파일 | 내용 |
|---|---|

비공개 상담 원문·token ID·가중치는 발표 산출물에 넣지 않는다. 완료 전 **원자료 해시 / 사례 연결 / 분모 일치 / 오류·누락 보존 / 계산식·단위 / JSON 파싱 / 재계산 결과**를 확인한다. 비율 차이는 `%p`, NLL 차이는 손실값, NLL 감소율은 `%`다. 자료 집계 완료와 본학습 완료는 구분한다.
