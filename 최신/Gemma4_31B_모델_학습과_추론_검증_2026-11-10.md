기준일: **2026-11-10, Asia/Seoul**. 대상은 새 LoRA로 학습한 `malssi-gemma4-31b-cards-final-step4723`이다.

세 단계의 각 1 epoch 학습과 전체 validation loss 계산은 끝났다. 최종 체크포인트는 생성됐지만 **역할별 생성 품질 평가가 남아 있어 `training_complete=false`**다. 최신 GPU 실험에서는 출력 압축을 끄고 검토 묶음을 유지한 상담 한 턴이 **2회 호출·261.230초**에 통과했다. 이어진 최종 카드는 초기 검토 묶음의 컨텍스트 예산 초과로 완료되지 않았다.

## 학습 데이터와 방식

### 데이터 구성

실제 코스의 학습 자료는 **37,773행**, 검증 자료는 **3,793행**이다. 아래 숫자는 학습 예제 행 수이며 독립 상담 수가 아니다. 단계별 검증 집합이 다르므로 단계 간 loss의 절댓값으로 과제 난도를 비교하지 않는다.

| 단계 | 학습 행 | 검증 행 | 실제 학습 | optimizer step 증가 |
| --- | ---: | ---: | --- | ---: |
| 원상담 기초 `00_original_warmup` | 37,065 | 3,618 | 1 epoch | 4,634 |
| 카드 수정 `01_card_repair` | 20 | 5 | 1 epoch | 3 |
| 카드 생성 `02_card_generation` | 688 | 170 | 1 epoch | 86 |
| 합계 | **37,773** | **3,793** | 단계마다 1회 | **4,723** |

카드 생성 학습은 script·doList·next·care 각각 142행과 avoid 120행이다. 검증은 앞의 네 과제 각각 35행과 avoid 30행이다. 전체 데이터의 원문·정답은 이 문서에 포함하지 않는다. 출처·분할·데이터 생성 계약은 [학습 데이터 구성](../docs/model_training_review_2026-11-01/01_학습_데이터_구성.md)을 참조한다.

### 새 LoRA와 단계 연결

첫 단계는 기본 Gemma 4 31B IT에서 **새 LoRA**로 시작했다. 이전 step100·v11·canary 어댑터를 시작 가중치로 사용하지 않았다. 다음 단계는 바로 앞 단계에서 새로 만든 어댑터를 이어받으며, 단계 시작마다 optimizer를 새로 만든다.

| 항목 | 실제 실행 설정 |
| --- | --- |
| 학습 대상 | LoRA 파라미터 61,214,720개. 기반 모델 가중치는 동결 |
| LoRA | rank 8, alpha 8, dropout 0, `CAUSAL_LM` |
| optimizer | `torch.optim.AdamW`, learning rate `2e-5`, weight decay `0.01`, `foreach=False` |
| 배치 | micro batch 1, gradient accumulation 8, gradient clip 1.0 |
| 장치 배치 | 두 GPU에 레이어 분할, `layer_split=28` |
| 입력 계약 | 최대 32,768토큰, 입력 자르기와 packing 없음 |
| loss | 각 예제의 마지막 응답 target에만 적용. 예제별 target 평균 CE에 행 가중치와 `K/N`을 곱해 optimizer 창별로 합산 |
| seed | 3407, epoch shuffle은 `3407 + epoch` |

loss 계수의 `K`는 해당 epoch의 optimizer 창 수, `N`은 전체 학습 행 수다. 마지막 불완전한 창도 같은 계수를 사용하며 그 창의 행 수로 다시 나누지 않는다. 모든 예제를 유지한 채 창별 update loss의 평균이 전체 행에 대한 가중 평균 목적함수와 대응하도록 구성했다.

기존 NF4 4비트 기반 모델에 LoRA를 학습한 구성이다. 이번 추론 테스트를 위해 새로 양자화한 별도 모델을 만든 것은 아니다. 입력은 전체를 보존하며 loss에 포함되는 응답 위치를 구분한다. 실행 코드에 학습률 scheduler를 적용한 근거가 없어 고정 learning rate로 기록한다.

학습 전 canary는 최장 입력 **25,316토큰**, 최대 target **3,922토큰**, 새 프로세스에서 optimizer·RNG 상태 복원을 검증했다. 이는 학습 적합성 검증이며 아래 앱의 대형 검토 요청이 모두 컨텍스트에 들어간다는 보장은 아니다.

## 상담과 카드의 모델 호출 구조

### 상담 한 턴

정상 통합 경로는 **초안 1회 + 독립 검토 묶음 1회**, 총 2 POST다. 검토 묶음 안에서도 상태 검토, 필요한 질문 선택 검토, 안전 검토를 각각 검증한다. 문맥상 불필요한 질문을 생략하는 기능은 유지하며, 생략한 문항의 답을 만들어 근거로 사용하지 않는다.

형식 오류, 의미 반려·수정, 개별 검토 fallback이 발생하면 실제 호출 수가 늘어난다. “2회”는 모든 요청의 상한이 아니다.

### 최종 카드

상태가 준비돼 있고 수정·용량 오류가 없는 경우 정상 카드 경로는 다음 6 POST다.

1. 분석·전략 초안 생성.
2. 분석과 전략의 독립 검토 묶음.
3. 카드 초안 생성.
4. 카드별 검토와 전체 카드 검토를 포함한 11개 검토 묶음.
5. 발화 상세 생성.
6. 발화 상세 독립 검토.

전체 논리 검토 **14개**는 분석 1개, 전략 1개, 카드별 발화·지원 검토 7개, 전체 품질·발화·지원·교차 검토 4개, 발화 상세 검토 1개다. 반환 전 필수 승인과 최종 발화·상세 excerpt의 정확 일치를 확인한다.

내부 카드 테스트는 초기 상태가 없는 입력에서 시작하므로 상태 관찰·관계 기억·상태 검토가 먼저 필요할 수 있다. 이 준비 호출, 형식 재시도, 의미 수정, 용량 초과 시 분할 호출은 6회 외에 발생한다. 최신 GPU 테스트는 생성·검토 경로를 검사했으며 브라우저 표시 시간과 실제 DB 저장·재조회까지 포함한 31B 서비스 검증은 아니다.

## 출력 압축 해제와 재시작 수정

GPU 비교 실험에서 출력 압축을 켠 응답은 JSON 닫힘·중첩 오류와 claim 위치에 맞지 않는 판정 코드 때문에 거절됐다. 같은 28개 답변과 동일한 첫 초안으로 출력 압축만 끈 조건은 기존 검증을 통과했다. 해당 결과는 당시 고정한 압축 구현에 대한 것이다. 이후 로컬에서 수정한 v4 압축 구현의 31B 검증 결과로 옮겨 쓰지 않는다.

검증 실패가 요청당 최대 3회 시도(최초 포함)와 기존 의미 수정·재검토를 소진한 뒤에도 `ModelGateway.operation()`이 전체 작업을 재시작하던 문제를 고쳤다. **소진된 `MODEL_INVALID_RESPONSE`는 호출자에게 실패를 반환한다.** 기존 검증 항목·기준·요청 재시도·작업 내부 의미 수정은 유지한다. 통신 장애·시간 초과에 대한 복구와 취소는 별도 정책을 따른다.
