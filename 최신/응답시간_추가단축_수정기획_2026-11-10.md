## 4. R1 — 검토 묶음의 중복 원문 제거

### 현재 동작과 근거

[final-review-bundle.js](../app/src/final-review-bundle.js)는 payload의 최상위 값이 완전히 같을 때만 `shared_inputs`로 묶는다. 각 검토의 `retrieval`은 `stage`와 검색 이유 등이 달라 같은 원문 문서가 내부에 반복된다. [relationship-agent.js](../app/src/relationship-agent.js)의 `runReviewBundle()`은 묶음 전체 retrieval도 추가한다.

선행 검토의 합성 fixture에서 다음을 확인했다.

| 항목 | 결과 |
| --- | --- |
| 대상 | `final-review-bundle.test.js`의 합성 정상 최종 요청, `json_schema`, 비스트리밍 mock |
| 중복 | 서로 다른 원문 문서 5개가 retrieval 내부에 총 60번 등장 |
| 기존 요청 본문 | 96,323 bytes |
| 공통 출처표를 넣은 메모리 내 전송 시제품 | 86,160 bytes |
| 차이 | 10,163 bytes, 약 10.55% |
| 복원 검사 | 모든 입력·검토별 문서·검색 이유를 복원한 뒤 원본과 deep equality 통과 |

이 수치는 **합성 입력 한 건의 본문 크기 비교**다. 새 참조 규칙을 설명할 추가 프롬프트 비용을 제외했으며 토큰·실모델 시간·의미 품질 감소율이 아니다. 시제품을 앱에 반영한 상태도 아니다.

### 구현 방향

1. 기존 논리 검토 요청을 먼저 완성하고, 모델 전송 직전에만 같은 문서의 공통 표를 만든다. 공통 표도 해당 요청 본문 안에 포함한다.
2. 각 검토에는 문서 참조 목록과 그 검토의 `retrieved_for` 등 메타데이터를 보존한다. 묶음 전체 문서가 있다는 이유로 개별 검토의 허용 근거 범위를 넓히지 않는다.
3. 문서의 사람·문항·답변 구성요소·원문·질문 등 완전한 내용을 기준으로 동일성을 확인한다. 짧은 인용문이나 `source_id` 하나가 같다는 이유만으로 다른 객체를 합치지 않는다. 동일 ID의 내용 충돌은 거절한다.
4. 표에서 입력을 정확히 복원하는 함수를 두고 기존 검토 요청과 대조한다. 알 수 없는 참조, 중복 키, 누락된 문서는 거절한다.
5. 공통 지시 공유와 현재 `compactReviewInputs` 효과는 유지한다. 묶음 분할·개별 fallback에서도 필요한 문서 표와 허용 범위를 재구성한다.

### 완료 기준

- 정상·긴 원문·정정·복수 사람·동일 문구의 다른 출처에서 각 task의 원래 입력이 정확히 복원된다.
- 개별 검토의 스키마·validator·근거 범위와 최종 저장 payload가 같다.
- 추가 설명 프롬프트까지 포함한 전체 요청 크기와 실제 입력 토큰을 비교한다. 짧은 입력에서 표의 오버헤드가 더 크면 기존 표현을 유지할 수 있다.
- 실모델에서 참조 혼동·반려·형식 재시도가 늘지 않는지 확인한다. 크기 감소만으로 채택하지 않는다.

## 5. R2 — 검토 항목별 형식 복구

### 현재 동작과 위험

현재 `runReviewBundle()`은 지정된 형식·JSON·stale 오류가 3회 소진되면 묶음을 끄고 기존 개별 검토 순서로 복구한다. 이미 성공한 분할 결과도 폐기하는 것은 **앞 카드의 수정 전에 만들어진 전체 검토 승인을 잘못 재사용하지 않기 위한 의도된 보호**다. 관련 근거는 [검토 호출 최적화 계약](../app/docs/REVIEW_CALL_OPTIMIZATION.md)과 [기존 회귀 검사](../app/tests/final-review-bundle.test.js)에 있다.

합성 오류 주입에서 카드 하나의 audit 누락이 11개 전체 묶음의 3회 재시도를 일으키는 것을 확인했다. 다른 검토가 정상이라는 이유로 누락 항목을 승인하면 안 된다.

### 구현 방향

1. **완전하게 파싱된 JSON 객체**에 한정해 항목별 검증 결과를 구분한다. 응답 절단·파싱 실패·중복 JSON 키·예상 밖 최상위 키·전송 오류·취소는 부분 승인 재사용 대상에서 제외한다.
2. 각 필수 task를 `형식 오류`, `유효한 수정 필요 판정`, `유효한 통과 판정`으로 분리하되 검토별 기존 소비 함수를 유지한다. `approved` 하나로 공통 판정하지 않는다. 품질 task는 `improvements`가 남으면 수정이 필요하며, 카드 task는 모델 승인과 별도로 기존 `localCardIssues`도 통과해야 한다. task 누락은 승인으로 채우지 않고 유효한 반려도 원래 수정 순서에 전달한다.
3. 동일 실행 안에서만 task ID, 원문/후보 입력, 분석·전략, 프롬프트·스키마·validator·검토 정책·모델 설정의 지문에 결과를 결속한다. 일반 서비스의 영속 승인 캐시를 새로 만드는 작업과 구분한다.
4. 모델 요청 함수가 전체 묶음을 다시 시도하기 전에 항목별 결과를 받을 수 있도록 검증·복구 경계를 분리한다. 부분 결과를 일반 성공 응답으로 반환하지 않는다. 현재 유효 후보의 해당 단계에 필요한 task가 모두 해결돼야 그 단계를 통과한다. 앞 카드나 품질의 유효 반려가 확정되면 기존 수정 순서를 먼저 수행하고, 수정으로 무효화될 뒤 전체 검토는 이전 후보에서 복구하지 않고 보류·폐기한다.
5. 실패 항목은 원래 전체 검토 입력·스키마·validator로 다시 요청한다. 다른 task의 승인을 판단 근거로 전달하지 않는다. 여러 형식 오류를 다시 묶을지는 크기와 오류율을 비교해 결정한다.
6. 내용 수정은 기존 카드 → 품질 → 전체 검토 순서를 따른다. 카드가 바뀌면 그 카드와 품질·전체 검토 등 종속 결과를 무효화한다. 분석·전략 변경은 관련 하위 결과도 무효화한다.
7. 항목 복구가 기존 시도 한도 안에서 실패하거나 의존성을 확정할 수 없으면 현재 전체 폐기·개별 복구로 돌아간다. 실패 항목마다 중첩 무제한 재시도를 새로 만들지 않는다. 기존 작업 재시작 정책 변경은 상위 기획에서 별도로 다룬다.

### 완료 기준

- 같은 후보에서 한 task만 형식 오류일 때 유효한 형제 task를 반복 생성하지 않는다. 해결되지 않은 task가 있으면 공개·저장 완료로 처리하지 않는다.
- 정상 승인과 형식 오류뿐 아니라 **앞 카드 반려 + 뒤 전체 검토 형식 오류** 조합에서도 수정 전 승인이 살아남지 않는다. 곧 무효화할 뒤 검토를 먼저 재요청하지 않으며, `improvements`와 로컬 카드 오류도 수정 필요 판정으로 유지한다.
- 품질 수정, 분석 수정, 분할 묶음의 뒤쪽 실패, stale 지적, 긴급 전환, 취소·정정·삭제를 주입한다.
- 기존 fallback 검사는 기본 경로에서 유지한다. 새 opt-in 경로의 보호 조건을 별도로 증명한 뒤 명시적으로 기대값을 추가한다. 기존 안전 검사를 단순 삭제하지 않는다.
- 오류를 포함한 총 POST·출력 토큰·실제 완료시간이 줄고 의미 오류나 미완료 비율이 늘지 않는다.

## 6. R3 — 전략·발화 상세의 근거 ID 확장

### 현재 동작

[final-evidence-transport.js](../app/src/final-evidence-transport.js)의 최종 근거 ID 변환은 분석 및 분석 수정 단계에 한정돼 있다. 전략의 `opening_evidence`, 발화 상세의 각 단계 `evidence`에는 기존 인용 객체가 남는다. 대화문 상세의 excerpt는 이미 구간 경계를 선택한 뒤 서버가 원래 script에서 복원하므로 이 절감을 신규 효과로 세지 않는다.

### 구현 방향

- 먼저 `communication_plan`과 그 수정 경로, 이어 `speech_detail` 및 수정 경로의 정확한 근거 위치만 지원한다.
- 원래 schema의 허용 근거 객체를 짧은 ID로 표현한다. 위치마다 허용 ID 목록을 따로 유지하고 빈 후보·지원하지 않는 schema는 기존 전송으로 돌아간다.
- 모델이 선택한 ID를 정확한 `{subject, question_id, quote}`로 복원한 뒤 **기존 전체 스키마·근거·의미 검사와 독립 검토**를 수행한다.
- 반려 출력·수정 피드백·재시도에서도 ID가 다른 원문에 재배정되지 않도록 한다. 참조표는 요청/작업 범위 밖으로 공유하지 않는다.
- 반환·저장·독립 검토의 논리 payload에는 기존 인용 객체를 유지한다. `why`나 개인화된 의미 판단을 서버가 대신 생성하지 않는다.

### 완료 기준

- ID 왕복 복원, 위치 간 ID 혼용 거절, 부정·시점·사람 보존, 빈 후보, 잘못된 ID, 수정 후 오래된 ID를 검사한다.
- 상세의 세 excerpt를 합치면 확정 script와 같고, 상세 독립 검토·저장·재조회가 유지된다.
- 근거 표·지시문을 포함한 입력 비용과 인용 재출력 감소를 함께 측정한다. 긴 인용 사례에서도 재시도 포함 총시간이 좋아지는지 확인한다.

## 7. R4 — 승인된 후속 본문 즉시 표시

### 현재 동작

[ContinuationScreen.js](../app/public/js/components/ContinuationScreen.js)의 `perform()`은 POST 응답을 `accept()`한 뒤 `await this.list(sequence)`를 기다리고 `finally`에서 `draw()`한다. 승인 답변이나 저장된 카드가 이미 도착해도 회차 목록 GET이 느리면 화면과 busy 해제가 함께 늦어진다. `start()`·`open()`에도 목록 조회와 본문 표시의 결합이 있다.

### 구현 방향

1. 현재 화면 sequence·회차 ID·revision을 확인한 POST 성공 응답을 반영하고 기존 본문을 즉시 갱신한다. 서버 pending·완료 상태에 맞춰 입력 가능 여부를 결정한다.
2. 회차 목록 갱신은 별도 요청 수명으로 관리한다. POST 완료 처리와 목록 실패 처리를 분리해, 목록 오류 때문에 이미 전송한 입력을 복원하거나 성공한 POST를 재전송하지 않는다.
3. 목록 응답은 목록만 갱신한다. 화면 sequence와 별도로 목록 요청 번호·기준 record를 캡처해 최신 요청만 목록과 목록 오류를 반영한다. 같은 화면의 연속 요청에서도 오래된 목록이 최신 목록·성공 안내를 덮어쓰지 않게 한다. 화면 이동·다음 동작·정정·삭제 후 현재 본문·revision·새 초안을 덮어쓰는 것도 차단한다. 이전 목록 요청의 종료 처리는 새 POST의 `controller`·`busy`에 영향을 주지 않아야 한다.
4. POST의 `request_id` 재시도 계약, 입력 미리 작성, focus·scroll·복사 기능과 기존 디자인을 유지한다. `start()`·`open()`도 실제 선택 회차가 확정된 뒤 같은 원칙을 적용한다.

### 완료 기준

- POST 성공 후 목록 GET을 지연시켜도 승인 답변·카드가 보이며, 서버 상태가 허용하는 다음 입력을 사용할 수 있다.
- 목록 실패 때 성공한 메시지가 사라지거나 제출 입력이 중복 복원되지 않는다. 목록 재시도는 모델 POST를 유발하지 않는다.
- 목록 대기 중 새 전송·화면 이동·정정·삭제·완료를 수행해 오래된 응답의 덮어쓰기가 없는지 검사한다. 같은 화면에서 두 목록 응답의 순서를 뒤집고 이전 목록을 실패시켜, 최신 목록·안내·새 POST의 busy/controller가 보존되는지도 확인한다.
- 결과·기록·생성 중·좁은 화면에서 기존 카드 형식과 입력 보존을 확인한다.
- `POST 응답 수신 → 실제 본문 표시`를 별도 측정한다. 모델 시간 감소로 보고하지 않는다.

## 8. R5 — 과거 회차 일괄 조회

### 현재 동작

[continuations.js](../app/src/continuations.js)의 `sources()`는 기준 record와 회차 목록을 읽고 이전 회차마다 `await store.getContinuation()`을 실행한다. 각 조회는 [continuation-store.js](../app/src/continuation-store.js)에서 트랜잭션·owner SHARE 잠금·조회·복호화를 수행한다.

### 구현 방향

- 기준 record, 현재 회차의 존재·소유자·revision, 현재 회차 이전의 원문을 일관된 읽기 범위로 가져오는 Store 메서드를 추가한다.
- `owner + source_record_id + 현재 회차 이전 sequence` 조건과 DB의 순서를 유지한다. 미래 회차·다른 기준 기록은 포함하지 않는다. 현재 요청이 캡처한 revision과 다르면 기존 충돌 경로로 돌아간다.
- 기존 owner 잠금과 정정·삭제 직렬화 계약을 보존한다. 트랜잭션 안에서 모델·네트워크 작업은 하지 않는다.
- 전체 원문과 메시지 순서를 유지하고, 각 회차의 기존 AAD로 복호화한다. 왕복을 줄이는 작업이며 복호화 대상 원문이나 의미를 임의로 줄이는 작업은 아니다.
- [기존 복합 인덱스](../app/migrations/009_continuations.sql)를 먼저 활용한다. 쿼리 계획에서 필요성이 입증되지 않으면 인덱스·마이그레이션을 추가하지 않는다.

### 완료 기준

- 이전 회차 0/1/여러 개, 과거 회차 다시 열기, 앞 회차 정정·삭제, 다른 사용자 접근에서 기존 모델 입력과 동일하다.
- 이전 회차 수에 비례해 증가하는 조회·트랜잭션 왕복을 제거한다. 전체 처리시간·잠금 대기·복호화 시간은 따로 기록한다.
- 조회 후 모델 실행 중 정정·삭제가 발생해도 최종 저장의 revision 검사가 늦은 결과를 차단한다.

## 9. R6 — 진행 조회 경량화

### 현재 동작과 분리 원칙

[server.js](../app/src/server.js)의 progress GET은 공통 `store.browser()` 인증 후 `store.intake()`로 상담 전체를 복호화한다. [store.js](../app/src/store.js)의 `browser()`는 매번 `last_active_at`을 UPDATE하며, 이 잠금은 만료·삭제와 경합할 때 세션이 되살아나는 것을 막는 역할도 한다.

따라서 이 항목을 두 단계로 나눈다.

| 단계 | 구현 범위 | 경계 |
| --- | --- | --- |
| R6-a 우선 | 활성 진행 조회에서 owner·존재·revision만 읽고 해당 실행의 progress 사용 | 기존 인증·활동 갱신 유지 |
| R6-b 조건부 후속 | 활동 갱신의 빈도 제어 가능성 조사 | 만료·삭제·보존기간 의미가 같다는 증거 전에는 변경하지 않음 |

### 구현 방향

- 활성 실행 탐색에는 최소 메타데이터 조회를 사용한다. 메모리의 실행 존재만으로 권한이나 상담 존재를 인정하지 않는다.
- `savedRevision`으로 연결된 실행, 취소된 실행, 저장 직후 경합을 현재 계약대로 구분한다.
- 활성 실행이 없으면 기존 전체 상태·저장 record 확인 경로를 유지한다. 기록이 실제 없는데 progress만 보고 완료로 응답하지 않는다.
- R6-b에서는 단순한 메모리 인증 캐시나 일정 시간 UPDATE 생략을 바로 도입하지 않는다. 만료 직전 사용, 정리 작업, 다중 프로세스, 전체 삭제와의 경합 및 실제 보존기간 변화부터 검증한다. 동등성을 확보하지 못하면 기존 UPDATE를 유지한다.

### 완료 기준

- 활성 progress 반복 조회에서 전체 상담 복호화가 제거되면서 응답 의미가 같다.
- 삭제된 상담, 만료 세션, 다른 owner, 이전 revision, 저장 직후, 프로세스 재시작 뒤 조회를 검사한다.
- 긴 생성·다중 탭에서 DB query·쓰기·복호화 횟수와 지연을 각각 측정한다. R6-a만 적용했는데 인증 UPDATE까지 줄었다고 보고하지 않는다.

전송·복구 변경은 기존 기본 경로와 비교 가능한 opt-in으로 도입한다. 플래그 이름은 구현 시 설정·구성 검사·문서에 함께 정의한다. 원문이나 개인정보를 캐시 키 진단 로그에 노출하지 않고 비가역 지문·크기·단계만 기록한다. 되돌리기는 새 작업부터 기존 경로로 적용하며 진행 중 작업의 계약을 섞지 않는다.

## 11. 시간 비교와 채택 기준

- 같은 합성 입력·모델·설정에서 변경 전후를 교차 실행한다. 짧은/긴 원문, 정정, 후속 여러 회차, 정상/형식 실패/의미 반려를 분리한다.
- 모델 비교는 입력·출력 토큰, 실제 POST 시도, 재시도·fallback, 첫 승인 카드와 전체 저장 완료시간을 함께 기록한다. 실제 토큰을 알 수 없으면 본문 bytes와 구분해 미측정으로 남긴다.
- R4는 POST 이후 표시 지연, R5/R6는 DB 왕복·잠금·복호화 시간을 별도로 본다. 서로 겹치는 시간 절감을 합산하지 않는다.
- 반복 수·동시성·워밍업·최초 로딩과 대화 2초/카드 600초 판정은 상위 기획의 검증 조건을 따른다. 실패·초과·취소를 숨기지 않는다.
- 고정 합성 응답은 전송·저장 계약 검증에 사용한다. 실제 생성·검토 품질과 처리시간은 로컬 실모델에서 별도로 검증한다.
- 최종 채택은 기능·근거·검토·삭제·격리·디자인을 보존하면서 해당 구간과 전체 사용자 대기가 개선되는지로 판단한다. 효과가 작거나 오류가 늘면 그 변경만 보류한다.
