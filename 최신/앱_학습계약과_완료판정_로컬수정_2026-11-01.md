# 앱·학습 계약과 완료 판정의 우선순위 및 로컬 수정

2026-11-01, Asia/Seoul. 네 종합 문서의 재검토 결과를 바탕으로 코드와 로컬 정책을 수정했다. GPU 서버 접속·추론·학습·배포는 수행하지 않았다. 기존 미커밋 변경, 동결 데이터, 실행 중인 서비스와 과거 체크포인트는 보존했다.

## 1. 앱 계약 검사

[check_training_app_contract.py](../ai/scripts/check_training_app_contract.py)는 현재 앱 파일을 동결 스냅샷과 비교한다. [Node 검사기](../ai/scripts/check_training_memory_contract.mjs)는 저장된 memory_review 행의 실제 입력·정답을 현재 앱의 요청 생성과 검증 콜백에 전달한다. 모델은 호출하지 않는다.

```sh
python3 -B ai/scripts/check_training_app_contract.py \
  --root training_data/gemma4_12b_review_versions_20261101_v2/gemma4_12b_B_reviewer_20261101_v2
```

현재 B/C와 검토 원본의 memory_review **800행**은 콜백 반려 0, 스키마 차이 0, 입력 차이 0이다. 그러나 프롬프트 차이는 **800행**, 고유 앱 파일 해시 차이는 **3개**다. `review_required`와 종료 코드 2를 반환한다. 같은 원천에서 파생한 B/C/원본을 더해 2,400개 독립 검증 사례로 세지 않는다. A는 memory_review 행이 없으므로 그 과제는 `not_covered`다.

검사기는 manifest에 묶인 스냅샷·COURSE·검사 대상 messages를 확인하고 실행 전후 코드·데이터 변경도 검사한다. 전체 tokenizer 수치 감사나 모든 과제의 의미 품질을 대신하지 않는다. `training_ready=false`, `previous_semantic_approval_reused=false`를 유지한다.

**이번에는 데이터의 프롬프트나 정답을 덮어쓰지 않았다.** 구조적으로 통과한 정답이 새 프롬프트에서도 의미적으로 올바른지는 별도 검토가 필요하다. 자동 해시 갱신으로 과거 승인을 재사용하는 것을 수정으로 취급하지 않는다.

## 2. 최신 A/B/C 정책

[training_stop.py](../ai/scripts/training_stop.py)에 명시적 `--chat-variant`와 평가·앱 계약 결합을 추가했다. 단순히 ‘아무 단계 수나 허용’하도록 제한을 제거하지 않았다. 알려진 A/B/C별 단계 순서와 과제 목록, 분할·손실·가중치·원본 결합을 검사한다. 기존 cards 정책과 legacy API는 유지한다.

다음 새 로컬 폴더에 정책을 생성하고 실제 각 단계의 `bound_indexes()` 검사를 통과했다.

| 묶음 | 새 정책 | 현재 상태 |
|---|---|---|
| A | [POLICY v3](../training_data/training_completion_abc_A_20261101_v3/POLICY.json) | 기존 개발 평가에 생성 과제 범위가 있음. 앱 계약 검토·실제 baseline/후보 판정은 남음 |
| B | [POLICY v3](../training_data/training_completion_abc_B_20261101_v3/POLICY.json) | answer_review·memory_review 평가와 의미 판정 계약 미비로 pending |
| C | [POLICY v3](../training_data/training_completion_abc_C_20261101_v3/POLICY.json) | 새 04_result_review 단계 결합. 같은 두 검토 과제의 평가 미비로 pending |

새 검토 단계의 자원 보호 상한 2는 보수적인 초기 설정이며 성능상 최적 횟수나 완료 기준이 아니다. 손실 개선·최종 품질 기준을 낮추지 않는다. 기존 데이터·평가 manifest는 변경하지 않았다. 실제 결합 조건·CLI는 [종료 정책 설명](../ai/scripts/training_stop_README.md)을 따른다.

최종 제공본은 v3이다. 구현 중 생성한 v1/v2는 이전 준비 스냅샷으로 보존하며 새 완료 계약에 사용하지 않는다. v3은 `variant_completion_contract=task_coverage_and_current_app_contract_v1`을 정책 해시에 결합한다. **A도 앱 drift가 남으면 최종 완료가 불가능**하다. 앱 match 보고서가 있더라도 최종 채점 때 현재 검사를 재실행해 해시·상태가 같아야 통과한다. 코드·데이터를 바꾸고 이전 match만 재사용하는 경로를 차단한다.

## 3. 31B 최종 평가 연결

[cards31b_completion.py](../ai/scripts/cards31b_completion.py)와 [trainer](../ai/scripts/train_cards_31b.py)의 `--completion-config`를 연결했다. 실제 baseline·suite·policy를 새 실행 전에 고정하고 전체 journal과 checkpoint를 검사해 기존 `training_stop.decide()`에 넘긴다.

마지막 epoch의 실제 role evidence가 없으면 pending을 유지한다. 증거가 들어오면 재시작에서 모델 로드 전에 검사한다. 같은 후보가 손실·품질 기준을 모두 만족해야 완료하고, 계속 조건이면 다음 epoch, 미달 종료 조건이면 incomplete로 멈춘다. 이전 소비 증거의 변경이나 과거 후보의 평가로 승인하지 않는다.

**현재 실행에 소급 적용하지 않는다.** 새 소스·config는 runner binding에 포함되므로 기존 checkpoint의 binding을 덮어써 맞추면 안 된다. 새 reference 실행용 opt-in 경로이며 실제 baseline이 없는 상태에서 빈 양식을 채워 완료 설정을 만들지 않았다. 자세한 준비·전달 절차는 [연결부 사용 안내](../ai/scripts/cards31b_completion_README.md)에 있다.

## 4. 검증과 남은 작업

핵심 검증은 합성 CPU 자료로 수행한다. 실제 memory 검토 행의 검사는 읽기 전용이며 원문을 로그·문서로 복사하지 않았다. 독립 코드 검토에서 발견한 빈 checkpoint 승인과 단계 사이 재시작의 과거 증거 검사 누락은 수정하고 회귀를 추가했다.

| 실행 검사 | 결과 |
|---|---|
| 종료 정책 `test_training_stop.py` | 77개 통과 |
| 새 completion bridge `test_cards31b_completion.py` | 19개 통과 |
| 기존 31B runner `test_train_cards_31b.py` | 30개 통과 |
| Python 앱 계약 검사 | 13개 통과 |
| Node 메모리 계약·기존 투영 검사 | 18개 통과 |
| 채팅 확장 회귀 | 6개 통과 |
| 역할 평가 데이터 회귀 | 2개 통과 |

새 정책 세 개는 실제 전체 단계의 index·연결 파일을 검증했으며 원본 dataset/evaluation manifest의 변경이 없음을 대조했다. 위 회귀는 실제 모델 학습 성능을 측정한 결과가 아니다.

남은 작업은 새 프롬프트 기준 데이터 재생성 후보의 독립 의미 검토, B/C 검토 역할 평가셋·판정 기준, 실제 학습 전 baseline 및 학습 후 후보 평가다. GPU 실행은 사용자 재허용 전까지 수행하지 않는다. 모델 학습·미노출 시험·배포가 완료됐다는 주장은 하지 않는다.
