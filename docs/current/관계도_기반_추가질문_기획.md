# 관계도 기반 추가 질문·답변 기능 기획

- 작성일: 2026-11-01
- 상태: 구현·로컬 기능 검증 완료 · 실제 모델 전체 실행 미확인
- 작업 브랜치: `codex/relationship-followup-plan`
- 최초 기획의 코드 확인 기준: `dc02c6832029e54268090d95a50fcad7db95fc5c` (`main`)
- 목적: 기존 질문으로 생성·저장한 사용자의 관계 정보를 활용하여, 결과 확인 후에도 사용자가 추가 질문을 입력하고 맥락에 맞는 답변을 받을 수 있게 한다.
- 구현 범위: 후속 대화 저장·API·모델 검토·화면과 사용자가 요청하는 새 카드 생성을 추가한다. 기존 질문은행·관계도·결과 카드 표시는 유지한다.
- 사용자 추가 요청(2026-11-01): 추가로 생긴 상황을 이야기한 뒤 버튼으로 새 카드 생성에 진입한다. 자동 재생성 없이 `새 카드 만들기`로 실행한다.

## 1. 사용자에게 제공할 경험

“처음부터 다시 설명하지 않고, 지난 이야기에서 이어서 이야기한다.”

사용자가 완료된 결과나 기록에서 **추가 질문하기**를 선택하면, 서비스는 그 기록에 담긴 관계와 이전 답변을 참고한다. 사용자는 “이런 상황에서는 어떻게 말을 꺼내면 좋을까요?”처럼 궁금한 내용을 바로 입력하고 답변을 받는다. 더 설명해 달라고 하거나, 상황을 추가하거나, 답변에 다시 질문하며 대화를 이어갈 수 있다. 답변에 꼭 필요한 정보가 부족할 때만 서비스가 확인 질문을 한 번에 하나씩 제시한다. 사용자는 확인 질문을 건너뛰거나 언제든 마칠 수 있다.

핵심은 **사용자가 묻고 서비스가 기존 관계 맥락에 근거해 답하는 양방향 대화**다. 서비스가 먼저 묻는 추가 질문은 필요한 확인을 위한 보조 기능이다. 기존 질문지를 완주시키거나 새 설문을 강제하지 않는다. 상대방에게 직접 연락하거나 메시지를 보내는 기능은 포함하지 않는다.

아래 표는 최초 기획 기준 커밋에서 확인한 기존 동작이다. 이후 절은 이 브랜치에 반영한 후속 기능과 검증 기준을 설명한다. 실제 모델·브라우저 완료 검증은 별도 실행 증거로 확인한다.

| 현재 확인한 구조 | 기획에 반영할 사항 |
| --- | --- |
| `relationship_analysis`에는 대상자·이용자 요약, 관찰, 관계 역할·특징·강점·한계, 미확인 사항과 안전 정보가 있다. | 이 문서의 “관계도”는 이 구조화된 분석을 뜻한다. 별도 노드·간선 그래프나 새 시각화 구축은 이번 범위에 넣지 않는다. |

| 익명 세션·CSRF·암호화·버전 검증·삭제/취소 계약이 있다. | 새 대화에도 같은 소유권과 저장·삭제 경계를 적용한다. |

## 3. 1차 범위와 제외 범위

### 구현 범위

1. 완료 결과·기록에서 후속 대화를 시작하고, 진행 중인 대화가 있으면 이어서 연다.
2. 선택한 기록의 관계 분석과 검증 가능한 원문, 해당 기록에 연결된 후속 답변을 문맥으로 사용한다.
3. 사용자 추가 질문 → 관계 맥락에 근거한 답변 → 사용자 재질문/새 상황 입력의 흐름을 제공한다. 필요한 경우에만 확인 질문 1개를 덧붙인다.
4. 말 꺼내기·구체적 표현·상대 반응에 대한 다음 행동·사용자 부담에 관한 질문에 답한다. 답변을 위해 변화 확인·장면 구체화·정보 정정이 필요하면 보조 질문을 사용한다.
5. 미응답·모름·거절·건너뜀을 구분하고, 서비스의 확인 질문 반복을 막으며, 새로고침 후 대화를 복원한다.
6. 사용자가 마치면 검토된 사실 인용 또는 고정 종료 안내를 저장한다. 필요할 때 다음 회차를 시작할 수 있다.
7. `새 카드 만들기`를 누르면 실제 추가 보고를 재검토하고 기존 카드 생성 경로로 새 카드를 만든다. 원본 기록은 보존하고 새 카드는 후속 회차 안에 저장한다.

### 이번 범위에서 제외

- 배포·학습·GPU 서버 사용. 기존 로컬 모델 전송 계층을 재사용한다.
- 여러 사람의 기록을 합친 인맥 그래프, 계정 간 공유, 자동 연락·알림·예약 메시지.
- 기존 질문은행 문구·순서 변경, 기존 질문 생략 기능 제거, 모든 질문에 대한 답변 강제.
- 기존 카드 디자인 변경, 원래 카드 교체, 사용자 요청 없는 카드 자동 재생성.
- 진단·위험 점수·상대 마음 판정, 상담 효과나 관계 개선 효과에 대한 보장.

## 4. 사용자 흐름

| 단계 | 사용자 경험 | 내부 처리 |
| --- | --- | --- |
| 진입 | 결과·기록의 카드 바깥에 `추가 질문하기` 버튼을 둔다. | 원본 완료 여부·소유권·근거 가용성 확인. 해당 기록에 진행 중인 후속 대화가 있으면 재개한다. |
| 시작 | “이 관계에 대해 더 궁금한 점을 물어보세요.”와 자유 입력을 제공한다. | 첫 질문에서 현재 요청을 파악한다. 이전 상황이 지금도 같다고 가정하지 않는다. 별도 목표 문항을 강제하지 않는다. |
| 소재 선택 | 입력이 막힐 때 `어떻게 말을 꺼낼까요?`, `이렇게 답하면 어떨까요?`, `제 부담은 어떻게 말할까요?` 같은 질문 예시를 제공한다. | 예시는 입력 보조다. 예시를 고른 것만으로 행동·감정이 실제로 발생했다고 저장하지 않는다. |
| 대화 | 사용자의 질문에 먼저 답하고, 추가 질문을 계속 입력할 수 있게 한다. 답변에 필요한 경우에만 확인 질문 하나를 제시한다. | 검증된 원문으로 문맥 갱신 → 답변 및 필요한 확인 질문 작성 → 근거·전제·주체·부담 검토 → 답변 공개. |
| 방향 전환 | 사용자가 다른 이야기를 입력하면 그 내용을 먼저 다룬다. | 새 목표를 반영하고 무관해진 후보는 생략한다. |
| 정정 | “지난번 이야기는 잘못 전달됐어요”처럼 정정할 수 있다. | 해당 근거와 연결된 후속 해석·질문을 무효화하고 정정된 문맥으로 이어간다. |
| 새 카드 | 추가 상황을 입력한 뒤 `새 카드 만들기`를 누른다. | 실제 보고를 검토하고 새 카드 문맥을 구성한다. 기존 카드 생성·검토를 통과한 전체 카드 스냅샷만 후속 회차에 추가한다. |
| 잠시 멈춤 | 나갔다 돌아와도 마지막 저장 답변과 질문을 이어서 본다. | 진행 중 회차를 저장하고 복원한다. 답변·확인 질문 대기 중에는 기존 점 세 개 표시를 사용한다. |
| 마무리 | `여기까지 이야기하기`를 선택한다. | 마지막 검토에서 확인한 사실 인용 또는 고정 종료 안내를 저장한다. 원래 결과 카드는 보존한다. |
| 다시 시작 | 완료한 후속 대화는 읽기 전용으로 보고 새 회차를 연다. | 같은 원본에 연결된 이전 회차의 유효한 근거를 이용하되 현재 상황을 다시 확인한다. |

사용자 질문 횟수나 확인 질문 개수로 대화를 강제 종료하지 않는다. `여기까지 이야기하기`를 항상 제공하고 사용자가 직접 마친다. 답변을 마친 뒤에는 입력 가능한 상태로 기다리며, 질문을 매번 돌려주거나 새로운 문제를 만들어 대화를 늘리지 않는다.

원문 문맥을 확인할 수 없는 이전 기록은 `SOURCE_CONTEXT_UNAVAILABLE`로 후속 대화 생성을 거절하고 새 대화에서 상황을 입력하도록 안내한다. 입력받지 않은 과거 사실을 복원하지 않는다.

## 5. 추가 질문에 대한 답변과 보조 질문 규칙

### 사용자 질문 처리

- 질문·새 사실 보고·정정·가정 상황·일반 표현 요청을 구분한다. “만약 답이 없다면요?”는 실제 무응답 사건의 보고로 저장하지 않는다.
- 원래 결과의 표현을 설명하거나 대안을 제시할 수 있지만, 모델의 이전 답변과 제안은 사용자 사실의 근거로 삼지 않는다.
- 사용자가 요구한 답을 먼저 제공한다. 단순 문구 수정에는 불필요한 추가 설문을 하지 않는다.
- 사실 확인이 꼭 필요하면 부족한 점을 짧게 밝히고 확인 질문 하나를 한다. 일반적인 선택지를 조건부로 제안할 수 있을 때는 사용자를 기다리게 하는 확인 질문을 강제하지 않는다.
- 상대방의 진단·속마음을 묻는 질문에는 단정하지 않고 관찰 가능한 내용과 직접 확인할 방법을 구분한다.
- 현재 기록과 무관한 다른 사람의 상황은 자동으로 기록을 합치지 않는다. 가정으로 답하거나 별도 상담을 시작하도록 안내한다.

| 사용자의 추가 질문 예시 | 기대 답변 방식 |
| --- | --- |
| “지난 안내보다 짧게 말을 꺼내고 싶어요. 어떻게 말하면 될까요?” | 기존 목적과 확인된 장면을 유지한 짧은 표현을 제안한다. 원래 카드는 바꾸지 않는다. |
| “아직 말을 못 걸었는데 뭐부터 하면 좋을까요?” | 실행하지 않았다는 현재 보고를 반영해 작은 선택지를 제안한다. 상대 반응을 지어내지 않는다. |
| “만약 답장이 없으면 다시 연락해도 될까요?” | 가정 상황임을 유지하고 선택권·부담을 고려한 조건부 대안을 제시한다. |
| “저도 지쳤다는 말을 어떻게 전하면 좋을까요?” | 사용자가 밝힌 부담에 근거해 한계를 전하는 표현을 제안한다. 무제한 돌봄을 요구하지 않는다. |
| “그 사람이 저를 싫어하는 걸까요?” | 상대 마음을 확정하지 않고 실제 관찰과 가능한 확인 방법을 구분한다. |

아래의 후보 선정·질문 예시는 **서비스가 필요한 때만 묻는 보조 질문**에 적용한다.

### 질문에 사용할 문맥

- 사용자가 직접 선택한 하나의 원본 기록과 연결된 intake의 원문·문항 스냅샷.
- 근거 검증을 통과한 `relationship_analysis`와 관계 메모리. 설명의 방향을 잡는 보조 정보로 사용하며 원문을 대체하지 않는다.
- 같은 원본에 연결된 후속 대화의 실제 답변, 정정 이력, 최신 목표, 이미 묻거나 거절한 주제.
- 답변 작성 시점과 답변에서 명시한 사건 시점을 구분한다. 오래된 정보를 현재 사실로 자동 승격하지 않는다.

### 후보 선택 순서

1. 명시적인 안전 상황이면 기존 검증된 안전 종료 흐름을 우선한다.
2. 사용자의 정정·새 요청·지금 이야기하고 싶은 목표를 우선한다.
3. 다음 질문이 사실을 전제하게 되는 중요한 불확실성부터 열린 형태로 확인한다.
4. 이전 대화 이후 변화나 실제로 시도한 행동이 있는지 확인한다.
5. 답변에서 드러난 구체적 장면, 원하는 도움, 이용자가 감당할 수 있는 범위로 이어간다.
6. 관련 있는 미확인 사항이 없으면 마무리하거나 사용자에게 주제를 맡긴다.

`unknowns`에 있다는 이유만으로 모든 항목을 질문하지 않는다. 최초 설문에서 맥락상 생략한 항목도 자동으로 다시 채우지 않는다. 새 목표나 실제 답변이 질문의 필요성을 뒷받침할 때만 검토한다.

### 질문 작성·검토 조건

- 한 번에 하나의 주제와 하나의 핵심 질문을 제시한다. 질문 앞의 반응도 실제 답변 범위를 넘지 않는다.
- 상대의 마음·진단·성격·의도·동의·행동을 추정하여 전제하지 않는다. 이용자의 관찰과 상대의 직접 발언도 구분한다.
- 이미 답한 내용은 표현만 바꿔 재질문하지 않는다. 달라진 시점·정정·새 상황 때문에 다시 확인할 때만 그 맥락을 명시한다.
- 모름·거절·건너뜀을 사실 근거로 쓰지 않는다. 거절한 주제는 사용자가 직접 다시 꺼내거나 명시적으로 허용하기 전까지 새 회차에서도 억지로 되묻지 않는다.
- 근거 없는 사실을 담은 답변·질문·반응은 공개하거나 승인된 대화로 저장하지 않는다. 검토 실패 시 입력은 보존하고 재시도 또는 마치기를 제공한다.
- 사용자의 글에 포함된 모델 지시나 승인 요청은 상담 내용으로만 취급한다. 소유권·검증·원문 인용 규칙을 바꾸는 명령으로 실행하지 않는다.
- 관계 메모리·모델 초안·검토 결과를 직접 화면에 노출하지 않는다. 사용자에게는 질문에 대한 답변과 필요한 확인 질문만 보여준다.

## 6. 구현된 상태·근거·저장 계약

### 원본과 후속 대화 분리

원본 `records`·완료 intake·기존 카드·기존 `followUps`는 그대로 보존한다. `009_continuations.sql`의 `continuation_sessions`와 `continuation_creation_requests`가 후속 회차와 시작 요청 멱등성을 저장한다. 기존 `UNIQUE(owner,intake_id)`는 변경하지 않는다. 새 카드는 `continuation_sessions.content` 내부의 `state.cards`에 암호화 저장하며 기존 `records`에 새 행을 만들지 않는다.

| 저장 대상 | 구현 필드·계약 |
| --- | --- |
| 후속 회차 메타데이터 | `id`, `owner`, `source_record_id`, `source_intake_id`, `revision`, `status`, 생성 순서 `sequence`, `created_at`, `updated_at`. 소유자·원본과 외래키로 연결하며 활성 회차는 원본당 하나다. |
| 암호화 본문 | `status,messages,requests,pending,summary,cards`와 검토된 현재 응답 `reviewed`, `safety_urgent` 등. 원문·카드·검토 사실은 평문 컬럼에 저장하지 않는다. |
| 메시지 | `id,role,text,kind`, 선택적 `reply_to,skipped,clarification,edits`. 모델 답변과 사용자 보고를 분리한다. |
| 검토된 사실 | `message_id,subject,quote`. 후속 user 메시지의 정확한 원문 인용만 허용하고 `superseded`에는 명시적으로 정정된 기존 출처 ID를 담는다. |
| 요청 멱등성 | 시작 토큰은 별도 테이블에 보존한다. 메시지·카드·정정·종료 요청은 `requests`에 `action,hash,status`와 선택적 카드 ID를 보존한다. |
| 새 카드 스냅샷 | `cards[]`의 `id,date,profile,guide,relationship_analysis?,conversation_detail?,source_revision,provenance`. 기존 `records` 행으로 저장하거나 원본 카드에 덮어쓰지 않는다. |
| 회차 간 문맥 | 같은 원본의 앞선 회차를 DB 생성 순서로 매번 읽는다. 이후 회차를 과거 회차 문맥에 포함하지 않으며 별도 복제 기억으로 원문을 남기지 않는다. |


기존 설문의 `subject`는 문항 구성에 연결되어 있다. 후속 자유 입력에 두 사람의 이야기가 섞이면 실제 화자는 이용자임을 유지하고, 진술 대상이 불명확한 문장을 상대의 직접 보고로 저장하지 않는다. 확인 질문으로 주체를 구분하거나 미확인으로 남긴다.

### 턴 처리와 정정

1. 소유권·Origin/CSRF·현재 revision·`conversation_epoch`를 검증한다.
2. 사용자가 보낸 원문과 멱등 요청 ID를 먼저 암호화 저장한다. 사용자 답변 저장과 모델 해석 승인을 분리한다.
3. 원본의 유효 근거와 현재 회차까지의 답변으로 추가 질문에 대한 답변·필요한 확인 질문·메모리 변경안을 만든다.
4. 구조·원문 인용·주체·질문 중복·가설 단정·안전 검토를 통과한 결과만 현재 상태로 채택한다.
5. 저장 직전에 삭제·정정·버전 변경을 다시 확인한다. 오래된 요청의 결과는 저장·표시하지 않는다.
6. 동일 요청 ID의 재전송에는 같은 처리 결과를 반환한다. 동일 ID로 내용이 달라지면 충돌로 처리한다.

현재 처리 상태는 `active → pending → active`, 사용자 종료 또는 긴급 안전 종료 시 `completed`다. DB는 `retryable`도 허용하지만 모델 실패는 `pending`과 입력을 유지하여 같은 요청 ID로 재시도한다. 대기 중 종료는 해당 작업을 취소하고 저장된 내용으로 마친다. `NO_NEW_FACTS`는 해당 카드 시도만 무효화하고 대기를 해제한다. 삭제는 모든 상태에서 가능하며 늦게 도착한 모델 결과가 회차를 되살릴 수 없다.

정정된 원문은 이력으로 구분해 보존하고, 정정된 답변에 의존하는 후속 질문·해석·요약은 다시 검증한다. 원래 결과는 당시 기록으로 남기되 앞으로의 후속 대화에는 정정된 문맥을 사용한다. 사용자가 새 사실을 보고한 것과 시스템이 원본 결과를 수정한 것을 혼동하지 않는다.

### 보유·삭제

- [기존 보유·삭제 계약](../../app/docs/DATA_RETENTION.md)을 그대로 상속한다. 후속 대화만 별도 무기한 보유하지 않는다.
- 원본 record/intake 삭제, 전체 대화 삭제, 삭제 키 사용, 만료 정리는 연결 회차·턴·근거·이력·초안·진행 작업도 함께 제거한다.
- 후속 회차만 삭제하면 원본은 보존한다. 삭제한 회차를 참조한 이후 회차의 메모리·질문·요약도 제거하고 이후 모델 요청에서 남은 원문을 다시 검토한다. 사용자 메시지는 남기며 이후 완료 회차의 완료 상태는 유지한다. revision을 증가시키고 요청 ID에는 `action,hash,status=invalidated`만 남겨 오래된 작업과 재전송을 막는다.
- 원문은 URL·진단 로그·분석 이벤트에 넣지 않는다. 학습 데이터로 자동 전환하거나 Git에 저장하지 않는다.
- 익명 세션을 잃으면 기존 계약대로 접근할 수 없다. 삭제 키는 조회·복구 키로 사용하지 않는다.

## 7. API·화면 연결

다음 경로를 구현했으며 [API 계약](../../app/docs/API.md)과 [OpenAPI](../../app/docs/openapi.json)에 요청·응답을 함께 정의한다.

| API | 용도 |
| --- | --- |
| `POST /api/records/:recordId/continuations` | `{request_id, conversation_epoch}`로 새 회차 시작 또는 활성 회차 반환. 중복 생성 방지. |
| `GET /api/records/:recordId/continuations` | 해당 원본의 회차 목록. 목록에 원문을 싣지 않는다. |
| `GET /api/continuations/:id` | 현재 질문·저장된 로그·revision·대기 상태 복원. |
| `POST /api/continuations/:id/messages` | `{revision, request_id, text, reply_to?, skipped?}`로 자유 질문·보고·확인 답변 제출. `reply_to`는 실제 확인 질문에 답할 때만 사용하며, 질문 ID 없이 자유 질문 가능. 건너뜀은 대기 확인 질문이 있을 때만 허용. |
| `POST /api/continuations/:id/corrections` | `{revision, request_id, answer_ref, replacement}`로 근거 정정. 오래된 생성 취소·후속 상태 무효화. |
| `POST /api/continuations/:id/cards` | `{revision, request_id}`로 실제 추가 상황을 반영한 새 카드 생성. `{continuation,card}`를 반환하고 회차에 스냅샷을 저장한다. |
| `POST /api/continuations/:id/complete` | `{revision, request_id}`로 종료. 추가 모델 없이 검토된 사실 인용 또는 고정 종료 안내를 저장한다. |
| `DELETE /api/continuations/:id` | 선택 회차와 종속 근거 제거. 원본 기록 보존. |

공통으로 소유하지 않은 자원은 404, 버전 충돌은 409로 처리한다. 변경 요청은 기존 Origin·CSRF·소유권 검사를 따르며, 모델에 소유자 또는 접근 범위 선택을 맡기지 않는다. 답변·확인 질문 생성 오류에는 기존 오류 형식과 재시도 UX를 재사용한다.

화면은 결과·기록 화면의 카드 외부에 진입 버튼을 연결하고, `/continuations/:id`의 후속 대화 화면에서 회차 목록·질문 입력·새 카드 만들기·종료·삭제를 제공한다. 주소에는 불투명 회차 ID만 사용한다. 기존 카드의 배치·색상·마스코트·전체 발화·복사 버튼·정보 범위는 [UI 정보 원칙](../../app/docs/UI_CONTENT_POLICY.md)을 그대로 따른다. 대화 답변은 일반 말풍선으로 표시하고 기존 결과 카드를 매 턴 재생성하지 않는다. 내부 질문 선정 이유나 근거 목록은 신규 상세 패널로 노출하지 않는다.

완료된 새 카드는 기존 `GuideCards`의 돌봄·전체 발화·실천/회피·다음 단계·관계 표시를 재사용한다. 기존 원본 기록의 관계도는 변경하지 않는다. 후속 카드 생성에는 별도 부분 카드 진행 API를 추가하지 않고 전체 검토·저장 완료 스냅샷을 표시한다.

후속 대화에서도 불씨는 대화 중 표시하지 않는다. 명시적 안전 신호는 기존 안전 검토와 긴급 종료를 유지하고, 종료 화면에서 기존 공용 안전 카드를 표시한다. 후속 대화 중 기관 분류·추천을 새로 띄우지는 않는다. 일상 질문을 상담·위험 답변으로 유도하지 않는다.

새 저장 계층은 `app/src/continuation-store.js`, 대화 처리는 `app/src/continuations.js`, 모델 문맥·검토는 `app/src/continuation-model.js`, 화면은 `app/public/js/components/ContinuationScreen.js`에 둔다. 기존 전송·카드 생성·공용 표시 컴포넌트를 재사용하고 새 의존성은 추가하지 않는다. 기존 고정 확인 질문 enum은 바꾸지 않는다.

### 모델 검토 경로

기존 모델 전송 계층을 통해 `continuation_answer` → `support_review_continuation` → `safety_review_continuation`을 실행한다. 지원 검토는 답변·확인 질문·보고 사실·기존 근거 정정을 대조한다. 안전 검토는 추출 사실뿐 아니라 건너뛰지 않은 사용자 메시지 전체를 확인한다. 새 카드는 검토된 실제 보고를 기존 원문에 결합한 문맥으로 기존 `respond` 카드 생성·검토 경로를 실행한다. 질문이나 가정뿐이고 긴급 안전 상황도 아니면 새 카드를 만들지 않는다.

모델이 의미를 모두 정확히 판단한다는 보장은 이 구현으로 주장하지 않는다. 실제 모델 실행·품질 확인은 별도 검증이며, 이번 문서 갱신은 완료 증거를 대신하지 않는다.

## 10. 현재 결정과 후속 검토 사항

현재 기획의 기본안은 **사용자 자유 질문과 서비스 답변, 한 원본 기록에 여러 회차, 활성 회차는 하나, 필요한 확인 질문만 한 번에 하나, 원본 결과는 보존**이다. 대화는 사용자가 직접 시작하며 자동 알림은 없다. 이번 결과물에는 질문 유형·예시·저장/API 계약·수용 기준까지 포함한다.

후속 사용성 검토 항목은 추가 질문 진입 문구와 입력 예시, 후속 요약의 짧은 표시 형식, 별도 회차 삭제 시 이후 회차 재검증 UX다. 사용자가 요청한 새 카드 생성은 이번 구현에 포함한다. 여러 관계 기록 통합과 자동 연락·알림은 향후 별도 기획으로 다룬다.

### 실제 로컬 모델 연결 검증 (2026-11-01)

- `PREVIEW_MODEL_MODE=local`로 별도 포트 9012에서 로컬 `http://127.0.0.1:11434/v1`의 `gemma4:12b`를 연결한다. 원본은 합성 관계도·카드이며 후속 답변·새 카드는 빈 상태에서 실제 모델로 생성한다. 예전 모의 응답 모드는 9011에서 그대로 사용할 수 있다.

- 첫 실제 카드 검증에서 미리보기 원문에 `rel`이 빠져 화면의 “친구” 관계와 불일치한 것을 확인했다. 합성 원문에 관계 문항을 포함하고, 원문·표시 프로필의 관계 일치 회귀 검사를 추가했다. 불완전한 예시 데이터로 진행하던 작업은 취소하고 새 격리 스키마에서 재검증했다.
- 수정 후 전체 앱 검사 **2,041개 모두 통과(실패·생략 0)**, JavaScript 구문·JSON 검사도 통과했다.
- 실제 브라우저에서 새 상황과 질문을 전송했고 `continuation_answer` → `support_review_continuation` → `safety_review_continuation`을 마친 실제 답변이 표시됐다. 390×750 모바일에서도 답변·생성 대기 표시를 확인했다.
- **실제 새 카드 생성은 실패했다.** 추가 상황 재검토와 관계 분석, 대화 계획, 개별 카드 작성·검토·수정, 전체 품질 개선까지 실행했으나 `guide_quality_check`가 남은 개선 항목을 반환했다. 서버는 `MODEL_INVALID_RESPONSE` / `agent_quality_review_rejected`로 HTTP 502를 반환했다. 모델 HTTP 응답의 `reason:success`는 해당 출력의 형식 처리가 성공했다는 뜻이며, 검토기의 내용 승인을 뜻하지 않는다.
- 검증 요청 ID는 `3a5caeee-bb83-4c1a-95fa-4c71112f33a0`이다. 검증은 시간 제한으로 취소된 것이 아니라 위 품질 재검토 거절로 종료됐다. 전체 카드 생성·저장·저장 카드 재전송 성공은 이번 실제 실행에서 입증하지 못했다. 자동 검사 통과와 실제 모델 전체 성공을 구분한다.

### 품질 재검토 거절 후 수정 (2026-11-01)

- 이전 실행은 품질 재검토의 거절 사실만 기록했으므로, 당시 모델이 지적한 문장과 이유까지 확정할 수는 없다. 이번에는 합성 예시 입력의 단계별 작성·검토 결과를 로컬 임시 파일로 분리해 확인했다. 실제 이용자 대화나 모델 응답 원문을 저장소에 추가하지 않았다.
- 카드 품질 수정 경로는 검토에서 지적하지 않은 카드까지 전체 재작성할 수 있었고, 첫 수정 후 남은 오류의 수정 지시는 즉시 실패로 끝나 사용되지 않았다. 이제 지적된 카드만 수정하고 다른 카드·분류·안전 판단은 스키마와 서버 검증으로 고정한다. 재검토의 실제 남은 지적은 한 번 더 수정에 반영한다(총 두 번). 무수정 결과는 거절하며, 남은 오류가 있으면 최종 검토·저장으로 넘어가지 않는다.
- 새 실제 모델 추적에서는 상대의 통화 제안·이용자의 가능 시간·이용자의 질문을 한 개의 이용자 사실로 묶은 출력이 독립 검토에서 승인되는 문제를 확인했다. 사실을 주체별 연속 원문으로 나누도록 명시하고 각 사실의 주체·실제 보고 여부를 별도 판정하도록 보강했다. 전체 승인 표시만으로 개별 판정의 불일치·누락을 무시할 수 없다. 이 입력 오류가 이전 품질 거절의 직접 원인이었다고 단정하지 않는다.
- 검증용 API 클라이언트의 기본 응답 헤더 대기 제한으로 한 재현 요청이 중단돼, 임시 검증 스크립트는 기존 장시간 요청 전송 유틸리티를 사용하도록 수정했다. 서비스의 요청 제한·검토 정책을 완화한 변경은 아니다.
- 사실·답변의 의미 검토 거절은 형식 오류와 분리했다. 정확한 이전 후보·검토 결과를 작성자에게 전달해 한 번 수정하고 새 독립 검토를 받는다. 두 번째 의미 거절은 `agent_review_rejected`로 종료하므로 운영 기본 재시도 설정에서도 같은 생성을 무한 반복하지 않는다. 안전 검토에는 계속 사용자 원문 전체를 전달한다.
- 누락·중복 사실 감사, 전체 승인과 개별 판정 충돌, 재시도 설정에서의 제한 종료, 실제 피드백 반영, 미지적 카드 보존, 무수정 거절, 최신 품질 지적 반영과 미승인 저장 차단을 회귀 검사로 확인했다. 격리 로컬 DB의 전체 검사 **2,048개 모두 통과(실패·생략 0)**, JavaScript 구문·JSON·문서 링크 검사와 `git diff --check`도 통과했다.
- 추가 실제 실행에서 `guide_quality`가 `repair`(최대 180자)에 187자 대화문 전체를 세 번 반복해 `agent_schema`로 실패하고 전체 생성을 재시작하는 문제도 확인했다. 서버는 정확한 길이·경로 정보를 이미 전달하고 있었다. 원인은 피드백 누락이 아니라 검토기가 편집 지시와 발화 예문을 혼동하며 실패 출력을 반복한 것이었다. 같은 실패 단계의 실제 입력에 편집 지시 작성 역할을 명시한 진단 실행에서는 지적 두 개를 보존하면서 짧은 수정 지시로 응답했다. 길이 제한을 늘리거나 오류 항목을 잘라서 승인하지 않았다. 이 단계별 진단은 전체 카드 저장 성공을 대신하지 않는다.
- 품질 검토와 품질 재검토에서 `improvements[n].repair`의 길이 오류가 날 때에만 검토기의 작성 역할을 재강조한다. 원문·거절된 후보·스키마와 기존 3회 형식 수정 한도는 유지한다. 해당 오류가 끝까지 반복되면 전체 카드 생성을 다시 시작하지 않고 기존 품질 검토 실패로 종료한다. 다른 단계·다른 스키마 오류·취소에는 적용하지 않는다.
- 이 추가 수정 후 전체 회귀 검사 **2,051개 모두 통과(실패·생략 0)**. 실제 실패 입력을 별도 안내 없이 수정된 `agentComplete` 경로로 재실행한 결과도 정상 형식의 품질 지적을 반환했다. 이 재실행은 첫 응답에 통과했으므로 특화 재시도 분기가 실모델에서 실행됐다는 증거로 사용하지 않는다. 분기 자체는 합성 회귀 검사와 앞선 실모델 진단으로 구분해 검증했다.
- 다음 전체 실행에서는 카드 품질 검토에 도달하기 전에 `speech_write`가 허락 질문을 두 번 반복해 세 번 거절됐고 전체 생성을 다시 시작했다. 부분 작성 결과의 허락 질문을 통합 단계가 그대로 복사한 것으로 확인했으며, 검사 오탐이나 서로 충돌하는 문장 규칙은 아니었다. 이 재시작도 실제 실패 원문을 임시 추적 파일로 확인했다. 중복 문장 자체를 자동 삭제해 승인하거나 검증 기준을 완화하지 않는다.
- 중복 허락 질문 오류에는 실제 검출 문장·횟수·원문 보존 지시를 함께 전달하고, 통합 작성자가 미검증 부분 초안의 반복 질문을 다시 복사하지 않도록 수정 지시를 보강했다. 기존 세 번의 수정 시도 후에도 중복이 남으면 원래 오류로 종료한다. 자동 중복 삭제나 판정 완화는 하지 않는다. 전체 회귀 검사 **2,052개 모두 통과(실패·생략 0)**, 구문·JSON 및 diff 검사와 독립 코드 검토도 통과했다. 실패 입력의 별도 실모델 재실행에서는 허락 질문 한 번을 확인했으나, 이 부분 검사만으로 발화 전체나 카드 저장 성공을 주장하지 않는다.
