## 1. 새 결함과 재현 근거

### HR5 · MEDIUM · P1 — 생성한 인계본의 입력 해시와 사용한 내용이 불일치

[human_review_bundle.py:86](../../data/counseling_pipeline/human_review_bundle.py:86)의 `_snapshot()`은 파일 해시를 계산하고, [152행](../../data/counseling_pipeline/human_review_bundle.py:152)에서 초기 입력 목록을 고정한다. 그러나 pending JSONL은 [165행](../../data/counseling_pipeline/human_review_bundle.py:165)에서 별도로 읽는다. 이때 읽은 사례로 패킷을 만들면서 manifest에는 초기 해시를 기록한다. [233행](../../data/counseling_pipeline/human_review_bundle.py:233)과 [279행](../../data/counseling_pipeline/human_review_bundle.py:279)의 재검사는 입력이 원래 바이트로 복원되면 통과한다.

합성 입력 **A → B → A**의 실제 파일 쓰기 순서를 주입했다. pending 파일을 읽기 직전에 합성 응답만 B로 바꾸고, 원래 `Path.read_bytes()`가 B를 읽은 직후 A로 복원했다. 생산 해시 함수·파서·`main()`·생성기·검증기는 그대로 사용했다. 작성 동작이 정확히 한 번 실행됐고 반환 전 파일이 복원됐는지도 단언했다.

| 관측 | 실제 결과 |
|---|---|
| 정상 생성·정상 묶음 복원 대조 | 모두 종료 **0** |
| 읽기 순서를 주입한 생성 | 종료 **0**, `verified:true`, stderr 없음 |
| 생성된 manifest의 pending 입력 해시 | 원래 **A**의 해시 |
| 생성된 전문 검토 패킷의 응답 | 잠깐 읽힌 **B**의 내용 |
| 반환 시 원본 입력 | **A로 복원** |
| 같은 pin으로 즉시 일반 `--verify` 실행 | 종료 **2**, `invalid`, stderr 없음 |
| 승인 상태 | 사람 승인 **0**, 학습 허가 **false** 유지 |

생성 중 임시 묶음 검증은 같은 메모리 계획과 비교하므로 이 불일치를 놓친다. **선언한 입력에서 재현할 수 없는 묶음을 성공으로 발행**한 것이 핵심이다. HR3가 고친 manifest 읽기 자체의 일관성과 다른 경계이며, 반환 이후 파일 불변을 요구하는 지적도 아니다. 기존 `_r5`가 이 문제로 오염됐거나 사람 판단을 위조했다는 증거는 없다.

재현은 실제 임시 파일의 읽기·쓰기 순서를 제어한 **계측된 subprocess의 `main()` 실행**이다. 수정 없는 CLI에서 우연히 경쟁 조건을 이긴 빈도나 원격 공격 가능성을 측정한 검사는 아니다. 독립 검토자의 Python 3.14.3 실행과 주 검증자의 별도 경로·Python 3.12.14 재실행에서 같은 결과를 얻었다.

**완료 기준:** 각 데이터 입력의 캡처한 바이트에서 해시와 파싱 결과를 함께 만들고, 검증·패킷 생성이 그 바이트를 사용하게 한다. pending만 고쳐서는 부족하다. 릴리스 검사기의 재읽기, 질문은행 탐지, legacy 참조, 계약 사본도 동일한 소비 바이트에 결속해야 한다. 최종 안정성 검사는 보조로 유지한다. A→B→A·지속 변경·정상·복원·생성 직후 같은 pin 재검증을 회귀에 넣고, 이전 묶음은 보존한 채 새 버전을 발행한다.

### HR6 · LOW · P2 — 유효한 Unicode JSONL의 파싱·직렬화 왕복 실패

[_parse():46](../../data/counseling_pipeline/human_review_bundle.py:46)은 JSONL을 `text.splitlines()`로 나눈다. 이 함수는 LF뿐 아니라 문자열 안의 **U+2028**도 나눈다. 스키마 검사를 통과한 합성 `question_need`에 이 문자를 넣으면 하나의 유효한 JSON 레코드가 분리돼 거절된다.

| 대조 | 결과 |
|---|---|
| raw U+2028·이스케이프 표현 | `json.loads()` 결과가 동일하고 사례 스키마도 통과 |
| 직접 JSONL 파싱 | raw 표현 실패, 이스케이프 표현 통과 |
| 전체 생성 CLI | 두 표현 모두 종료 **2**, `invalid` |
| 이스케이프 입력도 실패하는 이유 | 자체 `_jsonl()`이 `ensure_ascii=False`로 raw 문자를 다시 쓰고, 임시 묶음 검증에서 거절 |
| ASCII 정상 대조 | 종료 **0** |

권한 우회나 데이터 손상은 아니지만 허용된 문자열을 인계할 수 없는 **기존 입력 호환성 결함**이다. 새 HR3·HR4 수정 때문에 발생한 회귀로 단정하지 않는다. 실제 반례는 U+2028이며 U+2029 등 다른 구분 문자는 추가 회귀 대상으로 남긴다.

**완료 기준:** JSONL 레코드는 LF 경계로 나누고 문자열 내부 Unicode를 보존한다. raw/escaped U+2028·U+2029, LF/CRLF, 기존 빈 줄 정책, 생성→같은 pin 검증의 왕복을 확인한다. 오류를 묵살하거나 문자열을 삭제하는 방식으로 통과시키지 않는다. HR6에는 별도 추가 점수를 차감하지 않았다.
