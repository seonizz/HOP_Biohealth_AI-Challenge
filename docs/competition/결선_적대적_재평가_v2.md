## 1. 판정

**v1보다 구현과 설명의 정합성은 좋아졌다. 그러나 최종 31B 모델의 목적 달성, 독립적인 의미·안전 평가, 현장 적용 근거가 확보됐다고 판단할 단계는 아니다.** 보수적 모의 점수는 **46/90점으로 v1보다 7점 상승**한다. 현장 발표·질의응답 10점은 계속 유보한다. 공식 심사 결과나 수상 가능성 예측은 아니다.

상향 근거는 실제 코드 통합, DB를 포함한 앱 검사, 과장된 서비스 설명 제거, 새 발표 기준본의 수치 정합성이다. **모델 성능 점수는 8/20으로 유지한다.** 현재 12B 합성 사례의 자동 통과와 최종 31B의 독립 성능 검증은 구분해야 한다. 새 경계 검사에서는 위험 문맥의 부정 표현 누락과 평가 요청 수 중복 집계도 재현됐다.

가장 먼저 방어해야 할 질문은 다음 세 가지다.

1. **대회 데이터로 학습한 31B가 주변인 지원에 어떤 이득을 주는가?** 현재 증거는 분류 기준 모델, 원본 상담사 응답 학습, 임시 12B 앱으로 나뉜다.
2. **근거 인용이 있으면 의미도 정확한가?** 긴 원문에서 현재 위험을 부정하는 부분이 잘린 인용도 긴급 판단 근거로 승인될 수 있다.
3. **테스트 통과가 즉시 현장 적용을 뜻하는가?** 이번 실제 모델 1건은 188.456초가 걸렸으며 전체 웹 세션·동시 이용·사람 검토·운영 비용은 검증하지 못했다.

## 5. 새로 확인한 적대적 지적

다음은 **v2 검토에서 새로 발견한 문제**다. 최신 수정이 원인이라는 회귀 판정은 하지 않는다. P1은 의미 신뢰성상 우선 해결, P2는 평가·운영 증거의 정확성 문제를 뜻하며 공식 감점 등급이 아니다.

### N1. [P1] 긴 원문에서 현재 위험 부정이 빠진 인용도 긴급 근거로 승인된다

**관측·확신도 높음:** `aroundRisk`는 위험 단어가 포함된 문장이 길면 160자 주변 인용으로 자른다. `groundedEvidenceSchema`는 이 짧은 후보를 safety evidence의 허용값으로 사용하고 `canonicalRelationship`도 같은 후보를 승인한다. [E05][E06]

독립적으로 만든 **319자 합성 한 문장**은 앞부분에서 과거의 자해 언급을 설명하고 끝부분에서 현재 생각과 위험이 없음을 명시했다. 생성된 위험 인용은 159자였고 끝의 현재 부정은 빠졌다. `urgent:true`에 그 인용을 넣으면 승인됐지만, 부정까지 있는 전체 원문을 넣으면 `agent_safety_context`로 거절됐다. 전체 인용의 거절은 현재 위험 부정의 의미를 이해한 결과가 아니라, 허용된 위험 인용 후보와 문자열이 일치하지 않기 때문이다. [E16]

**판단:** 출처가 원문이라는 사실만으로 시점·부정이 보존되지는 않는다. 안전 근거의 허용값 자체가 불완전하므로 ‘원문 근거 검증으로 의미 오류를 막는다’는 설명을 방어하기 어렵다.

**입증하지 않은 것:** 실제 모델이 이 사례를 긴급으로 오판했다는 증거는 아니다. 전체 context는 모델에 제공될 수 있다. 이번 재현은 **잘린 근거로 잘못된 판단을 승인할 수 있는 계약의 빈틈**을 입증한다.

**해소 증거:** 위험 문장의 사람·시점·부정을 함께 보존하는 근거 계약, 160자 경계 전후 및 긴 문장의 정정·부정 회귀 검사, 그 사례들의 실제 생성과 별도 원문 대조. 단순히 문자열 한 개를 금지하는 수정으로 종결하면 안 된다.

### N2. [P2] 재시도 대기 중 제한시간이 끝나면 한 요청을 두 요청으로 센다

**관측·확신도 높음:** `ModelGateway.request`는 첫 실패를 기록한 뒤 재시도 대기가 제한시간으로 끝나면 같은 `generation/attempt`를 다시 `model_attempt`로 기록한다. `attemptMetrics`는 trace의 행 수를 요청 수로 센다. [E07][E08]

네트워크를 쓰지 않는 mock으로 HTTP 503, `Retry-After: 1`, timeout 100ms를 적용했다. 실제 fetch 호출은 **1회**, 로그는 `http_transient`와 `deadline` **2행**, 결과 집계는 **attempts 2·failed_attempts 2·retries 0**이었다. [E16]

**판단:** 실패 분모를 기록한다는 방향은 맞지만 요청과 대기 종료 사건이 섞여 있다. 이 경로의 요청 수·실패 수·요청별 지연 분포를 그대로 성능·비용 근거로 사용할 수 없다. 이번 대조한 기존 7건과 신규 성공 1건에서 이 중복 경로가 관측됐다는 뜻은 아니다.

**해소 증거:** 실제 호출마다 유일한 식별자, 대기 종료와 호출 실패의 구분, `fetch 횟수=요청 수` 회귀 검사. 전체 경과시간과 모델 호출 대기도 분리해야 한다.

### N3. [P2] 모델 alias가 같으면 다른 서버의 결과도 같은 실험군으로 묶일 수 있다

**관측·확신도 높음:** `evaluationIdentity`는 요청 모델·소스·평가 코드·프롬프트 등을 기록하지만 모델 endpoint 또는 배포 인스턴스를 식별하지 않는다. `summarizeRuns`의 그룹 키에도 이 값이 없다. [E08]

모델 이름과 나머지 조건을 같게 두고 endpoint만 가상의 `server-a.invalid`와 `server-b.invalid`로 바꾼 순수 함수 검사는 **동일 identity**, 두 실행을 **1개 그룹**으로 집계했다. 네트워크 호출은 없었다. [E16]

**판단:** 같은 alias가 같은 로딩 모델·하드웨어·운영 설정임을 보장하지 않는다. 서버를 바꾸어 재실행하면 지연이나 성공률 비교가 섞일 수 있다. 현재 7개 기록을 이미 서로 다른 서버에서 섞었다는 증거는 아니다.

**해소 증거:** 비밀키를 제외한 실행 환경·서버 식별 해시와 로딩 증명 수준을 기록하고 집계 키에 반영한다. 선언한 checkpoint 해시와 실제 로딩 확인은 계속 구분한다.

### N4. [P2] 웹 smoke 실패 파일에는 실패한 요청의 대기시간이 빠지고 재실패가 덮어써진다

**관측·확신도 높음(정적 코드):** 답변 POST와 context GET이 모두 성공한 뒤에만 `timings`에 행을 넣는다. 실패 catch는 기존 성공 turns와 오류 코드만 저장하며, 실패 요청의 소요시간·전체 경과시간을 저장하지 않는다. 같은 run-id로 실패를 재개하면 동일 failure 파일에 기본 `writeFileSync`로 기록한다. [E09]

**판단:** 새 모델 평가기의 고유 실행 파일과 별개로, **전체 웹 세션의 실패 시간·실패 이력 분모**는 완전하지 않다. 장시간 대기 뒤 실패하거나 반복 실패한 세션을 분석할 때 비용과 사용자 대기를 작게 볼 수 있다.

**검증 경계:** 운영 웹 세션을 고의로 실패시키지는 않았다. 이 항목은 저장 경로·실행 순서에 대한 코드 검토 결과이며 실제 발생 횟수는 미확인이다.

**해소 증거:** 각 시도 시작·종료·성공 여부·실패 대기를 남기는 추가 전용 로그와 고유 실행 ID, 동일 세션 재개 시 실패 이력을 보존하는 검증.
