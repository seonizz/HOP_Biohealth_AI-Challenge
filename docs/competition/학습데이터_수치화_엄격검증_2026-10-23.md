# 학습 데이터 수치화 엄격 검증 — 2026-10-23

**판정: 현재 묶음의 학습 입력 수치화는 통과했다. 독립적인 서비스 성능 평가와 위험도 점수의 타당성은 입증되지 않았다.**

대상은 `training_data/two_stage_training_20261022/`의 전체 원상담 → 서비스 보정 묶음이다. 원본 묶음과 ZIP은 보존했다. 검사에는 로컬 CPU를 사용했으며 모델 학습은 실행하지 않았다. 모델 성능이나 속도에 점수를 부여하지 않는다.

## 1. 전수 재계산 결과

| 검사 | 실측 결과 | 판정 |
|---|---:|---|
| 전체 행 | 41,276행, 14개 task/split 파티션 | 전수 확인 |
| 토큰 ID | 232,414,341개 | 원문 재계산과 불일치 0 |
| 정답 토큰 | 3,443,613개 | 최종 assistant 정답과 종료 부분에만 손실 |
| prefix·target·sequence 길이 | 전체 행 | 불일치 0 |
| 로더의 labels·attention | 전체 행 | 잘못된 이동·마스킹 0 |
| 정수 범위·unknown·padding 혼입 | 전체 행 | 위반 0 |
| 템플릿 적용 후 encode→decode | 전체 행 | 문자열 불일치 0 |

주 학습 경로는 train 37,249행, validation 3,680행이다. 선택 보조 과업은 train 200행, validation 147행이며 주 경로에 자동 혼합하지 않는다.

새 검사기는 exporter·`AutoTokenizer`·기존 `encode_example`을 호출하지 않는다. 지원되는 텍스트 대화 형식을 독립적으로 직렬화하고, 고정된 `tokenizer.json`을 저수준 `tokenizers`로 읽어 모든 행을 다시 인코딩했다. 재계산한 값과 실제 `IndexedDataset`이 읽은 토큰·마스크를 비교했다. 검사 전후 전체 묶음의 해시와 구조도 다시 확인했다.

독립성에는 범위가 있다. tokenizer 엔진과 사전은 공유한다. native Jinja 템플릿과 독립 직렬화의 직접 비교는 실제 경계·최장 행 52개와 합성 역할·공백 조합 8개에서 수행했다. 나머지 행도 독립 직렬화·재토큰화는 전부 수행했지만, native Jinja를 전 행에서 다시 실행했다고 주장하지 않는다.

## 2. 무조건적인 무손실 변환은 아니다

정답 **175행**에서 템플릿이 양끝 공백을 제거한다. 전체 대화에서는 공백 제거가 발생한 메시지 출현이 24,080회다. 동일 원문이 여러 접두부에 반복될 수 있으므로 고유 메시지 수가 아니다. 원본 `messages`는 바뀌지 않았고 정답 공백 처리 여부는 인덱스에 기록돼 있다. 위의 encode→decode 통과는 **템플릿 처리 후 문자열**에 대한 결과다.

전체 시퀀스 최대 길이는 **25,316토큰**이다. 원상담 train 22,305행이 4,096토큰을 넘는다. 전 행을 유지하려면 이 길이를 수용하는 학습 구성이 필요하다. `uint32` 저장값은 모델 입력에서 정수형으로 유지하고, `-100` 손실 마스크는 부호 있는 정수로 구성해야 한다. 이 검증으로 GPU 메모리 적합성을 확인한 것은 아니다.

## 3. 기존 구조 검증기의 통과만으로는 충분하지 않다

**재현한 반례:** 바이너리의 토큰 하나를 다른 유효한 ID로 바꾸고 파일 해시를 다시 만들면 기존 `staged_dataset.verify()`는 통과한다. 이 함수는 해시·범위·길이·출처를 검사하지만 원문으로 토큰을 다시 계산하지 않기 때문이다. 실제 배포 데이터가 손상됐다는 의미는 아니다.

새 `audit_staged_numeric.py`는 이 반례를 검출한다. native 템플릿 표본에 포함되지 않는 행의 바이너리를 변경하는 회귀 검사에서도 토큰·마스크 불일치가 정확히 1행 검출됐다. 미리 이동한 labels, 정답 전체 마스킹, 입력 attention 제거, 반복 정답에 의한 경계 오인도 반례로 검사했다. 숫자의 범위가 맞는다는 사실과 숫자가 원문에 대응한다는 사실을 구분했다.

정확 분수 가중치의 정답 질량은 모든 파티션에서 보존됐다. float32 질량 합의 최대 상대 오차는 약 **1.22×10⁻⁷**이다. 실제 행 가중치와 합성 손실값을 이용한 불균등 누적창 계산은 기준 목적함수와 **10⁻¹² 미만**의 오차로 일치했다. 별도 작은 logits 수치 실험에서는 이동된 인과 손실의 대상 위치와 패딩·비대상 위치의 0 기울기를 확인했다. 실제 모델의 backward·optimizer·단계 간 어댑터 연결을 실행한 검사는 아니다.

## 4. 서비스 검증셋의 독립성은 부족하다

전체 주 경로를 합쳐 정규화 후 연속 **200자 이상**의 검증 정답이 train assistant 발화 안에 있는지 검사했다.

| 대상 | 검증 행 | 해당 중복 |
|---|---:|---:|
| 원상담 | 3,618 | 0 |
| 주변인 보정 | 29 | 0 |
| 서비스 JSON 보정 | 33 | **28** |

28행 모두 서비스 보정의 train 정답과 겹쳤으며 원상담에서 넘어온 중복은 아니다. 각 행의 가장 긴 일치 구간은 정답의 **47.1%~88.2%**다. 정답 전체가 완전히 동일한 행은 0이다.

이 수치는 동일 인물·동일 상담 사례의 누출을 증명하지 않는다. 반복 JSON 구조와 안내·심사 문구가 포함된다. 구조를 제외하고 문자열 값도 따로 검사한 결과, 서비스 검증 29행에서 train과 동일한 20자 이상 문자열 값이 확인됐다. 반복 필드는 `audits[].reason`과 `doList[]`이며 가장 긴 동일 문자열 값은 140자다. 200자 이상 문자열 값 자체의 완전 일치는 0이다.

따라서 **200자 중복 28행을 모두 개인정보 누출로 단정하거나, 반대로 형식만 겹친다고 무시하면 안 된다.** 현 validation은 형식 회귀 검사에 쓸 수 있지만, 새로운 사례에서의 결론 품질을 독립적으로 입증하는 자료로 승인할 수 없다. 템플릿 계열·판단 근거·사례가 학습과 분리된 추가 평가셋이 필요하다. 28행을 제거한 나머지 5행을 충분한 독립 평가셋으로 간주하지 않는다.

출처 group/root의 train·validation 교집합은 전체 과업에서 없었다. 다만 ID 분리가 실제 사람의 동일성까지 증명하지 않는다. 원상담 train 37,083행은 177개 source group, 943개 대화에서 파생됐다. 서비스 validation 33행은 6개 source group이다. 행 수를 독립 사람 수나 독립 사례 수로 보고하면 안 된다.

이 검사는 의미상 유사한 표현, 떨어진 구간을 이어 만든 중복, train user 발화 내부의 중복까지 찾는 검사는 아니다. 기존 validation은 개발에 노출된 자료다.

## 5. 위험도를 수치 점수로 평가할 근거는 별도로 필요하다

원상담 40,701행의 정답은 응답 텍스트이고, 서비스·보조 575행은 JSON이다. JSON의 중첩 객체·배열까지 검사했지만 명시적인 위험 등급·긴급도·위험 확률 정답 필드는 확인되지 않았다. `approved`와 `audits[].verdict`는 서비스 결과의 승인·검사 필드이며 이를 당사자의 위험 등급으로 바꾸어 해석하지 않았다.

**토큰 ID는 범주 식별자다. ID의 숫자 크기가 위험의 크기를 뜻하지 않는다.** 현재 묶음으로 입력을 숫자로 공급할 수는 있지만 위험도 점수의 정확성·보정 상태·기관 연결의 적절성이 검증된 것은 아니다. 이를 평가하려면 위험 등급 정의, 출처에 근거한 정답, 검토자 간 불일치 처리, 학습과 분리된 평가 사례가 추가로 필요하다. 이번 검사에서 임의의 위험 점수나 정답을 새로 만들지 않았다.
