# 학습데이터 주변인 지원 과업 정합성 개선·적대적 재검증 v9

검증일: 2026-10-16. 대상은 학습 데이터의 목적·원문·맥락·분할·추적성이다. 모델 크기·학습 진행률·생성 성능·속도는 평가하지 않는다. [사용자 지정 평가 범위](05_평가범위와_학습데이터_기준.md)를 따르며 공식 결선 평가표나 과거 프로젝트 점수를 변경하지 않는다.

**원상담 v8을 그대로 보존하고, 주변인 관점의 입력·정답과 현재 앱 두 단계의 JSON 후보를 별도 구성했다.** 주변인 대화는 기존 20대화·24응답에서 **44대화·72응답**으로 확장했다. 별도로 **합성 앱 맥락 12개에서 24개 단계 정답쌍**을 만들었다. 빈 작성 요청만 늘린 결과가 아니며 실제 입력·정답·문장 기능·근거 span이 저장돼 있다.

**구조·분할·원문 재구성과 별도 AI 의미 검토를 통과했지만, 새 후보의 실제 토큰 길이는 미검증이다.** 출력 **8,192**, 입력 상한 **65,536**, 합산 **69,632**, 유효 입력 **61,440**을 검사 계약에 적용했다. 기존 서버의 토크나이저 접근은 SSH 인증 실패로 중단됐으며 새 후보의 토큰 적격 수는 **0 / 미확인**으로 유지한다. 사람·전문가 승인, 실제 원천 이용 권한, 독립 test가 생긴 것으로 처리하지 않는다.

## 1. 해결할 과업 차이와 대안 비교

원상담 SFT의 질문자는 원래 내담자이고 정답은 상담사의 다음 발화다. 말씨는 가족·친구 등 이용자가 전한 정보를 바탕으로 상대에게 건넬 말, 가능한 도움, 이용자의 부담과 경계를 다룬다. 상담사 응답의 분포를 균등하게 만드는 것만으로 이 과업 차이가 사라지지는 않는다.

현재 앱은 `relationship-v3.9-grounded-details-safety-selection`의 단계별 `system + user JSON → assistant JSON` 계약을 사용한다. 기존 `action/components/question_id/user_text` 6행동 형식은 정책 의미를 표현하지만 현재 앱 전체 요청·응답 형식과 같지 않다. [실제 요청 코드](../../app/src/model.js)와 [단계 구성 코드](../../app/src/relationship-agent.js)를 기준으로 비교했다.

| 대안 | 기대되는 개선 | 원문·맥락·분할 영향과 한계 | 판단 |
|---|---|---|---|
| 원상담의 표본·가중치만 재조정 | 분포 편중 완화 | 상담사 다음 응답이라는 목적은 유지됨. 주변인 의향·부담 정답을 새로 제공하지 못함 | v8 보존, 이번 목적 개선의 주수단으로 사용하지 않음 |
| 내담자를 주변인으로 재명명하거나 상담사 응답을 주변인 정답으로 전용 | 겉보기 대량 확보 | 화자·누가 무엇을 아는지·동의 주체가 달라짐. 원문 보존과 충돌 | 제외 |
| 주변인 관련 단어가 있는 원상담만 선별 | 관련 사례 후보 탐색 | 친구·가족을 언급했다고 주변인 발화가 되는 것은 아님. 의미·출처 확인 없이 자동 승격 불가 | 실제 관점 검토를 위한 후속 탐색에 한정 |
| 원상담을 근거로 주변인 사례를 새로 각색 | 원자료 연결과 목적 정답 확보 가능 | `adapted_from_source` 계보·원래 split·권리 근거·사람 검토가 필요. 현재 승인되지 않은 원천을 synthetic으로 세탁할 수 없음 | 기존 승인 경로 유지, 자동 학습용으로 내보내지 않음 |
| **독립 합성 주변인 대화 + 현재 앱 단계 후보, 원상담 별도 보존** | 관점·행동·근거·실제 JSON 형식을 직접 다룸 | 합성 자료·AI 검토라는 한계가 남지만 원상담을 바꿀 필요가 없음 | **적용** |

상담 후보와 주변인 후보를 행 단위로 무작정 합치지 않는다. 대화 생성, 문장 기능 분류, 근거 span 분류, 앱 단계 JSON은 다른 학습 목표다. 새 구성기는 자동 연결·복제·상향 표집을 하지 않으며, 실제 정답 토큰을 측정하기 전에는 혼합 비율을 확정하지 않는다. 원상담의 큰 분량이 주변인 목표를 다시 압도하지 않도록 용도를 명시적으로 나눴다.

## 2. 실제 적용한 구성

### 주변인 대화와 주석

| 단위 | 기존 v2 train / validation | 추가분 train / validation | 최종 v9 train / validation |
|---|---:|---:|---:|
| 합성 대화 | 15 / 5 | 12 / 12 | **27 / 17** |
| 다음 응답 정답 | 19 / 5 | 24 / 24 | **43 / 29** |
| 문장 기능 정답 | 42 / 12 | 44 / 47 | **86 / 59** |
| 근거 span 정답 | 49 / 13 | 53 / 63 | **102 / 76** |

문장·span은 같은 대화에서 파생한 정답이다. **72응답·145문장·178span을 독립적인 395개 상담이나 사람으로 세지 않는다.** 기존 20개 대화와 그 파생 140행은 그대로 유지한다. 추가 24개는 모두 두 번 응답하는 합성 대화이며, 각 split에 가족·친구·동료를 4개씩 배치했다. [구성 manifest](../../data/outputs/private/composition_v9_supporter_task_20261016/supporter/manifest.json).

| validation의 부족 항목 | 기존 | 최종 |
|---|---:|---:|
| 다중턴 대화 | 0 / 5대화 | **12 / 17대화** |
| 첫 응답 이후의 정답 | 0 / 5응답 | **12 / 29응답** |
| 동료 관계 대화 | 0 | **4** |
| `corrected` span | 0 | **3** |
| `refused` span | 0 | **8** |
| `subject:unknown` span | 0 | **1** |

새 사례에는 당사자의 거절, 이용자의 한계·자기돌봄, 모름, 정정, 제3자의 전언, 확인되지 않은 화자, 침해적인 요구에 대한 제한, 종료 요청을 포함했다. 검토한 행동은 `CLARIFY`, `SUPPORT`, `SUPPORT_LIMITED`, `END`다. 임상 안전 절차나 질문은행 권리를 가정하지 않았으며 `ASK_CFI`·`SAFETY_SUPPORT`의 기존 보류는 유지한다. 이 표는 새로 저작한 합성 대화의 다중턴 보강이며 **원상담의 후반 ¼ 부족을 해결한 수치가 아니다.**

### 실제 앱 형식의 두 단계

| 단계 | 입력·정답 | 범위 |
|---|---|---|
| `state_observations` | 현재 answers·검색 근거·동적 schema → 인용 사실·미확인 사항·이름 근거 | 12쌍, train 6 / validation 6 |
| `relationship_memory` | 같은 현재 맥락과 앞 단계의 저작 정답 → 주체별 `reported` 근거 | 12쌍, train 6 / validation 6 |

현재 앱의 프롬프트, 검색, schema와 검증 함수를 직접 재사용했다. summary·interpretation·user_goal처럼 서버가 생성하는 항목을 모델 정답에 억지로 넣지 않았다. 관계 가설은 빈 배열이며, 두 번째 단계에는 첫 단계의 정답을 입력하는 **teacher forcing**을 명시한다. 예측 오류가 전파되는 실제 전체 흐름을 검증한 것은 아니다.

합성 transcript와 context를 snapshot에 보존하고 각 답변 요소의 원문 위치를 연결한다. **앱 입력은 현재 구조화 답변·검색 결과·schema이며, transcript 전체를 채팅 메시지로 보내는 방식은 아니다.** 일반 주변인 대화의 전체 prefix 보존과 이 앱 단계의 출처 보존을 구분한다. 실제 DB 질문 이력인 것처럼 표현하지 않고 `synthetic-supporter-context-v1`을 사용했다. [앱 단계 manifest](../../data/outputs/private/composition_v9_supporter_task_20261016/app_stages_r2/manifest.json).

## 3. 원문·맥락·분할 보존 판정

- **원상담 v8:** 기존 선택·원행·화자·전체 접두부·정답·보류·split·후기 대표·패널을 수정하지 않았다. 기존 구성 명령의 `--verify`로 전체 연결을 다시 검사했다. [재검증 결과](../../runtime/data-composition-supporter-task-20261016/v8-fresh-verify-result.json).
- **기존 주변인 v2:** 20대화의 원문·주석·ID·root/group·split·AI 검토와 3종 파생 행을 그대로 유지했다. 전체 v9와 함께 정규화된 중복 대화·확장 접두부 및 그룹의 split 교차를 검사했다.
- **새 대화:** 정답 시점 전의 사용자·이전 응답을 순서대로 모두 보존했다. 정답·라벨·미래 발화·검토 메타데이터를 접두부에 넣지 않았다. 최종 정답에만 정수 손실 마스크를 둔다.
- **새 앱 맥락:** 인용은 해당 주체·문항의 현재 원문과 검색 결과에서 일치해야 한다. unknown/refused/skipped를 동의나 확정 사실로 승격하지 않는다. 같은 맥락의 두 단계는 같은 root/group/split을 공유한다.
- **저작 수정 이력:** 신규 대화 5개에서 응답 3곳·인용 시점 3곳을 수정했다. 사용자 발화·계보·split은 고정했고, 앞선 응답 수정으로 달라지는 후속 접두부 2개는 수정된 발화를 온전히 반영했다. 앱 맥락 1개의 미확인 서술도 수정했다. 최초 저작본은 별도 보존한다. 이는 신규 AI 초안의 교정이며 원상담 원문 수정이 아니다.
- **평가 노출:** 새 train·validation 모두 개발 중 저작·검토된 자료다. 개발 노출을 기록하고 독립 test 승격을 차단한다. 정규화 중복 검사는 의미적 패러프레이즈·동일 인물·모집단 독립성을 입증하지 않는다.

원상담의 입력·정답 집중도와 총량은 v8 파일 자체를 보존했으므로 그대로다. 짧은/긴 후보의 입력은 **2,089,385 / 14,183,561토큰**, 정답은 **75,231 / 213,050토큰**, 절차성 플래그는 **387 / 1,198**이다. 새 합성 자료를 섞은 전체 토큰 집중도가 개선됐다는 주장은 하지 않는다. 짧은 원상담 validation의 후기 2셀·마지막 ¼ 0행, 긴 validation 입력의 v5 대비 +1,456토큰, 짧은 후보의 v5 대비 신규 절차성 셀 1개도 남는다. [보존된 v8 결과](학습데이터_입력총량과_절차문맥_개선_재검증_v8.md).

## 4. 출력 8,192 기준

| 검사 대상 | 적용 조건 | 결과 |
|---|---|---|
| 보존 원상담 v8 | 저장된 실제 토큰 장부의 내용·버전 연결, target ≤8,192, prefix+8,192 ≤69,632 | 기존 짧은 1,052행·긴 2,376행 및 패널 105행 재검증 통과. 새 토큰화는 아님 |
| 새 주변인·앱 후보 | 새 입력·정답을 해당 tokenizer/template로 다시 인코딩해야 함 | **미검증**, 기존 원상담 토큰 수 재사용 금지 |
| 새 토큰 배치 계약 | 정답 ≤8,192, 입력 ≤65,536, 입력+8,192 ≤69,632, 전체 ≤69,632 | 경계 회귀 통과. 유효 입력은 61,440 |
| 별도 짧은 후보 조건 | 실제 prefix+target ≤4,096 | 예약 출력 8,192와 구분. 새 후보를 아직 4,096 이하라고 인증하지 않음 |
| 현재 앱의 두 단계 설정 | 각 단계의 실제 `max_tokens=1,800` | 변경하지 않음. 평가용 8,192 예약이 운영 설정 변경을 뜻하지 않음 |

정답이 8,192토큰 길이가 되도록 늘린 것이 아니라 허용 상한과 예약 조건을 적용했다. `check_lengths`는 **61,440+8,192**를 허용하고 **61,441+1**, **1+8,193**, bool/실수/0 길이를 거절한다. `token_batch`는 고정된 실제 template의 새 인코딩과 정답 경계를 사용하며 초과 입력·정답을 잘라 통과시키지 않는다. 미확인 토큰 길이·사람 승인·독립 test를 manifest에서 임의로 승격하면 감사가 실패한다.

토크나이저가 로컬에 없고 기존 서버의 읽기 전용 확인도 인증 실패했다. 모델 가중치·생성·학습을 실행하지 않았고 원상담을 전송하지 않았다. 문자 수를 토큰 수로 환산하지 않는다. [접근 시도와 제한](../../runtime/data-composition-supporter-task-20261016/tokenizer-access.json).

## 6. 남은 제한과 사용 판정

현재 판정은 **주변인 목적에 더 맞는 실험 후보 구성이며, 완성된 학습 승인본은 아니다.** 구체적인 관점·응답·근거 및 두 앱 단계의 형식 적합성은 개선했다. 다음 제한은 해소되지 않았다.

1. 새 후보의 실제 31B tokenizer 검증이 없어 토큰 총량·집중도·8,192 적격 비율을 확정할 수 없다. 정상 인코딩 근거 없이 학습 배치로 승격하지 않는다.
2. 합성 사례의 다양성과 AI 검토는 실제 주변인 모집단·기관·사용자 검토를 대체하지 않는다. 44대화는 작은 저작 집합이며 동일한 공감·경계 표현의 반복과 의미 근접성은 남을 수 있다.
3. 앱의 원문 관찰과 reported 기억만 직접 다뤘다. 질문 계획, 안전 판단, 관계 가설, 계획·말문·행동·자기돌봄 가이드, 검토·수정의 전체 앱 단계 정답은 갖추지 못했다. 일반 대화의 4행동 정답도 앱 전체 wire 호환성을 뜻하지 않는다.
4. 실제 원상담 각색은 기존 이용 근거·사람/전문가 검토 경로가 필요하다. 기존 질문은행·안전 초안의 보류 4개와 원상담 의미 검토 대기 상태를 이번 합성 결과로 풀지 않는다.
5. 같은 개발 과정에서 저작·검토한 validation이다. 독립 test, 미지의 가족·친구 상황에 대한 일반화, 실제 생성 품질을 입증하지 않았다. 로컬 해시는 변경 추적 근거이지 작성자 신원이나 악의적인 전체 기록 재작성에 대한 인증이 아니다.

별도 사람 검토 인계 도구의 기존 HR5/HR6 문제를 이번 구성기 수정으로 해결했다고 주장하지 않는다. 이번 두 구성기는 자신이 읽은 bytes와 파생·hash를 결속했으며, 기존 도구는 변경하지 않았다. 전체 프로젝트의 과거 점수도 자동으로 올리지 않는다.
