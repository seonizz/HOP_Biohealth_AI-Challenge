## 4. G2: UTF-16 JSON이 원문 반입 검사를 우회한다

**확인 사실.** 별도 임시 Git 저장소와 새로 만든 합성 원문만 사용했다. 같은 80자 이상 문자열을 JSON 값으로 넣어 UTF-8과 UTF-16으로 각각 스테이징했다. 실제 프로젝트 원문·인덱스는 바꾸지 않았다.

| 대조 | UTF-8 JSON | UTF-16 JSON |
|---|---|---|
| JSON을 해석한 값 | 같은 합성 문자열 | 같은 합성 문자열 |
| 검사 대상 | 실제 인덱스 blob | 실제 인덱스 blob, 454바이트 |
| 원문 일치 파일 | 1 | **0** |
| 처리 경로 | JSON 내용 검사 | **`binary_not_scanned: 1`** |
| 파싱 오류 보고 | 없음 | **없음** |
| 검사 결과 `passed` | `false`, 정상 차단 | **`true`, 잘못된 통과** |

스테이징 후 작업 파일을 빈 JSON으로 바꾼 조건에서도 동일했다. 따라서 작업 폴더를 읽어서 생긴 착각이 아니라 **실제 스테이징 내용에 대한 누락**이다. Python의 JSON 바이트 파서는 두 파일을 같은 값으로 복원했다.

원인은 [audit_git_privacy.py:112](/Users/chihun/Documents/ChatGPT/HOP-Final/tools/audit_git_privacy.py:112)에서 `.json` 확장자를 처리하기 전에 UTF-8 해석 실패 또는 NUL 문자를 만나면 `binary_not_scanned`로 반환하는 순서다. JSON 파싱까지 도달하지 않아 오류로도 잡히지 않는다. [검사 도구의 계약](/Users/chihun/Documents/ChatGPT/HOP-Final/tools/README.md:13)은 JSON 검사가 불완전하면 실패한다고 설명하지만 이 경계에서는 지켜지지 않는다.

**영향에 대한 판단.** 확장자가 `.json`인 원문 사본도 인코딩에 따라 검사 통과로 표시될 수 있다. 현재 정상 사례·압축·Office 관련 검사 14개가 모두 통과한다는 사실로 이 경계가 보호된다고 주장할 수 없다. **현재 프로젝트에 UTF-16 상담 원문이 다시 들어왔거나 원격에 공개됐다는 증거는 아니다.**

**최소 수정과 완료 조건.** 선언된 JSON/JSONL은 일반 바이너리 건너뛰기보다 먼저 처리하고, 허용하지 않은 인코딩·해석 불가능한 내용은 통과시키지 않는다. 지원할 인코딩을 명시적으로 해석하는 방식도 가능하다. 같은 합성 원문에 대해 UTF-8 대조와 UTF-16·NUL·잘못된 인코딩, 압축된 JSON, 실제 인덱스 blob 경로를 회귀검사한 뒤 현재 인덱스 전체를 다시 검사해야 한다. 이 보고서 작업에서는 수정하지 않았다.
