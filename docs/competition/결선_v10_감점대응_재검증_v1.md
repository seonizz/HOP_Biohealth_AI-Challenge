# 결선 v10 감점 대응·재검증 v1

작성일: 2026-10-16, Asia/Seoul. [v10](결선_적대적_재평가_v10.md)의 남은 감점 중 로컬에서 해결할 수 있는 검토 준비·검증 누락·자료 정합성을 수정했다. 사람 검토, 사용 권한, 실제 이용자·기관·운영 증거는 별도 [외부 증거 확인 목록](결선_외부증거_확인목록_v1.md)에 대기로 정리했다. 과거 v10과 발표 v4는 보존했다.

**같은 내부 기준의 점수는 76/90을 유지한다.** 코드·자료 준비가 진전됐지만 남은 감점의 핵심인 실제 사람·현장 증거는 생기지 않았다. 모델 자체·처리시간은 제외하고 현장 발표·Q&A 10점은 유보한다. 이번 작업을 실제 사람 승인이나 배포 완료로 계산하지 않았다.

## 2. 사람 검토 인계와 새 경계 결함 수정

[인계 생성·검증기](../../data/counseling_pipeline/human_review_bundle.py)는 기존 `agent_dataset` 감사와 검토 계약을 재사용한다. 현재 응답·AI 판정·미래 발화를 가린 접두부, 나중에 볼 응답·주석, 빈 검토 요청을 나누고 같은 검토 단위 해시에 묶었다. 원본 split·출처 연결은 보존하지만 독립 test로 승격하지 않는다.

현재 인계본은 Git 제외 경로 `data/outputs/private/human_review_v10_20261016_r2/`다. 6개 파일을 원본에서 다시 구성해 검증했다. 검토자·검토 시각·판정은 비워 두었고 `pending_human_review`, `review_only`, `human_approved:false`, `training_authorized:false`를 유지했다. 별도 기록으로 보관할 manifest SHA-256은 `3a07fe7a797fa821df8b11d3d6094f67080ccb8f7dad0bd540cb79dfb007efe7`이다.

AI 검토 20기록·고유 검토자 ID 1개는 사람 검토가 아니다. 새 요청 28단위, 기존 큐 391개, 작성 요청 6개는 서로 다른 준비 분모이며 학습 사례 수로 합산하지 않는다. 정답·판정을 실제로 작성한 뒤에도 기존 학습용 스키마·검토·권한·분할 조건을 별도로 충족해야 한다. 자세한 실행·인계 방법은 [사람 검토 인계 절차](../../data/docs/support_agent/사람검토_인계_절차_v1.md)에 정리했다.

새 도구의 독립 검토에서 **HR1**을 발견하고 수정했다. pending JSONL에 객체 대신 `[]`가 있으면 `.get`에서 traceback과 CLI 1이 발생했다. 객체·행·접두부·판정 등의 컨테이너 타입을 먼저 검사해 일반 오류 JSON, **CLI 2·stderr 없음·출력 묶음 없음**으로 처리한다. 신규 CLI 회귀 4메서드를 추가했고 수정 전 18개 하위 조건 실패를 재현한 뒤 수정 후 관련 50개가 통과했다. 첫 인계본은 보존하고 수정 코드 해시의 `_r2`를 생성했다.

## 3. 최신 데이터 구성의 실제 결과와 한계

이 작업과 독립적으로 `source_budget_composition.py`·관련 검사·v3 문서가 변경되고 있었다. 첫 검증 중에는 입력 변경을 감지해 완료로 인정하지 않았다. 안정된 현재 구현과 입력으로 **새 경로** `data/outputs/private/remediation_v10_source_20261016/`에 생성한 뒤, 선별 장부와 원문·전체 접두부·분할을 다시 계산해 검증했다. 기존 v3 export는 덮어쓰지 않았다.

| 현재 코드로 확인한 프로파일 | train | validation | 합계 | 상담 수 | 전반부 비중 | 마지막 ¼ |
|---|---:|---:|---:|---:|---:|---|
| 주 예산 후보 `runtime_budget` | 2,127 | 238 | **2,365** | 1,038 | **55.98%** | train 451 + validation 45 |
| 전체 4,096 이하 `strict_4096` | 1,585 | 158 | **1,743** | 1,036 | **97.13%** | train 1 + validation 0 |

각 길이 조건의 적격 풀에서 먼저 선별하므로 작은 후보는 주 후보의 단순 부분집합이 아니다. 두 프로파일에는 **1,008행이 겹치며 합산할 수 없다.** 짧은 풀의 적격 후기 134행은 50개 상담×구간 셀에 속하며 50셀을 모두 보존했다. 선택된 후기 50행은 셋째 ¼ 49행·마지막 ¼ 1행이다. 이는 발화 순서의 위치이며 실제 상담 시간이나 임상 단계를 뜻하지 않는다.

v2 전체 2,365행의 전반부 **56.15%·1,035상담**, v2 짧은 부분집합 **1,023행·99.22%**와 위 수치를 섞지 않는다. v3의 후기 셀 보존은 선별 누락을 줄였지만, 원천 적격 풀에 없는 validation 마지막 ¼ 사례를 만들어내지 못한다. 현재 자료의 사람 의미 검토·라벨 정의·실제 인물 독립성·독립 test·사용 허가는 여전히 확인되지 않았다.

입력 36파일과 기존 export를 포함한 46파일의 해시가 검증 전후 같았다. 새 산출물 9파일은 모두 Git 제외·미추적이다. 새 export manifest SHA-256은 `cbf2e975bc9b26d05e307255143fb8ea7f367bf19c2e45798544da83df70d415`다. 모델이나 tokenizer를 실행해 품질을 평가한 결과가 아니라 저장된 길이 장부·파일·선별 계약을 재검증한 결과다.

후속 외부 작업의 출력 예산 **8,192** export도 현재 `prepare(output_budget=8192)`와 `verify_artifacts`로 읽기 전용 검증했다. 합산 예산 69,632·유효 입력 61,440 조건이며 현재 서버 실행 상태의 확인은 아니다. 위 4,096 출력 예산 산출물과 학습 gzip 4개는 압축·해제 바이트가 모두 같았다. 출력 확대 자체로 행이나 과업이 추가되지 않았고, 입력 36개를 포함한 59파일과 산출물 목록을 보존했다. 8,192 manifest SHA-256은 `d105f733f80e5ee17b08cd83d52aff6903929fa504545e58ed7e4ae69a992afb`다.

## 4. 운영 증거 점검과 실제 운영의 구분

[운영 점검기](../../app/scripts/check-operations.js)와 [빈 템플릿](../../app/docs/operations-evidence.template.json)을 추가했다. 정책 승인·실제 설정·현재 앱 소스 해시, DB·WAL·복제본·백업·내보내기·외부 사본의 6영역, 위치별 만료, 복원 후 삭제 재적용·만료 접근 차단, 실패 대응 책임을 확인한다. 근거는 목록 폴더 안의 로컬 상대 경로와 SHA-256으로 연결한다.

점검기는 `.env`, DB, 네트워크를 사용하거나 배포·복원·삭제를 실행하지 않는다. 실제 이름·파일 내용·원문·입력 경로를 결과에 내보내지 않는다. 중복 키·손상 인코딩·누락·placeholder·해시 불일치·심볼릭 링크·상위 경로·미완료 배포는 차단한다.

새 경계 재검토에서 **OP1: 빈 JSON `{}`도 해시만 맞으면 증거로 통과**, **OP2: 증거의 `synthetic:true`를 남긴 채 목록만 actual로 바꿔도 통과**를 재현했다. JSON의 무내용 구조와 명시적 합성·실제 충돌을 거절하도록 보강하고 회귀에 고정했다. 이는 운영 승인의 진위를 인증한 검사가 아니라 기계적으로 확인할 수 있는 증거 누락·모순을 차단한 수정이다.

운영 회귀는 신규 4개를 포함해 **22개 통과**했고, 새 4개가 수정 전 실패하는 것도 확인했다. 빈 실제 템플릿은 누락 59개·근거 확인 0개로 pending이며 종료 코드 1이다. 합성 완성 fixture는 근거 참조 16개를 확인한 synthetic_checks_passed / CLI 0이지만 operational_evidence_complete는 false다. 원래 두 독립 반례는 각각 EVIDENCE_JSON_EMPTY, EVIDENCE_SYNTHETIC_CONFLICT를 포함한 pending으로 바뀌었다.

정상 형식의 문서라도 진짜 승인·배포·삭제를 수행했는지는 자동 확인할 수 없다. `production_ready`, `human_approval_authenticated`, `physical_deletion_verified`는 항상 false다. 특히 보유기간 만료 청소만으로 **기간 안에 수동 삭제한 데이터가 백업 복원 후 되살아나지 않는다**고 주장하지 않는다. 삭제 재적용 절차·실제 복원 리허설은 운영 증거로 남아 있다.
