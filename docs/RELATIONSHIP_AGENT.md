# 모델 교체형 관계 에이전트 v3.7-grounded

## 사용자 제공 예시 기반 개선 — v3.7

`답변 예시1.txt`의 선택 표시와 자유 답변을 `HOP_agent/local_api/agent_data/sibling_computer.json`으로 매핑했습니다. 현재 UI에서 합쳐진 대처/받아 본 도움은 원문 두 답변을 줄바꿈으로 함께 보존했습니다. 문항 밖 제목·메모·UI 지시와 미응답은 사실 근거로 넣지 않았습니다. 직접 `ModelGateway.respond`를 호출하여 실제 상태 생성부터 다섯 카드 검토까지 평가합니다. 이 평가 자체는 브라우저 입력·DB 저장을 다시 실행하는 검사가 아닙니다.

첫 출력에서는 지원 방향 반전, 원문에 없는 가족의 방관 평가, 회복 재촉, 실제 발화 대신 작성 지시를 권하는 오류가 나타났습니다. 1차 수정 뒤에도 혼자 돌보고 있다는 사실 추가와 거절 이유 추정이 남아 `support_review`를 추가했습니다. 전체 카드 주장 검토 뒤 next/care만 원문과 다시 대조하고, 기존 공유 수정 예산 안에서 해당 카드만 고친 뒤 재검토합니다. 현재 위험이 확인된 경우에는 기존 고정 긴급 행동을 그대로 유지합니다.

프롬프트는 원문의 목적을 보존하되 회복을 재촉하는 말을 작은 선택 제안으로 바꾸며, 선택권을 주는 “편할 때/원하면”을 잘못 거부하지 않도록 구분합니다. 반복 관찰된 오류에는 서버 검증도 추가했습니다. 가족 대응 의견을 방관으로 확대하거나 감정을 근거 없는 인용에 연결한 해석, 지원 방향 반전, 회복 재촉, 지시문을 그대로 발화하라는 대안을 제한된 재작성으로 돌립니다. 이 규칙들은 모든 의미 오류를 판정하는 완전한 검증기가 아닙니다.

모델 교체 시 `MODEL_PROTOCOL=relationship_agent`를 유지합니다. 모델 이름·주소·응답 형식은 역할 프롬프트와 분리했습니다. `MODEL_AGENT_FORMAT`은 `json_schema/json_object/prompt`, `MODEL_REASONING_EFFORT=omit`은 확장 옵션 생략입니다. 모든 모드가 같은 서버 검증을 거칩니다. 코드 적용 도구는 기존 모델 설정을 덮어쓰지 않습니다. [실행·모델별 비교 방법](../README.md#자체-파인튜닝-모델로-교체).

아래 v3.6 실측 기록은 이전 완료 기록입니다. v3.7 사용자 예시의 반복 평가 결과는 비공개 `HOP_agent/outputs/relationship_agent/provided_sibling_computer*.json`에 구분해 저장합니다. 새 자체 파인튜닝 모델의 성능은 아직 검증하지 않았습니다. 제공 예시는 기준 실행과 여섯 차례 후속 실행을 보존했으며, 두 실행은 검증 실패로 결과를 확정하지 않았습니다. 최종 실행은 약 99.6초이며 두 차례 카드 수정 후 통과했습니다. 최신 자동 테스트 272개가 통과했습니다. 최종 코드로 실제 모델 회귀 4건(제공 예시의 누적 상태 갱신, 기존 부모·자녀 최종 답안, 현재 위험 상태, 부정된 위험 상태)도 모두 통과했습니다. 원문과 다섯 카드의 전후 검토는 비공개 `sibling_example_review.txt`에 있습니다.

## 현재 로컬 구성 — 2026-10-11

Linux의 기존 Ollama 0.33.3에 `gemma4:12b` Q4_K_M을 추가했습니다. 기존 26B 모델과 Ollama 서비스 설정은 변경하지 않았습니다. RTX 5070 Ti 16GB에서 모델을 호출합니다. 모델 주소는 `http://127.0.0.1:11434/v1`, API는 `http://127.0.0.1:9000`, PostgreSQL은 Docker의 `5433`입니다. 실행 방법은 [README](../README.md)를 따릅니다.

한 모델이 여러 역할을 **독립된 요청으로 순차 실행**합니다. 이전 응답은 다음 역할의 검토 자료이며 새로운 사실 근거가 아닙니다. 사용자 답변마다 다음 단계를 실행합니다. `question_review`는 생략·추가 확인 제안이 있을 때 실행합니다.

| 단계 | 맡은 일 |
| --- | --- |
| `state_observations` | 현재 원문에서 대상자·이용자의 보고를 선택합니다. 이전 요약은 입력에서 제외합니다. |
| `relationship_memory` | 새 관찰과 현재 원문으로 관계 가설·미확인을 갱신합니다. |
| `state_review` | 주장별 `audits`에서 전체 주장 지지 여부와 확실성을 확인합니다. 누락·중복·근거 부족 승인은 서버가 거절합니다. |
| `question_plan` | 같은 사람의 원문으로 이미 답한 질문의 생략이나 추가 확인을 제안합니다. 현재 위험도 확인합니다. |
| `question_review` | 생략 근거가 질문 전체에 답하는지, 추가 확인이 중복인지 독립적으로 판정합니다. 단지 관련된 내용이면 생략을 취소하고 원래 질문을 묻습니다. |
| `safety_review` | 진행자가 현재 위험을 제안했을 때 일반적 고통·부정·과거 위험과 지금 신체 위험을 구별합니다. 별도 확인을 거친 현재 신체 위험만 일반 질문을 종료합니다. |

상태 검토에서 거절되면 관찰부터 한 번 다시 만들고 재검토합니다. 최신 답변은 서버가 전체 원문으로 보존하므로 모델이 초기 근거만 고르는 경우에도 최신 보고가 사라지지 않습니다. 후속 답변의 정정이 가장 최신입니다. `reported` 해석은 서버가 “대상자에 관한 이용자 답변 원문” 등 귀속 표현으로 만들고, 모델의 인과·마음 해석은 `tentative`로 제한합니다. `unknowns`는 미확인 정보입니다.

최종 결과는 다음 역할을 각각 호출합니다.

1. `relationship_analysis` → `analysis_review`: 현재 원문으로 관계를 다시 분석하고 주장별로 대조합니다.
2. `communication_plan` → `plan_review`: 실제 장면·사용자 목적·상대의 선택·사용자 경계를 설계하고 검토합니다. 사용자의 목적을 대상자의 속마음 해석으로 바꾸거나 상대의 반응을 예측하면 수정합니다.
3. `guide_write` → `guide_quality`: 기존 다섯 카드(`script`, `doList`, `avoid`, `next`, `care`)를 작성하고 구체성·실행 가능성을 검토합니다.
4. 필요 시 `guide_refine` → `guide_quality_check`: 개선한 결과를 다시 검사합니다.
5. `speech_write` → `speech_review`: 관찰 장면과 사용자 목적에 집중하는 별도 요청으로 발화문을 다시 작성합니다. 전체 카드 초안의 발화는 임시 자료이며 저장하지 않습니다. 전담 작성 결과와 다른 카드의 각 항목을 모두 분리하여 관찰·사용자 마음·열린 질문인지, 상대의 마음이나 원인을 단정했는지 검토합니다. 피할 표현의 부정 문맥과 조건부 행동 제안은 사실 주장과 구분합니다.
6. `support_review`: `next`와 `care`만 다시 원문과 대조해 돌봄 역할 추가·거절 이유 추정을 확인합니다.
7. `guide_review`: 전체 카드의 근거·역할·목적·동의·위험 처리의 중대한 오류를 최종 확인합니다.

오류 재작성에는 문제가 된 해석과 해당 원문을 피드백으로 제공하며 운영 로그에는 이를 남기지 않습니다. 카드 수정에서는 지적받지 않은 필드를 스키마 enum으로 고정해 이미 검증한 내용을 보존합니다.

분석·전략은 각각 한 번, 최종 카드 오류는 최대 두 번 수정하고 독립된 검토 요청을 다시 거칩니다. JSON·인용 검증 실패는 단계당 최대 세 번 시도합니다. 요청 전체에는 600초 공통 마감 시간이 있으며 오류가 남거나 시간이 끝나면 결과를 꾸며 저장하지 않습니다. 생성 단계 수·재시도·시간은 실행 기록으로 남고 운영 로그에는 원문이나 비밀값을 넣지 않습니다.

RAG는 현재 대화의 원문만 검색합니다. 사람·문항·부정·시점·정정을 함께 확인하며 이전 모델 요약과 다른 대화는 검색 자료가 아닙니다. 인용 문자열 일치 검증과 모델의 의미 검토는 별개입니다. 의미 검토 역시 같은 모델이 수행하므로 무오류를 보장하지 않습니다. 실제 출력에서 발견한 실패는 회귀 검사와 역할 프롬프트에 반영합니다.

실제 모델에서 진행자와 검토자가 모두 행동 묘사를 다른 사람의 의견이나 가장 큰 걱정의 답으로 오인하는 실패가 있었습니다. 기본 `concern`은 명시적 우선순위 표현, `others_why`·`others_help`는 다른 화자의 발언 단서가 인용에 있을 때만 생략 후보가 됩니다. `extra`는 추가 정보를 말할 기회를 보존합니다. 이 조건도 의미 판정을 대신하지 않으며 모델 검토를 함께 거칩니다.

추가 확인은 최대 세 개이며 답변·모름·거절을 모두 소비된 질문으로 처리합니다. 기본 문항을 넘어 임의로 끝없이 질문하지 않습니다. 위험 근거가 확인되면 보통 질문을 종료하고 조건부 즉시 도움 안내를 먼저 표시합니다. 최종 긴급 행동 카드는 고정된 도움 연결 문구를 사용하며 동의를 기다리게 하지 않습니다.

Ollama의 JSON grammar 반복 제한을 피하려고 실행기에 전송하는 스키마에서 문자열 `maxLength`만 제거합니다. 서버의 원본 스키마·길이 검증은 유지합니다. 모델의 숨은 추론 길이에 의존하지 않고, 기록·분석·검토·수정이라는 외부 단계를 명시적으로 실행합니다.

## 로컬 검증 결과 — 2026-10-11

- JavaScript·JSON 문법 검사와 `bash -n scripts/run-local.sh` 통과.
- PostgreSQL을 포함한 통합 회귀검사 **264/264 통과**, 건너뛴 검사 없음.
- 실제 웹 API에서 **32개 답변**(기본 29개 + 확인 3개)을 입력하고 최종 다섯 카드 생성·저장·재조회 통과. 최종 생성 80.851초. 서버 재시작 뒤 대기 답변을 이어서 처리하는 경로도 확인했습니다. 합성 기록은 검사 뒤 앱에서 정리했으며 비공개 보고서는 보존했습니다.
- 이후 발견한 카드 내 마음 단정·접촉 동의·호칭 문제에 대한 서버 검사와 재작성 규칙을 추가했습니다. 같은 32답변 원문에서 최신 최종 생성 재검증 **62.739초 통과**. 이 추가 교정 뒤 32답변을 전부 새로 입력한 것으로 보고하지 않습니다.
- 현재 신체 위험 합성 사례: 상태 갱신·`safety_review` **16.106초**, 즉시 도움 안내 최종 생성 **45.568초** 통과.
- 위험을 부정하고 관계가 미확인인 합성 사례: 상태 판단 **12.326초**, 최종 생성 최신 재검증 **46.157초** 통과. 현재 위험으로 바꾸지 않았습니다.
- 초기 문맥 이후 이용자 부담·지지 원문을 추가하는 누적 상태 평가 **46.793초** 통과. 초기 메모리와 갱신된 메모리를 함께 보관합니다.

평가 파일은 `HOP_agent/outputs/relationship_agent/`에 있으며 Git에서 제외합니다. 운영 로그와 달리 합성 평가 파일에는 검증용 원문과 모델 초안이 들어 있습니다. `docker_web_smoke-v36-final.json`은 API 통합 결과, `attached_mother_child-web.json`은 후속 최종 생성, `current_danger_friend*.json`, `denied_risk_unknown_relation*.json`은 위험 비교, `attached_mother_child-incremental-state.json`은 누적 평가입니다. 파일 이름의 `docker_web_smoke`는 기존 도구 이름이며 이번 API는 호스트 Node.js로 실행했습니다.

자동 검토의 승인이 의미적 정확성을 보장하지는 않습니다. 실제 모델이 근거 밖 표현이나 잘못된 생략을 승인한 사례를 확인하여 별도 역할과 회귀 조건을 추가했습니다. 검토 예산 안에서 해결되지 않는 응답은 최종 결과로 저장하지 않습니다. 새 관계·표현에 대한 평가는 계속 확장할 수 있습니다.

# 인수인계 이력: Gemma4 12B 관계 에이전트 v3.5-rag

현재 개발 구성은 Mac의 native Ollama `gemma4:12b`, `MODEL_PROTOCOL=relationship_agent`, 프롬프트 버전 `relationship-v3.5-rag`입니다. 현재 대화의 원문을 검색하여 근거로 제공하고, 하나의 모델을 답변별 상태·관계 메모리 갱신, 최종 관계 분석·분석 검토·말하기 전략·가이드 작성·품질 개선·중대한 오류 검토 역할로 순서대로 호출합니다. 기존 `src/server.js`, `public` 화면, `compose.yaml`, PostgreSQL 저장 구조에서 동작하며 새 의존성을 추가하지 않습니다. v3.5는 대상자·이용자 관찰을 정확한 원문 인용으로 선택하고 서버가 표시 요약을 구성합니다. Docker 반영과 통합검사 229개를 통과했습니다. 이전 v3.4의 합성 29문항 최종 생성·저장·재조회는 약 268.6초에 통과했으며 버전별 실제 모델 검증은 아래에 구분합니다.

| 프로토콜 | `relationship_agent` |
| 공통 제한 시간 | `MODEL_TIMEOUT_MS=600000` |

Mac에서 Ollama와 Docker Desktop을 실행하고 `ollama list`에서 모델을 확인합니다. 서버 전용 `.env`의 모델 설정을 위 표에 맞춘 뒤 `docker compose up -d --build`로 실행합니다. 호스트에서 개발할 때는 PostgreSQL만 Compose로 실행하고 `npm start`를 사용합니다. 앱 연결 검사에는 비어 있지 않은 `MODEL_API_KEY`도 필요하며 실제 값은 문서·브라우저·로그에 기록하지 않습니다. DB 암호와 `CONTENT_KEY`도 기존 값을 보존합니다.

`npm run setup`은 기존 `.env`를 유지하고 기본 DB 설정을 준비합니다. `--model-env`는 기존 게이트웨이용 `json_schema` 설정을 가져오므로 현재 관계 에이전트 설정을 대신하지 않습니다. `/health`의 `model_configured`는 연결 설정 유무를 나타내며 실제 모델 생성 성공은 별도로 검증합니다.

`malssi-gemma4-31b-step100`은 따로 선택하는 학습 모델·API·SSH 터널 경로입니다. 기존 학습·runtime 자료와 실행 경로는 유지하며, 현재 문서의 12B 실행 절차로 전환하거나 덮어쓰지 않습니다. [README의 별도 31B 안내](../README.md#별도-31b-학습-모델-경로)와 [이전 서버 이동 기록](DOCKER_HANDOFF.md)을 확인합니다.

## 답변별 상태 갱신과 최종 생성

사용자 답변은 먼저 PostgreSQL의 대기 상태와 버전 이력에 저장합니다. 모델은 매 답변 뒤 누적된 현재 답변 원문 전체와 현재 원문으로 검증된 이전 상태·관계 메모리, 현재 대화에서 검색한 `retrieval.documents`를 읽습니다. 기본 답변·직접 입력·후속 답변과 `answered`/`unknown`/`refused`/`skipped` 상태를 구분하여 기존 `patient_state`, `name_index`와 별도 `relationship_memory`를 반환합니다. 관계 프로토콜에서는 사용자가 허용된 문항을 건너뛰어도 모델 갱신을 수행하지만, 건너뜀을 새 사실이나 동의로 해석하지 않습니다.

최신 pending 질문의 문항·사람 metadata를 현재 원문의 해당 항목과 연결하여 `latest_answer={subject,question_id,question,status,answers}`로 전달합니다. STATE는 새 관찰·생활 변화·정정·이용자 부담·도움의 한계·지원 자원을 확인한 뒤 요약과 finding을 갱신합니다. 현재도 유효하고 중요한 이전 내용은 유지하되 더 구체적인 근거나 정정이 있으면 이전 해석을 수정·교체합니다. 새 정보가 없을 때 의미 없는 변화를 만들도록 요구하지 않습니다.

서버 검증이 성공하면 두 메모리를 암호화된 대화 상태와 이력에 저장하고 다음 질문으로 진행합니다. 실패한 답변은 보존하며 같은 질문에서 수정하거나 재시도할 수 있습니다. 같은 답변의 재시도는 대화 기록을 중복 추가하지 않습니다.

### 별도 내부 관계 메모리

| 모델 출력과 저장 위치 | 내용 |
| --- | --- |
| `patient_state` → `agentMemory` | 기존 상태 요약·원문 사실·미확인 내용·이용자 목적을 유지합니다. |
| `relationship_memory` → `agentRelationshipMemory` | `patient`, `supporter`, `relationship`의 관찰·해석을 각각 0~2개와 별도 `unknowns`로 저장합니다. |
| `relationship_state` → `prior_relationship_memory` | 다음 모델 호출에서 현재 원문으로 다시 검증한 관계 메모리만 제공합니다. 근거가 오래되었거나 사람·문항이 맞지 않으면 이전 메모리를 승인하지 않습니다. |

관계 메모리의 각 finding은 `interpretation`, 정확한 원문 `evidence`, `certainty`를 가집니다. `patient`와 `supporter`의 직접 보고된 행동은 `reported`로 남깁니다. 원인·동기·마음이나 여러 답변 사이의 인과관계를 추론한 해석은 `tentative`로 표시하며 원문에 없는 원인을 확정하지 않습니다. `relationship`의 모든 finding은 관계 패턴에 대한 가설로 취급하여 스키마에서 `certainty=tentative`로 제한합니다. `patient` finding은 대상자 문항의 근거만, `supporter` finding은 이용자 문항의 근거만 사용합니다. 모름·거절·건너뜀은 확정 근거로 쓰지 않으며 확인되지 않은 정보는 `unknowns`에 남깁니다.

매 턴 상태 출력 스키마는 각 사람의 실제 `answered` 원문을 확인합니다. 이름을 제외한 근거가 없으면 해당 `patient` 또는 `supporter` 배열의 `maxItems`를 `0`으로 지정합니다. 이용자 목적의 답변을 다른 사람의 원문으로 옮겨 넣을 수 없도록 근거의 `subject`도 해당 사람으로 제한합니다. 이름만을 근거로 한 finding은 서버 검증에서도 거절합니다.

`agentRelationshipMemory`는 기존 대화 상태의 AES-256-GCM 암호화·버전 저장 구조에 포함하며 별도 평문 파일이나 새 DB 테이블에 저장하지 않습니다. 뒤로가기·정정은 이후 `agentMemory`, `agentRelationshipMemory`, 모델 결과·최종 기록을 무효화합니다. 새 답변과 이전 근거가 맞지 않으면 현재 원문을 기준으로 다시 생성합니다.

최종 `relationship_memory`는 검토를 통과한 `relationship_analysis`에서 다시 구성합니다. 승인된 강점·한계 중 해당 사람의 근거만 가진 항목을 `patient`와 `supporter`에, 승인된 관계 특징을 `relationship`의 `tentative` 항목에 반영하고 미확인 내용도 승인된 분석에서 가져옵니다. 이전 메모리의 거절된 해석을 최종 상태에 다시 저장하지 않습니다.

최종 결과는 다음 순서로 준비합니다.

| 단계 | 역할과 검증 |
| --- | --- |
| 상태 확인 | 기존 상태와 관계 메모리가 모두 현재 원문에 유효한지 확인합니다. 어느 하나라도 없거나 부적합하면 최종 문맥에서 두 메모리를 다시 생성하고 검증합니다. |
| `relationship_analysis` | 대상자·이용자별 `observations`에 정확한 원문 인용을 최대 2개 선택하고 관계 특징·강점·한계를 분석합니다. 서버가 관찰 요약을 인용 그대로 구성하며 각 해석의 근거를 실제 답변과 대조합니다. |
| `analysis_review` | 가이드를 만들기 전에 분석 자체의 중대한 오류를 현재 원문과 대조합니다. |
| 필요 시 `analysis_repair` → `analysis_review_after_repair` | 분석을 한 번 수정하고 다시 검토합니다. 다시 거절되면 전략·가이드 생성으로 넘어가지 않고 실패합니다. |
| `communication_plan` | 실제 관찰 장면과 이용자의 목적을 바탕으로 말투·첫마디 근거·상대의 선택·이용자 자기돌봄을 설계합니다. |
| `guide_write` | 기존 카드에 들어갈 첫마디·행동·피할 표현·다음 단계·자기돌봄을 작성합니다. |
| `guide_quality` | 실제 장면·이용자 목적·대화 허락·상대의 선택·행동 대안·자기돌봄을 살펴보고 문장 개선점을 최대 3개 제안합니다. |
| 필요 시 `guide_refine` | 품질 개선 제안을 한 번 적용합니다. 없는 사실을 보충하지 않고 이후 중대한 오류 검토를 받습니다. |
| `guide_review` | 원문과 분석·최종 안내를 대조하여 사람 혼동, 없는 사실·성별·동의 확정, 강압, 진단·치료 지시, 현재 위험 누락 등을 검토합니다. |
| 최종 검토에서 분석 오류 발견 시 | 분석 수정 예산이 남아 있으면 `analysis_repair_after_guide_review` → `analysis_review_after_guide_review_repair`를 실행합니다. 승인된 새 분석으로 전략·가이드·품질 검토·필요 시 다듬기·최종 오류 검토를 다시 수행하며 이 단계들은 `_after_analysis_repair` 접미사를 사용합니다. 분석 수정 예산이 없거나 재검토도 거절되면 실패합니다. |
| 필요 시 `guide_repair` → `guide_review_after_repair`, 전체 최대 두 차례 | 가이드 오류를 수정하고 각 수정 뒤 다시 검토합니다. 두 번째 수정에는 `_2`가 붙습니다. 분석 수정 후 가이드를 다시 작성해도 이미 사용한 가이드 수정 횟수를 초기화하지 않습니다. 마지막 검토도 거절되면 최종 결과를 저장하지 않습니다. |

관계 분석 → 분석 검토 → 전략 → 가이드 → 품질 검토·필요 시 다듬기 → 중대한 오류 검토는 순차 실행합니다. 각 단계는 완전한 JSON Schema 출력과 서버 검증을 통과해야 다음 단계로 넘어갑니다. 품질 검토는 문장의 구체성·사용성을 개선하는 단계이고, 분석·최종 오류 검토는 중대한 오류의 승인 여부를 판단하는 단계입니다. 제한된 수정 후에도 분석·최종 오류 검토에 부적합하면 실패로 처리합니다.

최종 결과에는 `relationship_analysis`와 `provenance.agent`의 `prompt_version`, 실행 `stages`, `reviewed:true`, `quality_reviewed:true`, `retrieval`을 저장합니다. `retrieval`에는 검색 방식과 단계별 색인 원문 수·선택한 `source_ids`가 있습니다. 원문 내용은 이 추적 metadata에 넣지 않습니다. `reviewed:true`는 최종 중대한 오류 검토를 통과했다는 뜻이고 `quality_reviewed:true`는 문장 품질 검토를 수행했다는 뜻입니다. 사람의 검토나 임상 타당성 확인을 뜻하지 않으며 `clinically_validated:false`를 유지합니다.

상태 갱신 한 번과 최종 에이전트 실행 한 번은 각각 `600000`ms의 공통 제한 시간을 사용합니다. 최종 생성의 모든 분석·검토·재시도·수정은 같은 마감 시간 안에서 실행하며 단계마다 10분이 새로 부여되지는 않습니다. 일시적 연결 오류나 형식·근거 검증 실패에 따른 재요청은 단계별 최대 3회입니다. 분석 수정·재검토는 초기와 최종 검토 후를 합쳐 전체 1회, 중대한 가이드 오류 수정·재검토는 재작성 전후를 합쳐 전체 2회입니다. 품질 개선은 각 작성 흐름에서 필요할 때 한 번 수행합니다. 이들 제한과 공통 마감 시간 안에서 검토를 통과하지 못하면 최종 결과를 저장하지 않습니다.

## 원문 관찰과 관계 해석 분리

v3.5의 모델 분석·분석 수정 출력은 `observations`, `relationship`, `unknowns`, `safety`만 허용합니다. `observations.patient`와 `observations.supporter`는 해당 사람의 현재 `answered` 원문에서 고른 근거 객체를 각각 최대 2개 갖습니다. 이름만을 근거로 한 관찰과 다른 사람의 인용은 거절하며, 근거가 없으면 빈 배열로 남깁니다.

서버가 `patient_summary`와 `supporter_summary`를 원문 인용과 출처를 알리는 고정 문구로 구성합니다. 이 요약에 모델이 원인이나 성향을 새로 서술할 수 없으며 저장 전에도 관찰 인용과 정확히 일치하는지 검사합니다. 대상자 문항 역시 앱 이용자의 관찰·전언이라는 점을 표시합니다. 각 요약은 최대 2개의 1,000자 인용을 보존하도록 2,400자로 제한합니다. `observations`는 최종 저장 결과에도 유지합니다. 기존 `observations` 없는 기록은 이전 계약으로 검증하지만 새 모델 생성 경로에서는 자유 요약 필드를 허용하지 않습니다.

관계 해석은 별도 `relationship`에 근거와 함께 남기며, 원문 인용이 일치하더라도 해석의 모든 의미가 맞는다는 보장은 없습니다. 이 부분은 분석 검토·최종 검토와 사례 평가로 계속 확인합니다.

## 현재 즉각적 위험의 행동 계약

원문 근거와 분석 검토에서 `safety.urgent=true`가 유지되면 `script`, `doList`, `avoid`, `next`, `care.tips`의 긴급 행동은 검토된 문구로 제한합니다. `urgentGuideActions`가 검증된 이름만 선택적으로 넣고, 생성 스키마의 문자열·배열 enum과 서버의 정확한 일치 검사로 같은 문구를 요구합니다. 현재 위험에 동의 대기나 나중 대화를 권한 초기 실패 출력을 조용히 덮어쓰지 않고 거절하여 다시 생성합니다. 모든 재시도가 실패하면 결과를 저장하지 않습니다.

분석을 나중에 수정해 긴급 여부가 바뀌면 작성·품질 수정·오류 수정마다 현재 분석으로 스키마를 새로 만듭니다. 긴급 행동 계약은 `agent.safety_guidance_version=immediate-help-v1`로 추적합니다. 일반적인 대화에는 이 고정 행동을 적용하지 않습니다. 원문 관찰·관계 해석은 계속 현재 대화의 RAG 근거를 사용하고, 긴급 시 `care.feel`에는 이용자가 보고한 감정만 반영하도록 요청하고 최종 검토합니다. 위험 판정이나 자유로운 해석의 의미 전체가 자동으로 검증된다는 뜻은 아닙니다.

## 대화 원문 기반 RAG

`sourceDocuments`는 호출 시점의 현재 대화 문맥에서 `answered`인 대상자·이용자·이용자 목적 답변만 문서로 만듭니다. 각 문서는 사람, 문항, 질문, 선택/직접 입력/후속 답변의 정확한 원문과 원문 내용에서 만든 `source_id`를 가집니다. 매 호출 새로 색인하므로 정정 전 원문, 생성한 메모리·가이드, 다른 세션을 검색 자료로 사용하지 않습니다. 모름·거절·건너뜀은 검색 근거에서 제외하고 응답 상태로 따로 전달합니다.

검색 방식 `conversation_lexical_v1`은 NFKC 정규화·소문자 변환 후 단어와 문자 bigram을 추출합니다. query와 원문 문서에 겹치는 항목의 역문서빈도 가중치를 합하고 문서 항목 수로 정규화하여 순위를 매깁니다. BM25나 임베딩·vector 검색을 구현한 것은 아닙니다. 대상자 상태, 이용자 부담, 관계 상호작용, 지지 자원의 역할별 query와 이용자 목적을 사용하며 최종 단계에서는 분석 요약·검토 의견도 query에 보탭니다.

검색 상위 개수는 같은 답변의 원문·직접 입력 변형 수가 아닌 서로 다른 문항 수로 계산합니다. 고정 선택하는 이름·관계·목적은 순위 슬롯을 소비하지 않습니다.

최신 답변, 이름·관계·이용자 목적, 위험 표현을 포함한 원문은 순위와 관계없이 선택합니다. 상태 호출의 검증된 이전 메모리와 최종 단계 payload에서 이미 인용한 문항의 원문도 유지합니다. 짧은 대화는 전체 답변을 선택합니다. 검색된 문항은 선택 보기·직접 입력·후속 답변이 함께 들어가도록 묶고 원문 전체를 제공합니다. 위험 표현이 포함되었다는 이유로 긴급 상태를 확정하지 않으며 부정·화자·시점도 원문과 함께 읽습니다.

매 상태 갱신과 최종 생성의 모든 단계에 `retrieval` payload를 전달합니다. 전체 현재 `answers`도 원문 대조 자료로 유지합니다. 근거 객체 enum은 해당 호출에서 선택한 원문으로 제한하고, 생성 후에도 인용의 사람·문항·quote가 검색 원문에 실제 포함되는지 검사합니다. 검색 밖의 인용은 `agent_retrieval_evidence`로 거절하며 기존 현재 원문 검증도 함께 수행합니다. 이는 인용 출처의 범위를 확인하는 장치이며 해석의 타당성이나 의미 검색의 완전성을 인증하지 않습니다.

최종 `agent.retrieval`은 `method`와 단계별 `stage`, `indexed_sources`, `source_ids`를 남깁니다. 운영 진단 로그에 원문이나 생성 내용을 기록하지 않습니다. 검색 자료는 서버 내부 모델 입력에 쓰며 별도 벡터 DB나 외부 검색 서비스로 보내지 않습니다.

## 전체 원문과 문맥 한계

현재 관계 프로토콜은 누적된 원문을 읽으며 입력을 조용히 삭제하거나 축약하는 복구를 수행하지 않습니다. Ollama **0.40.0 MLX**에서 OpenAI 호환 채팅은 `ChatHandler`로 연결되고 MLX 분기에서 `truncate=false`를 사용합니다. 근거는 고정 커밋의 [채팅 입력 처리](https://github.com/ollama/ollama/blob/0d0720e51fb2fd9aa58781c3d720c06d720c2e7b/server/routes.go#L3183-L3188)입니다.

MLX runner는 토큰화한 입력을 모델 문맥 한계와 비교하여 한계에 도달한 입력을 오류로 처리합니다. 모델이 HTTP 400과 `input length (N tokens) exceeds the model's maximum context length (M tokens)` 메시지를 반환하면 앱은 `MODEL_CONTEXT_TOO_LONG`으로 명시 실패합니다. 현재 관계 프로토콜에서는 이 오류를 원문 축약으로 재시도하지 않고 입력 답변·대기 상태를 보존합니다. [MLX runner의 입력 한계 검사](https://github.com/ollama/ollama/blob/0d0720e51fb2fd9aa58781c3d720c06d720c2e7b/mlxrunner/pipeline.go#L73-L82).

`/api/ps`에서 관측한 `context_length:32768`은 그 응답의 표시값입니다. 이 숫자만으로 실제 모델·runner의 최대 입력 하드 한계를 확정하지 않습니다. 실제 거절 여부와 한계는 해당 버전의 입력 검사 및 오류 응답과 함께 확인합니다.

## 원문과 사람 구분

`patient`는 도움받을 대상자, `supporter`는 앱 이용자, `user_goal`은 이용자가 전하려는 말과 바라는 결과입니다. 내부 필드명 `patient`가 임상 진단을 의미하지 않습니다. 대상자의 증상·지원망과 이용자의 감정·부담·지원망을 구분합니다. 질문 ID와 대상은 대화 시작 시 보존한 질문 스냅샷에서 가져오므로 문항 수나 고정 ID 목록에 의존하지 않습니다.

- 각 근거의 `subject`와 `question_id`가 실제 응답 대상·문항과 일치해야 합니다.
- `quote`는 해당 답변의 원문·선택/직접 입력·후속 답변에 있는 연속 부분 문자열이어야 합니다.
- 관계 특징·강점·한계의 해석마다 최소 한 개의 검증된 근거를 요구합니다. 모름·거절·건너뜀을 확정 근거로 사용하지 않습니다.
- 관계 이름은 실제 관계 답변에 있어야 합니다. 관계 답변이 미확인이면 관계 이름과 역할을 `확인되지 않음`으로 남깁니다.
- 안전 근거는 위험 단어만 발췌하지 않고 부정·화자·시점을 확인할 수 있는 문맥을 보존합니다. 긴급 위험 표시에는 실제 근거가 필요하고 가이드의 안전 표시도 분석과 같아야 합니다.
- 이용자의 해석과 관계 패턴은 `tentative`로 표시하고 대상자 자신의 의사·동의처럼 아직 알 수 없는 내용은 `unknowns`에 남깁니다. 정정된 답변은 이전 메모리보다 우선합니다.

서버가 확인하는 것은 출력 형식·문항·사람·인용의 일치입니다. 해석의 모든 의미가 옳음을 기계적으로 인증하지는 않습니다. 같은 모델의 별도 검토 단계로 중대한 의미 오류를 다시 확인하며 프롬프트와 평가 사례를 계속 개선합니다. 진단·성격 판정·임상 점수·치료 변경을 생성하도록 요청하지 않습니다. 모델이 위기 연락처를 새로 생성하지 않으며 화면의 기존 안전 안내를 사용합니다.

입력 답변은 분석 자료로 취급합니다. 답변에 포함된 역할 변경·프롬프트 지시·출력 요구는 모델 지시로 따르지 않도록 각 역할 프롬프트에 명시합니다. 모델 출력은 검증이 통과하기 전까지 승인된 상태나 최종 기록으로 저장하지 않습니다. 원래 사용자 답변과 실패 이력은 보존합니다.

### 근거 객체 enum

`groundedEvidenceSchema`는 각각의 사람·문항·인용을 따로 선택하는 대신 `{subject,question_id,quote}` 전체 객체를 하나의 enum 후보로 고정합니다. 해당 호출에서 검색한 `answered` 원문·완전한 문장·연속 인용 발췌를 후보로 만들고 중복을 제거합니다. 사람은 한 답변에서, 인용은 다른 답변에서 가져온 조합을 생성 단계에서 제한합니다.

이 스키마는 최종 분석·분석 수정·말하기 전략의 근거와 답변별 상태·관계 메모리의 근거에 적용합니다. 생성 제약과 함께 기존 서버 validator의 현재 원문 포함 여부·사람·문항·응답 상태 검증도 유지합니다. 긴 답변의 인용 후보는 발췌로 만들 수 있지만 전체 입력 원문은 그대로 전달합니다. 후보 발췌가 모델 입력을 요약하거나 축약하는 동작은 아닙니다.

위험 근거는 일반 인용 발췌와 다른 후보 목록을 사용합니다. 부정·화자·시점을 보존한 완전한 위험 문장 또는 전체 원문만 사용하며 위험 단어만 잘라서 후보를 만들지 않습니다. 후보가 없으면 빈 enum 속성을 추가하지 않고 기존 사람별 빈 배열 제한과 서버 검증을 유지합니다. native `gemma4:12b`의 실제 객체 enum probe 통과 기록은 아래 검증 현황에 구분하여 적습니다.

## 질문과 화면

현재 관계 에이전트는 `question_plan.skip=[]`를 사용합니다. 모델 판단에 따른 자동 질문 생략과 임의 질문 생성은 하지 않습니다. 기존 질문 조건·선택 보기·후속/보충 질문·필수 입력·사용자 건너뛰기·되돌리기는 그대로 서버가 처리합니다. 허용된 사용자 건너뛰기도 모델 상태·관계 갱신을 거치며, 사용자 정정이나 되돌리기는 이후 두 메모리와 결과를 무효화하여 이전 해석이 새 답변을 덮어쓰지 않게 합니다.

결과 화면은 기존 안내 5개(자기돌봄, 첫마디, 해볼 행동, 피할 표현, 다음 단계)를 유지합니다. **함께 살펴본 관계** 카드는 접힌 상태로 추가하며 펼치면 그분의 상황·이용자의 마음·관계 특징·강점·서로의 한계·미확인 내용을 표시합니다. 원문 근거도 별도 접힌 영역에서 확인할 수 있습니다. 추정은 확인이 필요하다고 표시하고 생성 문장과 인용은 HTML 이스케이프합니다. 칼럼용 분류는 화면에서 `경향` 대신 `안내`로 표시합니다.

기록 화면에도 같은 분석을 보여 주며 `relationship_analysis`가 없는 이전 기록은 기존 안내와 대화 기록을 그대로 표시합니다. 기존 위기 안내 카드와 하단 연락처는 유지합니다. 최종 생성은 하나의 서버 요청으로 처리하며 내부 단계별 실시간 진행률을 브라우저에 전송하지 않습니다. 오류가 나면 저장된 답변으로 재시도할 수 있습니다.

`npm test`는 `TEST_DATABASE_URL`이 없으면 PostgreSQL 검사를 건너뜁니다. `npm run test:integration`은 설정한 로컬 DB에 격리된 임시 테스트 스키마를 생성하고 검사 뒤 제거합니다. 자동 회귀검사 성공과 실제 모델 호출 성공, 웹 전체 검증 완료는 각각 별도의 확인 결과입니다. 이번 최종 저장 검증은 기존 합성 29문항 세션을 재사용했습니다. RAG 버전으로 29개 질문 전부를 처음부터 다시 입력하는 검증과 새 버전의 다른 관계·위험 사례 실제 모델 평가는 아래에 구분하며 프롬프트 최적화 종료를 선언하지 않습니다.

실행 코드는 [모델 게이트웨이](../src/model.js), [관계 에이전트](../src/relationship-agent.js), [대화 원문 검색](../src/relationship-retrieval.js), [역할 프롬프트](../src/relationship-prompts.js), [서버](../src/server.js)에 있습니다. 최적화 목표는 사용자의 `ok` 전까지 활성 상태로 유지합니다. 이전 31B·UI 검증 이력은 [검증 기록](VALIDATION.md)에서 날짜와 모델 경로를 확인합니다.

### 합성 사례에서 발견한 후속 보완

첫 v3.4-rag native 웹 문맥 재현에서는 생성·검토 단계가 모두 응답했지만, 품질 수정 후 script에서 이용자가 선택한 상담 제안과 관찰 장면이 사라져 평가가 실패했습니다. 검색이 짧은 일반적 답변에 치우친 점도 확인했습니다. 관찰·우려·지지 자원·장벽·이용자 부담·대처를 각각 검색하도록 주제를 나누고 긴 답변의 점수 불이익을 줄였습니다. 같은 해석을 여러 분석 그룹에 복제하는 출력은 거부하고, 명시적으로 선택한 상담/진료 목표는 긴급 안전 상황을 제외하고 script에도 남도록 검사합니다. 품질 수정 지침은 180자로 제한하고 장면·목표를 삭제하지 않도록 지시합니다. 해당 수정의 회귀검사는 통과했으며 실제 모델 재검증은 별도로 기록합니다. 내부 finding과 관계 요약에서 인용에 없는 완벽주의·강박·수면장애 명칭을 새로 붙이는 출력도 거부하며, 이는 반복 관측된 표현에 대한 제한이지 의미 전체의 자동 인증은 아닙니다.

RAG 연속 상태 갱신 실호출(합성 29문항): 초기 원문 23개 중 12개, 갱신 원문 29개 중 16개를 검색했습니다. 두 state 호출 및 새 이용자 근거 반영 검사를 약 108.7초에 통과했습니다. 다만 사람이 읽은 결과에 인용 밖 특성 명칭과 여러 주장을 한 인용으로 뒷받침하는 한계가 남아 있어, 그 명칭에 대한 검증을 추가하고 답안 의미 검토는 계속합니다.

추가한 원문 밖 명칭 검증의 실제 state 호출은 첫 출력의 `agent_unreported_label`을 거부한 뒤 두 번째 출력이 통과했습니다(총 약 123.6초). 저장된 합성 웹 결과는 강화한 관계·메모리 validator에도 통과했습니다. 발화문에서 발견한 `(줄바꿈)` 편집 표시는 저장·검토 전에 실제 문단 구분으로 변환하며 회귀검사를 추가했습니다. 여전히 요약의 인과 표현과 인용이 해석의 모든 세부 주장을 지지하는지는 사람 검토가 필요한 개선 항목입니다.

### v3.5 후속 평가

이전 v3.4의 친구 사례는 실제 로컬 모델의 최종 생성과 원문 검증을 약 211.1초에 통과했습니다. 이용자의 야간 휴식 경계와 상담 제안을 유지했습니다. 위험을 부정하고 스팸 지시문을 인용한 관계 미확인 사례도 약 182.6초에 안전 표시 `false`와 관계 미확인 검사를 통과했지만, 품질 수정에서 장면이 사라지고 허락 질문만 반복되는 문제가 남았습니다. v3.5는 허락 질문 반복을 줄이고 비강압적 관찰·걱정 표현을 보존하도록 보완했습니다. 이 이전 두 결과를 v3.5의 실제 모델 통과로 계산하지 않습니다.

초기 v3.5 현재 위험 합성 사례는 약 178.7초에 원문 관찰·위험 판정·기계 검사를 통과했지만, 답안 검토에서 긴급 도움을 동의 뒤로 미루는 오류를 발견했습니다. 모델의 `guide_review`도 이를 승인했으므로 이 실행을 의미 품질 통과로 보지 않습니다. 이를 일반 대화 허락 규칙과 긴급 도움 연결 규칙의 분리로 수정합니다.

긴급 도움 원칙의 공식 근거는 [NIMH 자살 FAQ](https://www.nimh.nih.gov/health/publications/suicide-faq)와 [Manchester NHS의 친구 지원 안내](https://mft.nhs.uk/camhs/supporting-a-friend/)입니다. 현재 즉각적 위험에는 도움 요청을 동의나 대답을 기다리느라 늦추지 않고, 이용자 자신의 안전을 우선하며 가능한 안전한 범위에서 곁에 있고, 전문 도움·주변 지원과 역할을 나눕니다. 모델은 확인되지 않은 연락처 번호를 생성하지 않습니다.

실제 Ollama `gemma4:12b`에서 긴급 행동의 배열 enum을 작은 합성 요청으로 확인했으며 HTTP 200과 지정된 배열의 정확한 반환을 확인했습니다. 전체 위험 사례와 웹 저장 검증을 대신하는 결과는 아닙니다.

긴급 행동 계약 적용 후 같은 실제 12B 위험 사례는 약 **201.2초**, 분석부터 최종 수정 검토까지 9단계로 통과했습니다. `immediate-help-v1`의 고정 행동을 작성·품질 수정·오류 수정 내내 보존했고 최종 `care.feel`도 이용자가 보고한 놀람·두려움·도움 필요의 범위였습니다. 품질 검토가 고정된 script를 수정하려 하고 최종 검토가 표준 행동을 원문에 없는 사건처럼 평가하는 불일치는 남아 있습니다. 해당 문구는 생성·서버 계약으로 바뀌지 않았고 재검토가 통과했지만, 이 불필요한 검토 비용은 후속 개선 항목입니다.

새 v3.5 합성 29문항 대화의 실제 Docker 웹 검증을 시작했습니다. 기존 완성 기록을 재사용하지 않으며 답변마다 관계 메모리 내용과 마지막 원문 관찰 저장·재조회를 검사합니다. 진행 중이므로 전체 웹 통과로 기록하지 않습니다.


## v3.8 상세 작성과 진행 표시

- care, doList, avoid, next 전담 작성은 각각 감정·부담·자원, 방법·목적·예시, 피할 표현·이유·대안, 반응별 후속 행동을 다룹니다. 첫 초안을 그대로 복사하는 입력은 제외합니다.
- speech_opening은 permission/observed_scene, speech_listening은 user_intent/open_question/wait_for_answer, speech_offer는 small_invitation/help_choice/decline_choice로 내용을 분리합니다. speech_write가 원문과 대조해 자연스러운 발화로 통합합니다.
- 이후 근거·사용자 부담·최종 검토와 제한된 수정이 끝난 최종 script만 speech_detail이 설명합니다. speech_detail_review는 설명에 붙인 인용이 개인화 주장 전체를 뒷받침하는지 확인합니다. 설명과 수정 전 발화가 어긋나지 않도록 순서를 고정합니다.
- 모델 호출 성공 이벤트를 서버 진행 조회로 전달합니다. 로딩은 실제 완료 단계당 한 칸이며 실패·재시도 중에 가짜 진척을 늘리지 않습니다.
- 결과와 기록의 행동/주의 카드는 각각 전체 폭으로 위아래 배치합니다. 첫 대화 카드에는 세 단계, 선택 이유, 접어 둔 근거 원문, 전체 발화와 복사 버튼을 표시합니다.
- 31B 및 자체 학습 모델도 MODEL_PROTOCOL=relationship_agent를 유지하면 동일한 흐름과 검증을 사용합니다. 모델 크기 증가 자체로 품질을 보장하지 않으며 변경된 모델로 재평가해야 합니다.

초기 v3.8 실제 실행은 형식 검증을 통과했으나 사람의 검토에서 초안 반복, 회복을 외식 조건으로 제시하는 표현, 가족 의견 차이를 혼자 책임지는 부담으로 확대하는 설명이 발견되었습니다. 전담 입력과 역할별 필드를 수정하고 이러한 알려진 오류의 검사 범위를 확대했습니다. 실제 출력 평가는 계속 진행 중이며, 단위·통합 검증 통과를 임상적/의미적 정확성 보장으로 취급하지 않습니다. 원문이나 실제 출력은 Git에 보관하지 않습니다.
