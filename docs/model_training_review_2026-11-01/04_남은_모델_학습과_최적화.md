# 앞으로 남은 모델 학습과 최적화

기준일: **2026-11-01, Asia/Seoul**. 현재 로컬 코드·데이터 메타데이터·검증 기록에서 확인되는 미완료 사항과 앞으로 시험할 후보를 정리했다. 아래 실험 순서와 채택 기준 중 ‘제안’이라고 표시한 내용은 앞으로의 작업안이며, 이미 실행한 결과가 아니다.

**같은 날 후속 로컬 수정 반영:** 앱 계약 검사기, 명시적 A/B/C 종료 정책 지원, 새 31B reference 실행용 최종 평가 연결을 구현했다. 실제 데이터의 프롬프트 불일치·새 검토 과제의 평가 부족은 해결된 것으로 표시하지 않는다. 우선순위·새 정책 경로·검증은 [로컬 수정 기록](../current/앱_학습계약과_완료판정_로컬수정_2026-11-01.md)을 따른다.

## 1. 현재 출발점

데이터 준비, 실행기 구현, 모델 학습 완료, 서비스 적용은 구분해야 한다. 최신 데이터 묶음이 검증을 통과했거나 실행 코드가 존재해도 해당 모델이 학습·평가·배포까지 끝났다는 뜻은 아니다.

| 대상 | 현재 확인된 상태 | 남은 핵심 작업 |
|---|---|---|
| 12B 생성용 A | 생성 역할을 분리한 로컬 데이터 묶음 준비 | A에 맞는 정책·평가·baseline 결합과 실제 학습 |
| 12B 검토용 B v2 | 답변·메모리 검토를 확대한 로컬 묶음 준비 | 표본 밖 의미 검토, 검토 역할 평가셋, 실제 학습 |
| 12B 통합용 C v2 | 생성·검토 역할을 함께 담은 로컬 묶음 준비 | 생성 능력과 검토 능력의 간섭·편향 비교, 실제 학습 |
| 31B 카드 모델 | 원상담→카드 수정→카드 생성 데이터, 학습 실행기·수치 검증 도구 존재 | 현재 후보의 완료 증거·역할 평가 연결, 학습 환경 적합성 및 전체 단계 완료 확인 |
| 앱의 호출·입력 최적화 | 검토 묶음·재사용·병렬화와 관련 로컬 검증 기록 존재 | 대표 사례의 실모델 비교, 실행 서비스별 적용 상태 확인 |

최신 12B 경로는 A의 `gemma4_12b_three_versions_20261101/`와 B/C의 `gemma4_12b_review_versions_20261101_v2/`다. **이전 종료 정책은 새 B/C 데이터 해시에 재결합되지 않았다.** 10월 31일 역할 평가를 검토용 B에 그대로 적용해 완료로 판정할 수 없다. 정확한 구성과 수량은 [학습 데이터 구성](01_학습_데이터_구성.md)을 따른다.

후속 로컬 수정에서는 기존 정책을 보존하면서 `training_completion_abc_{A,B,C}_20261101_v3/`를 새로 결합했다. 새 정책이 존재해도 앱 계약 drift와 B/C의 검토 역할 평가 누락 때문에 최종 판정은 대기한다. 아래 ‘기존 정책’ 설명은 10월 31일 원본의 상태를 가리킨다.

기존 문서의 ‘학습 실행기 미설치’는 작성 당시 설명이다. 현재 저장소에는 [31B 실행기](../../ai/scripts/train_cards_31b.py)가 있다. 초기 재검토 때 없었던 최종 평가 연결은 후속으로 `--completion-config` opt-in 경로에 구현했다. 옵션 없는 기존 실행은 종전 대기 동작을 유지한다. 새 연결도 실제 baseline·후보 판정이 필요하며, 구현을 실제 학습 완료로 해석하지 않는다.

후속 재검토에서는 로컬에 저장된 [31B 복귀 확인 기록](../../runtime/gpu-lora31b-opt-20261101/FINAL_FALLBACK_VERIFIED.json)을 발견했다. 해당 기록의 warmup은 **baseline 평가 1,080/3,618, 별도 장부 1,085행**, 복원 체크포인트는 **epoch 0·step 0**, `training_complete=false`, `adopted_optimizations=[]`다. 따라서 ‘새 31B 학습의 실행 증거가 전혀 없다’고 해석해서도 안 된다. 이는 저장 당시 상태이며 현재 원격 프로세스의 생존·진행률을 새로 확인한 결과는 아니다. 1,080과 1,085는 서로 다른 상태·장부 관측값이므로 한 값으로 고쳐 쓰지 않는다.

## 2. 진행 경계

현재 사용자 지침상 **GPU 서버 접속·작업·추론·학습은 재허용 전까지 금지**돼 있다. 이 문서 작성에서 서버에 접속하거나 학습을 실행하지 않았다. 지금 가능한 일은 로컬 데이터·코드 검증, 평가 설계, 합성 회귀검사, 허용된 로컬 모델을 이용한 검증 준비 등이다.

GPU 실험은 추후 명시적으로 재허용된 경우에만 실행하며, 지정 작업 경로·격리 환경·출력/캐시/임시 경로·사용 중인 GPU 확인, 이번 작업 프로세스만 종료하는 기존 경계를 그대로 적용한다. 허용된 검토용 Ollama API와 금지된 GPU 서버는 서로 다른 허용 범위다. [프로젝트 운영 지침](../../AGENTS.md).

모델 성능·크기·학습 진척·처리시간은 사용자 지정 대회 내부 평가의 채점 대상이 아니다. 아래 실험은 모델 개발을 위한 검증이며, 그 결과를 다른 평가 항목의 간접 감점 사유로 바꾸지 않는다. [평가 범위](../competition/05_평가범위와_학습데이터_기준.md).

## 3. 학습 전에 먼저 확정할 것

### 3.1 데이터·정책·평가를 같은 버전에 결합

1. 실험별 `COURSE.json`, `MANIFEST.json`, tokenizer/config/template, 데이터 검사 결과의 해시를 고정한다.
2. A/B/C를 각각 다른 후보로 기록하고, 공통 원상담을 중복 합산해 독립 데이터가 늘었다고 보고하지 않는다.
3. 새 B/C v2의 과제 목록과 단계에 맞게 종료 정책을 갱신하고 데이터 해시를 다시 결합한다.
4. baseline 모델·후보 체크포인트·평가 요청·참조·판정 파일을 해시로 연결한다.
5. 개발 평가와 최종 확인 자료의 사용 이력을 남긴다. 결과를 보고 수정한 test는 이후 미노출 시험으로 부르지 않는다.

**완료 증거:** 어떤 데이터·코드·정책·체크포인트·평가 파일로 판단했는지 한 실행 ID에서 추적 가능하고, 누락·불일치가 검사기에 의해 거절되는 상태. 기존 정책 파일을 이름만 바꿔 재사용하는 것은 완료가 아니다.

실제 재대조에서 확인한 호환성 공백은 다음과 같다.

- 최신 12B `APP_CONTRACT.json`에 고정한 앱 파일 7개 중 `relationship-agent.js`, `relationship-turn.js`, `relationship-prompts.js` **3개 해시가 현재 코드와 다르고 4개는 일치**한다. 문서상 ‘혹시 다를 수 있음’이 아니라 현재 통합 검증이 필요한 상태다. 해시 차이가 데이터 정답의 오류를 곧바로 뜻하지는 않는다.
- `training_completion_20261031/POLICY.json`의 chat 데이터는 이전 `gemma4_12b_expanded_20261031`에 결합돼 있고 새 `04_result_review` 단계가 없다. 후속으로 `training_stop.validate_policy()`와 bind에 알려진 A/B/C의 정확한 단계·과제 목록 지원을 추가했다. 기존 정책을 덮어쓰지 않고 새 정책을 생성했으며, 평가 범위 부족과 앱 계약 검토가 남으면 최종 완료로 판정하지 않는다.
- 기존 역할 suite에는 새 `answer_review`·`memory_review` 전용 평가가 없다. `memory_review` 학습 출력의 questions/safety는 null이므로 새 검토 행을 턴 전체의 질문·안전 검토 학습으로 계산하지 않는다.

### 3.2 검토 학습 데이터의 의미 품질 보강

신규 답변 검토 800행과 메모리 검토 800행은 기존 가상 200사례에서 파생됐다. 과제별 80행, 즉 **각 과제 10%**가 독립 의미 표본검토를 받았다. 전수 구조·원문·분할·수치 검증과 전수 의미 검토는 다르다.

후속 제안은 다음과 같다.

- 과제×오류 유형×정상/반려×분할별로 아직 의미 검토하지 않은 영역을 집계한다.
- 정상 사례를 잘못 반려하는 오류와 잘못된 출력을 승인하는 오류를 따로 검토한다.
- 결정적 합성 변형 외에 새로운 사례에서 실제 생성된 오류를 별도 수집한다. 평가용 사례를 학습용으로 이동시키지 않는다.
- 정답을 바꾸면 사례·검토·토큰·manifest를 다시 결합하고 과거 승인을 재사용하지 않는다.
- 사람·전문가 검토가 필요한 범위를 별도 기록한다. AI 검토 통과를 사람 승인으로 바꾸지 않는다.

**완료 증거:** 검토한 행/사례의 분모·검토자·판정·수정 이력·보류 사유가 추적되며, 표본 밖 항목에 대한 미검토 상태도 그대로 공개된다. [v2 채택 메타데이터](../../training_data/gemma4_12b_review_expanded_20261101_v2/ADMISSION.json).

## 4. 12B 학습과 비교 계획

### 4.1 A/B/C를 비교할 질문

| 후보 | 검증할 질문 | 중점 지표 |
|---|---|---|
| A 생성용 | 생성 역할에 집중하면 현재 맥락·원문을 더 정확히 반영하는가? | 사실 추가, 화자 오류, 반복 질문, 생략 사유, 상태·메모리 정확성 |
| B 검토용 v2 | 생성 초안의 오류를 더 잘 찾으면서 정상 출력도 보존하는가? | 오류 승인율, 정상 오반려율, 주장 감사 누락, 수정 지시의 정확성 |
| C 통합용 v2 | 한 모델이 생성·검토를 함께 학습할 때 두 역할을 유지하는가? | 생성/검토 각각의 성능과 역할 간 퇴행, 동일 오류의 공동 승인 |

이는 제안하는 비교 설계다. 현재 A/B/C 중 하나가 더 좋다는 실측 결론은 없다. 같은 모델을 작성·검토에 사용하는 구성은 서로 비슷한 오류를 놓칠 수 있으므로 별도 원문 대조를 둔다.

### 4.2 비교를 공정하게 만드는 조건

- 같은 기본 모델·tokenizer·평가 입력·출력 계약을 사용하고 후보별 데이터와 역할 구성을 명시한다.
- A/B/C 전체를 한 번에 바꾸지 말고, 생성 모델을 고정한 검토 비교와 검토 모델을 고정한 생성 비교를 분리한다.
- 프롬프트·검토 묶음·상태 모드·샘플링 설정도 고정한다. 모델 변화와 앱 최적화 효과를 섞지 않는다.
- 정상·오류를 각 50%로 구성한 학습 비율은 실서비스 오류 비율이 아니다. 평가에서는 오류 유형별 결과와 전체 분포를 함께 기록한다.
- 사례당 여러 행을 독립 이용자 사례로 세지 않는다. 파생된 모든 요청을 원천 사례군 단위로 묶는다.

### 4.3 새 검토용 평가에 필요한 항목

기존 역할 평가의 생성·질문·메모리 항목에 더해, B/C 검토 역할에는 다음을 제안한다.

| 평가 축 | 필요한 대조 사례 | 판정 방법 |
|---|---|---|
| 사실 날조 탐지 | 존재하지 않는 행동·요청·감정과 정확한 바꿔쓰기 | 오류 반려와 정상 승인 각각 집계 |
| 정정·부정·시점 | 이전 사실의 정정, 명시적 부정, 과거/현재 구분 | 현재 유효 사실과 근거 일치 |
| 검토 완전성 | 여러 주장을 가진 출력, 근거가 일부만 맞는 문장 | 주장 ID 누락·중복과 일부 지지의 잘못된 승인 검사 |
| 수정 지시 품질 | 오류를 최소 수정하면 되는 사례 | 새 사실·잘못된 예문·스키마 밖 요구의 생성 여부 |
| 질문 생략 | 기답, 미응답이지만 불필요, 모름, 거절, 여전히 필요한 질문 | 생략 결정과 이유의 정확성을 각각 판정 |
| 지원 방향·범위 | 발신자/수신자, 도움 요청/추정, 동의/철회 | 주어·대상·조건·범위 보존 |

새 검토 suite의 수량·오류 분포·통과선은 실행 전에 고정해야 한다. 기존 40 개발/20 최종 사례군을 근거 없이 검토용 평가 완료로 간주하지 않는다.

## 5. 31B 학습에서 남은 작업

### 5.1 단계별 목적과 연결

| 단계 | 목적 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| `00_original_warmup` | 원상담 전체 이전 대화로 다음 상담사 발화 학습 | 전체 validation 손실 기준 통과, 채택 체크포인트 고정 |
| `01_card_repair` | 승인된 오류 수정 자료로 카드 수정 학습 | 해당 단계 시작 모델 대비 손실 기준 통과 |
| `02_card_generation` | `script/doList/avoid/next/care` 역할 학습 | 손실 기준과 같은 체크포인트의 역할 품질 기준 모두 통과 |

첫 단계만 새 LoRA를 만들고 다음 단계는 앞 단계의 승인된 어댑터를 이어받는다. 12B 어댑터를 재사용하거나 단계 사이에 임의 초기화하지 않는다. 단계 전환의 어댑터 연결과 optimizer 상태 정책은 별도로 기록한다. [31B 데이터 계약](../../ai/scripts/expanded_card_training_README.md).

현재 실행기는 AdamW, 기본 학습률 `2e-5`, accumulation `8`, 최대 길이 `32768`을 사용하도록 정의돼 있다. 이 값은 현행 코드의 기본값이며 최적값이라는 결과가 아니다. 실제 학습 실행은 데이터·기본 모델·라이브러리 버전·fused loss 코드·실행 코드의 binding, canary 및 새 프로세스 복구 검증에 의존한다.

### 5.2 전체 데이터와 손실 보존

손실은 아래 목적함수를 유지한다.

`L = sum(weight_i × mean_CE(last_assistant_target_tokens_i)) / N`

입력·이전 assistant·padding은 제외한다. labels를 중복 shift하지 않고, target 길이를 다시 곱해 긴 정답이 가중치를 독점하게 만들지 않는다. train 전체 행이 epoch에서 정확히 한 번 소비되는지, validation 전체를 평가했는지 확인한다. 긴 원상담을 편의를 위해 4,096토큰으로 자르지 않는다.

### 5.3 실행기와 최종 평가 연결

기존 `loss_decision(..., final=True)`만 사용하는 경로는 첫 전체 epoch 뒤 **손실 개선 여부와 관계없이** 평가 대기로 멈춘다. 후속 추가한 [completion bridge](../../ai/scripts/cards31b_completion.py)는 새 reference 실행의 baseline·행별 validation·epoch coverage·체크포인트를 `malssi-training-history-v2`로 결합해 `training_stop.decide()`를 호출한다. 실제 role evidence가 없으면 대기하고, 같은 후보의 손실·품질 판정에 따라 다음 epoch·미완료 중단·최종 채택으로 전환한다.

연결 코드는 구현·CPU 회귀검증했지만 실제 baseline·후보 판정과 GPU 실행 검증은 남아 있다. config·소스 해시를 실행 전에 고정하므로 기존 실행의 binding을 덮어써 소급 연결하지 않는다. 단계 사이 재시작의 이전 승인 검사, 빈 체크포인트 거절, 이미 소비한 증거 변경 차단도 적용했다. 준비·운영 절차는 [연결부 안내](../../ai/scripts/cards31b_completion_README.md)를 따른다.

필요한 산출물은 현재 epoch의 체크포인트 해시, 전체 validation 결과, baseline/후보 실제 역할 출력, 독립 항목별 판정, suite/policy 해시, 완료 또는 중단 결정이다. 평가가 대기 중이면 다음 epoch로 계속 학습해 평가 대상 체크포인트를 바꾸지 않는다.

`train_cards_31b.py`는 모델·환경뿐 아니라 같은 실행 디렉터리의 `bootstrap.py`, `boundary.py` 및 별도 legacy-kit 코드도 binding에 요구한다. 저장소의 단일 스크립트만으로 실행 가능한 완성 배포 묶음이라고 해석하지 않는다. 허용된 실행 환경의 이 의존 파일까지 확인해야 한다. 과거 GPU 학습 기록은 과거 자료로 보존하며, 이번 재검토에서도 원격 현재 상태나 최신 31B 후보의 학습 완료·서비스 적용은 확인하지 않았다.

## 6. 학습 종료와 채택 기준

기존 성능 기반 정책을 출발점으로 사용하되, 새 12B v2에는 다시 결합해야 한다.

| 항목 | 기존 기준 | 해석 |
|---|---|---|
| 단계별 손실 개선 | 시작 loss보다 `max(0.001, 시작 loss × 0.005)` 이상 감소 | 해당 단계 전체 validation 기준 |
| 최종 중대 오류 | 지정한 critical 항목 오류 0건 | 평균 점수로 중대 오류를 가리지 않음 |
| 최종 품질 | 각 quality 항목 사례군 통과율 95% 이상 | 개발 40사례군이면 항목별 38개 이상 |
| 학습 전 대비 | 모든 평가 항목에서 baseline보다 후퇴하지 않음 | 95%를 넘더라도 baseline보다 낮으면 실패 가능 |
| 체크포인트 일치 | loss와 역할 평가가 같은 현재 후보를 가리킴 | 서로 다른 epoch의 좋은 결과를 조합하지 않음 |
| 자원 상한·정체 | 목표 미달 상태의 중단 사유 | 학습 완료 사유가 아님 |

10월 31일 역할 평가에는 모델별 개발 40사례군·최종 확인 20사례군이 준비돼 있다. 12B는 사례당 8요청, 31B는 사례당 5요청이며 개발 요청은 각각 320·200개다. 공유 원천 60개를 모델별로 더해 120개 독립 원천으로 세지 않는다.

0.5%·0.001·95% 등의 값은 프로젝트의 초기 운영 목표다. 최적성이 입증된 통계적 보증이 아니다. 기준 변경이 필요하면 결과에 맞춰 현재 실행의 문턱을 낮추지 않고 새 정책·새 실행으로 기록한다. [성능 기반 종료 계약](../../ai/scripts/training_stop_README.md), [평가 출력 검증기](../../ai/scripts/validate_role_outputs.mjs).

아래는 **추가 비교 실험 제안**이다. 기존 구현을 다시 미구현 목록으로 취급하지 않고 실모델 확인이 남은 부분을 구분한다.

| 우선순위 | 후보 | 비교 방법 | 채택 조건·보존할 것 |

측정 시 POST 수, capability GET 수, 입력/출력 토큰, 전송 바이트, 재시도, 내용 수정, 사용자 요청의 성공률을 별도 기록한다. 전체 작업 호출 수에는 실패·중단·재검토도 포함하고, 성공 경로 호출 수는 따로 표시한다. 최신 실제 실행처럼 분석·초안을 이어받았다면 해당 범위를 명시한다.

O5처럼 검토를 없애거나 승인을 넓게 재사용하는 변경은 단순 성능 옵션으로 채택하지 않는다. 상세 저장·독립 검토·문맥상 질문 생략·원문·카드 디자인을 보존한다. [현재 호출 최적화](../../app/docs/REVIEW_CALL_OPTIMIZATION.md), [입력 최적화](../../app/docs/MODEL_INPUT_OPTIMIZATION.md).

추론 계산 쪽에도 이미 저장된 10월 31일 후보 실험이 있다. C1의 제한된 1회 요청 개선, prefill/precision 탈락, 단계별 attention 후보와 별도 서비스 적용 기록은 [최적화 결과의 GPU 추론 실험](02_최적화_방법과_결과.md)에 구분했다. 이를 전부 새 미실험 후보로 반복하지 말고 기존 실패 조건·측정 범위를 출발점으로 삼는다. 당시 별도 서비스에 적용했다는 기록은 현재 사용자 서비스에 적용돼 있다는 증거가 아니다.

## 8. 앞으로 시험할 학습 계산 최적화

저장소에는 계산 최적화 후보와 진단 도구가 있고, 일부 후보의 **실제 성공·탈락 결과도 로컬에 보존돼 있다.** 이를 모두 미실험으로 표시한 초기 문서의 누락을 바로잡는다. GPU 관련 새 실행은 재허용 이후에만 가능하다.

### 8.1 저장된 실험 결과에서 이어가야 할 일

| 후보 | 확인된 로컬 기록 | 다음 판단 |
|---|---|---|
| 학습 head 계산 후보 | normal8 gradient 상대 L2 **0.059768 > 한도 0.005**, AdamW 상대 L2 **0.028105 > 한도 0.01**, `rejected_numerics` | 그대로 채택하지 않고 수치 차이 원인을 수정한 별도 후보로 재검증 |
| 평가 pipeline 후보 | warmup 후 9행 시간 **15.0368% 감소**, 기존 baseline 783행 비교 통과, `deployed=false` | 부분 평가 개선과 실제 배포를 구분. 전체 validation·판정 경계·실행 환경 결합 후 채택 결정 |
| paired training 후보 | `Unexpected decoder checkpointer`로 거절 | 요구 checkpoint 계약과 실제 모델의 호환성부터 해결 |
| 단일 GPU replica | model_load에서 `CPU/disk weight offload is forbidden`, 학습 update **0회** | 배치 위치 검증 실패. CUDA OOM이나 하드웨어 메모리 불가능으로 단정하지 말고 배치·로더 적합성부터 확인 |
| 최종 적용 | `adopted_optimizations=[]`, 원래 실행으로 복귀한 기록 | 현재 문서에서 검증된 최종 가속 채택본으로 보고할 항목 없음 |

학습 후보의 normal8 단일 시간 쌍은 119.2908→119.0297초였지만 수치 기준을 실패했다. extreme3은 104.9225→105.2518초였다. 이 값으로 전체 epoch 속도 향상을 주장하지 않는다. 위 수치는 [저장된 복귀 확인 결과](../../runtime/gpu-lora31b-opt-20261101/FINAL_FALLBACK_VERIFIED.json)에 근거하며 새로 GPU를 실행해 측정한 것이 아니다. 세부 검증 결과와 출처는 [최적화 방법과 결과](02_최적화_방법과_결과.md)에 정리했다.

### 8.2 코드별 추가 검증 항목

| 후보 | 현재 코드 | 앞으로 필요한 검증 |
|---|---|---|
| evaluation/optimized compute profile | `train_cards_31b.py`, `cards31b_compute.py` | reference 대비 행별·전체 loss, 학습 gradient·update, 메모리, 실제 시간 |
| 검증 배치·token budget | 실행기의 기본 max batch 4, token budget 16,384 | 다양한 길이·최장 행·대상 토큰 분포, padding·mask 및 전체 평가 범위 보존 |
| serial/pipeline 평가 | `cards31b_pipeline.py` | 순서·누락·중복·수치 차이·장치 간 전송·중단 후 재개 |
| 학습 파이프라인 후보 | `cards31b_training_pipeline.py` | accumulation과 목적함수, gradient/update 동등성, 오류·복구 경계 |

`reference`가 기본 프로파일이고 비기준 경로는 qualification 파일과 binding 검증을 요구한다. 최적화 loss가 종료 판정 임계값 근처이면 기존 기준 계산으로 다시 확인하는 경로도 있다. 계산 차이 때문에 학습 통과·중단 판정이 달라지는지 확인해야 한다.

학습률·accumulation·LoRA 설정 등의 탐색은 그다음 실험 후보다. 한 번에 한 축을 바꾸고 전체 데이터·동일 평가·고정 seed 및 설정을 기록한다. 현재 기본값이 최적이라는 주장이나 새 하이퍼파라미터 추천값은 이 문서에서 확정하지 않는다.

## 9. 실행 순서와 단계별 완료 증거

다음 순서를 제안한다. 지금 즉시 모두 실행했다는 뜻은 아니다.

1. **데이터 동결:** 최신 A/B/C·31B의 버전·해시·통계·의미 검토 범위를 확정한다.
2. **평가 준비:** 검토 역할 suite와 baseline을 준비하고 개발/최종 확인 사용 경계를 고정한다.
3. **로컬 계약 검증:** 앱과 데이터의 프롬프트·스키마·원문·검토·저장 계약 차이를 해결한다.
4. **학습 실행 자격 확인:** 서버 재허용 후 경로·환경·모델·메모리·canary·중단/재개를 확인한다.
5. **기준 학습:** 이미 남아 있는 reference 실행 기록과 체크포인트 계보를 먼저 확인한다. 기존 진행 상태를 무시하고 새 학습을 시작하지 않으며, 실행 재허용 후 실제 상태·binding을 확인해 재개 또는 새 실행을 결정한다.
6. **성능 판정:** 현재 체크포인트의 손실과 역할 평가를 결합한다. 미달이면 원인에 따라 새 실험을 설계한다.
7. **최적화 비교:** 고정된 기준에 대해 후보별 수치·품질·실행량 차이를 측정한다.
8. **서비스 전체 검증:** 답변→질문 생략→상태→카드→상세→저장→재조회와 취소·정정·실패 복구를 확인한다.
9. **최종 확인:** 후보를 고른 후 미노출 평가를 사용한다. 배포는 별도 실행·승인 범위에 따른다.

각 실행 기록에는 실험 ID, 목적, 데이터/코드/모델/정책 해시, 설정, 전체 입력·정답 범위, loss, 역할별 critical/quality 결과, 실패·중단·재시도, 채택 여부와 이유를 남긴다. 실제 상담 원문·학습 행·토큰·모델 가중치는 Git 제외 로컬 경로에 보관하고 문서에는 원문 없는 집계만 기록한다.

## 10. 완료로 보고할 수 있는 시점

‘학습 완료’는 데이터 ZIP 생성이나 정해진 epoch 소진으로 판정하지 않는다. 모든 단계의 성능 기준을 만족한 같은 계보의 체크포인트가 있고, 최종 역할 평가 및 baseline 비교 증거가 결합돼야 한다.

‘최적화 완료’는 호출 수·메모리·시간 중 한 지표만 좋아진 상태가 아니다. 해당 최적화가 목표 지표를 개선하면서 원문·질문 생략·독립 검토·상세 저장·취소·카드 디자인 계약을 유지했다는 증거가 필요하다. 실험 결과가 없는 후보는 계속 ‘시험 예정’으로 기록한다.

## 11. 이번 재검토의 확인 범위

현재 학습 실행기의 최종 대기·재시작 처리, 정책 검증기의 단계 수 제한, 최신 데이터와 앱 스냅샷 차이, 저장된 GPU 실험 최종 영수증을 대조했다. `python3 -B -m unittest discover -s ai/scripts -p test_train_cards_31b.py`로 **CPU 전용 30개 검사 통과**를 새로 확인했다. 최종 단계의 loss 개선·미달·악화 모두 평가 대기로 멈추는 동작도 기존 회귀에 포함된다. 이 검사는 실제 모델 학습·GPU 수치 동등성·외부 평가 연결의 완료 증거는 아니다.
