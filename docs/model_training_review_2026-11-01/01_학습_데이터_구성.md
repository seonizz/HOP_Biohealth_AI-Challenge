# 학습 데이터 구성

작성 기준: **2026-11-01 로컬 작업 폴더**. 이 문서는 준비된 데이터의 구성과 사용 계약을 정리한다. 데이터 준비·구조 검증 완료와 모델 학습 완료는 구분한다. 현재 작업 폴더에는 미커밋 코드와 Git 제외 데이터가 있으며, 아래 파일이 존재한다는 사실은 원격 저장소 반영·GPU 학습·서비스 배포를 뜻하지 않는다.

원상담·합성 사례의 원문, 학습 정답, 개별 라벨 행렬은 이 문서에 복사하지 않았다. 표는 원문 없는 집계다. `training_data/`와 `data/데이터셋/` 링크는 로컬 전용 자료이며 공개 저장소만 받은 환경에서는 열리지 않을 수 있다.

## 1. 전체 구조

현재 자료는 크게 네 층으로 나뉜다.

| 층 | 자료 | 목적 | 주의할 점 |
|---|---|---|---|
| 원천·보존 | 원상담, 원천 DB, 주석, 선별·보류 장부 | 출처와 처리 이력 보존 | 보존 폴더의 모든 파일이 학습 허용 자료는 아니다 |
| 원상담 기초 SFT | 과거 대화 전체 → 다음 상담사 응답 | 대화 문맥과 응답 형식의 기초 학습 | 상담사를 가족·친구 등 주변인 역할로 바꿔 부르지 않는다 |
| 서비스 역할 SFT | 주변인 대화·질문·상태·메모리·검토 또는 최종 카드 | 실제 서비스 역할에 맞춘 보정 | 원상담과 목적·출력 형식이 다르다 |
| 평가·보조 | 분류 3종, 개발 평가, 최종 확인 suite | 데이터 분석·검증·후보 선택 | 기본 학습 코스에 자동 혼합하지 않는다 |

현재 주요 모델 역할은 **12B의 대화·질문·상태·메모리·검토**와 **31B의 최종 카드 작성**이다. 12B는 생성 전용 A, 검토 전용 B, 통합 C로 나눈 비교용 데이터가 있다. A/B/C는 같은 출처와 분할을 공유하는 선택지다. 세 개를 합쳐 독립 데이터가 세 배 늘었다고 세지 않는다.

### 2.2 A/B/C의 선택 의미

| 선택지 | 포함하는 역할 | 비교하려는 것 |
|---|---|---|
| A 생성 | 대화, 질문 선택, 보고 사실 추출, 관계 메모리, 통합 초안 | 생성 역할에 집중했을 때의 동작 |
| B 검토 v2 | 질문 검토, 답변 전체 검토, 메모리 검토 | 생성과 분리한 검토자의 판정 능력 |
| C 통합 v2 | A 역할과 B 검토 역할 | 한 모델이 생성·검토를 함께 학습했을 때의 동작 |

각 ZIP에는 공통 원상담과 자기 역할의 자료가 들어 있다. 새 기반 모델이면 원상담 단계부터 시작한다. 동일 모델·데이터로 만든 공통 원상담 체크포인트를 재사용할 때는 그 해시를 기록하고 역할 단계에서 분기한다. **A → B → C 어댑터를 순차로 이어 학습하는 코스가 아니다.** 비교 후보 사이의 초기 조건도 맞춰야 한다.

### 3.2 한 행의 의미

한 원상담에는 여러 상담사 응답이 있으므로 한 상담에서 여러 SFT 행이 나온다. 각 행은 **해당 정답 이전의 전체 대화 접두부**를 입력으로 받고, 바로 다음 상담사 응답을 맞히는 과제다.

- 정답 시점 이후의 대화는 입력에 넣지 않는다.
- 이전 assistant 발화는 문맥으로만 사용하고 그 행의 학습 정답에는 포함하지 않는다.
- 원상담의 화자·목표·내용을 주변인 지원 서비스의 정답으로 재명명하지 않는다.
- 현재 코스는 4,096토큰 이하 후보만 골라 사용하는 방식이 아니다. 적격 긴 행도 포함한다.
- 데이터 길이가 길다는 이유로 원문을 조용히 자르거나, 요약으로 바꾸거나, 행을 건너뛰지 않는다.

현재 공통 기초의 출처 집계는 train **942개 source root / 177개 source group**, validation **96개 source root / 21개 source group**이다. root와 group은 데이터 계보의 단위이며 확인된 고유 사람 수와 동일하지 않다. 이 수량은 [최신 12B COURSE](../../training_data/gemma4_12b_review_expanded_20261101_v2/COURSE.json)의 원상담 단계 메타데이터다.

### 4.2 신규 가상 200사례와 파생 행

2026-10-31 대화 확장은 가상 사례 **200개**, train 160개 / validation 40개다. 사례마다 첫 발화·응답과 후속 발화·응답, 보고 사실, 정정 전 정보, 미확인 정보, 질문 근거를 준비했다.

이때 사례당 대화·질문 5행과 상태·메모리 3행, 총 8행을 만들어 **1,600행**을 추가했다. 기존 역할 96행(train 55 / validation 41)과 합쳐 1,696행이 됐다.

2026-11-01 v2는 **같은 200사례**에서 답변 검토 800행과 메모리 검토 800행을 추가했다. 각 과제는 사례당 두 시점 × 정상/오류의 네 행이다. 따라서 최신 역할 자료는 **3,296행**이고, 이 증량으로 늘어난 독립 원천 사례 수는 **0개**다.

| 범위 | 구조·분할·수치 검증 | 독립 의미 검토 |
|---|---|---|
| 200개 대화 원천 | 원문 인용·출처·분할 등을 검사 | 기존 독립 AI 검토 유지 |
| v2 신규 검토 1,600행 | 전수 구조·원문·분할·토큰 검사 | **과제별 20사례·80행**, 각 과제의 10% 표본 |
| 사람·임상 전문가 | 해당하지 않음 | 수행 완료로 기록되지 않음 |

신규 검토 행의 오류는 결정적 합성 변형이다. 실제 모델이 만드는 오류 비율, 장기 대화, 복합 오류, 위기·임상 상황의 분포를 대표한다고 볼 수 없다. `ADMISSION.json`의 `all_new_rows_semantically_reviewed=false`를 보존해 읽어야 한다.

### 4.3 앱 계약과의 관계

`answer_review`는 별도 학습 데이터 계약이다. 이 과제가 준비됐다는 이유로 앱의 모든 답변 검토 경로가 자동으로 이 모델에 연결됐다고 판단하지 않는다.

`memory_review`는 생성 시점 앱의 `turn_review` 프롬프트·출력 스키마·검증 콜백을 이용하고, 전체 사용자 원문인 `reported_dialogue`를 추가한 입력 확장이다. 출력의 `state`에 claim별 audit·issues·approved를 채우고 **`questions=null`, `safety=null`**로 둔다. 따라서 메모리·상태 검토 자료이며 질문·안전까지 포함한 전체 턴 검토 학습을 대체하지 않는다. 현재 앱의 모든 요청과 완전히 같은 입력이라는 뜻도 아니다. 생성·상태 과제 일부는 작성자가 구조화한 원문 조각을 받으므로, 전처리 없는 긴 대화에서 모든 사실을 직접 찾는 능력과도 구분한다.

관련 구현은 [답변 검토 투영](../../ai/scripts/project_answer_review_cases.py), [메모리 검토 투영](../../ai/scripts/project_memory_review_cases.mjs), [검토 데이터 결합·검증](../../ai/scripts/expanded_review_dataset.py)에 있다. 2026-11-01 재검토에서 [APP_CONTRACT.json](../../training_data/gemma4_12b_review_expanded_20261101_v2/APP_CONTRACT.json)의 7개 앱 파일 해시를 현재 파일과 대조했다. `relationship-agent.js`, `relationship-turn.js`, `relationship-prompts.js` 3개는 달라졌고 나머지 4개는 일치했다. 별도로 신규 메모리 과제를 기록한 [MEMORY_REVIEW_APP_CONTRACT.json](../../training_data/gemma4_12b_review_versions_20261101_v2/gemma4_12b_B_reviewer_20261101_v2/provenance/MEMORY_REVIEW_APP_CONTRACT.json)의 5개 파일도 같은 3개가 불일치하고 2개는 일치했다. 파일 변경 자체가 계약 파손을 뜻하지는 않지만, 저장된 앱 계약 검증을 현재 앱과의 재통합 검증으로 대신할 수는 없다.

문맥상 불필요한 질문의 생략은 유지한다. 생략한 문항의 답변을 만들어 저장하는 것은 별개의 오류다. 질문 선택·검토 자료가 있다는 이유로 모든 `not_needed` 상황이나 안전 검토가 충분히 학습됐다고 표시하지 않는다.

## 5. 31B 카드 데이터의 상세 구성

| 학습 순서 | 단계 | train | validation | 목적 |
|---|---|---:|---:|---|
| 1 | `00_original_warmup` | 37,065 | 3,618 | 원상담 기초 |
| 2 | `01_card_repair` | 20 | 5 | 기존 승인된 카드 오류 수정 |
| 3 | `02_card_generation` | 688 | 170 | 다섯 카드 필드 생성 |

카드 생성 858행은 기존 승인 생성 108행과 신규 가상 150사례 × 다섯 필드 = 750행을 합친 것이다. 신규 사례는 train 120개 / validation 30개이며, 같은 사례의 다섯 필드는 같은 출처 ID와 split을 가진다. 실제 생성 task별 행 수는 script·doList·next·care가 **각 142/35**, avoid는 **120/30**(train/validation)이다. 기존 108행에는 현재 typed avoid가 없으므로 다섯 필드의 행 수가 같지 않다. 수정 25행에도 avoid 수정 정답은 없다. 다섯 필드를 생성한다는 설명을 모든 필드에 같은 양의 생성·수정 자료가 있다는 뜻으로 읽지 않는다.

| 필드 | 역할 |
|---|---|
| `script` | 상대에게 실제로 건넬 말 |
| `doList` | 이용자가 시도할 행동 |
| `avoid` | 피할 말, 그 이유, 대안: `avoid_phrase`, `reason`, `alternative` |
| `next` | 조건에 따른 다음 행동 |
| `care` | 이용자 자신을 돌보는 안내 |

입력에는 보고 사실과 그 사실로 만든 검색 문서를 넣는다. 다른 카드 정답·교사용 근거표·검토 결과는 생성 입력에서 제외한다. 기존 카드 추출에서도 승인 여부와 claim/audit 대응을 검사하고, 동일 task/split/messages는 중복을 제거하면서 계보를 합친다.

신규 150사례는 다섯 필드 모두 통과한 현재 해시만 채택한다. 독립 AI 검토의 실제 채택자는 로컬 Ollama 112사례와 native Codex 검토자 38사례로 기록돼 있다. 이는 사람·임상 검증이 아니다. 오류 대조군은 검토자의 판별을 확인하는 데 사용하며 학습 데이터에는 넣지 않는다. 사례 내용을 수정하면 이전 해시의 승인은 재사용하지 않는다.

신규 사례끼리 및 기존 카드 사실과 정규화 문자 4-gram 유사도를 비교했고 0.75 이상을 보류하도록 했다. 저장된 최대 유사도는 약 0.1064이며 표시된 보류 쌍은 없다. 이 수치는 의미적 독립성이나 원상담 전체와의 완전 비중복을 증명하지 않는다.

근거: [31B README](../../training_data/gemma4_31b_expanded_20261025/README.md), [ADMISSION.json](../../training_data/gemma4_31b_expanded_20261025/ADMISSION.json), [확장·검증 구현](../../ai/scripts/expanded_card_dataset.py), [공통 역할 추출](../../ai/scripts/role_dataset.py)의 `approved_fields`, `derive_cards`, `deduplicate`.

## 6. 파일 형식, 정답 마스크, 손실 가중치

### 6.1 파일별 책임

| 파일 | 내용·용도 |
|---|---|
| `COURSE.json` | 모델 역할, 학습 단계 순서, split별 경로·행 수·task, tokenizer 및 loss 계약 |
| `data/<phase>/<split>.jsonl.gz` | messages, 마지막 assistant 손실 마스크, 출처·계보·가중치 |
| `encoded/<phase>/*.tokens.bin` | little-endian uint32 토큰을 패딩 없이 연속 저장 |
| `encoded/<phase>/*.index.jsonl` | 토큰 offset, prefix/target/sequence 길이, 행 ID·해시·가중치 |
| `MANIFEST.json` | 파일 목록·크기·해시를 통한 무결성 결합 |
| 원본 확장본의 `TOKENIZATION.json` | 단계별 토큰 총량·최장 길이·인코딩 방식. A/B/C 분리 ZIP 루트에는 이 파일이 없음 |
| 원본의 `NUMERIC_AUDIT.json`, 분리본의 `provenance/SOURCE_NUMERIC_AUDIT.json` | 별도 경로의 재인코딩 또는 검증된 기존 토큰 바이트 대조. 분리본은 원본 감사와 자기 원행·토큰 연결을 함께 읽음 |
| `VERIFICATION.json` | 해당 버전을 만들고 검사했을 때의 결과 |
| `provenance/` | 원본 연결, 승인·보류, 계약 스냅샷과 검토 이력 |

행의 메타데이터·검토 기록·provenance를 그대로 프롬프트에 붙이지 않는다. 모델 입력은 해당 과제의 messages 계약을 따른다. 토큰 offset의 단위는 토큰이므로 바이너리 바이트 주소는 `offset_tokens × 4`다.

### 6.2 마지막 assistant만 학습

```text
labels = [-100] × prefix_length + input_ids[prefix_length:]
```

입력·이전 assistant·padding은 손실에서 제외한다. labels를 미리 한 칸 이동하지 않는다. `loss_message_mask`와 토큰 정답 경계가 같은 마지막 assistant를 가리키는지 확인한다. 이전 대화의 모든 assistant에 손실을 주는 일반 SFT 설정으로 바꾸면 다른 학습이 된다.

### 6.3 현재 역할 데이터의 가중 목적함수

```text
L_i = 행 i의 마지막 assistant 정답 토큰에 대한 평균 CE
전체 목적함수 = sum(weight_i × L_i) / N
sum(weight_i) = N
```

한 단계·split 안에서 과제별 총 질량을 같게 하고, 과제 안에서는 서로 연결된 출처 가족별 질량을 같게 한다. 따라서 길거나 같은 원천에서 많은 행이 나온 사례가 단순 개수만으로 전체 손실을 지배하는 것을 줄인다.

가중치는 정확 분수로 저장한다. A/B/C로 과제를 분리하면 해당 부분집합에 맞춰 다시 계산한다. 행 평균 CE에 정답 토큰 길이를 다시 곱하거나 길이가 다른 배치의 토큰 평균을 단순 평균하면 이 계약이 달라진다. 분산·누적 학습에서도 전역 정규화를 유지해야 한다.

이는 과거 575행·두 단계 패키지의 토큰 질량 중심 가중식과 다르다. 과거 `source_weight`는 출처 정보이며 최신 `weight`를 대신하지 않는다. 실제 로더는 [role_dataset.py](../../ai/scripts/role_dataset.py)의 `IndexedTokens`, 가중치는 `balance`, 구조 계약은 `check_row`에서 확인한다.

### 6.4 길이와 토크나이저

현재 12B v2와 31B 확장본은 최대 인코딩 용량 **32,768토큰**을 계약으로 둔다. 저장된 공통 원상담 최대 길이는 **25,316토큰**이다. 12B v2의 역할 자료 최대는 상태·메모리 train **12,195토큰**, 신규 검토 train **8,180토큰**이다.

원문 절단, packing, split 재배정, validation 역전파는 비활성 계약이다. 다른 모델·템플릿을 사용하려면 messages부터 다시 인코딩하고 마스크·길이를 검증해야 한다. 동일 vocabulary 해시만으로 12B/31B 템플릿이 같다고 가정하지 않는다. 길이 검사를 통과했다는 사실은 GPU 메모리에 적합하거나 장문 이해 성능이 확보됐다는 뜻이 아니다.

근거: [12B 토큰 집계](../../training_data/gemma4_12b_review_expanded_20261101_v2/TOKENIZATION.json), [31B 토큰 집계](../../training_data/gemma4_31b_expanded_20261025/TOKENIZATION.json).

## 7. 분할·누출 방지·검증 범위

1. **기존 split 보존:** validation을 train으로 이동하지 않는다. 신규 사례도 작성 전에 사례별 분할을 고정하고 생성·검토·카드 변형을 같은 split에 둔다.
2. **연결 출처 단위 확인:** `source_group_ids`, `source_root_ids`와 계보를 이용해 train/validation 교차를 검사한다. 연결된 원천의 변형은 하나의 출처 가족으로 취급한다.
3. **동일 입력 검사:** 마지막 정답을 제외한 messages를 키 순서가 고정된 compact JSON으로 직렬화한 해시를 비교한다. 이는 **정확 입력 일치** 검사이며 문자열의 의미·공백·동의어까지 정규화한 중복 검사는 아니다. 원상담 시작 입력 충돌 18행 보류가 여기에 해당한다.
4. **미래·교사 정보 차단:** 정답 이후 대화, 다른 카드 정답, 검토 결과를 생성 입력으로 누출하지 않는다.
5. **해시 결합:** 메시지, 토큰, 인덱스, tokenizer, 검토 승인을 현재 버전의 해시에 묶는다. 파일 수정 뒤 과거 검증 결과를 그대로 사용하지 않는다.
6. **수치 감사:** 최신 12B 역할 3,296행은 빌더와 별도 AutoTokenizer 경로에서 재인코딩한 저장 기록상 불일치 0건이다. 원상담은 manifest에 연결된 검증 12B 원본의 messages·인덱스·토큰 바이트와 일치시킨다.

최신 B/C v2의 저장된 검증 결과는 출처 계보 교차 0, 동일 입력 교차 0, 원행·토큰 동일성 확인이다. 다만 정확 일치가 없다는 사실이 의미 중복 없음·실제 사람 단위 독립성·임상 정답성을 보장하지 않는다. 일반 `verify`의 무결성 검사는 매번 새 토큰화를 수행하는 수치 재감사와도 구분한다.

근거: [B/C SUMMARY](../../training_data/gemma4_12b_review_versions_20261101_v2/SUMMARY.json), [12B 수치 감사](../../training_data/gemma4_12b_review_expanded_20261101_v2/NUMERIC_AUDIT.json), [package_chat_variants.py](../../ai/scripts/package_chat_variants.py)의 `verify`.

## 8. 학습 자료와 분리해서 관리하는 평가 자료

[2026-10-31 역할 평가](../../training_data/role_evaluation_20261031/README.md)는 별도의 가상 원천 **60사례**를 사용한다. 두 모델이 같은 원천의 서로 다른 역할을 평가받으므로 120개 독립 사례로 합산하지 않는다.

| 모델 | 개발 평가 | 최종 확인 |
|---|---|---|
| 12B | 40사례군 / 320요청 | 20사례군 / 160요청 |
| 31B | 40사례군 / 200요청 | 20사례군 / 100요청 |

개발 평가와 학습 코스의 validation은 후보 선택·개선에 사용한다. 최종 확인은 후보와 생성 설정을 고정한 뒤 확인하며, 이를 보고 반복 튜닝하면 더 이상 미노출 최종 확인으로 취급할 수 없다.

평가 suite는 입력·참조·rubric·실제 출력·평가자의 판정을 나눈다. 빈 출력·판정 양식은 평가 완료 증거가 아니다. 최신 B/C v2의 답변·메모리 검토는 기존 질문 검토 평가만으로 대체할 수 없고, 새로운 역할 평가·baseline 및 종료 정책 해시 연결이 남아 있다. 실제 [POLICY.json](../../training_data/training_completion_20261031/POLICY.json)의 12B binding은 `gemma4_12b_expanded_20261031`을 가리키며 단계는 `01_dialogue_warmup`, `02_supporter_dialogue`, `03_state_memory`뿐이다. 신규 `04_result_review`가 없다. 각 A/B/C ZIP에 별도 최종 test를 담았다는 뜻도 아니다.

평가 `INPUTS.jsonl`은 **한 행에 한 사례와 `requests` 배열**을 담는다. 따라서 12B 개발 파일 40행은 요청 40개가 아니라 320개다. [COVERAGE.json](../../training_data/role_evaluation_20261031/COVERAGE.json)은 급성 위기, 임상 진단, 실제 이용자 분포, 31B 전체 다단계 실행, 미응답 문항의 `not_needed` 생략, `turn_review`, `safety_review`를 미평가 범위로 명시한다. 12B의 기존 사례당 8개 요청에 최신 답변·메모리 검토 요청이 추가됐다고 가정하지 않는다.

### 9.2 분류용 3종은 생성 SFT와 다른 데이터

| 단위 | train | validation | 라벨 근거 |
|---|---:|---:|---|
| 상담 전체 | 990 | 117 | 원자료 class의 코호트 분류 매핑 |
| 문장 | 1,440 | 206 | 문장 내용·문맥을 읽은 AI 의미 주석 |
| 단어 | 302 | 76 | 단어 자체의 의미 주석 |

분류 라벨은 우울=0, 중독=1, 불안=2, 기타=3이다. 문장은 다중 라벨을 지원하며 기타를 다른 라벨과 동시에 사용하지 않는다. 기타가 건강·무증상·불확실을 의미하는 것은 아니다. 원상담 전체 라벨을 문장·단어에 자동 복사하지 않는다.

입력은 `text`, 정답은 `labels_multihot`이다. TF-IDF 어휘·IDF는 train에서만 만들고 validation은 변환만 한다. 상담·문장의 기존 split과 단어의 관련 어휘군 분리를 유지한다. 이는 분류 연구용이며 현재 12B/31B 기본 SFT 코스에 자동 포함되지 않는다. 원자료의 정의가 미확정인 depression/addiction/anxiety 수치를 임의의 이진 정답으로 바꾸지 않는다.

| 실제 사용자·위기·임상 대표성 | 현재 비임상 성인 가상 사례만으로 입증되지 않음 |
| 최신 B/C 학습 종료 정책 | 후속으로 A/B/C v3 정책을 새 데이터에 결합했으나 현재 앱 drift·새 검토 과제 평가 부족으로 완료 gate는 pending. 아래 후속 수정 기록 참조 |
| 학습 완료·성능 | 패키지의 `training_started=false`는 패키지 생성 시 메타데이터이며 실시간 학습 상태가 아님. 별도 31B 실행 스냅샷은 있으나 최신 코스 완료·성능 통과와 구분 |
| 실행기 구현 상태 | 데이터 README의 과거 서술과 별개로 현재 학습 코드에서 확인해야 함 |
| GPU 작업 | 사용자 재허용 전 접속·학습 금지. 이 문서 작성에서 수행하지 않음 |

### 문서 작성 시 확인 범위

최초 작성 시 2026-11-01에 위 네 선택 묶음의 `COURSE.json`, 각 gzip JSONL의 실제 행·task 수, 토큰 인덱스 행 수와 최대 길이를 읽어 집계·대조했다. 이 대조는 원문을 출력하거나 복사하지 않는 읽기 전용 확인이다. 과거 `NUMERIC_AUDIT.json`의 재인코딩 결과는 **저장된 수치 감사 기록**으로 인용했다. 후속 재검토에서는 아래와 같이 현재 파일의 무결성·원본 결합을 다시 검증했지만, 전체 토큰 재인코딩·의미 재검토·모델 학습을 다시 수행한 것은 아니다.

학습 원문·정답·분할·토큰·라벨 행렬·ZIP은 Git 제외 경로에 보존한다. 원문 없는 코드·스키마·집계·문서만 버전 관리 대상으로 삼는다. 보류 장부와 과거 버전을 삭제하거나 원문을 문서에 옮겨 업로드 제한을 우회하지 않는다.


## 11. 후속 재검토 — 2026-11-01

최초 작성 문구를 그대로 신뢰하지 않고 빌더·로더·평가 코드와 현재 로컬 파일을 다시 대조했다. 상담·학습 원문은 출력하거나 문서에 옮기지 않았다. 아래 검증은 `python3 -B`로 실행했고 데이터·검증 결과 파일을 다시 쓰지 않는 `verify` 경로만 사용했다.

세 분리본 검증은 `--source`를 지정했으므로 원본의 필터링된 messages·메타데이터·토큰 정체성과 재계산한 가중치를 직접 대조했다. 출처 계보·정확 입력의 train/validation 교차는 모두 0이었다. 토큰 총량은 입력과 정답을 포함한 전체 시퀀스 재고이며 정답 토큰 수나 서로 다른 원천 수가 아니다. 공유 원상담을 포함하므로 A/B/C 토큰 총량을 합산하지 않는다.

재검토에서 다음 누락·모호함을 수정했다.

- `memory_review`는 state 판정이며 questions/safety를 함께 학습하는 과제가 아님을 명시했다.
- 앱 계약 스냅샷과 현재 파일 사이의 실제 해시 차이를 기록했다.
- 31B의 필드별 행 수 차이와 avoid 수정 정답 부재를 추가했다.
- 분리 ZIP에 없는 루트 `TOKENIZATION.json` 및 수치 감사의 실제 저장 위치를 바로잡았다.
- 입력 중복 검사는 canonical JSON 정확 일치이며 의미·공백 정규화 검사가 아님을 구분했다.
- 평가 JSONL의 사례 행과 내부 요청 수를 구분하고, 실제 종료 정책에 신규 검토 단계가 없음을 확인했다.

이번 검증은 이미 저장된 독립 수치 감사·의미 검토 증거의 일관성을 다시 확인했다. 새로운 토큰 재인코딩, 모든 신규 검토 행의 의미 전수 검수, GPU 메모리 적합성, 학습 전후 모델 품질, 현재 앱과 학습 계약의 의미적 호환성을 새로 입증하지는 않았다.

후속으로 확인한 31B 실행·최적화 미채택 영수증은 [최적화 결과 3.2절](02_최적화_방법과_결과.md), 실행기와 최종 평가 연결의 미완료 사항은 [남은 학습](04_남은_모델_학습과_최적화.md)을 따른다. 패키지 정적 플래그만으로 별도 실행 이력까지 없었다고 판단하지 않는다.

같은 날 재검토 후 실제 코드 수정에서 계약 검사기·최신 코스 정책·31B 새 실행용 평가 연결을 추가했다. [우선순위와 로컬 수정 기록](../current/앱_학습계약과_완료판정_로컬수정_2026-11-01.md)을 따른다. 데이터 원문·정답·동결 manifest는 보존했으며 새 코드가 과거 의미 검토를 자동 갱신하지 않는다.
