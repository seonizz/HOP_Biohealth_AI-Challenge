# 현재의 출력 검증 방법

기준일: **2026-11-01, Asia/Seoul**. 현재 로컬 작업 폴더의 코드와 검증 기록을 기준으로 작성했다. 미커밋 구현을 포함하며 배포된 서비스의 버전·설정까지 확인한 문서는 아니다. 상담 원문과 실제 생성 문장은 싣지 않는다.

## 1. 검증 구조의 핵심

현재 검증은 **JSON·스키마 검사 → 원문·근거 검사 → 독립 모델 검토 → 필요한 부분 수정과 새 검토 → 저장·재조회 확인**의 여러 층으로 구성된다. 출력 모양이 올바르다는 것, 인용이 실제 존재한다는 것, 그 인용이 문장 전체를 의미적으로 뒷받침한다는 것은 서로 다른 판정이다.

작성과 검토는 별도 요청·역할로 수행한다. 같은 모델을 작성자와 검토자로 사용하는 로컬 검증도 있으므로, 여기서 ‘독립 검토’는 다른 가중치나 사람·전문가의 독립성을 보장한다는 뜻이 아니다. 검토 요청을 묶더라도 각 검토의 입력·스키마·검증 함수와 승인 항목을 유지한다.

| 층 | 확인하는 내용 | 통과만으로 알 수 없는 내용 |
|---|---|---|
| 출력 구조 | JSON, 필수 키, 자료형, enum, 길이·배열 한도 | 문장 의미의 정확성 |
| 원문 근거 | 화자·질문 ID·답변 상태·인용의 원문 포함 여부 | 인용에서 해당 해석을 도출해도 되는지 |
| 주장별 검토 | 모든 주장에 대한 판정과 이유, 확실성 수준 | 검토 모델이 모든 의미 오류를 발견했는지 |
| 로컬 표현 검사 | 이미 확인된 귀속·시간 추세·약속 등 특정 오류 | 모든 자연어 표현의 정확성 |
| 단계별 최종 검토 | 분석·계획·카드·전체 일관성·상세 설명 | 임상적 타당성·실제 이용자 효용 |
| 저장 검사 | 승인 상태, 취소·revision, 암호화, 재조회 일치 | 저장된 문장의 의미적 정답 여부 |

구현 근거: [관계 에이전트](../../app/src/relationship-agent.js), [턴 처리](../../app/src/relationship-turn.js), [주장 감사](../../app/src/grounding-audit.js), [API 저장 진입점](../../app/src/server.js).

## 2. JSON·스키마와 전송 표현 검사

### 2.1 모델의 구조화 출력도 다시 검사한다

`validateSchema()`는 모델 제공자가 JSON Schema 출력을 지원하더라도 앱에서 다시 실행하는 **프로젝트 전용 부분 검증기**다. 객체는 `properties`에 정의된 키를 모두 요구하고 추가 키를 거절한다. object/array/string/boolean/null, `anyOf`, `const`, `enum`, 배열 min/maxItems, 문자열 비공백·maxLength 등을 검사한다. 범용 JSON Schema의 모든 키워드를 구현한 것은 아니다. 예를 들어 number/integer의 일반 자료형·수치 범위와 일반 `minLength`를 모두 처리하지 않으므로 해당 항목은 enum이나 별도 단계 검증에 의존하는지 확인해야 한다. 스키마 파일이 존재한다는 사실만으로 모든 제약을 런타임이 강제한다고 주장하지 않는다.

형식 수정 시에는 신뢰하는 스키마 경로와 기대 조건을 피드백으로 제공한다. 배열 초과에는 해당 위치·현재 개수·허용 한도를 전달한다. 서버가 넘치는 항목을 임의로 잘라서 통과시키는 방식이 아니다. 모델이 다시 작성하고 원래 검증을 받는다.

전송 응답도 검사한다. `ModelGateway.request()`는 단일 choice·message·완료 사유를 확인하고, 일반 경로의 `finish_reason=stop` 또는 허용된 로컬 스트리밍 JSON 완료 경로만 받아들인다. HTTP 200이나 JSON 시작만으로 성공하지 않는다. 전송·스트리밍 검사와 단계별 출력 검사도 서로 다른 층이다. [Gateway](../../app/src/model.js), [스트리밍 검사](../../app/src/model-stream.js).

### 2.2 근거 ID 전송과 원래 객체의 복원

관계 기억 등 일부 요청은 긴 인용 객체를 `source_N` 같은 요청 내부 ID로 표현한다. `(subject, question_id, quote)`가 정확히 같은 근거는 같은 ID를 사용하고, 재시도에서 제거된 ID를 다른 원문에 재할당하지 않는다.

검사 순서는 다음과 같다.

1. ID 형태의 모델 출력을 해당 요청의 스키마로 검사한다.
2. 분기별 허용 ID 목록을 확인한다. 다른 분기에만 허용된 근거를 가져올 수 없다.
3. 검증된 ID를 원래 근거 객체로 복원한다.
4. 원래 객체 스키마와 원문 근거 검사를 다시 실행한다.
5. 독립 상태·질문·안전 검토를 거친다. 저장에는 원래 근거 객체를 사용한다.

이는 전송 표현을 줄이는 최적화이며 근거 검사 생략이 아니다. [ID·배열 수정 기록](../../app/docs/EVIDENCE_ID_ARRAY_FIX.md), [ID 회귀검사](../../app/tests/relationship-evidence-ids.test.js).

### 2.3 원문 보존을 전제로 하는 제한적 정규화

‘모든 배열 초과와 enum 불일치는 재생성한다’는 설명은 현재 코드와 다르다. `relationship-turn.js`에는 다음 두 예외가 있다.

- `normalizeEvidenceExcerpts()`: patient/supporter 관계 기억의 인용이 실제 원문과 검색 범위에는 일치하지만 enum에만 없을 때, 같은 화자·질문에서 이를 포함하는 유일한 최소 완결 문장 또는 전체 답변 후보로 확장한다. 경쟁 문장 등 모호함이 있으면 거절한다. 확장 전후 원문·검색·스키마를 검사하고 원문 대신 길이·해시 진단을 남긴다.
- `normalizeReportedOverflow()`: 그룹 상한 2개에 **reported 2개+tentative 1개**가 나온 특정 경우, 원래 각 행을 먼저 검증하고 두 보고의 인용을 보존하는 reported 한 행으로 합친다. 최종 그룹 상한은 2개를 유지하며 합친 보고 근거는 전용 retained 스키마의 최대 6개까지 허용한다. 잘못된 행을 숨기거나 가설을 사실로 바꾸지 않는다. reported 1개+tentative 2개 등 다른 초과는 재작성 대상으로 남는다.

두 경로 모두 전체 상태 검사와 새 독립 검토를 거친다. 이는 검증을 생략한 자동 승인이나 내용 생성이 아니라 제한된 표현 정규화다. [발췌 정규화 검사](../../app/tests/combined-evidence-excerpts.test.js), [보고 병합 검사](../../app/tests/combined-reported-normalization.test.js), [최신 사실 슬롯 검사](../../app/tests/combined-latest-capacity-feedback.test.js).

## 3. 실제 원문과 근거의 일치

`validateEvidence(ref, context)`는 근거가 가리키는 입력 필드를 찾고, 해당 필드의 질문 ID가 일치하며 `answered` 상태인지 확인한다. 인용 `quote`는 해당 입력의 허용 원문 중 하나에 실제로 포함돼야 한다. 모델이 만든 새 문장이나 검토자의 수정 예문은 사용자 원문이 아니다.

검색을 사용하는 최종 생성에서는 선택된 검색 문서에 속한 근거인지도 `assertRetrievedEvidence()`로 확인한다. 따라서 전체 입력 어딘가에 있는 문장이라고 해서 현재 요청의 허용 검색 범위를 벗어나 인용할 수 있는 것은 아니다. 원문 검색과 전송 입력의 중복 제거는 별도 처리된다.

중요한 한계는 **인용 포함 검사와 의미적 지지 판정의 차이**다. 인용이 존재해도 화자·시점·부정·정도·인과를 잘못 해석할 수 있다. 이 부분은 다음의 주장별 감사, 독립 모델 검토, 제한된 표현 검사로 추가 확인한다. [근거·검색 구현](../../app/src/relationship-agent.js), [검색 처리](../../app/src/relationship-retrieval.js).

## 4. 답변을 받을 때의 상태·질문·안전 검증

### 4.1 작성과 조합 검사

`combined_blocks`에서는 환자 상태 → 이름 → 관계 기억의 상태 처리 체인과 질문 작성 분기를 병렬로 수행한다. 질문 작성 입력에는 상태 블록의 생성 결과를 끼워 넣지 않는다. 두 분기가 끝나면 전체 초안을 조합하고 상태·이름·질문 계획·관계 기억·근거를 검증한다.

일부 블록이 성공했거나 먼저 화면에 진행 상태가 표시됐다는 사실은 턴 전체의 승인이 아니다. 구조 오류 복구에 성공한 블록을 재사용할 수 있어도, 현재 입력·프롬프트·스키마 등이 일치해야 하고 재사용 값 및 전체 조합을 다시 검사한다.

### 4.2 상태 감사

상태 검토는 각 주장 ID를 빠짐없이 한 번씩 검사한다. `validateAudits()`의 판정값은 아래와 같다.

| 판정 | 의미 | 승인 경계 |
|---|---|---|
| `supported` | 원문이 해당 주장 전체를 직접 지지 | `reported` 사실은 이 판정이 필요 |
| `plausible` | 원문에 근거한 가능성이고 가설 표현을 유지 | 실제 보고된 사실로 승격할 수 없음 |
| `unsupported` | 인용 밖 사실·행동·감정·인과 등이 포함됨 | 전체 승인과 양립할 수 없음 |

위 세 값은 내부 canonical 판정이다. **미확인 정보의 실제 모델 요청에는 전용 네 값**을 사용한다.

| 미확인 정보의 전송 판정 | 내부 변환 | 승인 의미 |
|---|---|---|
| `still_unknown` | `supported` | 같은 사람·시점·범위가 미확인이며 현재 판단에 필요한 한계 |
| `already_answered` | `unsupported` | 이미 답해졌거나 최신 정정과 모순됨 |
| `not_needed` | `unsupported` | 현재 판단과 무관한 불필요한 미확인 항목 |
| `review_uncertain` | `plausible` | 검토자가 해당 미확인 범위를 확정하지 못함 |

미확인 항목은 `still_unknown`에 해당하는 적극적 확인이 있어야 승인 가능하다. 이 표의 `not_needed`는 **미확인 목록 항목의 판정**이며 질문 생략 판정과 같은 필드가 아니다.

요청에 들어간 감사 ID의 누락·중복·알 수 없는 ID·잘못된 판정·빈 이유를 거절한다. patient_state와 relationship_memory의 unknowns에 **원문 문자열이 정확히 같은 항목**이 있으면 반대 그룹의 한 쌍만 검토 요청에서 공유하고, 응답을 원래 두 ID로 확장해 전체 검증을 다시 수행한다. 같은 그룹 중복이나 유사한 문구를 임의로 합치지 않는다. 따라서 전송 시 항상 원래 주장 수만큼 독립 감사를 요청한다고 설명하면 부정확하다.

`approved`와 issues의 비어 있음이 일치해야 한다. `reported`를 `plausible`로만 평가하면서 승인하거나, 검토자 자신의 audits 형식 문제를 생성 초안 오류로 떠넘기는 응답도 거절한다. [상태 감사 구현](../../app/src/relationship-turn.js), [검토 범위 회귀](../../app/tests/relationship-turn-review-scope.test.js).

### 4.3 질문 선택·생략 검토

조건에 따라 질문 검토가 실행되어 이미 답한 질문, 추가 질문, 생략 이유와 근거를 검사한다. **아직 직접 답하지 않은 질문도 앞선 문맥에서 불필요하면 생략하는 기능은 유지한다.** 다만 미응답이라는 사실 자체가 불필요하다는 근거는 아니며, 생략된 문항에 답변 사실을 만들어 넣을 수 없다.

질문 검토에서는 받은 연락을 이용자가 먼저 건넨 말로 바꾸는 등 발신자·수신자 오류도 다룬다. 선택 질문을 사용자가 건너뛴 상태와 답변을 직접 제공한 상태는 구분해 보존한다.

### 4.4 안전 검토

적응형 턴의 안전 검토는 현재 원문을 기준으로 판단·이유·근거를 반환한다. 긴급 판정에서는 기존 계약대로 추가 질문과 생략 목록을 비운다. `urgent=false`는 임상적 안전 확인이나 위험 부재의 증명이 아니다.

검토된 안전 판단은 전체 답변 출처 스냅샷과 함께 보존한다. 최종 생성 시 같은 원문이라면 검증된 true/false 판단 모두 전달한다. 원문이 바뀌었거나 이전 기록에 출처 스냅샷이 없으면 독립 안전 재검토가 필요하다. 동일 원문의 검토 결과를 생성 단계의 새로운 추측으로 뒤집지 않도록 한다.

### 4.5 병렬화와 검토 묶음

개별 모드에서는 상태·조건부 질문·안전 검토를 병렬로 시작한 뒤 필요한 모든 결과를 기다린다. 턴 묶음 옵션이 활성화되면 하나의 HTTP 요청에 해당 검토들을 넣되 각 결과를 기존 검증기로 검사한다. 턴 묶음 안에서는 안전을 매번 새로 검토하며 단독 안전 검토 캐시를 대신 사용하지 않는다.

검토 의미 반려는 통신·인증·형식 오류와 다르게 처리한다. 반려 초안과 검토의 짝, 이미 확인한 위험을 다음 수정에 전달한다. 실행 오류·취소 시 형제 분기를 정리하고 늦게 도착한 응답은 폐기한다. 모든 필요한 검토를 끝내기 전 승인 상태를 반환하거나 저장하지 않는다.

## 5. 최종 카드 생성의 검증

일반 안내의 상세 기능을 유지하는 경로를 기준으로 설명한다. 긴급 안내는 별도 고정 안내·상세 생략 계약을 따른다.

| 단계 | 검사 대상 | 반려 또는 변경 시 처리 |
|---|---|---|
| 관계 분석 | 관찰·관계 해석·미확인·근거·안전 일관성 | 분석 수정 뒤 새 분석 검토 |
| 안내 계획 | 발화 방향·인용·원문과 계획의 관계 | 계획 수정·재검토. 인용에 설명 키를 강제로 추가하지 않음 |
| 다섯 카드 | `script`, `doList`, `avoid`, `next`, `care`의 역할·내용 | 문제가 있는 카드 수정·재검토 |
| 카드별 검토 | 다섯 카드의 발화/근거 검토, `care`와 `next`의 지원 검토 | 총 7개 논리 검토. 로컬 표현 오류도 반려에 반영 |
| 품질 검토 | 상황 적합성·실행 가능성·개선할 필드 | 설정에 따라 지적된 필드만 수정하고 전체 병합 결과 검사 |
| 전체 안내 검토 | 발화·지원·카드 간 일관성 등 | 수정이 영향을 준 기존 승인을 무효화하고 재검토 |
| 상세 발화 | 최종 script와 구간 설명·근거의 일치 | 상세 수정·새 독립 검토 |

O4는 한 번 작성한 카드 초안을 재사용하는 경로다. **정상 O4의 14개 논리 검토를 유지하면서 검토 HTTP 요청을 묶을 수 있다.** 카드별 7개·품질 1개·전체 3개를 한 요청에 담고, 분석·계획·상세 검토는 의존하는 생성 뒤에 별도로 둔다. 정상 고정 합성 응답에서 POST 18→8이 확인됐지만, 수정·재시도·예산 분할이 발생하면 더 늘어난다.

묶음에서 일부 검토가 통과했다고 나머지 검토까지 승인하지 않는다. 한 검토의 승인을 다른 검토의 근거로 쓰지 않는다. 다만 **어느 단계에서 수정됐는지에 따라 재검토 범위가 다르다.** 초기 카드 수정에서는 해당 카드 검토와 품질·전체 검토를 갱신한다. 품질 수정 뒤에는 품질 재검토와 전체 발화·지원·안내 검토를 수행한다. 마지막 전체 검토가 반려한 카드의 부분 수정 뒤에는 `reviewGuide()`의 전체 검토를 다시 수행하며, 품질·개별 카드 7개를 모두 처음부터 재실행하는 것은 아니다. 기존 문서의 ‘관련 모든 검토를 재실행’처럼 읽힐 수 있는 표현을 이 경로 구분으로 한정한다. [묶음 구현](../../app/src/final-review-bundle.js), [실제 수정 분기](../../app/src/relationship-agent.js), [O4 문서](../../app/docs/FINAL_DRAFT_REUSE.md).

### 안내 문장과 보고 사실의 검토 구분

`claimReviewRequest()`는 실제 전송에서 `certainty` 대신 안내 역할을 보낸다. 일반 안내는 `claim_kind=guidance`와 `sound_guidance / problem_in_guidance / unclear`, 피할 말은 `avoidance_guidance`와 `sound_avoidance / problem_in_recommended_content / unclear`를 사용한다. 서버는 ID·판정 집합을 검사한 뒤 내부의 supported/unsupported/plausible로 변환한다. 내부 `reported` 표식이 있다고 해서 모든 제안·질문을 실제 발생 사실로 간주하는 것은 아니다.

피할 예문에 부적절한 말이 있다는 사실만으로 반려하지 않고, 권장 내용·이유·대안의 역할을 구분한다. 이용자가 아직 하지 않은 휴식이나 부담 나누기를 선택지로 제안할 수 있으며, 단순히 더 구체적으로 쓸 수 있다는 품질 차이를 사실 위반으로 처리하지 않는다. 반대로 존재하지 않는 감정·동의·지원 자원을 사실로 추가하면 반려한다.

검토가 반려한 claim의 field에는 대응하는 issues가 있어야 한다. 수정 지시가 반려한 문장과 동일한 경우(`agent_review_noop`), 이전 이력에만 남은 인용을 현재 오류라고 지적하는 제한된 패턴(`agent_review_stale`)도 검토 응답 오류로 돌려보낸다. 자동 승인으로 바꾸지 않는다. [안내 역할 회귀](../../app/tests/claim-review-roles.test.js).

## 6. 모델 검토가 놓친 오류에 대한 추가 검사

실제 로컬 실행에서 모델이 승인한 문장에도 원문 범위를 벗어난 내용이 발견됐다. 현재 `knownSpeechIssues()`, `localCardIssues()`, `sourceAttributionIssues()`는 확인된 특정 오류를 추가로 차단한다.

| 오류 유형 | 확인하는 경계 |
|---|---|
| 도움 요청의 귀속 | 이용자가 도움이 필요하다고 판단한 것과 대상자가 실제 요청한 것을 구분 |
| 지원 의사의 방향 | 누가 누구를 돕겠다고 했는지 보존. 주어·수신자 역전 검사 |
| 노력·속마음 단정 | 원문에 없는 정도·내면을 직접 확인한 사실처럼 말하지 않음 |
| 무제한 약속 | 이용자가 밝히지 않은 무제한 청취·응답 가능성을 약속하지 않음 |
| 기간과 변화 추세 | 혼자 있는 시간이 길다는 정적 보고를 이전보다 늘었다는 변화로 바꾸지 않음 |
| 미확인 정보 오염 | 이미 해결된 항목의 삭제 지시·수정 경과를 새로운 미확인 사실로 남기지 않음 |

실제 요청, 조건부 제안, 한정된 시간, 감사, 과거 전언, 피할 예문, 후속 철회·정정 등 반례를 구분한다. 위반 시 **모델에게 수정하게 하고 새 독립 검토를 실행**한다. 서버가 문장을 임의 교정해 승인하는 방식이 아니다.

이 검사는 제한된 표현을 다룬다. 모든 자연어 오류를 완전히 판별하는 검증기라고 볼 수 없다. 공통 원문 충실성 프롬프트도 함께 사용하며 검토 이유와 수정 지시 역시 사실 확장을 하지 않도록 요구한다. [원문 충실성 기록](../../app/docs/SOURCE_FIDELITY_FIX.md), [도움 귀속 구현](../../app/src/guidance-source-attribution.js).

최종 `guide_review`는 이전 파생 메모리 `prior_relationship_memory`를 answers에서 제외하고 **현재 analysis·guide와 이용자 원답변**을 대조한다. 감정 자기보고의 동의어·요약은 화자·시점·부정·조건·강도를 보존하면 허용하도록 지시한다. 단어가 다르다는 이유만으로 추론으로 바꾸거나 삭제된 과거 초안을 현재 오류로 지적하지 않게 하는 프롬프트 경계다. 자연어 의미를 결정적으로 증명하는 새 검사기로 해석하지 않는다. [최종 대상 보존 검사](../../app/tests/relationship-final-preservation.test.js).

## 7. 상세 발화·표시·저장 검증

### 7.1 상세 발화

일반 경로의 `conversation_detail`은 최종 승인 script를 세 구간으로 나누고 각 구간에 설명과 원문 근거를 연결한다. 모델이 출력한 구간 경계의 순서를 검사하고, 세 excerpt를 순서대로 합쳤을 때 최종 script와 공백 정규화 기준으로 일치해야 한다. 누락·중복·문구 변경을 허용하지 않는다. 설명 `why`의 개인화 사실도 별도 주장 감사와 독립 검토를 받는다.

긴급 분기에서 상세를 생성하지 않는 것은 기존 계약이다. 긴급 저장 성공 사례로 일반 상세 경로의 성공을 대신 주장하지 않는다.

### 7.2 표시와 완료 상태

완료된 카드의 중간 표시와 최종 기록 저장은 구분된다. 반려된 카드를 승인 카드처럼 먼저 표시하지 않으며, 변경·취소 시 진행 카드 이벤트를 정리한다. 일부 카드가 보인다고 전체 결과가 저장 완료됐다는 뜻은 아니다.

기존 카드 디자인은 고정한다. 검증용 상세·근거 자료를 추가 저장하는 것이 화면에 단계별 설명이나 근거 인용을 새로 노출할 권한은 아니다. [UI 정보 원칙](../../app/docs/UI_CONTENT_POLICY.md)을 따른다.

### 7.3 저장과 재조회

원답변은 처리 중 pending 상태로 저장할 수 있지만, 모델의 일부 초안을 승인된 상태로 저장하지 않는다. API는 모델 처리 완료 후 취소와 revision을 확인하고 승인된 상태를 저장한다. 최종 기록도 관련 검토 완료와 현재 상태 확인 후 저장한다.

DB 검사에서는 원답변·상태·최종 카드·상세의 보존, 암호화, 소유자 경계, 재조회 일치를 확인한다. 재조회는 저장된 결과를 읽으며 모델을 다시 호출하지 않는다. [서버](../../app/src/server.js), [저장 구현](../../app/src/store.js), [최종 안전 저장 검사](../../app/tests/final-safety-persistence.test.js).

## 8. 실패·재시도·복구의 원칙

- 형식 오류를 자동 승인하거나 근거 없는 내용을 기본값으로 채우지 않는다.
- **최종 검토 묶음**의 입력 예산이 초과하면 원문을 자르는 대신 묶음을 재귀 분할한다. **턴 검토 묶음**은 동일 오류에서 원래 개별 병렬 검토로 복구한다. 두 경로의 예산 복구 방법은 다르다.
- 특정 묶음 형식 오류가 기존 3회 요청 시도를 소진하면 해당 작업에서 개별 검토 경로로 복구한다. 실패한 묶음의 부분 승인은 버린다.
- 의미적 반려·전송 오류·취소를 단순 형식 복구와 혼동하지 않는다. 복구가 승인 우회가 되어서는 안 된다.
- 각 단계의 수정 횟수와 요청 재시도는 구분한다. 모든 단계에 동일한 무제한 재시도 정책이 있는 것은 아니다.
- 원문·출처·모델·스키마·검토 정책이 달라지면 관련 재사용 결과를 무효화한다. 같은 생성 초안을 이어받아도 이전 승인 전체를 그대로 이어받는 것은 아니다.

### 9.2 이 문서 작성 중 새로 확인한 검사

다음 6개 테스트 파일을 현재 로컬 소스에서 실행했다. **135개 통과, 실패·취소·건너뜀 0개**다. 실제 모델 추론·DB·GPU 서버를 사용한 검사가 아니라 집중 회귀검사다.

node --test \

  app/tests/final-review-bundle.test.js \

  app/tests/relationship-evidence-ids.test.js \

### 9.3 사용자 요청에 따른 코드 재대조

같은 날 후속 재검토에서 실제 판정 라벨, 미확인 항목 감사 공유, 발췌 확장·reported 병합, 안내/사실 구분, 수정 단계별 재검토, 턴/최종 묶음의 다른 복구 경로를 추가 확인하고 수정했다. `relationship-turn-review-scope`, `claim-review-roles`, `combined-evidence-excerpts`, `combined-reported-normalization`, `combined-latest-capacity-feedback`, `relationship-final-preservation`, `turn-review-bundle`, `final-review-bundle`의 **8개 테스트 파일에서 210개 통과, 실패·건너뜀 0개**를 새로 확인했다. 최초 135개 검사와 중복되므로 합산하지 않는다. 실제 모델·DB·GPU를 재실행한 검사는 아니다.

별도 지정 Ollama 검토 API는 연결 재시도에서 `Host is down`으로 응답하지 않아 검토 결과를 얻지 못했다. 위 수정은 실제 코드와 로컬 회귀 결과에 근거한다.

## 10. 아직 남아 있는 검증 과제

1. 중간 미확인 정보에서 받은 도움·지지 인물·주변 권고의 범위를 더 정확히 분리해야 한다.
2. 원문에서 언급하지 않은 것을 명시적으로 ‘모른다’고 답한 것처럼 설명하는 질문 생략 이유를 보완해야 한다. 문맥상 질문 생략 기능 자체는 유지한다.
3. 모델 검토가 승인해도 사실 오류가 남을 수 있으므로, 다른 사례와 독립 평가자에 의한 원문 대조를 늘려야 한다.
4. 실제 사례의 성공은 전체 이용자 분포·임상 정확성·독립 test 통과를 의미하지 않는다.
5. 실제 모델의 취소·재시도·오류 주입, 새로운 가중치와 검토 모델 조합, 묶음의 검토 누락 여부는 별도 실험이 필요하다.

학습 이후 모델 성능 평가의 기준·사례군 분리·완료 판정은 [남은 학습과 최적화](04_남은_모델_학습과_최적화.md)에서 별도로 다룬다.
