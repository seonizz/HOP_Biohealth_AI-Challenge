# 이때까지 최적화한 방법과 그 결과

작성 기준: **2026-11-01, 한국 시간**. 현재 작업 폴더의 코드와 프로젝트에 저장된 검증 기록을 대조한 정리다. 미커밋 파일도 현재 구현에 포함한다. 이번 문서 작성 과정에서 학습·추론·GPU 서버 접속이나 배포를 새로 수행하지 않았다.

이 프로젝트의 최적화는 세 방향으로 진행됐다. 첫째, 학습 데이터의 목적 적합성·대표성·가중치를 개선했다. 둘째, 실제 학습을 작은 GPU 메모리 안에서 수행하고 중단·재개할 수 있도록 했다. 셋째, 앱에서 중복 생성·중복 입력·불필요한 재시도를 줄이면서 검토와 저장을 유지했다.

## 1. 결과를 읽는 기준

| 표시 | 의미 | 해석 시 주의점 |
|---|---|---|
| 코드 구현 | 현재 로컬 코드에 기능·설정·검사가 존재 | 실행 중인 서비스에 적용됐다는 뜻은 아님 |
| 합성·mock 검증 | 고정한 입력·응답 또는 테스트 HTTP로 전후 비교 | 실제 모델 품질·속도 개선율로 확대하지 않음 |
| 실제 로컬 모델 검증 | Mac Ollama의 실제 생성과 앱 처리 기록 | 해당 사례와 설정의 성공이며 전체 입력의 보장은 아님 |
| 과거 GPU 실측 | 당시 승인된 GPU 학습·검증 기록 | 현재 서버 상태·현재 재실행 권한을 뜻하지 않음 |
| 구현된 실험 후보 | 최적화 코드와 자격 검증 절차가 존재 | 검증 결과 없이 채택·가속 성공으로 계산하지 않음 |

모델 POST, capability GET, 논리 검토 항목 수, UTF-8 바이트, 토큰, CE 손실은 서로 다른 단위다. 특히 호출 수 감소율을 그대로 시간·품질·토큰 감소율로 표현하지 않는다. 각 시점의 전체 테스트 수는 당시 검사 집합의 크기이므로 서로 더하지 않는다. 모델 성능·크기·속도는 사용자 지정 프로젝트 평가 점수에서 제외하며, 아래 운영 지표는 최적화 경과를 설명하기 위한 것이다.

## 2. 학습 데이터 구성 최적화

### 2.1 원상담의 선택·대표성·집중도 개선

원상담의 과거 발화를 잘라 짧게 만드는 대신, 기존 원행 중 목적과 길이 조건을 만족하는 대표를 고르고 그 정답 시점까지의 전체 맥락을 보존하는 방향으로 진행했다.

| 단계 | 해결하려던 문제 | 적용한 방법 | 기록된 결과 | 남은 한계 |
|---|---|---|---|---|
| v2: 목적별 후보 분리 | 원상담의 다음 상담사 발화와 앱의 주변인 지원 과업을 같은 정답으로 취급할 위험 | 원상담 후보와 주변인 지원 합성 후보를 구분하고 원천·분할·보류 이력을 유지 | 이후 원상담 v3–v8, 주변인·앱 v9–v11로 이어지는 별도 검증 경로 확보 | 후보 구성은 사람 검토·임상 승인과 다름 |
| v3: 짧은 후보의 후기 선택 누락 보완 | 전체 길이 4,096 이하 후보에서 적격 후기 셀까지 누락 | 짧은 적격 풀을 별도로 구성하고 후기 셀을 우선 보존 | 짧은 후보 1,743행, 후기 50/50셀, 마지막 ¼ 0→1행 | 전반부 97.13%, 마지막 ¼ validation 0행 |
| v3: 출력 예약 8,192 검증 | 입력·출력 예약과 실제 학습 길이의 혼동 | 입력+출력 예약, 정답 길이, 실제 전체 길이를 별도 검사 | 4,096→8,192 예약 변경 전후 선택 행 변경 0, 압축 데이터 4개 해시 동일 | 출력 한도 증가 자체로 후기 데이터가 늘어난 것은 아님 |
| v4: 긴 후보의 후기 보강 | 주 후보에 적격 후기 셀이 덜 포함됨 | 기존 행을 보존하면서 빠진 후기 252행 추가 | 2,365→2,617행, 전반부 55.98%→50.59%, validation 후기 96→105행 | 새 상담 수는 0; 같은 상담의 추가 시점이며 독립 test가 아님 |
| v5: 출처 그룹의 행 수 집중 완화 | 일부 그룹에 선택 행이 과도하게 몰림 | 상담·후기 대표와 split을 고정하고 전기 대표 선택 제한 | 짧은 전기 비중 97.13%→95.25%, 그룹 최대 16→10행; 긴 후보 최대 25→19행 | 정답 길이가 달라 정답 토큰 집중도 7지표는 악화 |
| v6: 정답 토큰 집중 완화 | 행 수를 분산해도 긴 정답의 영향력이 집중 | 같은 상담·선택 구간에서 정답 길이가 상쇄되는 쌍 교체 | 악화 7지표 해소, 정답 토큰 18지표가 v5·이전 기준 이하 | 일부 입력 접두부 집중도와 입력 총량 증가 |
| v7: 입력 접두부 집중 완화 | 정답 균형을 맞추는 과정에서 입력 집중 악화 | 같은 정답 길이의 전기 대표로 짧은 1행·긴 2행 교체 | 입력 18지표가 `min(v5,v6)` 이하; 정답 집중도·총량 보존 | split별 입력 최대 0.126578% 증가, 절차성 플래그 각각 1행 증가 |
| v8: 입력 총량·절차성 증가 회수 | 집중도 개선을 위해 입력 분모만 늘린 부작용 | 짧은 5행·긴 4행을 기존 적격 원행으로 교체하고 최종 조건 동시 검사 | v7 대비 입력 4,674·6,859토큰 감소, 절차성 플래그 2·1행 감소, 입력 18지표 개선, 관련 329검사 통과 | 긴 validation은 v5 대비 +1,456토큰; 짧은 신규 플래그 셀 1개와 의미 동등성 미검증 잔존 |

이 수치는 **각 버전의 비교값**이다. v4의 2,617행을 현재 전체 학습 행 수라고 부르거나, v3–v8의 서로 겹치는 후보를 합산하지 않는다. v8 보존 집계는 짧은 후보 입력 2,089,385·정답 75,231토큰, 긴 후보 입력 14,183,561·정답 213,050토큰이다. 짧은 후보 마지막 ¼ validation의 적격 자료 부족은 선택 알고리즘만으로 해결하지 못했다.

### 2.3 최신 역할 분리·데이터 증량과 검토 보강

## 3. 모델 학습·계산 경로 최적화

### 3.1 실제 GPU 실행으로 확인한 과거 v11 학습

아래는 **2026-10-17 당시 기록**이며 현재 GPU 사용 허가를 뜻하지 않는다.

| 최적화·운영 방법 | 구체적인 설정·방법 | 당시 확인된 결과 |
|---|---|---|

## 4. 앱의 생성·검토 호출 최적화

### 4.1 전체 초안을 다시 쓰던 중복 제거: O4

기존 최종 결과는 전체 안내 초안을 만든 뒤 대화문 네 단계와 나머지 네 카드를 다시 작성했다. `MODEL_REUSE_FINAL_DRAFT=true`이면 전체 초안의 다섯 카드 필드를 기존 검증·카드별 독립 검토에 연결하고, 문제가 있는 카드만 고친다.

| 비교 항목 | 기존 | O4 | 확인 방식 |
|---|---:|---:|---|
| 정상 최종 생성 POST | 26 | 18 | 실제 Gateway + mock HTTP |
| 그중 작성 | 12 | 4 | 중복 작성 8개 제거 |
| 그중 논리 독립 검토 | 14 | 14 | 검토를 생략하지 않음 |
| 대화문 수정 1회+재검토 1회 사례 | 별도 | 20 | 지정 합성 사례의 관측값 |

상태가 준비된 비긴급·전체 기능 경로에서, 묶음은 끄고 수정·재시도·fallback이 없을 때 8회·30.8% 감소다. 답변 처리·기관 분류·조건부 상태 보완은 이 표에 포함하지 않는다. 전략·품질·저장용 상세를 유지하며 `MODEL_SKIP_FINAL_EXTRAS=true`와 함께 사용할 수 없다. 당시 전체 앱 검사 1,880통과·85건너뜀은 DB 미실행 시점의 기록이다.

근거: [O4 구현·검증](../../app/docs/FINAL_DRAFT_REUSE.md), [현재 생성 코드](../../app/src/relationship-agent.js).

### 4.2 검토 요청 묶음: 검토 항목 유지, POST 감소

2026-11-01 후속 구현은 O4의 14개 논리 검토를 유지하면서 독립 항목들을 하나의 HTTP 요청에 담는다. 각 항목의 입력·스키마·검증기는 남고, 작성 요청과 검토 요청도 분리한다. 공통 지시와 정확히 같은 입력만 공유한다.

| 정상 경로 | 묶음 이전 POST | 묶음 적용 POST | 조건 |
|---|---:|---:|---|
| O4 일반 최종 | 18 | 8 | 수정·형식 재시도·입력 분할 없음 |
| 긴급 최종 | 7 | 6 | 기존 긴급 고정 안내·상세 생략 계약 |
| O4 미사용 최종 | 26 | 21 | 개별 카드 작성은 유지 |
| 블록 답변 처리 | 7 | 5 | 이름 작성 필요, 적응형 질문 제안이 있어 상태·질문·안전 3검토가 모두 필요한 경우; 작성 4회+묶음 1회 |
| 같은 원문에서 선택 질문 건너뛰기 | 7 | 4 | 검토된 이름 재사용 가능, 작성 3회+묶음 1회 |
| 턴 묶음 없이 이름·안전 재사용 | 7 | 5 | 전체 원문·요청·검토자 정책 일치 |

최종 묶음은 카드별 근거·지원 7항목, 품질 1항목, 전체 3항목을 묶고, 의존 단계가 다른 분석·계획·상세 검토는 별도로 둔다. 원문 예산을 넘으면 원문을 자르지 않고 묶음을 분할한다. 형식·stale 오류가 기존 3회 시도를 소진하면 해당 작업에서 개별 검토로 복구한다. 유효한 반려·통신 오류·취소를 승인으로 바꾸지 않는다. 카드나 품질 수정이 발생하면 관련 이전 승인을 무효화한다.

O4 8 POST의 구성은 분석 작성·검토 2, 계획 작성·검토 2, 전체 초안 1, 초안 이후 11개 검토 묶음 1, 발화 상세 작성·검토 2다. 총 4개 작성 요청과 4개 검토 요청 안에서 14개 논리 검토를 수행한다. 같은 모델을 별도 요청으로 호출하는 독립 검토이며 서로 다른 모델 사용을 보장한다는 뜻은 아니다.

설정은 `MODEL_BUNDLE_FINAL_REVIEWS`, `MODEL_BUNDLE_TURN_REVIEWS`이며 코드 기본값은 false다. 최종 묶음은 `relationship_agent` 및 `skipFinalExtras=false`, 턴 묶음·검토된 이름/안전 재사용은 `relationship_agent + combined_blocks`가 필요하다. 8회 경로에는 `MODEL_REUSE_FINAL_DRAFT=true`도 필요하다. 위 조건을 벗어난 활성화는 `ModelGateway.configured` 검사에서 거절한다. 문서에는 검증 후 로컬 `.env` 활성화 및 기존 앱 프로세스 미재시작이 기록돼 있다. 이번 정리에서는 실행 프로세스의 적용 여부를 다시 조회하지 않았다.

근거: [최신 호출 최적화](../../app/docs/REVIEW_CALL_OPTIMIZATION.md), [묶음 구성기](../../app/src/final-review-bundle.js), [턴 처리](../../app/src/relationship-turn.js), [설정](../../app/src/model-config.js).

### 4.3 같은 원문에서 이름·안전 판단 재사용

이름은 같은 intake의 전체 실제 답변, 추출 요청·스키마·검증 버전, 모델·전송·토큰 정책이 모두 같은 경우에만 재사용한다. 독립 상태 검토가 승인한 값만 저장하고 재사용 때 다시 검증한다. 이름 정정·거절·의미 있는 미응답을 비교에서 빼지 않는다.

안전 단독 검토 재사용도 전체 실제 원문·제안 판단·검토자 계약의 일치가 필요하다. **턴 검토 묶음 모드에서는 매번 안전을 새로 검토**하며 단독 안전 캐시를 사용하지 않는다. 최종 분석이 같은 원문의 독립 안전 판단을 다시 뒤집거나 근거 ID를 임의로 다시 생성하지 않도록 검증된 판단·근거를 보존한다. 원문이 바뀌거나 이전 출처 스냅샷이 없으면 재검토한다.

이 경로는 전역 사용자 캐시나 다른 원문의 승인 재사용이 아니다. 설정은 `MODEL_REUSE_REVIEWED_NAME`, `MODEL_REUSE_REVIEWED_SAFETY`이며 후속 기록의 로컬 구성은 이름 재사용 true·단독 안전 재사용 false다.

핵심 구현: [입력 축소](../../app/src/turn-input-scope.js), [Gateway](../../app/src/model.js), [토큰 정책](../../app/src/model-token-policy.js), [Python API](../../ai/trained_model_api/server.py), [설정 검사](../../app/scripts/check-model.js).

입력 옵션은 `MODEL_BLOCK_SCOPED_INPUTS=true`일 때 `MODEL_STAGE_SCOPED_QUESTION_RULES=true`도 요구한다. 두 옵션의 실제 블록 입력 축소는 `combined_blocks`에만 적용한다. 토큰 정책 재사용은 옵션뿐 아니라 discovery와 서버 revision 계약이 필요하며, 생성·검토 Gateway는 각각 자기 정책을 사용한다. 기본 상태 모드는 `combined`이고 GPU overlay가 명시되지 않은 모드를 `combined_blocks`로 준비하므로, 옵션 목록만 보고 적용을 확정하지 않는다.

API의 `trained_chat` 프로필은 서버 요청 계약에 맞춰 `agentFormat=prompt`, `reasoningEffort=omit`, 스트리밍 비활성 조건을 요구한다. 서버 GPU 전용 모드에서는 모델명·인증·목적지를 명시하고 작성·검토·기관 분류 목적지가 일치해야 한다. 이는 구성 검증이며 실제 하드웨어·배포 상태의 증거가 아니다.

근거와 당시 검사: [입력 최적화](../../app/docs/MODEL_INPUT_OPTIMIZATION.md)는 앱 1,902통과·85건너뜀, [추가 반영](../../app/docs/REMAINING_MODEL_OPTIMIZATIONS.md)은 앱 1,928통과·85건너뜀 및 Python 73통과를 기록한다. 각각 당시 범위의 결과이며 최신 묶음 호출 수를 대체하지 않는다.

## 6. 독립 작업 병렬화

### 6.1 상태·질문·안전 검토 동시 시작

`combined`와 `combined_blocks`에서 전체 초안 검증을 마친 후 상태·조건부 질문·안전 검토를 함께 시작하도록 변경했다. 정상 호출 수는 조건에 따라 3→3, 2→2, 1→1로 동일하다. 후속 턴 묶음 옵션을 쓰면 이 항목들을 한 요청으로 묶으며, 개별 검토 복구 경로는 유지한다.

모든 결과가 끝난 뒤에만 질문·안전 판단을 반영한다. 실패한 분기의 형제는 취소하고 모두 정리될 때까지 기다린다. 검토별 operation 상태를 분리해 한 검토의 새 token revision이 다른 검토의 이전 출력 예산에 섞이는 경합을 수정했다. 취소 뒤 늦게 도착한 응답은 폐기한다.

### 6.2 질문 작성과 상태 블록 처리 동시 시작

기존에는 환자 상태→이름→관계 기억→질문 순서였다. 현재 블록 모드에서는 상태 체인과 질문 작성을 함께 시작하되, 상태 내부 순서는 유지한다. 질문에 선행 생성 블록을 넣지 않고 전체 원문 기반으로 작성한다. 두 분기가 끝나야 전체 조합 검증·독립 검토·저장으로 진행한다.

구조 복구에서는 **취소 전에 검증을 마친 블록만** 실제 요청·원문·스키마·재작성 단계 일치 시 재사용한다. 성공 블록을 재사용하더라도 전체 검증과 새로운 독립 검토를 생략하지 않는다.

### 6.3 실제 로컬 확인 결과

| 사례 | 실제 모델 POST | 결과 |
|---|---:|---|
| 일반 관계 답변 | 6 | 원문·근거 보존 및 검토 승인 |
| 이미 답한 질문 생략 | 7 | 상태·질문·안전 승인 |
| 현재 위험 부정 | 6 | 부정 원문 보존·긴급 false |
| 이름 없는 입력 | 5 | 이름 호출 없음·null 및 검토 유지 |
| 별도 앱 API 저장 사례 | 6 | pending·승인·암호화·재조회 11항목 통과 |

Mac Ollama의 합성 4사례 24 POST와 저장 사례 6 POST, 합계 30회 기록이다. 작성·검토 요청의 시작 시각 중첩을 확인했으며 **물리 GPU 추론의 동시 실행이나 전후 속도 향상률을 측정한 것은 아니다**. 당시 일회용 DB 포함 전체 앱 2,032검사가 통과했다.

## 8. GPU API·대기열의 운영 준비 개선

P0 구현은 생성·검토·기관 분류의 요청 계약을 맞추고 물리 요청별 슬롯·FIFO 대기·취소 완료·backend readiness를 명시한다. operation 전체에 슬롯을 잠가 교착시키지 않고 요청 단위로 관리한다. 취소 접수나 HTTP 연결 종료만으로 원격 작업 완료를 간주하지 않는다.

서버 정책 revision이 다르면 추론 전에 409로 거절하고 앱이 정책을 다시 조회한다. 이는 토큰 정책 캐시를 안전하게 쓸 조건이기도 하다. 기존 worker의 오류 응답과 idle 해제 순서 경합을 로컬 추출 코드에서 재현하고 호환 패치를 준비했다.

당시 합성 backend·가짜 subprocess·localhost HTTP 검사 65개 통과가 기록돼 있다. 현재 서버에 패치가 배포됐거나 실제 추론 처리량이 늘었다는 증거로 사용하지 않는다. GPU 서버 사용은 재허용 전까지 금지이며 이 문서 작성에서는 원격 접속을 하지 않았다.

근거: [GPU P0 계약](../../app/docs/SERVER_GPU_P0.md), [서버 API](../../ai/trained_model_api/server.py).

## 10. 최신 실제 완료 기록과 아직 주장할 수 없는 것

최신 호출 최적화 기록의 실제 로컬 검증은 다음처럼 범위를 나눈다.

| 기록 | POST 수·검증 결과 | 해석 |
|---|---|---|
| 마지막 이어받기 최종 실행 | 11 POST, 같은 generation 추가 시도 0, 내용 수정 2 POST, 저장·재조회 등 16검사 통과 | 실제 분석·초안 두 개를 검증 후 이어받음. 모든 승인은 새로 검토 |
| 답변→초안 준비→마지막 실행을 연결한 완료 경로 | 6+6+11 = **23 POST**, 동일 단계 추가 시도 1회 | 한 버전에서 처음부터 새로 만든 단일 실행과 구분 |
| 실패·중단·내용 재검토를 포함한 이번 수정 작업 전체 | **97 POST** | 개발 과정 전체 비용이며 정상 경로 목표 호출 수와 다름 |
| 고정 합성 응답의 O4 비교 | **18→8 POST** | 전후 동일 조건의 호출 감소 근거 |
| 최신 문서의 앱 전체 회귀 | **2,352통과, 실패·건너뜀 0** | 전용 로컬 DB 포함 당시 검사. 이번 문서 작성에서 새로 실행한 수치는 아님 |

저장 결과 전체와 재조회 결과가 일치했고 재조회 모델 호출은 0회다. 이전 저장 결과 27회는 안전 분기가 달라 실제 절감률 비교에서 제외했다. 호출 묶음 형식 검증을 통과한 뒤에도 내용 오류가 발견돼 수정된 이력이 있으므로, 정상 POST 8회만 달성하면 품질 검증이 완료된 것으로 보지 않는다.

남은 사항은 중간 미확인 정보의 범위 구분, 생략 사유에서 원문 미언급을 명시적 모름으로 오해하는 문제, 새로운 독립 평가셋·사람 검토, 카드 학습 계산 후보의 실측 자격 검증, 허용된 배포 후 실제 설정·저장·취소 확인이다. 문맥에 따른 질문 생략과 기존 카드 디자인은 유지한다.

### 이번 문서 재검토에서 새로 확인한 범위

2026-11-01 재검토에서는 위 원문 없는 결과 JSON과 COURSE 메타데이터를 직접 읽고 현재 구현·설정 조건을 대조했다. 앱에서 `node --test tests/final-review-bundle.test.js tests/turn-review-bundle.test.js tests/model-config.test.js`를 실행해 **84개 통과, 실패·건너뜀 0개**를 확인했다. 이 검사는 합성 응답으로 O4 18→8, 비O4 26→21, 긴급 7→6, 턴 7→5 및 이름 재사용 후 5→4, 원문·검토·복구·설정 경계를 검증한다. 실제 모델·GPU·운영 DB를 호출한 결과로 보고하지 않는다.
