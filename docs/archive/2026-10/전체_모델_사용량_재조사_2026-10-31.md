# 전체 모델 사용량 재조사

이 사용량을 바탕으로 한 후속 후보와 검증 결과는 [추가 최적화 검토](모델_호출_추가_최적화_검토_2026-10-31.md)를 따른다.

후속 [모델 입력 최적화](../../../app/docs/MODEL_INPUT_OPTIMIZATION.md) 구현 후에는 이름 스키마가 null로 고정된 combined_blocks 답변이 **6~7→5~6회**, 비적응형 상태 갱신은 **4→3회**가 된다. 이름 추론이 필요한 경우와 O4 최종 18회는 그대로다. 아래 표는 추가 개선 전 조사 기준이며, 운영 실행본에 적용했다는 뜻은 아니다.

조사일: 2026-10-31 KST. 현재 `app/` 소스, 로컬 실행 프로세스·설정 파일, 모의 HTTP 회귀검사를 대조했다. GPU 서버·SSH·실제 모델 추론·DB 연결은 사용하지 않았다. 이 표의 단위는 별도 표시가 없으면 **모델 생성 API POST 요청 횟수**다. 토큰·GPU 실행 횟수·시간을 뜻하지 않는다.

**O4의 18회는 최종 안내 생성만의 정상 수치다. 답변 처리·기관 분류·상태 보완·오류 복구를 더해야 전체 상담 사용량이 된다. 현재 9060 실행본은 별도 복사본이며 O4가 적용된 실행본이 아니다.**

## 1. 구현·설정·실행 상태 구분

| 대상 | 생성 / 검토 설정 | 답변 모드 | 최종 생성 설정 | 확인 범위 |
| --- | --- | --- | --- | --- |
| 현재 `app/` 소스 기본값 | 생성 모델 기본 `gemma4:12b`; 검토 별도 설정 가능 | `combined` | O4 false, extras 생략 false → 정상 26회 | 코드 기본값 |
| 로컬 `app/.env` | 둘 다 로컬 11434의 `gemma4:12b` | `combined_blocks` | O4·extras 생략 미지정 → 정상 26회 | 설정 파일. 이 설정으로 앱이 실행 중이라는 증거와는 별도 |
| 로컬 9060 실행본 | 생성 18090의 `malssi-gemma4-31b-v11-epoch3`, 검토 로컬 11434의 `gemma4:12b` | `combined_blocks` | `skipFinalExtras=true`, O4 옵션·구현 없음 → 정상 생략 경로 13회 | PID 60360의 진입 파일·ready 영수증·설정 파일·소스 대조 |
| 준비한 GPU overlay | 생성·검토·기관 분류를 같은 서버 목적지·모델로 강제 | 기본 Compose의 `combined` 또는 명시 설정 | O4 true, extras 생략 false → 정상 18회 | 배포 설정만 준비. 이번 조사에서 실행하지 않음 |

9060은 `runtime/gpu-ready-20261030/app-entry.mjs`가 그 하위 `app/` 복사본을 불러온다. 현재 `app/src/` 수정이 자동으로 이 실행본에 반영되는 구조가 아니다. 9060·18080·11434의 로컬 수신 프로세스는 확인했으며, 관찰 시점에 18090 수신은 없었다. 준비 gate가 요청 시 backend를 기동할 수 있으므로 이 사실만으로 영구 장애를 판정하지 않는다. 요청을 보내거나 gate를 작동시키지 않았고 원격 GPU 준비 상태는 미확인이다.

9060의 **이번 프로세스 로그 파일 한 개**에는 ready 1건만 있고 `model_attempt`·토큰 기록은 없었다. 이는 전체 프로젝트 누적 추론량이 0이라는 뜻이 아니다. 설정의 모델명도 실제 로드된 체크포인트를 검증했다는 뜻이 아니다.

실제 UI 문맥은 `adaptive_questions:true`다. 다음 표의 적응형 수치를 일반 답변 처리에 사용한다.

| 상태 모드 | 생성 | 검토 | 답변 1회 합계 | 적응형 질문을 사용하지 않는 내부 경로 |
| --- | ---: | ---: | ---: | ---: |
| `combined` | 통합 초안 1 | 상태 1 + 안전 1 + 조건부 질문 0~1 | **3~4** | 1 + 상태 검토 1 = 2 |
| `combined_blocks` | 상태·이름·관계·질문 4 | 상태 1 + 안전 1 + 조건부 질문 0~1 | **6~7** | 상태·이름·관계 3 + 상태 검토 1 = 4 |
| `staged` | 관찰·이름, 관계, 질문 3 | 상태 1 + 안전 1 + 조건부 질문 0~1 | **5~6** | 관찰·이름, 관계 2 + 상태 검토 1 = 3 |

질문 검토는 질문 생략 또는 clarification 제안이 있을 때 발생한다. 안전 검토는 적응형 처리마다 수행한다. `combined_blocks`가 현재 `app/.env`와 9060 설정이며, 코드/Compose 기본값 `combined`와 구분해야 한다.

## 3. 정상 최종 생성의 전체 단계

| 단계 | 기존 생성 | O4 생성 | 기존·O4 검토 | O4 합계 |
| --- | ---: | ---: | ---: | ---: |
| 관계 분석 | 1 | 1 | 1 | 2 |
| 대화 전략 | 1 | 1 | 1 | 2 |
| 전체 안내 초안 | 1 | 1 | 0 | 1 |
| 대화문 도입·경청·제안·합성 | 4 | 0 | 0 | 0 |
| 돌봄·실천·피할 말·다음 단계 작성 | 4 | 0 | 0 | 0 |
| 다섯 카드 독립 검토 | 0 | 0 | 5 | 5 |
| 돌봄·다음 단계 지원 검토 | 0 | 0 | 2 | 2 |
| 전체 품질 검토 | 0 | 0 | 1 | 1 |
| 전체 발화·돌봄·통합 검토 | 0 | 0 | 3 | 3 |
| 저장용 발화 상세 | 1 | 1 | 1 | 2 |
| **합계** | **12** | **4** | **14** | **18** |

기존 합계는 12+14=26회, O4는 4+14=18회로 **8회·30.8% 감소**다. 정상 비긴급·수정 없음·특수 seed 재사용 없음 기준이며, O4가 검토 14회나 상세 저장을 없애서 줄인 수치가 아니다.

## 4. 기관 분류와 추가 호출

| 기관 안내 조건 | 분류 호출 |
| --- | ---: |
| 유효한 분류 캐시 / 승인된 현재 긴급 신호 / 분류할 원문 없음 / 제공자 비활성 | 0 |
| 신규 1차 분류가 긴급 | 1 |
| 나머지 신규 분류 | 2: 1차 + 같은 원문에 대한 독립 2차 |

두 분류는 검토 Gateway가 아니라 **classifier 역할로 생성 Gateway**를 사용한다. UI가 최종 생성 전·저장 후 `/guidance`를 두 번 요청해도, 같은 소스의 분류 캐시가 새 revision으로 이월되면 뒤 요청은 0회다. API 요청 두 건을 모델 호출 네 번으로 계산하지 않는다. 캐시 만료·원문/정책/제공자 변경 시에는 다시 분류한다.

| 추가 조건 | 정상 경로 대비 증가 | 설명 |
| --- | ---: | --- |
| 최종 생성에 상태·관계 메모리 부재 | +3 | 관찰·이름 + 관계 + 상태 검토. `stateMode`와 무관 |
| 오래된 긴급 안전 승인 재확인 | +1 | `safety_review_required`일 때만 |
| 분석 또는 전략 반려 후 한 번 수정·승인 | +2 | 수정 + 새 검토 |
| 대화문·실천·피할 말 카드 반려 후 한 번 수정·승인 | +2 | O4 대화문 사례는 총 20회 검사 통과 |
| 돌봄·다음 단계의 첫 검토에서 반려 | +2 | 기존 정상 지원 검토에 더해 수정·첫 검토가 추가됨 |
| 돌봄·다음 단계의 지원 검토에서 반려 | +3 | 수정 + 첫 검토 + 지원 검토 |
| 품질 개선 또는 발화 상세 재작성 1회 | +2 | 작성 + 재검토 |
| 전체 검토에서 카드 k개 반려 | k+1 / k+2 / k+3 | 전체 발화 / 지원 / 통합 검토에서 최초 반려된 경우. 나머지 새 오류 없음 |
| 최종 통합 검토에서 분석 자체 반려 | +16 → 정상 O4 총 34 | 분석 수정·검토 후 전략·초안·카드 승인부터 다시 수행. 전후 비긴급·새 오류 없음 |
| combined 구조 오류 3회 후 블록 fallback | 답변 총 9~10 | 실패 3 + 블록 생성 4 + 검토 2~3, 추가 오류 없음 |
| 개별 stage의 형식·전송 오류 | stage 요청당 최대 3 attempts | 실패 시도도 합계에 포함 |
| operation 자동 재시작 | 조건별 추가 | 현재 `app/` 기본 총 시간 0·재시작 횟수 상한 없음. 전체 최대 N회로 고정할 수 없음 |

모든 오류가 무한 재시작되는 것은 아니다. 분석·전략·품질·전체·상세 검토의 의미 반려 한도를 소진한 오류는 재시작에서 제외된다. 검증된 블록을 동일 문맥에서 재사용하는 복구도 있어 모든 실패에 전체 생성 횟수를 더하면 과대 집계한다. 9060 별도 실행본에는 별도 bounded recovery 설정이 있으므로 현재 `app/` 재시작 정책과 혼합하지 않는다.

## 5. 상담 전체 계산

현재 `combined_blocks` 설정에서, 모델 처리가 발생한 답변 제출 횟수를 N, 그중 조건부 질문 검토 횟수를 Q(0≤Q≤N), 전체 기관 분류 횟수를 R이라 하면:

**O4 전체 = 6N + Q + 18 + R + 상태/안전 보완 + 수정·재시도.**

답변 10회, 신규 기관 분류 2회, 상태·안전 보완 및 수정·재시도 없음의 예:

| 답변 모드 | 기존 전체 기능 | O4 | 절감 |
| --- | ---: | ---: | ---: |
| `combined` | 58~68 | 50~60 | 8회 |
| `combined_blocks` | **88~98** | **80~90** | **8회** |
| `staged` | 78~88 | 70~80 | 8회 |

범위의 양 끝은 조건부 질문 검토가 0회 / 10회인 경우다. 같은 질문 검토 조건끼리 비교한다. 예를 들어 combined_blocks 88→80은 전체 상담 기준 9.1% 감소다. 질문 자동 생략으로 실제 제출 N이 달라지거나 기관 안내를 새로 분류하면 전체 합계도 달라진다.

## 6. 토큰·GPU 사용량에서 확인 가능한 것

| 지표 | 현재 조사 결과 |
| --- | --- |
| 정상 논리 호출 수 | 소스와 mock HTTP로 위 표 확인 |
| 실제 HTTP 시도 | `model_attempt`의 operation·attempt 단위로 집계 가능. 논리 호출·GPU dispatch와 다름 |
| 실제 입력/출력 토큰 | 응답의 `usage.prompt_tokens`, `completion_tokens`, `total_tokens`가 있어야 합산 가능 |
| 요청별 최대 출력 토큰 | backend의 `/healthz` 한도 발견 결과를 사용. 미광고 backend는 해당 backend 기본값 적용. 한도는 실제 소비량이 아님 |
| 이번 9060 프로세스의 관찰 로그 | ready 1건만 있음. 실제 토큰 합계 산출 불가 |
| 실제 GPU 메모리·점유·추론 시간 | 이번 조사에서 미측정. GPU 서버 사전 승인 전 접근하지 않음 |

O4 통합 초안 프롬프트는 기존보다 요구사항이 많다. 제거한 요청 8회의 입력·출력이 절약되는 효과와 통합 초안/추가 수정의 토큰 변화를 함께 측정해야 한다. **호출 30.8% 감소를 토큰·GPU 시간 30.8% 감소로 주장할 수 없다.** family별 계수는 한 요청이 여러 family에 포함되므로 합산해 전체 호출 수로 쓰지 않는다.

## 7. 예외 경로와 근거

- trusted local `finalDraftSeed`는 문맥이 정확히 같고 검증되면 분석·초안 생성 최대 2회만 재사용한다. 검토는 새로 수행하므로 조건 충족 O4는 16회가 가능하지만, 이는 **미구현 O5의 검토 축소 16회와 다른 경로**다. 일반 API 입력으로 활성화할 수 없다.
- legacy `json_prompt`·`json_schema`는 최종 1회 경로이며, `json_prompt`는 상태가 없으면 추가 1회다. `relationship_agent`의 독립 검토·상세 계약이 다르므로 기능 동등한 절감 비교에서 제외한다.
- `live-check.js`, 별도 평가·학습 스크립트의 수동 실행은 사용자 상담과 별도다. 특히 `live-check.js`는 상태 갱신과 최종 생성을 실제 요청하므로 단순 상태 조회가 아니다. 이번 조사에서는 실행하지 않았다.
