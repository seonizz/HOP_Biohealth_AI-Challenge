## 1. 작업 목적과 유지 조건

사용자가 본 다음 안내의 원인을 확인하고, 실제 모델에서 재현한 실패를 수정하는 작업이었다.

> 답변을 다시 확인했지만 아직 준비하지 못했어요. 대화 내용은 저장되어 있으니 다시 시도해 주세요.

목표는 로컬·LAN·API 연결 설정을 일관되게 처리하고, 다양한 대화에서 최종 결과를 생성·저장·다시 열 수 있도록 하는 것이다. 작업 중 다음 조건을 유지했다.

- 앞선 답변으로 충분히 설명됐거나 현재 맥락상 불필요한 질문은 모델이 생략할 수 있다.
- 생략한 문항에 답변을 만들어 넣거나 최종 결과의 사실 근거로 쓰지 않는다.
- 기존 카드의 배치·색상·모양·글자 위계·복사 버튼·표시 범위를 유지한다.
- 모델 응답은 형식, 원문 근거, 독립 검토를 통과한 뒤 사용한다.
- 기존 대화와 기록은 보존하고, 검증 자료는 Git에서 제외된 비공개 경로에 보관한다.

## 2. 오류 안내가 표시되는 조건

위 안내는 프런트엔드의 `MODEL_INVALID_RESPONSE` 표시 문구다. 모델 응답이 아래 검증을 수정 시도 후에도 통과하지 못하고 최종 오류로 반환될 때 표시된다.

| 실패 유형 | 확인한 사례 |
| --- | --- |
| JSON 형식·구조 오류 | 미완성 JSON, 반복 JSON, 배열 상한 초과, 잘못된 필드·인용 후보 |
| 스트림 종료 문제 | 완성된 JSON 뒤에도 계속 생성하거나 문자열 안에서 공백을 반복 |
| 원문 근거 오류 | 이름만 근거로 사용, 다른 사람의 지원 자원을 연결, 미확인 성품을 전제로 사용 |
| 검토·수정 반복 | 정상 제안을 사실 주장으로 오해하거나, 반려한 문장을 그대로 수정안으로 반환 |
| 최종 상세 생성 오류 | 전체 대화문을 각 상세 구간에 중복 복사 |

이 안내 자체가 입력 저장 실패를 뜻하지는 않는다. 실패한 입력과 대기 답변을 보존하고 재시도할 수 있는 계약은 유지했다. 연결·인증·시간 초과 등은 별도의 오류 유형으로 구분한다.

## 3. 주요 수정 내용

### 3.1. 로컬·LAN·Docker·API 설정 통일

- 호스트 실행, Docker, 별도 검토 모델, 기관 안내 모델, 연결 검사 도구가 공통 모델 설정을 사용하도록 정리했다.
- 서버 루트, `/v1`, `/v1/chat/completions` 주소를 공통 API 루트로 정규화했다.
- Docker에서는 loopback 주소를 `host.docker.internal`로 변환하고, 명시한 Docker 전용 주소를 우선한다. 지정한 LAN·외부 주소는 유지한다.
- 장애가 났을 때 임의의 다른 서버로 대화 원문을 전송하는 자동 목적지 변경은 추가하지 않았다.
- 새 로컬 설치에는 `combined_blocks`와 `json_schema`를 기본으로 적용한다. 기존 `.env`의 DB 암호, 저장 암호화 키, 사용자 모델 설정은 보존한다.
- API별로 `prompt`, `json_object`, `json_schema`와 추론 옵션 생략(`omit`), 스트리밍 여부, 모델 용량 조회 여부를 선택할 수 있도록 했다.
- 구형 `json_schema` 경로도 지정한 `reasoning_effort`를 따르고, `omit`이면 해당 필드를 전송하지 않도록 수정했다.
- 기관 안내의 모델 용량 조회 옵션은 별도 지정이 없으면 기본 모델 설정을 상속한다.
- 용량 조회 옵션을 빈 값으로 지정했을 때 Docker만 기본값으로 바꾸던 차이를 수정했다. 호스트와 Docker 모두 `true`·`false`를 검증한다.
- `check:model --generate`가 선택한 실제 모델 프로토콜과 검증 경로로 합성 입력을 검사하도록 수정했다.

### 3.2. 큰 상태 응답을 블록으로 나누어 생성

큰 통합 JSON에서 같은 구조 오류가 반복되는 현상을 확인했다. 새 로컬 기본값은 상태·이름·관계 기억·질문 계획을 블록으로 생성한 뒤 조합하는 `combined_blocks`다.

- 상태·관계·질문 블록은 불필요한 부모 객체를 반복하지 않도록 전송 형식을 단순화했다.
- 기존 `combined`·`staged` 선택지는 유지했다.
- 조합한 전체 결과에는 기존 원문 검증과 독립 상태 검토를 적용한다.
- 이름만 근거로 선택한 항목에는 문제가 있는 위치와 수정 안내를 전달해 같은 요청의 반복을 줄였다.

### 3.3. JSON 반복·공백 반복·종료 실패 복구

- 로컬 전용 `MODEL_STREAM_COMPLETE_JSON` 옵션을 추가했다. 완성된 JSON 객체를 수신하면 스트림을 끝내고 원래 전체 검증을 수행한다.
- 이 방식의 완료는 진단에 `json_complete`로 기록한다. 모델 서버가 정상 종료 사유를 보냈다고 표시하지 않는다.
- 이미 수신한 명시적인 실패 종료 사유는 계속 오류로 처리한다.
- 원래 스키마의 유한한 배열·문자열 상한을 명백히 넘은 스트림은 해당 시도에서 중단하고 수정 절차로 전달한다.
- 확인된 로컬 구조화 출력의 공백 반복 등 제한된 실패에는 다음 요청을 `json_schema`에서 `json_object`로 전환한다.
- 전송 형식이 바뀌어도 원래 스키마·원문 근거·독립 검토는 유지한다.
- 전체 응답의 새로운 시간·토큰·글자 수 제한을 추가하지 않았다. 기존 필드별 제한과 사용자의 시간 제한 해제 설정은 유지한다.

### 3.4. 질문 생략과 미확인 정보 검토 개선

| 항목 | 적용 내용 |
| --- | --- |
| 이미 답한 질문 | `already_covered`로 구분하고 실제 답변 근거를 확인 |
| 맥락상 불필요한 질문 | `not_needed`로 구분하고 생략 이유를 별도로 검토 |
| 미확인 정보 | “모른다고 답했다”는 보고와 “그 값이 확인됐다”는 상태를 구분 |
| 검토 입력 | 서로 다른 두 미확인 배열에서 정확히 같은 문구만 대응시키고 원래 저장 항목은 유지 |
| 수정 요청 | 검증된 반려 대상 ID와 문구를 전달해 수정할 범위를 명확히 함 |
| 질문 계획 | 검증 전 상태 초안의 영향을 줄이기 위해 질문 블록에서 `generated_blocks`를 제외 |

질문 계획에는 전체 원문, 질문 후보, 검색 근거와 별도 질문 검토를 유지했다. 생략된 문항의 답변이나 사실을 생성하는 방식은 사용하지 않았다.

### 3.5. 카드 작성·검토의 역할 구분

- 일반적인 행동 제안과 이미 일어난 사실 주장을 구분하도록 작성·검토 지침을 정리했다.
- 표현을 더 구체적으로 다듬을 여지는 품질 단계에서 다루고, 사실·안전·선택권의 오류와 구분한다.
- 카드 검토의 전송 판정을 일반 안내와 회피 안내에 맞게 구분했다. 결과는 원래 판정 체계로 대응시키되 승인값·이슈·이유·주장 ID를 그대로 검증한다.
- 과거 문안 때문에 현재 문장을 잘못 평가하는 경우, 현재 원문과 현재 문안으로 다시 검토하는 경로를 보완했다.
- 반려한 문장과 같은 수정안을 반환하는 검토는 `agent_review_noop`로 거절한다.
- 정해진 검토·수정 범위를 소진한 최종 검토 실패가 전체 안내의 무한 재생성으로 이어지지 않도록 했다.
- 대화 허락 질문과 거절·나중 대화에 대한 안내를 구분하고, 인용된 이용자의 도움 제안을 앱 자체의 지원 약속으로 오인하지 않도록 보완했다.

### 3.6. 실제 저장 결과에서 발견한 근거 오류 수정 — v3.19

기능상 저장까지 성공한 결과를 다시 원문과 대조해 두 가지 문제를 발견했다.

| 발견한 문제 | 수정 내용 |
| --- | --- |
| 미확인 대상자 성품을 권장 발화의 전제로 사용 | 실제 권장 문구의 해당 추정 전제를 보조 검사하고 수정 피드백 제공 |
| 이용자의 지원 자원 설명에 대상자 전용 자원 문항을 근거로 선택 | 명시된 자원 이용 주체와 선택한 전용 문항의 주체가 어긋나는 경우 반려 |

피할 예문, 직접적인 확인 질문, 이용자의 자기 표현, 명시적으로 보고된 발언 인용과 다른 질문에 포함된 실제 자기보고는 보존했다. 이 보조 검사는 확인한 오류 유형을 다루며, 의미 전체를 검증하는 독립 검토도 계속 수행한다.

### 3.7. 잘못된 카드 문안을 반복 복사하는 수정 경로 개선 — v3.20

모델이 반려된 대안을 세 번 동일하게 반환하는 실제 실패를 재생했다. 요청에는 현재 반려 사유와 그 문장을 적절하다고 평가했던 과거 검토가 함께 들어 있었다.

1. 과거 검토만 제외한 비교에서는 완성 카드의 중첩 복사가 사라졌지만 잘못된 성품 전제는 남았다.
2. 이전 완성 문안까지 제외하고 원문·계획·반려 사유로 해당 카드만 다시 작성하자 첫 생성 시도에 기존 검증을 통과했다.
3. 새 독립 검토도 첫 시도에 이슈 0개로 승인했다.

서비스에는 **‘피하면 좋아요’ 카드 수정 요청에만** 이 방식을 적용했다. 원문 검색과 스키마 구성은 기존 입력으로 먼저 수행한 뒤, 모델 전송 사본에서만 `current`·`review`를 제외한다. 검색 근거·내부 수정 이력·다른 카드의 입력·재시도 횟수·새 독립 검토는 유지한다.

### 3.8. 발화 상세의 중복 복사 방지

최종 발화를 세 구간에 각각 복사하던 문제를 수정했다. 모델이 순서 있는 원문 조각에서 두 경계를 선택하면 서버가 세 구간의 원문을 복원한다.

각 구간이 비어 있지 않은지, 원문 전체와 일치하는지, 순서대로 한 번씩 포함되는지, 설명의 인용이 실제 답변을 뒷받침하는지 확인하고 독립 상세 검토를 수행한다. 화면에 단계·이유·근거 설명을 새로 추가하지 않았다.

## 4. 유지한 화면과 저장 동작

기존 카드 디자인은 사용자 지정 `85fe360` 기준을 유지했다.

- 돌봄 카드: 연한 초록 배경, 왼쪽 마스코트, 오른쪽 공감 문단과 작은 도움말.
- 대화문 카드: 연한 크림 배경, 초록 점선 테두리, 전체 발화 문단과 오른쪽 위 복사 버튼.
- 행동·회피 카드: 넓은 화면에서 나란히 배치하고 좁은 화면에서 한 열로 전환.
- 생성 중 화면: 기존 연속 진행바와 점 세 개 대기 표시.

모델 병렬 호출과 완료 카드 표시에서도 기존 디자인 계약을 유지했다. 생성 중·결과·기록 화면을 확인했으며 최신 서버 재시작 후 기존 기록 화면도 다시 열었다.

저장 검증에서는 원본 기록을 보존한 상태로 읽기 해시 일치, 기록 목록 포함, 결과 요청의 중복 저장 방지, 다른 세션 접근 시 404, 재시작 후 재열기를 확인했다. 생략한 질문의 가상 답변과 해당 문항을 인용한 사실 근거도 검사했다.

| LAN 스트리밍 상황 검사 | 16 / 16 통과 | 고정된 턴 처리 코드에서 상태·질문 생략 검사 |
| LAN 비스트리밍 상황 검사 | 2 / 2 통과 | 응답 17개가 서버의 정상 `stop`으로 종료 |
| Mac·LAN 안내 검토 대조 | 각 환경에서 정상 3개 승인·허구 사실 4개 반려 | 같은 요청 본문을 사용한 검토 구분 검사 |
| 회피 카드 수정 재생 | 생성 1회·새 검토 1회에 통과 | v3.20에 반영한 입력 변경의 실제 Mac 비교 |
| Docker 실제 모델 연결 | 작성·검토 합성 생성 통과 | 기존 컨테이너 환경에서 모델 API 호출 |

집중 검사는 전체 검사와 겹치므로 개수를 합산하지 않는다. LAN 상황 검사와 검토 대조는 각각 수행 당시의 고정 코드에서 실행했으며, 최신 버전의 전체 서비스 재실행 횟수로 세지 않는다.

### 5.2. 처음부터 저장·재열기까지의 사례

| 사례 | 확인한 흐름 | 생략·근거 검사 |
| --- | --- | --- |
| 기존 브라우저 대화 | 실제 입력, 결과 생성·저장, 기록 열기·새로고침, 서버 복구 후 재열기 | 자동 생략 6개, 가상 답변 0개, 생략 문항 사실 인용 0개 |
| 가족 합성 사례 | LAN 모델에 답변 27개 입력 후 결과 생성·저장·재열기 | 자동 생략 2개, 최종 근거 20개 중 생략 문항 인용 0개 |
| 이전 동료 합성 사례 | v3.18에서 저장·재열기 성공 후 원문 대조로 내용 오류 2건 발견 | 기능 성공과 내용 검증 누락을 구분해 보존하고 v3.19 수정에 사용 |
| 새 동료 합성 사례 | LAN에서 답변 17개 입력 → Mac에서 최종 생성 → 저장·재열기 → 최신 서버 재시작 후 보존 | 자동 생략 12개, 가상 답변 0개, 최종 근거 21개 중 생략 문항 인용 0개 |

새 동료 사례는 30개 생성·검토 단계를 완료했다. 모델 시도 36회 중 형식 오류 6회가 있었고 기존 재시도와 두 차례 JSON 형식 전환으로 복구했다. 저장된 분석·안내는 검토한 최종 문안과 정확히 같았다. 별도 원문 대조에서도 앞서 발견한 성품 전제·지원 주체 오류가 남지 않았음을 확인했다.

### 5.3. 버전과 검증 범위 구분

- 새 동료 사례의 전체 최종 생성은 **v3.19를 로드한 서버**에서 실행했다.
- 생성 도중 적용한 v3.20 수정 경로는 **별도의 실제 모델 대조와 서비스 경로 회귀 검사**로 검증했다.
- 저장 완료 후 **v3.20 서버로 재시작**해 새 기록과 기존 가족·동료 기록의 해시가 같은지 확인했다. 이 재열기에는 새 모델 호출이 없었다.
- 새 동료 사례에서는 상황 설명 문항이 자동 생략되어 전화 고장에 관한 정정이 전달되지 않았다. 이 실행을 해당 정정의 검증 사례로 세지 않는다.
- 이전 동료 기록은 실패 분석용으로 보존했다. 다시 열렸다는 사실이 과거 내용 오류까지 수정됐다는 의미는 아니다.

## 7. 실행 설정과 남은 확인 범위

새 로컬 설치의 기본 조합은 다음과 같다. 별도 검토 모델에는 검토 전용 옵션을 따로 적용한다.

```dotenv
MODEL_BASE_URL=http://127.0.0.1:11434/v1
MODEL_NAME=gemma4:12b
MODEL_PROTOCOL=relationship_agent
MODEL_STATE_MODE=combined_blocks
MODEL_AGENT_FORMAT=json_schema
MODEL_REASONING_EFFORT=none
MODEL_STREAM_JSON=true
MODEL_STREAM_COMPLETE_JSON=true
MODEL_TIMEOUT_MS=0
```

설정 확인 명령은 `app/`에서 실행한다.

```sh
npm run check:model
npm run check:model -- --generate
```

첫 명령은 설정을 검사하고, 두 번째는 합성 입력으로 실제 모델 생성을 검사한다. 인증이 필요한 API의 키는 서버 환경에서 별도로 관리한다.

실제 확인한 범위는 Mac·허용된 LAN Ollama의 생성, Docker의 설정·합성 모델 연결, 정상 API의 저장·격리·재열기다. 상용 API별 실제 인증·전체 생성, 다른 운영체제의 전체 앱 실행은 아직 검증하지 않았다. 모델·서버·입력에 따라 내부 수정이나 재시도로 지연될 수 있으며, 모든 입력에서 오류가 발생하지 않는다는 보증은 아니다.
