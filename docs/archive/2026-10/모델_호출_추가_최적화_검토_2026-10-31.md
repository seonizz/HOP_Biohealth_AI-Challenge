# O4 이후 추가 모델 사용 최적화 검토

**추가 반영:** 토큰 한도 조회 재사용·최종 검토 입력 축소·지적 필드만 품질 수정·GPU overlay 설정 연결도 구현하고 독립 검토 후 수정했다. 최신 계약과 검증은 [미적용 최적화 후속 반영](../../../app/docs/REMAINING_MODEL_OPTIMIZATIONS.md)을 따른다. 정상 O4는 GET 15→2회, POST 18회 유지다. 실제 GPU 배포와 combined 비교 채택은 승인·실검증 전이며, 아래 표는 당시 후보 조사 기록이다.

**후속 구현:** 사용자가 선택한 공통 지시 중복 제거·null 이름 블록 생략·단계별 입력 축소를 구현하고 독립 검토·전체 로컬 검사를 완료했다. 최신 적용 조건과 결과는 [모델 입력 최적화 구현 기록](../../../app/docs/MODEL_INPUT_OPTIMIZATION.md)을 따른다. 아래 후보 비교 수치는 구현 전 조사 기록이다. combined 전환·capability 조회 캐시는 이번 구현에 포함하지 않았다.

2026-10-31 KST. 현재 `app/`와 별도 runtime 후보를 읽고 합성 요청으로 비교했다. **앱 코드·설정·실행 서비스는 변경하지 않았다. GPU 서버·SSH·실제 DB·GPU 추론도 사용하지 않았다.** 기존 검토, 질문 생략, 원문·저장 계약, 카드 디자인과 기본 총 시간 제한 0을 유지하는 후보만 우선한다.

## 1. 결론과 우선순위

가장 큰 호출 절감 후보는 이미 있는 **답변 통합 생성 `combined`의 비교 검증**이다. 그와 별도로 중복 지시 제거와 출력이 상수로 확정된 블록 생략은 좁은 범위로 구현할 수 있다. 정상 최종 생성 18회의 검토 14회는 그대로 둔다.

| 우선순위 | 후보 | 기대 효과·확인 결과 | 상태와 조건 |
| --- | --- | --- | --- |
| P1·효과 비교 우선 | 답변 `combined_blocks` → 기존 `combined` | 정상 **6~7→3~4회**, 답변당 **3회 감소** | 기존 구현 활용. 실제 모델의 구조 실패·의미 반려·총 토큰 비교 후 채택 |
| P1·작은 수정 | 대화문 수정의 공통 지시 중복 제거 | 합성 수정 요청당 **5,545 bytes 감소 가능** | `COMMON + SPEAK`의 SPEAK 안에 이미 COMMON이 있음. 지시 내용·검토 유지 |
| P1·작은 수정 | 이름 스키마가 정확히 null인 블록 생략 | 해당 블록 경로의 답변당 **1회 감소 후보** | 현재 schema가 `{type:'null'}`로 확정된 경우만. 이름 추정·턴 간 캐시와 구분 |
| P1·기존 후보 이식 | 단계별 불필요 질문 지시·입력 제외 | 합성 사례 요청 body **16.2% 감소**, 호출 7회 유지 | runtime에 이미 있음. 원문·상태 근거·모든 검토 입력 보존 후 현재 앱에 통합 검증 |
| P1·부가 요청 축소 | operation 안의 토큰 한도 조회 재사용 | 정상 O4의 capability **GET 15→2회 목표**, 모델 POST 18회 유지 | writer/reviewer 각각 한 번. readiness 검증·모델별 한도 분리 유지 |
| P2 | 검토 입력의 동일 script 복사본·타 카드 전용 지시 축소 | 합성 O4 정상 요청 메시지 **1.60% 감소**, 18회 유지 | runtime의 좁은 compact 옵션 활용. claims·원문·전체 검토 유지 |
| P2 | 품질 개선에서 지적 필드만 한 번에 재작성 | 출력량·불필요한 다른 카드 변경 감소 여지 | 현재 추가 호출 **+2회 유지 목표**. 필드마다 호출을 나누지 않음 |

호출 감소, body/message 바이트 감소, capability GET 감소는 다른 지표다. 위 절감률을 합산하거나 GPU 시간·토큰 감소율로 사용하지 않는다. `combined`와 블록 전용 개선은 적용 경로가 겹치므로 동일 답변에 절감 횟수를 모두 더하지 않는다.

현재 9060 서비스는 별도 복사본의 생략 모드이며 O4 전체 기능 실행본과 다르다. 우선 같은 소스·같은 기능의 기준선을 정해야 한다. **13회 생략 모드와 검토·저장 상세를 유지한 18회 O4를 성능만으로 비교하지 않는다.** GPU 전용 실행본의 적용·실험은 별도 사용자 승인 후 수행한다.

## 2. 답변 통합 생성의 효과와 실패 비용

`combined`는 네 블록의 작성을 한 요청으로 묶고, 기존 상태·질문·안전 검토를 계속 실행한다. 검토 호출을 없애는 옵션이 아니다.

| 조건 | 답변 처리 호출 |
| --- | ---: |
| `combined_blocks` 정상 | 6~7 |
| `combined` 첫 작성 성공 | 3~4 |
| `combined` 한두 번의 요청 수정 후 성공 | 4~6 |
| 통합 작성이 구조 오류로 3회 실패하고 블록 경로가 정상 성공 | 9~10 |

통합 구조 오류가 첫 번에 발생했다고 바로 블록으로 전환하지 않는다. 현재 코드에서는 3 attempts를 소진한 뒤 fallback한다. 따라서 실제 실패 사례까지 포함해 비교해야 한다. 단순히 첫 성공 또는 3회 실패 후 정상 fallback만 존재한다고 가정하면 `3 + q + 6p`회다(q는 질문 검토 0/1, p는 fallback 비율). 이 제한된 계산에서 p<50%가 호출 수 손익분기지만, 의미 반려·재시작·입출력 토큰을 포함한 채택 기준은 아니다.

답변 10회 + O4 최종 18회 + 기관 분류 2회, 보완·오류 없음의 예:

| 비교 | 전체 상담 |
| --- | ---: |
| O4 + `combined_blocks` | 80~90회 |
| O4 + `combined` | 50~60회 |
| **동일 질문 검토 조건의 차이** | **30회 감소, 33.3~37.5%** |

모델이 질문을 다르게 생략하거나 추가 질문을 만들면 답변 제출 횟수도 바뀐다. 고정된 답변·검토 조건의 비교와 실제 대화 전체의 완료율·호출량을 따로 보고한다. 실패·중단 사례를 분모에서 제외하지 않는다.

## 3. 작고 명확한 두 개선

### 공통 지시 중복

`repairCard()`는 대화문 수정에 `COMMON + SPEAK`를 사용한다. `SPEAK` 자체도 `COMMON`으로 시작해 같은 지시가 두 번 들어간다. 합성 O4 대화문 수정 요청에서 COMMON 2개를 확인했고, 그중 하나는 **5,545 UTF-8 bytes**였다. 해당 system prompt 15,763 bytes의 약 35.2%다. 이는 수정 요청의 system prompt 기준이며 정상 18회 전체 입력 감소율이 아니다.

수정 방법은 이미 COMMON을 포함한 SPEAK/WRITE에는 다시 붙이지 않고, 카드별 짧은 역할 지시에는 기존처럼 붙이는 것이다. 원래 지시 한 벌, 스키마, 수정 지적·거절 출력, 원문, 독립 검토는 유지해야 한다.

### null로 확정된 이름 블록

현재 `nameIndexSchema()`는 이름 원문이 없거나 답변되지 않았으면 정확히 `{type:'null'}`을 반환한다. 하지만 `generateDraftBlocks()`는 이때도 이름 블록을 모델에 묻는다. 이 경우의 null은 새 사실이나 추정이 아니라 기존 스키마의 유일한 허용값이다.

해당 경우만 이름 요청을 생략하고 기존 검증을 거쳐 null을 전달하면 combined_blocks의 생성 1회를 줄일 수 있다. 질문 생략 판단·상태 검토는 계속 수행한다. 이름이 답변된 nullable schema, 짧은 호칭 enum, 다른 답변에서 생긴 정정은 별개이며 임의로 이름을 확정하거나 이전 이름을 재사용하지 않는다. 해당 조건의 발생 빈도는 아직 측정하지 않았다.

## 4. 합성 입력 크기 비교

### 답변 블록의 질문용 입력 제외

별도 runtime의 `stageScopedQuestionRules`와 `blockScopedInputs`를 함께 켠 같은 합성 사례를 비교했다. 첫 세 생성 블록에서 해당 단계가 결정하지 않는 질문 지시·후보·질문용 retrieval을 제외하고, 이름에는 이름 전용 지시를 사용한다. 전체 원문, 상태 retrieval, 선행 생성값, 수정 지시는 보존한다.

| 단계 | 기존 POST body bytes | 후보 POST body bytes |
| --- | ---: | ---: |
| 상태 작성 | 31,834 | 26,102 |
| 이름 작성 | 30,853 | 11,601 |
| 관계 작성 | 37,368 | 31,636 |
| 질문 작성 | 33,439 | 33,439 |
| 상태 검토 | 29,419 | 29,419 |
| 질문 검토 | 14,141 | 14,141 |
| 안전 검토 | 12,203 | 12,203 |
| **합계** | **189,257** | **158,541** |

감소량은 **30,716 bytes·16.2%**다. 호출 7회와 검토 입력을 유지하고 기능 메타데이터를 제외한 반환값도 같았다. 이는 합성 fixture 한 건의 직렬화된 body 크기이며 토큰·실제 모델 출력 품질 검증이 아니다. 현재 `app/`에는 해당 옵션이 없으므로 그대로 켤 수 없다. 기존 후보를 통합할 때 현재 O4·근거 전송·복구 수정과 충돌을 확인해야 한다.

### 최종 검토 입력 축소

현재 입력은 같은 대화문을 최상위 `script`와 `guide.script`에 모두 담기도 한다. 기존 runtime 후보는 두 값이 완전히 같을 때 한 복사본을 제거하고, 단일 카드 검토에서 다른 카드에만 해당하는 지시를 제외한다.

합성 O4 정상 18요청에 이 투영을 적용한 **메시지 내용**은 **323,968→318,776 bytes**, 5,192 bytes·1.60% 감소했다. 위 답변 표의 전체 POST body와 측정 범위가 다르다. `guide`·`claims`·문장 ID는 각각 검토 계약이 있으므로 내용이 비슷하다고 삭제하지 않는다. 원문과 retrieval의 중복을 더 줄이는 공통 출처표는 별도 설계·검증 대상이다.

## 5. 토큰 한도 조회·품질 개선

별도 reviewer와 한도 발견을 켠 실제 Gateway + mock HTTP의 정상 O4에서 **writer GET 1/POST 4, reviewer GET 14/POST 14**를 확인했다. 검토마다 자식 operation이 열리며 한도를 다시 조회한다.

우선 부모 operation 범위에서 writer/reviewer 각각 capability를 한 번 확인해 **GET 15→2**를 목표로 한다. 같은 목적지·모델·인증·worker identity가 보장되면 공유 가능성을 추가 검토하되, 다른 검토 모델의 한도를 생성 모델에 섞지 않는다. 오류·한도 변경·worker 교체 시 무효화하며, 인증/일시 실패를 정상 값으로 캐시하지 않는다. **준비 상태나 취소 종료를 캐시하지 않고 실제 dispatch의 readiness 확인을 유지한다.** 기존 bridge가 이 경계를 보장하지 않으면 적용하지 않는다. 모델 생성 POST는 여전히 18회다.

품질 개선은 현재 한 필드만 지적돼도 전체 guide를 다시 출력한다. 한 번의 요청으로 지적된 필드만 출력하고 검증 후 병합하면 나머지 카드의 출력과 내용 변화를 줄일 수 있다. 전체 품질 재검토·교차 카드 검토·발화 상세는 계속 수행하고 수정되지 않은 값의 동일성을 검사한다. 필드 k개를 k회로 나눠 호출 수를 늘리지 않도록 한다. 절감 토큰·수정 실패율은 아직 미측정이다.

## 6. 우선 적용하지 않을 후보

- **O5 전체 검토 2회 제거:** 카드별 검토와 교차 카드 검토의 탐지 범위가 동등하다는 근거가 없다. 최종 18→16회는 현재 권장 적용안이 아니다.
- **턴 간 이름·최종 분석 무조건 재사용:** 원문 정정·부정·화자·목적 변경에 따른 의존성이 크다. 같은 이름 문항만 비교해 생략하지 않는다.
- **질문·안전 검토 생략:** 기존 기능 계약을 바꾸므로 이번 최적화 후보에서 제외한다.
- **기관 독립 2차 분류 제거:** 기존 독립 분류 계약을 유지한다. 같은 결과를 재요청할 때의 기관 캐시와 최종 revision 승계는 이미 구현돼 있다.
- **입력 원문 잘라내기·출력 토큰 일괄 축소:** 근거 손실과 잘림 재시도로 비용이 늘 수 있다. 실제 단계별 소비량·잘림률을 먼저 측정한다.
- **단일 GPU worker에 병렬 요청 증가:** 독립 추론 수용량이 확인되지 않았다. 공통 슬롯·취소 계약을 유지하며 하드웨어 수만으로 병렬 처리 효과를 가정하지 않는다.
- **기존 최적화를 새 성과로 중복 계산:** 공통 원문 `shareInputs`, 구조 복구의 검증된 블록 재사용, 분석 근거 ID 전송, 기관 캐시는 이미 있다. 후보와 기능이 겹치는 절감량을 더하지 않는다.

## 7. 검증과 다음 구현 단위

권장 작업 단위는 (1) COMMON 중복 제거·null 이름 상수 경로, (2) 단계별 입력 범위 후보 통합, (3) capability 조회 범위 정리, (4) 동일 사례의 combined 비교, (5) 품질 개선의 출력 범위 제한이다. 가장 큰 기대 절감은 combined에 있지만 실제 적용 여부는 모델 실패·전체 완료 데이터를 보고 결정한다.

각 변경은 opt-in 또는 좁은 조건으로 분리하고 기존 검토 요청·근거 후보·저장값·질문 생략 동작·취소 경계를 비교한다. 정상 사례뿐 아니라 정정·부정·다른 사람 이름·후속 답변·긴급·형식 오류·의미 반려·중단 사례를 포함한다. 실서버 비교는 같은 모델·원문·옵션으로 수행하며 요청한 전체 사례를 분모로 완료율과 총 호출·토큰을 집계한다.

이번 로컬 검토에서는 답변 복구·검토 검사 75개, runtime 입력·지시 검사 17개, compact 보존 검사 1개, 토큰 정책·검토 라우팅·계측 검사 23개가 통과했다. 겹치는 범위의 수치를 독립 전체 테스트 개수로 합산하지 않는다. 18 POST + 15 GET probe와 위 바이트 비교는 합성 응답을 사용했다.

지침에서 허용한 별도 Ollama 검토 API에도 개인정보·비밀값 없는 설계 요약으로 검토를 시도했으나 `Host is down`으로 결과를 얻지 못했다. 판단 근거는 두 독립 코드 조사와 로컬 검사다. 실제 GPU 모델의 성공률·토큰·시간은 미측정이며, GPU 서버 사용은 사용자 승인 이후다.
