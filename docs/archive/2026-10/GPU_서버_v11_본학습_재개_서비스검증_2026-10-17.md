# v11 본학습·새 프로세스 재개·실서비스 가능성 검증

작성: 2026-10-17 KST · Gemma 31B · RTX 4090 2대 · 주변인 지원 v11 · 출력 예약 8,192

**본학습과 새 프로세스 체크포인트 재개는 실제 GPU에서 통과했다.** 기존 본학습 CLI·루프에 v11 가중 소비기를 연결하고, train 243행을 누락·중복 없이 각 1회 학습했다. 5개 과업의 독립 어댑터를 각각 1에포크 완료했으며 총 32 optimizer step을 수행했다. validation 176행도 전체 평가했다.

**실서비스 판정은 준비 미완료다.** 새 추론 프로세스의 checkpoint 로드·실제 생성·8,192 출력 예약·앱 상태 갱신은 통과했다. 최종 안내는 기존 앱 검증의 600초 operation 제한으로 미완료이며, DB 통합·운영 증거도 미확인이다. 처리시간을 점수나 데이터 품질 감점으로 사용하지 않았으며, 최종 안내의 기능 완료를 증명하지 못했다는 범위만 기록한다.

- 최초 프로세스 A: **PID 2988289**, 36행·5 step. 각 과업의 첫 누적창을 실행하고 저장한 뒤 프로세스를 종료했다.

- 상태 관찰·관계 기억은 각각 6행·1창이므로 A에서 이미 완료됐다. B에서 이 둘은 **복원과 validation만** 수행했다. 신규 업데이트가 있었다고 계산하지 않았다.
- scheduler는 사용하지 않은 고정 learning rate 설정이다. `scheduler_equal=true`는 저장·복원 모두 `None`임을 뜻한다.

- 전체 train 행 순서·고정 seed 3407·full-task 계획 SHA·243개 유리수 계수·실제 float32 upstream gradient를 로그와 독립 재계산으로 대조했다. 누락·중복과 validation 혼입은 0건이다.

검증한 것은 **동일 초기화에서 출발한 5개 독립 어댑터**다. 단일 통합 다중 과업 어댑터, 여러 epoch 수렴, 중단 없이 실행한 별도 GPU 기준선과의 최종 bitwise 일치까지 주장하지 않는다. 위 validation loss는 개발용 CE이며 기존 모델 대비 개선, 생성 품질, 임상적 유효성의 증거가 아니다.

## 3. 가중치와 원문·맥락·분할 보존

실제 행 평균 정답 CE에 곱한 계수는 `K × w_i × n_i / Z`다. K는 전체 과업 train의 계획 창 수, w는 고정 v11 가중치, n은 정답 토큰 수, Z는 전체 과업의 가중 정답 총량이다. A의 일부 행이나 재개 후 남은 행으로 분모를 다시 계산하지 않았고 누적창 크기로 추가 나누지 않았다.

모든 업데이트에서 두 GPU에 유한하고 0이 아닌 gradient가 있었고, 모든 학습 가능 파라미터가 gradient를 받았다. **31/32창에 기존 clip norm 1.0이 적용**됐다. 가중 계수의 정확한 소비를 확인한 결과이며, clipping·AdamW 이후 파라미터 변화량이 원래 가중치 비율과 같다는 주장은 아니다. 최대 preclip norm은 약 91.59였다.

전체 입력 token ID·attention mask·label을 보존하고 원래 접두부를 모두 읽게 했다. 불필요한 prefix 출력 logits만 줄였고 입력 요약·절단·문장 재작성은 하지 않았다. 실제 최단 train의 선택 logits CE와 모델 native causal CE 차이는 약 0.0000023842로 사전 허용 오차 안이었다.

- 기존 419행: train 243 / validation 176을 그대로 유지했다. 대표 교체·재분할·행 복제·추가하지 않았다.
- 전체 재고: 입력 **157,668**, 정답 **17,220**토큰. 이 중 실제 역전파 train 정답은 **9,726**토큰이며 validation 정답까지 학습한 것이 아니다.
- 최대 prefix **3,806**, 정답 **145**, 전체 시퀀스 **3,909**토큰. 모든 행이 4,096 이하다.
- 학습 종료 시 기존 데이터·정책 묶음 **45파일**, 학습 코드 **21파일**, 서비스 코드 **4파일**의 SHA-256·크기가 고정 목록과 일치했다. entries SHA도 변하지 않았다.
- validation은 `eval`·`no_grad`로 수행했으며 adapter 해시와 gradient 불변을 확인했다. validation loss는 이번 실제 forward로 계산했다. 수집기는 해당 행 수·정답 총량·결속을 대조했으며 별도 모델로 loss를 재계산한 것은 아니다.

앞선 419행 전체 실제 토크나이저 재인코딩, 가중 집중도 90/90·총량 20/20 조건은 동일한 입력·정책 해시에 결속된다. 이번 학습에서 원천 전체를 새로 재구축하거나 의미·임상 타당성을 재승인하지 않았다. 무가중 원행 지표는 기존에 공개한 잔여 악화가 그대로이며, 가중 지표 개선을 원행 분포 개선으로 바꿔 표현하지 않는다. ## 4. 서비스 검증 결과

추론은 **PID 2989540**의 새 프로세스에서 수행했다. 5개 최종 checkpoint의 파일·정책·완료 cursor를 검증한 뒤 **상담 어댑터만** 실제 로드했다. 다른 네 어댑터는 manifest admission을 확인했으며 실제 추론 로드나 앱 단계별 선택 라우팅을 검증한 것이 아니다.

서버의 네트워크 설정이나 포트를 바꾸지 않고, 기존 HTTP API 코드를 Mac의 임시 loopback 서버에서 실행해 SSH 표준입출력으로 실제 GPU worker에 연결했다. 실제 `ModelGateway.updateState`·`respond`를 사용했으며 응답 보정·가짜 state 대체·검증기 우회는 하지 않았다. API 키는 메모리·자식 환경에서만 전달했고 요청 timing 원문 logger는 끈 상태로 합성 자료만 사용했다.

| 검사 | 실제 결과 | 판정 |
|---|---|---|
| 새 프로세스 PEFT 로드 | 최종 상담 step 6, 저장 adapter parameter SHA와 로드 결과 일치 | 통과 |
| 잘못된 인증·모델·출력 8,193·미지원 response_format | 각각 401/400, 모델 호출 전에 거부 | 통과 |
| health의 모델·checkpoint 식별 | 고정된 checkpoint·모델과 일치 | 통과 |
| 짧은 생성 | HTTP 200, 입력 29·출력 2토큰 | 통과 |
| `max_tokens=8192` 실제 요청 | HTTP 200, 실제 출력은 2토큰에서 종료 | 예약 계약 통과 |
| 앱 상태 갱신 | 관찰·관계 기억·검토 및 검토 후 재생성 6단계 완료 | 통과 |
| 최종 안내 | 분석·계획·수정·안내 초안·care/doList/avoid까지 검증, `card_next`에서 `MODEL_TIMEOUT / deadline` | 미완료 |
| 정상 종료 | shutdown 응답, worker `stopped`, SSH exit 0 | 통과 |

앱은 17번의 HTTP 요청을 시도했고 **16단계가 실제 앱 스키마·근거 검사를 통과**했다. 나머지 1개 `card_next` 요청은 operation 종료로 취소됐다. 별도의 짧은 생성 2번을 포함한 실제 GPU 요청은 19번이다. 마지막 GPU 요청은 앱의 취소 뒤에도 완료됐다. 앱은 18:50:22 KST에 deadline을 기록했고 worker는 18:50:40경 해당 생성을 끝냈으므로, 이번 SSH 중계 경로에서 클라이언트 취소가 GPU 생성 중단으로 즉시 전파되지 않았음을 확인했다. `guide_write` 초안이 통과한 것을 최종 안내 전체 통과로 표시하지 않았다. 검토 결과에 따른 정상 재작성 단계가 있었으나, 앱 trace에 응답 스키마 오류로 재시도한 기록은 없다.

이 검증의 v11 프로필은 **입력 최대 4,096·출력 예약 8,192·합산 context 최대 12,288**이다. 기존 일반 서비스 설정 파일을 바꾸지 않았다. 앱에서 HTTP 응답을 받은 최대 입력은 3,950토큰, 최대 출력은 798토큰이었다. 8,192토큰 전체 생성이나 더 긴 기존 서비스 입력 범위의 메모리 적합성을 검증한 것은 아니다.

합성 사례 한 건이며 추가 질문 기능을 켜지 않았다. 실제 이용자 자료·다중 사용자·모든 위기 분기·공개 배포·DB 저장/삭제까지 통과한 결과로 확대할 수 없다. 처리시간·속도는 기존 평가 제외 원칙을 유지한다. **최종 안내 미완료를 데이터 품질·생성 품질 실패나 프로젝트 점수 감점으로 바꾸지 않는다.** 기능 완결성은 이번 실행에서 확인하지 못했다.

공개 운영 전에 남은 항목은 다음과 같다.

1. 현재 deadline에서 미완료된 최종 안내의 전체 검증 경로와 요청 취소 전파를 확인해야 한다. 상태 갱신·안내 초안만으로 전체 앱 완료를 선언하면 안 된다.
2. 5개 독립 어댑터의 실제 사용 정책이 필요하다. 이번에는 상담 어댑터를 단일 endpoint에 연결했으며, 상태 관찰·관계 기억 어댑터로 자동 전환하지 않았다. 임의의 LoRA 합치기나 새 과업 혼합 정책을 도입하지 않았다. 데이터 계약도 `supporter_policy_tasks; not the complete relationship_agent wire schema`임을 명시한다.
3. 실제 DB 통합 60개 검사와 보관·삭제·백업·배포 운영 증거를 갖춰야 한다. 현재 운영 검사 결과는 준비 미완료다.
4. 기존 API의 일반 실행 경로는 timing 로그에 입력·출력을 기록할 수 있다. 이번 검증은 해당 logger를 껐지만 운영 경로의 로그 최소화·보관·삭제까지 수정·검증한 것은 아니다.

따라서 제한된 학습→checkpoint→추론→앱 상태 갱신 경로는 실제로 동작한다. 현재 자료만으로 전체 실서비스 준비 완료를 선언할 수 없다.

## 5. 서버 경계와 메모리

기존 가상환경을 재사용했다. 버전은 PyTorch 2.13.0+cu126, Transformers 5.17.0, PEFT 0.21.2, bitsandbytes 0.50.2다. NF4 4비트, BF16, SDPA, gradient checkpointing, LoRA rank/alpha 8, dropout 0, 학습 가능 파라미터 61,214,720개, microbatch 1·누적 최대 8행, AdamW lr 2e-5·weight decay 0.01 설정이다. 60개 층을 두 GPU에 28/32개로 나눴으며 CPU·disk offload를 쓰지 않았다.

각 GPU 총 메모리는 24,564 MiB다. 위 값은 PyTorch allocator 통계이며 드라이버 전체 최대 점유와 같지 않다. 이번 실제 길이의 학습에서는 OOM이 없었고 더 큰 입력·batch·rank·출력에 대한 보장은 아니다.
