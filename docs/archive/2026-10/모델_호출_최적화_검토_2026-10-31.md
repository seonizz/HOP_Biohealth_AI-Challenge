# 모델 호출 최적화 검토

O4 이후의 추가 후보·합성 입력 크기 비교·우선순위는 [추가 최적화 검토](모델_호출_추가_최적화_검토_2026-10-31.md)에 정리했다. 답변 통합 생성, 중복 지시 제거, 상수 이름 블록 생략, capability 조회 재사용을 검토·저장 유지 조건으로 비교한다.

그중 공통 지시 중복 제거·null 이름 블록 생략·단계별 입력 축소의 후속 구현과 검증은 [모델 입력 최적화](../../../app/docs/MODEL_INPUT_OPTIMIZATION.md)를 따른다. 기존 검토·저장 계약과 상태 모드는 유지하며 GPU 서버에는 적용하지 않았다.

- 작성일: 2026-10-31, KST
- 기획 전제 수정: 사용자의 후속 요청에 따라 **모든 모델 추론은 서버 GPU만 사용**한다. 생성·검토·안전 판단·기관 분류·수정 재생성 모두 포함한다.
- 목적: 서버 GPU의 공통 자원으로 모든 추론을 처리하면서 불필요한 생성·검토·재시도·입력 토큰을 줄일 지점과 검증 조건을 정리한다.
- 범위: 현재 `app/` 코드, 별도 GPU용 실행본, 같은 대화에서 확인한 실행 상태. 초기 기획과 후속 구현 기록을 함께 보관한다. P0와 O4는 소스·로컬 검사까지 완료했고 실행 설정·서버 배포는 변경하지 않았다.
- 실행 상태 기준: 2026-10-31 21:11 KST의 읽기 전용 조회는 **변경 전 구성의 기록**으로 보존한다. 목표 구성의 적용·가동 증거가 아니다. 초기 호출 횟수는 코드의 정상 경로 계산값이다. 후속 O4의 26/18회 비교는 mock HTTP 검사로 확인했으며 실제 GPU 호출 기록이 아니다.
- 재검토 반영: 서버 API 요청 형식, 물리 요청별 슬롯, 원격 취소 완료, 카드별 오류 전달의 네 가지 구현 선행조건을 추가했다. 무추론 요청 계약 검사 4개로 형식 호환성을 대조했다.

## 1. 핵심 판단

1. **검토 주소만 서버로 변경하면 현재 API에서는 실패한다.** 기존 GPU API는 `response_format`, `reasoning_effort`, streaming을 지원하지 않는다. 검토 기본 요청을 실제 validator에 넣어 거절을 재현했다. 먼저 요청 형식·인증·모델명을 맞춘 뒤, 생성·검토·분류가 공통 슬롯을 사용하도록 한다. GPU 슬롯은 operation 전체가 아니라 물리 요청 하나에만 부여한다.
2. **전체 초안을 만든 뒤 다섯 카드를 다시 생성하는 부분이 가장 큰 생성 중복이다.** 기존 초안을 카드별로 검증·검토하고 필요한 카드만 고치는 O4를 명시적 활성화 옵션으로 구현했다. 정상 경로 26→18회와 대화 전략·검토 14회·저장용 상세 유지가 로컬 검사에서 확인됐다. 실제 서버 적용은 승인 후 별도 검증한다.
3. **카드별 검토와 전체 검토는 일부 겹치지만 범위가 완전히 같지는 않다.** 원문·전략·카드·검토 정책이 동일한 경우에만 항목별 승인을 재사용하고, 카드 간 모순을 보는 최종 통합 검토는 남긴다. 전체 검토만 반려한 사례를 수집해 누락을 확인하기 전에는 두 호출을 제거하지 않는다. 16회는 조건부 계산값이며 채택된 구현 목표가 아니다.
4. **9070 실행본에는 이미 재시도 예산과 프롬프트 축소 기능이 있다.** 기본 `app/`에 없는 기능을 새로 설계하기 전에 기존 후보의 테스트·호환성을 확인한다. 모든 앱이 무제한 전체 재시도를 한다는 이전 설명은 정확하지 않다. 다만 사용자가 기본 총 처리 시간 제한을 제거하도록 지정한 계약은 유지하며, 후보의 deadline을 기본값으로 옮기는 것은 별도 정책 변경이다.
5. **13회 생략 모드를 그대로 기본 서비스에 적용하는 것은 권하지 않는다.** 검토는 유지하지만 대화 전략·품질·발화 상세를 생략한다. 특히 저장용 `conversation_detail` 계약까지 동등하게 보존한다고 볼 수 없다.

호출 수 감소, 입력 토큰 감소, 실패 감소, 지연시간 감소는 별도 지표다. 호출 수가 절반이 되어도 지연시간이나 품질이 같은 비율로 변한다고 주장하지 않는다. 이 문서의 성능 측정은 운영 최적화를 위한 것으로, 프로젝트 평가에서 제외한 모델 성능·처리시간을 평가 점수에 다시 반영하지 않는다.

## 2. 변경 전 실행 기록과 서버 GPU 전용 목표

### 2.1 변경 전 실행 기록

아래 표의 로컬 Ollama 경로는 당시 관측값이다. 개정 기획의 추론 경로에 포함하지 않는다.

| 앱 | 생성 경로 | 검토 경로 | 최종 경로 | 확인 수준 |
| --- | --- | --- | --- | --- |
| 9000 | 로컬 Ollama 11434, `gemma4:12b` | 같은 로컬 Ollama | 전체 | 실행 프로세스의 허용된 환경 항목과 앱 health 확인 |
| 9050·9051 | 로컬 18080 브리지 → SSH → GPU 31B | 로컬 Ollama 11434 | 전체 | 실행 프로세스 설정·브리지 health 확인; 현재 원격 생성 성공 미검증 |
| 9052 | 18081 추적 프록시 → 18080 → GPU 31B | 18082 추적 프록시 → 로컬 11434 | `skipFinalExtras=true` | 프로세스 설정·프록시 경로 확인; 현재 원격 생성 성공 미검증 |
| 9070 | 설정 파일상 18090 → GPU 31B | 설정 파일상 로컬 11434 | `skipFinalExtras=true` | 실행 스크립트와 그 설정 파일 대조; 18090 연결 거부 |

GPU 요청 모델명은 `malssi-gemma4-31b-v11-epoch3`이다. 요청 모델명이나 과거 연결 증거만으로 현재 로드된 가중치의 동일성을 확정하지 않는다. 9070 설정은 실행 진입 파일이 읽는 현재 파일 기준이며, 시작 이후 파일이 바뀌었을 가능성까지 배제한 프로세스 내부 상태 덤프는 아니다.

같은 시점의 원격 조회에서는 RTX 4090 두 대가 각각 11 MiB·30 MiB, 사용률 0%였고 GPU 연산 프로세스가 없었다. 18080 브리지의 `/healthz`는 `ready`를 반환했지만, 구현상 원격 worker의 생존 여부를 매번 검사하지 않는다. 브리지가 지정한 기존 SSH 공유 소켓도 없었다. 소켓 부재만으로 새 SSH 연결까지 반드시 실패한다고 단정할 수는 없으며, 자동 재연결·생성은 실행하지 않았다.

따라서 현재 자료로는 실제 GPU 처리량·429 발생률·단계별 지연시간을 계산할 수 없다. 본 작업에서는 모델 기동·종료·원격 변경을 하지 않았다.

### 2.2 목표 구성 — 모든 모델 추론을 서버 GPU에서 수행

| 구분 | 목표 실행 위치 | 역할·경계 |
| --- | --- | --- |
| 브라우저·앱·DB·HTTP/SSH 중계 | 현재 Mac 등 비추론 계층 유지 가능 | UI, 저장, 요청 전달, 규칙 기반 검증. Mac CPU/GPU에서 모델 추론하지 않음 |
| 상태·이름·관계·질문·카드·상세 생성 | 서버 GPU | 생성 Gateway의 모든 stage |
| 상태·질문·안전·분석·카드·최종 검토 | 서버 GPU | 검토 Gateway도 서버 GPU endpoint 사용 |
| 기관 안내 1차·독립 2차 분류 | 서버 GPU | 기본 생성 Gateway 또는 서버 GPU에 있는 별도 분류 endpoint |
| 수정 재생성·JSON 복구·재시도 | 해당 서버 GPU endpoint | 실패 시 Mac/LAN Ollama로 자동 전환하지 않음 |
| 모델을 사용하는 후속 실검증 | 서버 GPU | 로컬에서 수행하는 mock·정적 검사는 모델 추론이 아니므로 유지 가능 |

논리 경로는 `앱 → 공통 추론 대기열/중계 → 서버 GPU → 코드 검증·저장`이다. 로컬 loopback 주소가 중계 목적지인 것은 허용하지만, 최종 추론 backend가 서버 GPU인지 끝까지 추적한다.

- 초기 비교 구성은 **서버에 상주한 기존 31B 모델 하나를 생성·검토의 별도 역할로 호출하는 안**으로 둔다. 검토 요청의 프롬프트·스키마·원문·승인 조건은 유지한다. 현재 31B가 모든 검토 schema와 의미 검토를 통과한다는 검증은 없으므로 전환 전 확인이 필요하다.
- 동일 모델의 별도 호출은 생성과 분리된 검토 절차이지, 서로 다른 모델의 독립 판단을 보장하는 것은 아니다. 생성기의 자체 승인으로 대체하지 않으며, 기존 오류 반려 사례를 같은 서버 모델 검토로 다시 확인한다.
- 두 GPU를 생성 1대·검토 1대로 고정 배정하지 않는다. 31B가 두 장에 걸쳐 적재될 수 있으므로 가중치·KV 메모리·요청 수용량 검증 없이 두 모델 상주나 병렬 추론을 가정하지 않는다.
- 서버에 검토 모델을 따로 배치하는 안은 후속 선택지다. 모델 변경·추가 적재를 이 기획 수정에서 실행하지 않으며, 물리적으로 독립된 추론 용량이 확인될 때만 동시성을 높인다.
- `MODEL_*`, `MODEL_REVIEW_*`, 선택적 `REFERRAL_MODEL_*`의 최종 목적지를 서버 GPU로 맞추는 것이 후속 구현 범위다. 기존 로컬 검토 설정을 그대로 둔 채 서버 전용으로 전환됐다고 판단하지 않는다.

### 2.3 전환 시 기준선 재설정

전체 경로의 논리 호출 수는 26회로 같지만, 변경 전 혼합 구성의 **GPU 생성 12회 + 로컬 검토 14회**가 목표 구성에서는 **서버 GPU 26회 + 로컬 추론 0회**가 된다. 서버 부하는 늘 수 있으므로 기존 혼합 구성의 지연시간을 서버 전용 구성의 기준값으로 사용하지 않는다.

먼저 서버 전용·최적화 전 경로를 기준으로 측정하고, 같은 모델·자원 조건에서 O4·O5를 비교한다. 검토 모델의 실행 위치와 모델 자체가 바뀌는 효과를 호출 최적화 효과와 분리한다.

### 2.4 P0 선행조건: 현재 GPU API의 요청 형식

현재 18080 브리지가 사용하는 `ai/trained_model_api/server.py`의 `validate_request`는 다음 필드만 받는다: `model`, `messages`, `max_tokens`, `temperature`, `top_p`, `stream`, `n`. `stream`은 false, `n`은 1만 지원한다. 검토 Gateway의 기본 `json_schema`·`reasoningEffort:none`은 각각 `response_format`·`reasoning_effort` 필드를 보내므로 그대로는 HTTP 400 대상이다.

| 항목 | 현재 GPU API용 기획 프로필 | 보존·검증 조건 |
| --- | --- | --- |
| 오케스트레이션 | `MODEL_PROTOCOL=relationship_agent` 유지 | `json_prompt` 프로토콜로 바꿔 다단계 검토를 없애지 않음 |
| 모델명 | 실제 서버의 model ID와 일치 | 기존 검토의 `gemma4:12b` 이름만 남으면 31B endpoint가 거절 |
| 생성·검토의 agent format | 각각 `prompt` | response_format 필드 생략. user payload의 `output_schema`와 모든 로컬 validator는 유지 |
| reasoning effort | 각각 `omit` | `none`도 필드를 보내므로 호환되지 않음 |
| stream·complete JSON stream | 모두 false | `stream:true`와 `stream_options`를 보내지 않음. 부분 카드는 stage 완료 후 표시 |
| 인증 | 해당 서버 브리지에 유효한 인증값 | 로컬 Ollama용 기본값을 그대로 쓰지 않음. 비밀값은 문서·로그에 복사하지 않음 |
| 별도 기관 분류 endpoint | 같은 방식으로 capability 확인 | 생성 설정과 같다고 추정하지 않고 실제 request body 검사 |

설정 이름은 생성의 `MODEL_AGENT_FORMAT`, `MODEL_REASONING_EFFORT`, `MODEL_STREAM_JSON`, `MODEL_STREAM_COMPLETE_JSON` 및 검토의 대응하는 `MODEL_REVIEW_*`다. 이 표는 설정 변경을 실행한 기록이 아니라 기존 브리지에 맞춘 전환 후보다.

`prompt`는 서버 측 JSON grammar 강제를 제공하지 않으므로 형식 실패율이 증가할 수 있다. schema를 프롬프트에 포함하는 것과 서버가 출력을 강제하는 것을 구분한다. 생성·검토·안전·기관 분류의 실제 요청을 계약 검사한 다음, 서버 GPU 실검증으로 형식 통과율과 잘못된 승인 반려를 별도로 확인해야 한다. Structured Outputs·streaming을 서버에 추가하는 방법은 별도 구현 과제다.

| 네트워크 없는 검토 요청 probe | 결과 | 해석 |
| --- | --- | --- |
| 기본 `json_schema` + `none` | `reasoning_effort`, `response_format` 거절 | 주소·모델명만 바꾸는 전환은 불가 |
| `prompt` + `omit` + nonstream + 서버 model ID | 수용 | 요청 형식만 호환됨. 모델 출력 성공·의미 검토 성능 증거 아님 |
| `prompt` + `omit` + stream | `stream_options` 거절 | streaming 필드를 제거해도 `stream:true`는 API에서 별도로 거절 |
| 호환 형식 + 기존 `gemma4:12b` model ID | 모델명 불일치 거절 | 역할별 모델 설정도 함께 확인 필요 |

## 3. 서버 GPU 전용 기획의 호출 수 기준선

이 절의 생성·검토 구분은 **역할 구분**이다. 두 역할의 모든 호출이 서버 GPU 자원을 사용하며, 로컬 모델 호출은 0회다. 실제 라우팅 전환은 아직 수행하지 않았다.

### O1. 준비 상태를 연결 상태·모델 상태로 나누기

- 생성·검토·안전·기관 분류·복구 호출의 최종 backend가 모두 서버 GPU인지 확인한다. 중계 주소와 물리 추론 목적지를 구분하고, 서버 장애 때 로컬 모델로 넘어가는 fallback은 두지 않는다.
- 2.4절의 실제 요청 계약 검사를 선행한다. 인증·지원하지 않는 필드·모델명 불일치는 재시도로 고칠 수 없는 설정 오류로 분리한다. 검토기의 서버 승인·거절 의미는 요청 형식 수용과 별도로 검증한다.
- 앱 `/health`의 `model_configured`는 설정 존재, 브리지 `/healthz`의 `ready`는 현재 구현상 정적 메타데이터 응답임을 구분한다.
- 내부 진단에서 마지막 worker 확인 시각, worker 생존, 최근 확인한 모델/checkpoint identity, 요청 수용 가능 여부를 구분해 기록한다. API 키·상담 원문·전체 프롬프트를 기록하지 않는다.
- 연결 실패를 생성 결과 오류와 구분하고, endpoint가 불가한 동안 각 stage가 독립적으로 복구를 반복하지 않도록 짧은 실패 차단과 제한된 재확인을 검토한다. 정상 회복 시 차단을 해제한다.
- health 확인 자체로 모델을 로드하거나 학습을 시작하지 않는다. 잘못된 포트·오래된 소켓을 임의의 다른 서버로 우회하지 않는다.
- 9070의 18090 연결 불가를 해소하기 전에는 최종 생성 최적화의 지연시간을 비교하지 않는다.

검증: 모든 역할의 실제 서버 GPU 목적지, 로컬 모델 요청 0회, worker 없는 상태의 false-ready 방지, 끊김 후 복구, 잘못된 모델 identity, 인증 오류, 준비 상태 확인 중 취소. 503 같은 상태 코드가 최상위 무한 재시도로 증폭되지 않는지도 함께 확인한다.

### O2. 생성·검토·분류가 서버 GPU의 한도를 함께 사용하기

앱은 카드 worker 3개를 사용하지만 GPU HTTP 서버는 `BoundedSemaphore(1)`이며 점유 중 새 요청에 429·`Retry-After: 5`를 반환한다. 서버 GPU 전용 구성에서 이 슬롯은 생성·검토·기관 분류가 공유한다. RTX 4090이 두 대라는 사실이 HTTP 요청 두 개를 동시에 처리한다는 뜻은 아니다. 실제 429 빈도는 아직 측정하지 않았다.

- 기본 동시성은 **물리 backend 전체에서 1개**로 둔다. 생성 1개와 검토 1개를 각각 허용해 합계 2개가 되는 구조를 피한다. logical Gateway 객체가 달라도 같은 worker·모델 자원을 쓰면 슬롯을 공유한다.
- 이미 생성된 카드의 검토를 다음 불필요한 생성보다 먼저 처리하는 순서를 비교한다. 검토 통과 뒤 부분 표시하는 계약은 유지하며, 한 대화의 긴 작업이 다른 대화를 무기한 밀어내지 않도록 대화 간 공정성을 함께 설계한다.
- 안전 검토는 실행 중 작업을 강제로 중단하기보다 대기 중 작업의 우선순위로 처리한다. 선행 원문·초안이 준비되기 전에 검토를 실행하거나 필수 선행 검토를 건너뛰지 않는다.
- 기존 카드 worker 3개는 논리 작업 준비를 할 수 있지만, 실제 추론 요청은 공통 scheduler에서 직렬화한다. 단일 슬롯에서 생성과 검토를 겹쳐 실행해 얻는 성능 향상을 가정하지 않는다.
- 18080과 18081은 같은 물리 backend다. URL 문자열이나 생성/검토 역할이 다르다는 이유로 별개 대기열 용량을 부여하지 않는다.
- 여러 앱이 동시에 사용하는 상황에서는 프로세스 내부 semaphore만으로 부족하다. 공용 브리지에서 제한된 취소 가능 대기열을 제공하거나, 우선 검증 시 하나의 앱만 해당 backend를 사용하도록 실행 범위를 통제한다. 다른 작업 프로세스를 임의로 종료하지 않는다.
- 대기열 크기를 제한하고 취소된 작업은 실행 전에 제거한다. 대기 deadline은 명시적으로 제한된 후보 operation에서만 공유하고, 기본 총 시간 제한 제거 계약에 새 제한을 몰래 추가하지 않는다. 대기 중인 작업을 이미 추론 중인 것으로 표시하지 않는다.
- 서버 GPU에 독립 worker를 여러 개 상주시킬 수 있음이 검증된 경우에만 worker별 수용량으로 확장한다. GPU 수나 포트 수를 독립 용량의 근거로 사용하지 않는다.

예상 효과는 **정상 논리 호출 수 감소가 아니라 429 요청·대기·재시도 감소**다. 점유 시간과 queue time을 분리해 측정한다.

**대기열의 소유 위치와 슬롯 수명**

- 공용 GPU 브리지를 물리 자원 admission의 단일 책임 지점으로 둔다. 앱 Gateway는 stage 의존성·취소·예산을 전달하며, 별도의 장기 permit을 잡고 브리지 대기열을 기다리지 않는다. 프록시·앱마다 독립 semaphore를 추가해 합산 용량이 늘어나는 구조를 피한다.
- permit은 **한 번의 실제 추론 요청**에만 부여한다. 원격 완료를 확인한 뒤 반환하고, 후속 검토·repair는 새 요청으로 대기열에 넣는다. `agentComplete`가 검토 Gateway의 nested operation을 기다릴 수 있으므로 operation/card worker 전체에 permit을 잡으면 같은 슬롯을 재획득하며 교착할 수 있다.
- capability GET, 로컬 validator, retry backoff, 다음 stage 준비 중에는 추론 permit을 보유하지 않는다. 429 재시도도 다른 작업의 슬롯을 보유한 채 기다리지 않는다.
- 요청 크기·인증·stage 유효성은 queue 진입 전에 확인한다. 대기 항목 수와 입력 바이트 합계를 모두 제한하고, 취소·소유자 만료·revision 변경을 dequeue 직전 다시 확인한다. 포화 시 제한된 응답·대기를 사용하며 새 총 처리 시간 제한을 기본값에 추가하지 않는다.
- `queued`와 `upstream_dispatched`를 구분해 기록한다. queue에서 취소된 항목을 실제 GPU 요청으로 집계하지 않는다. 물리 요청 예산은 검증된 dispatch 시점에 소비하며, HTTP 400·429처럼 실제 보낸 요청은 별도로 센다. 기존 논리 family 계수와의 매핑도 테스트한다.

**취소는 로컬 연결 종료와 원격 추론 종료를 구분한다.** 현재 `local_live.py`는 연결 종료 시 cancel을 보내고 기다리지만, timeout 경로는 cancel 전송 후 예외를 낸다. HTTP 서버의 `finally: slot.release()`만으로 원격 GPU가 이미 멈췄다고 확정할 수 없다.

| 작업 상태 | 의미 | 다음 추론 허용 조건 |
| --- | --- | --- |
| queued | 아직 원격에 보내지 않음 | 취소하면 제거, 물리 요청 0회 |
| running | 해당 request가 원격에서 실행 중 | 원격 완료 확인 전 슬롯 유지 |
| cancelling/draining | 취소 요청·통신 오류 후 종료 확인 중 | cancel 접수 응답만으로 완료 처리하지 않음 |
| completed/failed/cancelled | 해당 원격 작업의 종료 또는 worker 종료 확인 | 늦은 출력 폐기 후 permit 반환 |
| backend unavailable | 원격 종료를 확인할 수 없음 | health 재확인만으로 작업을 중복 전송하지 않음. 요청 상태/worker 종료·idle 확인 후 재개 |

같은 request ID의 종료 증거를 추적해야 한다. 취소 중인 요청을 버리고 새 attempt를 즉시 시작하면 중복 추론 또는 잘못된 응답 연결이 생길 수 있다. 요청 상태·idle 확인이 현재 프로토콜로 불충분하면 그 프로토콜 보완을 선행 구현 범위에 넣는다. 다른 사용자의 PID 종료·GPU reset으로 해결하지 않는다.

### O3. operation 계측과 후보 예산을 분리해 검증하기

- 기존 후보 코드를 우선 검토한다. 같은 기능의 두 번째 구현을 만들지 않는다.
- [기본 시간 제한 제거 기록](../../../app/docs/REFERRAL_GUIDANCE.md)에 따라 기본 `timeoutMs:0` 계약을 유지한다. 후보의 20분·60분 deadline은 기존 격리 옵션의 검증 범위다. 기본 서비스의 총 시간 제한·복구 종료 정책 변경은 호출 계측 최적화와 분리하며, 이 문서를 재도입 허가로 해석하지 않는다.
- 기본 앱에는 우선 operation/family 계수와 종료 사유 계측의 통합 가능성을 검토한다. 제한을 적용하는 후보에서는 JSON 복구, 의미 수정, 전체 restart, 검토 Gateway가 하나의 operation deadline을 공유하는지 확인한다.
- `guide_write`와 `guide_repair`의 이름이 달라도 같은 카드 family 예산을 소비하도록 유지한다. `_after_review` 같은 접미사가 예산을 초기화해서는 안 된다.
- 새 stage 등록 누락은 실제 요청 전에 명확하게 실패시킨다. 정상 경로의 모든 stage가 등록돼 있는지 검사한다.
- 예산 초과는 부분 성공이나 자동 승인으로 처리하지 않는다. 원답변은 보존하고 미완료 결과를 저장 완료로 표시하지 않는다. 명시적 재시도는 새 작업으로 시작하되 중복 요청은 공유한다.
- 질문·안전 검토의 실패를 이유로 기능을 끄거나 미응답 답변을 생성하지 않는다.
- 생성 후 검토가 같은 GPU 슬롯을 기다리는 시간까지 계측한다. 서버 전용 전환으로 늘어난 검토 부하를 생성 모델 장애나 검토 누락의 근거로 삼지 않는다.

### O4. 전체 안내 초안에서 통과한 카드 재사용하기

O4를 끈 기존 full 모드는 `guide_write`가 전체 안내를 만든 뒤 `script`, `care`, `doList`, `avoid`, `next`를 다시 생성한다. 이 중 대화문은 4회, 나머지는 4회이므로 **추가 생성 8회**가 있다.

구현한 O4 흐름 (`MODEL_REUSE_FINAL_DRAFT=true`):

1. 관계 분석·독립 검토 → 대화 전략·독립 검토를 그대로 수행한다.
2. 전체 안내 초안을 생성한다. 제거할 추가 생성 단계의 `CARD_ROLES`·`SPEECH_PARTS`가 요구하는 구체성, 화자, 상담 목적, 직접 발화, 선택권, avoid 묶음의 완결성을 전체 초안 지시·검사에 보존한다. 동일한 텍스트를 여러 번 넣기보다 요구사항을 한 번씩 대응시킨다.
3. 전역 구조·안전 검증을 통과한 초안을 카드별로 검사한다. 카드별 의미 오류는 field가 있는 issue로 전달해 해당 카드의 `repairCard`와 독립 검토에 연결한다. 검토 가능한 카드도 기존 근거 검토를 받아야 한다.
4. 승인된 카드만 기존 디자인으로 부분 표시한다. 전체 품질·통합 검토와 `speech_detail` 생성·검토를 유지한다.

`guide_write`에 단순히 `checkSpeech:true`만 켜서는 이 흐름이 되지 않는다. 현재는 script 오류가 validator에서 throw되면 `ModelGateway.request`가 **전체 guide_write를 다시 호출**하며, 카드별 수정 루프에 도달하지 않는다. O4는 검증 경계를 다음처럼 분리했다.

| 오류 종류 | 처리 | 보존할 조건 |
| --- | --- | --- |
| 잘못된 JSON·필수 키/타입 누락·전역 안전 판단 불일치 | 기존 전체 초안 실패·복구 | 잘못된 구조를 채우거나 위험 판단을 덮어쓰지 않음 |
| 구조가 유효한 특정 카드의 발화·목적·내용 오류 | 해당 field의 미승인 초안 + issue로 카드 수정·검토 | 다른 네 카드 재생성 없이 각자의 검토 계속. 잘못된 카드 공개 금지 |
| 분석·전략 또는 여러 카드 간 모순 | 영향 범위 전체 무효화·필요 단계 재수행 | 단일 카드 오류로 축소하지 않음 |

미승인 초안은 해당 작업의 임시 수정 입력일 뿐 승인된 상태·사실·저장 결과가 아니다. 전체 초안 구조가 통과했다고 검토 없이 부분 공개해서도 안 된다. script 하나만 실패하는 사례에서 다른 네 카드의 추가 생성이 0회이고, script의 수정·독립 검토가 실행되는 계약 검사를 추가한다.

모든 초안 카드가 통과하면 생성 12→4, 검토 14 유지로 **26→18회(약 30.8% 감소)**가 된다. 초안의 실패율이 높으면 수정 호출로 절감분이 줄거나 없어질 수 있다. 평균뿐 아니라 가장 긴 실패 경로까지 비교한다.

기존 `skipFinalExtras=true`는 이 아이디어 일부를 구현하지만 전략·품질·상세까지 생략한다. O4는 별도 카드 재사용 옵션으로 구현하고 두 옵션의 동시 활성화를 거절한다. 같은 합성 사례에서 기존 반환·저장 payload의 동일성을 확인했다. 실제 DB와 모델 출력은 별도 검증 대상이다.

### O5. 같은 검토 결과를 정확한 범위 안에서만 재사용하기

카드별 `speech_review_card_*` 5회와 `support_review_card_*` 2회 뒤에 전체 `speech_review`, `support_review`가 다시 호출된다. 검토 범위의 일부는 겹치지만 전체 입력·전략·주장 목록·수정 이력이 다를 수 있다.

- 재사용 키에는 operation/소유자·대화 범위, 원문 revision/hash, 모델 identity, 프롬프트·스키마·검증기·정책 버전, 분석·전략, 검토 대상 카드·claims, 관련 수정 이력을 포함한다.
- 카드 문자열 hash만 같다고 재사용하지 않는다. 같은 문장도 화자·부정·시점·대화 목적이 바뀌면 다른 판단이 필요하다.
- 우선 같은 operation 내 메모리에서만 재사용한다. 대화 간 전역 승인 캐시를 새로 만들지 않는다.
- `guide_refine` 또는 late analysis repair가 내용을 바꾸면 영향을 받는 승인을 무효화한다. 분석이나 전략의 영향 범위를 증명하지 못하면 모두 무효화한다.
- 전체 `guide_review`는 카드 간 모순, 전체 목적, 분석과 안내의 일관성을 확인하는 별도 검토로 유지한다.
- 개별 검토가 전체 검토의 모든 항목을 포함한다는 검증이 성립한 경우에만 전체 발화·지원 검토 두 호출을 생략한다.
- 서버의 같은 모델을 두 역할로 사용해도 생성 결과를 곧바로 승인 캐시에 넣지 않는다. 별도 검토가 통과한 결과만 후보가 된다. 기관 분류 2차에 1차 분류 결과를 캐시로 재사용하지 않는다.

O4와 함께 모든 조건을 충족한 경로의 이론상 목표는 **생성 4 + 검토 12 = 16회**다. 전체 두 검토가 새로운 오류를 발견하는 빈도와 오류 종류를 먼저 측정해야 하며, 현재 구현에서 안전하게 바로 제거 가능하다는 결론이 아니다.

검증 단계에서는 카드별 검토와 기존 전체 검토를 모두 실행해 결과를 비교한다. 카드별 통과 뒤 전체 `speech_review`·`support_review`만 반려한 사례를 따로 모으고, 차이가 교차카드 문맥·추가 원문·claims 범위·수정 이력 중 무엇 때문인지 구분한다. 서로 다른 검토 입력은 hash 일치만으로 동등해지지 않는다. 최종 `guide_review`가 이미 남아 있다는 이유만으로 두 검토의 오류 탐지 범위를 자동 대체한다고 보지 않는다.

같은 모델의 두 번째 호출은 확률적 재검토 효과도 가질 수 있다. 이것을 정확히 같은 입력의 비용 중복과 구분해 평가한다. 승인 재사용 후보를 평가하는 동안에는 기존 전체 검토 결과를 최종 판정으로 유지하며, 추가 실험 호출 비용을 운영 절감 수치에 숨기지 않는다.

### O6. 입력 토큰을 줄이되 원문 의미는 그대로 보존하기

- 후보 실행본의 stage-scoped question rules처럼 해당 단계가 사용하지 않는 지시를 줄이는 방법을 우선한다. 질문·생략 판단 단계와 검토기의 완전한 계약은 유지한다.
- 실제 요청에서 `answers`, `retrieval`, `evidence_sources`, schema enum, 수정 이력에 동일 원문이 중복 직렬화되는 바이트·토큰을 측정한다. `retrievedContext`가 존재한다고 전체 `answers`가 이미 잘려 있다고 가정하지 않는다.
- 같은 요청 안의 동일 근거를 한 번만 보내고 안정적인 ID로 참조하는 방법을 검토한다. ID에 대응하는 완전한 원문과 답변 묶음은 모델이 볼 수 있어야 한다.
- ID는 원문 선택의 표현일 뿐이다. 서버가 근거를 대신 골라 주거나 검증 실패를 임의 인용으로 고치지 않는다. 교차 화자·교차 문항·교차 요청 ID는 거절한다.
- 추가 `MODEL_MEMORY_EVIDENCE_IDS` 기능과 이미 있는 evidence transport를 구분한다. 옵션이 켜져 있어도 현재 실행 stage에 적용되지 않으면 절감으로 계산하지 않는다.
- KV/prefix 캐시는 별도 후속 과제다. 서명 context만으로 캐시 적중을 주장하지 않는다. backend 지원, 모델·토크나이저 동일성, 메모리 상한, 세션 격리, 삭제·취소 시 제거를 검증하기 전에는 활성화하지 않는다.

### O7. 토큰 정책 조회와 출력 예산

`discoverModelTokenPolicy`는 operation 시작에 `/healthz`를 호출한다. 별도 검토 Gateway는 검토 단계마다 자체 operation을 만들므로 반복 조회가 생길 수 있다. 이는 생성 호출 수에는 포함되지 않는다.

- endpoint·모델·인증 범위·메타데이터 버전 기준으로 capability만 짧게 캐시하고 동시 조회를 합친다. worker 준비 상태와 token capability를 같은 캐시로 취급하지 않는다.
- 404·405에서 정책 없음으로 처리하는 기존 계약과 검토 모델의 독립 정책을 유지한다. 인증 오류·일시 실패를 정상 정책으로 저장하지 않는다.
- 생성·검토가 같은 서버 endpoint·모델·인증 범위를 사용하면 capability 조회 캐시를 공유할 수 있다. 역할이 다르다는 이유만으로 같은 한도를 반복 조회하지 않되, 서로 다른 모델의 한도는 공유하지 않는다.
- 단계별 출력량과 잘림률을 먼저 측정한 뒤 작은 구조 출력과 긴 카드 출력의 예산을 구분한다. 8,192는 허용 상한이지 매 호출에서 실제로 8,192토큰을 생성한다는 뜻이 아니다.
- `finish_reason=length`가 증가하면 전체 재시도로 비용이 더 커질 수 있다. 답변을 잘라 통과시키거나 필수 필드를 생략해 예산에 맞추지 않는다.

### O8·O9. 변하지 않은 블록과 최종 분석 중복

이름·호칭 블록은 이름 관련 입력이 변하지 않는 턴에 재사용 후보지만, 현재 추출이 다른 답변의 호칭 정정까지 읽는다면 의존성이 더 넓다. 모든 실제 의존 입력과 schema·prompt가 같음을 확인해야 한다. 텍스트 수정이 없다는 이유만으로 질문·안전 판단을 생략하지 않는다.

최종 `relationship_analysis`와 이전 `relationship_memory` 역시 근거 선택·해석이 겹칠 수 있다. 그러나 사용자 목적·최종 원문·새 주장 범위가 다르므로 승인된 중간 상태를 최종 분석으로 그대로 복사하지 않는다. 공통 원문 선택 부분만 재사용하고 새 주장에는 새 독립 검토를 유지하는 후순위 설계다. 현재 단계에서 확정 절감 수치를 제시하지 않는다.

### O10. 기관 안내는 호출 제거보다 기존 캐시·순서를 유지하기

현재 화면은 종료 후 기관 안내를 기다린 다음 최종 생성을 요청한다. 같은 GPU 단일 슬롯에서 두 흐름을 병렬로 보내면 429와 작업 경쟁만 늘 수 있다.

- 기존 기관 캐시의 적중과 최종 revision 승계가 정상인지 먼저 확인한다.
- 서버 GPU에 서로 독립된 추론 용량이 실제로 확보되고 안전·revision·취소 계약이 유지되는 경우에만 결과 화면 내 동시 진행을 비교한다. 로컬 Ollama로 기관 분류를 분산하는 안은 목표에서 제외한다.
- 일반 상담의 독립 분류 두 번, 긴급 조기 종료, 원문 인용, 대화 중 불씨 미표시 계약은 유지한다.

계측 항목:

- 실제 `POST /chat/completions` 수: stage·생성/검토/분류·물리 backend·operation·재시작별로 분리. 429 응답 요청도 물리 요청으로 센다. 서버 GPU 합계와 로컬 추론 0회를 따로 확인한다.
- 성공한 논리 stage 수, 생성/검토 요청 비율, 의미 거절·구조 실패·통신 실패·취소 수.
- 입력/출력 토큰 합계와 stage별 분포. usage가 없으면 미측정으로 표시하며 0으로 대체하지 않는다.
- 공통 GPU queue time을 생성·검토·분류별로 구분하고, 추론 시간·첫 승인 카드 시간·최종 저장 시간의 중앙값·상위 지연 분포를 측정한다. GPU별 메모리·사용률과 실제 동시 요청 수도 함께 확인한다.
- 기관 캐시·블록 재사용·검토 승인 재사용을 서로 구분한 hit/miss/invalidate 수.
- 저장 실패, 정정·취소 후 오래된 결과 차단, 결과·기록·생성 중 화면 계약 통과 여부.

비교 조건은 같은 합성 입력 묶음, 모델·checkpoint·옵션·source hash·검토 정책, 동시 사용자 수와 warm/cold 조건을 고정한다. **서버 전용의 최적화 전/후를 먼저 비교**하며, 과거 로컬 12B 검토가 포함된 성능 수치와 섞지 않는다. 같은 서버 모델의 검토가 기존 오류 반려 사례를 보존하는지도 별도로 확인한다. 한 성공 예제로 동등성을 선언하지 않는다. 개인 상담 원문은 새 보고서나 공개 fixture로 복사하지 않는다.

비교 결과는 성공 건만 골라 계산하지 않는다. 제출한 전체 사례 수를 분모로 완료율·실패율·취소율을 함께 보고, 실패·재시도에 쓴 요청·토큰도 포함한다. 조기에 실패해서 호출 수만 줄어든 결과를 최적화 성공으로 보지 않는다. O4의 실제 절감은 정상 경로 8회에서 추가된 수정·재검토·전체 복구 호출을 뺀 값으로 확인한다. 무제한 반복으로 미완료인 사례도 별도 표시한다.

필수 회귀 사례:

1. 상태 블록의 JSON 실패와 의미 거절을 구분하고, 실패 블록만 재사용에서 제외하는지.
2. 화자·부정·정정·최근 시점 변경과 이름/호칭 정정이 기존 승인을 무효화하는지.
3. 질문 생략·추가 질문 제안 및 긴급 종료를 독립 검토 없이 확정하지 않는지.
4. 카드별 승인이 있어도 전체 카드 간 모순·새 사실·목적 변경을 검출하는지.
5. 품질 수정·late analysis repair 후 변경 카드와 의존 검토가 다시 실행되는지.
6. 생성·검토·분류·여러 앱이 브리지 한 슬롯을 공유하고, 429·취소 중 queue 제거와 원격 요청 취소가 동작하는지.
7. deadline·stage family 예산이 재시작·검토 위임·형식 fallback으로 초기화되지 않는지.
8. 캐시가 소유자·revision·모델·schema·prompt·검증기·정책 변경을 넘어 재사용되지 않는지.
9. 일반 상담의 독립 두 분류와 기존 긴급 안내, 기관 캐시·최종 revision 승계가 보존되는지.
10. 모든 부분 카드 승인, 최종 상세 생성·검토, DB 저장 이후에만 완료가 표시되는지.
11. 정상·오류·복구·실검증 경로에서 로컬 모델 요청이 0회이며, 모든 모델 추론이 서버 GPU로 전달되는지.
12. 서버의 동일 모델을 생성·검토에 사용할 때도 별도 검토 요청과 거절 조건이 유지되고, 기관 독립 2차 분류가 1차 출력 캐시로 대체되지 않는지.
13. 생성·검토·기관 분류의 실제 request body가 endpoint validator에 수용되며, 지원하지 않는 필드·모델·인증 오류가 반복 복구로 감춰지지 않는지.
14. 단일 슬롯에서 writer→review→repair가 교착 없이 완료되고, backoff·capability GET 동안 permit을 보유하지 않는지.
15. 대기 취소는 실제 추론 0회, 실행 중 취소는 원격 완료 확인 전 다음 실행 0회, 오래된 결과 저장·표시는 0건인지.
16. script 단독 오류에서 다른 카드의 재생성 0회, 해당 카드 수정·독립 검토 필수, 전역 구조·안전 오류는 계속 전체 실패인지.
17. 전체 검토만 검출한 오류가 승인 재사용으로 사라지지 않고, 비교 실험 비용·실패 사례가 집계에서 빠지지 않는지.

이 기획 재검토 시점에는 단일 슬롯 scheduler와 O4 오류 분리가 제안 상태였다. 이후 P0와 O4의 로컬 구현 범위는 아래 10·11절에 구분한다. 동일 서버 모델의 의미 검토, 실제 GPU 대기열·원격 취소·최종 저장은 실서버 검증 대상이며 로컬 검사만으로 통과를 주장하지 않는다.

## 10. P0 구현 범위와 적용 경계

기존·현재 수정본·후속 후보의 순서도와 호출 수는 [모델 호출 흐름 비교](모델_호출_흐름_비교_2026-10-31.md)에 정리했다. **P0만으로는 26회이며, 후속 O4를 활성화하면 정상 경로 18회**다. O4 구현·검증은 11절을 따른다.

사용자의 구현 요청에 따라 P0부터 적용 가능한 소스와 검사를 추가했다. 상세 설정·검증 계약은 [서버 GPU 전용 P0 구현](../../../app/docs/SERVER_GPU_P0.md)에 정리한다. 실제 실행 설정·배포는 별도이며, **GPU 서버에 접속하거나 모델을 실행하기 전에 사용자 승인을 받는다.**

| 우선순위 | 로컬 구현 | 실제 적용 조건 |
| --- | --- | --- |
| 요청 호환성·목적지 고정 | `MODEL_SERVER_GPU_ONLY` opt-in, `trained_chat` prompt/omit/nonstream, 생성·검토·기관의 공유 목적지·인증 검증 | 승인 후 현재 bridge·checkpoint·인증과 대조. 별도 검토 요청 유지 |
| O1 준비 상태 | 명시적으로 시작하는 guarded worker, ready identity/PID 확인, 상태 조회의 시작·재시작 금지 | 실제 worker 프로토콜·checkpoint·GPU 상태 대조 |
| O2 물리 슬롯 | 공용 bridge의 요청별 FIFO 1슬롯, 대기 개수·바이트 제한, 취소된 대기 요청 제거 | 여러 앱과 alias가 같은 bridge를 사용하도록 별도 배포 |
| O3 복구·취소 | 완료 응답과 cancel 접수 분리, 종료 미확인 시 draining/unavailable, operation·family·HTTP 시도 계측 | 원격 중복 실행·종료·반환 실검증. 계측은 실제 GPU 추론 횟수와 구분 |
| 후속 O4 | P0와 별도 구현 완료, 11절 참고 | 로컬 정상 18회·검토 및 저장 payload 유지 확인. 서버 적용은 승인 후 |
| 후속 O5 등 | 미구현·적용 보류 | 서버 전용 기준선과 검토 범위 동등성 입증 후 판단 |

기본 총 시간 제한 0과 기존 재시도 정책을 유지한다. 운영 `.env`, 실행 중인 프로세스, 기존 runtime bridge, 카드 디자인은 이번 P0에서 변경하지 않는다. 생성·검토는 같은 서버 모델을 사용하더라도 독립 요청·기존 검증기를 유지한다. `compose.gpu.yaml`은 명시적으로 선택할 배포 overlay이며 이 작업에서 실행하지 않았다.

구현 후 독립 검토에서 전송·종료 정체, 종료 중 파일 번호 재사용, 서버 장애의 HTTP 분류, 기존 worker의 오류 응답 순서를 수정·보완했다. 재검토 후 앱 **1,858 통과·85 건너뜀·0 실패**, Python **65 통과·0 실패**를 확인했다. 기존 worker의 종료 순서 변경은 검증된 패치로 준비했으며 원격에 적용하지 않았다. 상세 변경과 미실행 실서버 검증은 위 구현 문서 6절을 따른다.


## 11. O4 구현·검토 후 수정

사용자의 후속 요청에 따라 O4를 구현했다. [구현·설정·검증 문서](../../../app/docs/FINAL_DRAFT_REUSE.md)와 [기존 대비 순서도](모델_호출_흐름_비교_2026-10-31.md)를 함께 본다.

- `MODEL_REUSE_FINAL_DRAFT=true`는 초안의 카드 5개를 독립 검토하고, 실패한 카드만 수정·재검토한다. 기본 false이며 GPU overlay에는 true와 `MODEL_SKIP_FINAL_EXTRAS=false`를 명시했다.
- 정상 최종 생성 **26→18회(8회·30.8%)**, 생성 12→4회·검토 **14회 유지**를 실제 Gateway + mock HTTP 검사로 확인했다. 대화문 수정·재검토가 한 번 필요한 사례는 20회였다.
- 전체 초안 작성에 기존 카드·발화 계약과 supporter 원문을 포함한다. JSON·필수 구조·안전 실패는 기존 전역 실패로 유지하고, 특정 카드 의미 오류만 해당 카드 수정으로 연결한다.
- `conversation_detail`과 최종 반환·저장 payload를 유지했다. O4 사용 메타데이터만 추가하며 기존 카드 UI와 긴급 고정 안내는 변경하지 않았다.
- 구현 후 두 독립 검토를 수행했다. 후속 검토에서 품질 개선 요청이 기존 초안 프롬프트를 쓰는 문제를 확인하고 O4 프롬프트 재사용으로 수정했다. 실제 요청 본문 검사에서 수정 전 실패·수정 후 통과를 확인하고 재검토했다.
- 앱 전체 **1,880 통과·85 건너뜀·0 실패**, JavaScript 구문·JSON·Compose 파싱 통과. 실제 DB 검사는 실행하지 않았다. 별도 허용 Ollama 검토 API는 `Host is down`으로 결과를 받지 못했다.

운영 `.env`, 실행 중인 서비스와 GPU 서버는 변경하지 않았다. 실제 GPU의 형식 통과율·수정 발생률·총 호출·토큰·처리시간·저장 완료는 승인 후 합성 사례로 확인한다. O5의 검토 삭제·승인 재사용은 적용하지 않았다.
