## 1. 서비스 목표와 설계 원칙

사용자가 전한 원문을 바탕으로 대상자의 상태, 사용자의 감정과 부담, 두 사람의 관계를 계속 갱신하고, 사용자가 실제로 건넬 수 있는 말과 행동을 만듭니다.

- 대상자: 관찰된 변화, 생활의 어려움, 도움에 대한 태도, 지원 자원.
- 사용자: 감정, 부담, 생활에 미치는 영향, 도울 수 있는 범위.
- 관계: 반복되는 상호작용, 갈등, 도움이 된 방식, 서로의 경계.
- 보고된 사실, 가능한 해석, 아직 모르는 내용을 구분합니다.
- 대상자에 관한 정보도 사용자의 관찰·전언임을 유지하고, 마음이나 진단을 직접 확인한 것처럼 단정하지 않습니다.
- 새로운 답변이나 정정이 들어오면 기존 해석을 수정합니다.
- 이미 답한 내용이나 거절한 질문은 불필요하게 반복하지 않습니다.
- 현재 즉각적인 위험이 확인되면 일반 대화 작성보다 신속한 도움 연결을 우선하는 별도 경로를 사용합니다.

## 2. 단일 생성에서 여러 역할의 모델 호출로 확장

한 번에 전체 답안을 만드는 대신 같은 모델을 역할별로 여러 번 호출하도록 구성했습니다. 여기서 에이전트는 서로 다른 모델을 반드시 사용한다는 뜻이 아니라, 역할·입력·출력·검토 책임을 나눈 호출 단계입니다.

### 대화 중 처리

원문 관찰과 상태 갱신 → 관계 메모리 갱신 → 근거 검토 → 필요한 추가 질문 결정·검토.

### 최종 답안 처리

| 순서 | 역할 | 주요 작업 |
| --- | --- | --- |
| 1 | 관계 분석 및 검토 | 현재 원문을 바탕으로 상태·관계·불확실성을 정리하고 검토 |
| 2 | 말하기 전략 및 검토 | 사용자의 목적, 관계, 관찰 장면, 부담과 경계를 반영 |
| 3 | 다섯 카드 초안 | 최종 응답의 기본 구성 작성 |
| 4 | 카드별 전담 작성 | 사용자 돌봄·행동·주의·다음 단계를 별도로 구체화 |
| 5 | 품질 검토 및 보완 | 부족한 내용과 구체성을 점검하고 필요 시 수정 |
| 6 | 첫 대화 세 부분 작성 | 첫마디·듣기·제안을 각기 다른 필드로 작성 |
| 7 | 전체 발화 통합 | 세 부분을 실제로 건넬 수 있는 자연스러운 문장으로 통합 |
| 8 | 근거·돌봄·최종 검토 | 주장과 원문, 사용자 부담, 최종 답안의 적절성 점검 |
| 9 | 카드별 오류 수정 | 문제 있는 카드만 재작성하고 나머지 카드는 보존 |
| 10 | 단계별 설명 및 검토 | 최종 발화를 나누고 이유·원문 인용을 연결하여 검토 |

검토-수정 라운드는 최대 2회로 제한합니다. 개별 생성의 형식·검증 실패에는 최대 3회 호출 제한을 적용하며, 단계별 설명은 별도의 제한된 수정·재검토를 거칩니다. 호출 수는 상태 준비 여부와 재시도에 따라 달라집니다. 검증 실패가 해소되지 않으면 결과를 꾸며 저장하지 않고 실패로 처리합니다.

## 3. 다섯 카드의 작성 방향

| 화면 카드 | 작성 내용 |
| --- | --- |
| 당신의 마음도 소중해요 | 보고된 감정에 대한 공감, 실제 부담, 지원 자원, 도울 수 있는 범위 |
| 이렇게 시작해 보세요 | 관계와 관찰 장면을 반영한 실제 발화, 단계별 이유와 근거 |
| 이렇게 해 보세요 | 구체적인 실행 방법, 목적, 예시 |
| 피하면 좋아요 | 피할 표현·행동, 그 이유, 사용할 수 있는 대안 |
| 다음 단계 | 대화에 응할 때, 거절할 때, 도움에 관심을 보일 때의 후속 행동 |

### ‘이렇게 시작해 보세요’ 세분화

- 첫마디: 이야기해도 되는지 묻기, 실제 관찰한 장면 말하기.
- 듣기: 사용자의 의도 전하기, 열린 질문, 답을 기다리는 말.
- 제안: 작은 행동 제안, 도움 선택지, 거절할 수 있는 여지.

분리 작성 후 전체 발화를 통합하고, 검토·수정이 끝난 발화에 대해서만 단계별 설명을 만듭니다. 화면에는 각 부분의 발화와 ‘왜 이렇게 말하나요?’, 접을 수 있는 원문 근거, 전체 발화를 표시합니다. 설명에 사용한 발화 조각이 최종 발화 전체와 일치하는지도 검사합니다.

## 4. 원문 근거와 오류 수정 보강

- 현재 대화의 원문을 사람·문항·주제별로 검색하는 RAG 흐름을 사용합니다.
- 이전 모델 요약을 새로운 사실의 근거로 삼지 않도록 구성했습니다.
- 인용의 존재와 정확한 원문 일치뿐 아니라 주장과 인용의 관계를 모델 검토 대상으로 삼습니다.
- 부정 표현, 화자, 시점, 정정 여부를 고려하도록 지시합니다.
- 설명·사용자 돌봄 단계에는 사용자 자신의 답변을 필수 검색 대상으로 추가했습니다.
- 상담/진료 권유를 선택한 경우, 일반적인 ‘도움받을 곳’ 표현만 남아 목적이 사라지지 않도록 검사·재시도 피드백을 보강했습니다.
- 수정 단계는 전체 답안을 다시 만들지 않고 문제 있는 카드만 반환하게 했습니다.
- 피하라고 인용한 표현과 실제로 권장하는 표현을 구별하도록 회귀 검사를 추가했습니다.

단, 원문 문자열 검사와 모델의 승인만으로 모든 의미적 오류를 잡을 수 있는 것은 아닙니다. 남은 실제 출력 문제는 아래에 별도로 기록했습니다.

## 5. 화면 변경

- ‘이렇게 해 보세요’와 ‘피하면 좋아요’를 각각 전체 폭의 가로로 긴 카드로 만들고 위아래로 배치했습니다.
- ‘다음 단계’를 연한 초록색 배경, 둥근 테두리, 캐릭터가 있는 독립 박스로 만들었습니다.
- 결과 화면과 내 기록 화면에서 공통 카드 렌더링을 사용합니다.
- 대화 기록은 기본적으로 접힌 상태이며 사용자가 펼쳐 볼 수 있습니다.
- 상세 발화 메타데이터가 없는 이전 기록은 기존 발화 표시 방식으로 열 수 있습니다.
- 원문과 모델 출력의 화면 삽입 시 이스케이프 처리 및 관련 검증을 포함했습니다.

### 실제 완료 단계 기반 로딩

서버에서 완료된 모델 단계가 추가될 때마다 로딩 칸을 하나씩 늘립니다. 시간에 맞춰 임의로 진행률을 올리지 않습니다. 현재 단계·재시도 상태를 표시하며, 실패한 시도만으로 완료 칸이 늘어나지 않도록 했습니다. 진행 조회는 해당 대화 소유자만 가능하고, 모델 내부 사고 과정이나 원문 대신 공개 가능한 단계 정보만 전달합니다.

## 6. 모델 연결과 향후 교체

기존 검증에는 로컬 Ollama의 `gemma4:12b`를 사용했습니다. 이후 31B 또는 자체 파인튜닝 모델로 교체할 수 있도록 모델 연결과 에이전트 흐름을 분리했습니다.

- `MODEL_PROTOCOL=relationship_agent`를 유지합니다.
- 서버 주소와 모델 이름은 `MODEL_BASE_URL`, `MODEL_NAME`으로 설정합니다.
- 서버 지원에 따라 `MODEL_AGENT_FORMAT`을 `json_schema`, `json_object`, `prompt` 중 선택합니다.
- 모델 서버는 현재 게이트웨이와 호환되는 `/chat/completions` 인터페이스가 필요합니다.
- 31B로의 실제 전환·품질 검증은 이번 구현 완료 항목에 포함되지 않습니다.
- 모델 교체 후에도 원문 근거, 정정, 관계별 발화, 부담·경계, 위험 상황을 같은 기준으로 다시 평가해야 합니다.

## 7. 검증 결과와 남은 한계

### 확인된 기록

| 항목 | 결과 |
| --- | --- |
| 자동 회귀·통합 검사 | 최종 작업 시 281개 통과, 실패 0개 |
| 실제 12B 최종 평가 | 약 178초, 모델 호출 29회, 자동 검토 통과 |
| 화면 확인 | 전체 폭 카드, 다음 단계 박스, 접을 수 있는 대화 기록을 실제 앱에서 확인 |
| 저장 여부 | 마지막 실제 모델 평가 출력은 앱 기록에 저장하지 않음 |

자동 검사 성공과 답안의 의미적 완성도는 구분해야 합니다. 최종 실제 출력에 대한 사람 검토에서는 다음 문제가 남았습니다.

1. 분리 작성한 열린 질문이 전체 발화 통합 과정에서 사라지는 경우.
2. ‘항상’, ‘언제든’처럼 사용자의 한계를 넘어 도움을 약속하는 표현.
3. 원문에서 확인되지 않은 고립감·방어기제 등으로 해석이 넓어지는 경우.
4. 단계별 설명에 붙인 인용이 설명의 모든 주장을 뒷받침하지 못하는 경우.
5. 사용자 돌봄이 사용자 자신의 휴식·경계보다 상대를 돕는 의무로 기우는 경우.

따라서 현재 상태는 다단계 작성·검토 구조와 UI 구현을 완료한 단계이며, 모든 실제 답안의 근거성과 자연스러움이 충분히 확보되었다고 판단한 상태는 아닙니다.

### 다음 개선 우선순위

- 통합 전후의 필수 내용 보존: 열린 질문, 사용자 목적, 거절 선택권, 경계.
- 설명을 개별 주장 단위로 검토하여 인용이 지지하는 범위를 명확히 제한.
- 사용자의 실제 자원·부담을 반영한 돌봄 카드 평가 강화.
- 다양한 관계·정정·도움 거절·위험 문맥의 반복 평가와 사람 평가 기준 정리.
- 31B 및 자체 모델 전환 시 동일 사례로 품질·실패율·시간 비교.

```bash
bash scripts/run-local.sh
```

```bash

npm test
npm run test:integration
```
