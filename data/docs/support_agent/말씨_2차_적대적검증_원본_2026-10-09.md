## 2. 이전 지적에서 실제로 개선된 부분

단순히 문서에 원칙을 추가한 것보다 진전됐다. 다음 방어는 코드와 실행으로 확인했다.

### 승인된 내용과 학습행을 연결한다

agent_training은 training_allowed=true 하나만으로 내보내지 않는다. 사례 해시, 독립 검토 기록, 검토 항목, 원천 사용 근거, 분할을 확인한다. 기존 9개 예시는 구조가 맞아도 학습 대상에서 제외된다.

내보낸 목표 응답을 바꾼 뒤 배치를 만들면 “serialized training row changed or was not approved” 오류로 차단한다. 다만 이 해시는 승인 진위의 인증 장치가 아니라 기록 사이의 일관성을 확인하는 장치이며, 자료도 이를 명시한다.

### 현재 턴 입력과 주석 화면을 제한한다

prepare_prefix와 annotation_view는 현재 사용자 턴까지의 입력을 만들고, 기존 정답 행동·목표 응답·미래 메타데이터가 입력으로 들어가지 않도록 분리한다. 과거 예시의 주석 절차는 legacy_unverified로 유지한다.

이는 이전의 “전향적 주석 명세 부족”을 일부 해결했다. 실제 주석자가 다른 경로에서 미래 내용을 보지 않았는지와 실제 기반 모델의 채팅 템플릿·토크나이저는 여전히 별도 검증 대상이다.

### 행동과 구성 요소를 분리했다

primary_action과 response_components를 구분하고 질문 필요 이유, 제한된 지원의 정보 한계, 종료 제약을 추가했다. 명료화 응답에 부적절하게 붙어 있던 Q16 참조도 변환 자료에서 제거했다.

따라서 이전의 “행동 코드 공존 규칙이 없다”는 지적을 그대로 반복하면 부정확하다. 이번에 확인한 문제는 추가된 구성 요소를 승인 조건이 끝까지 반영하지 못하는 경우다.

### 평가 기록의 누락과 변조를 검사한다

기본 평가 묶음은 30개 집단·34개 실행 단위이며, 모든 실행 단위의 기록을 요구한다. 빈 응답, 공백 응답, 누락·중복·알 수 없는 ID, 잘못된 사례 ID, 누락된 평가 항목, 오래된 검토 해시를 추가 반례에서 거절했다.

출력만 있고 검토가 없으면 needs_review, 일부 변형만 평가되면 집단은 incomplete로 유지했다. 전체 미실행 상태를 통과로 바꾸지 않았다.

### 분류 무결성과 통합 학습 경로를 분리한다

제출된 release_audit.json의 passed=true는 requested_gate=independent_classifier_integrity에 대한 결과다. joint_training_evaluation_gate.passed=false도 함께 기록되어 있다.

단어 378개의 원천 상담 연결 부재와 전체 통합 경로의 미확인을 명시한다. 이것을 전체 누출 방지 검증까지 통과했다고 읽어서는 안 된다.

또한 audit_features는 학습 텍스트에서 어휘·DF·IDF와 각 행의 TF-IDF를 다시 계산하도록 구현돼 있다. 단순히 manifest의 train-only 선언만 믿는 검사는 아니다. 이번에는 실제 데이터 대신 작은 합성 완전 패키지로 그 경로를 실행했다.

### F01. 명시적 안전 안내가 전문가 검토 없이 내보내짐

**코드 위치:** counseling_pipeline/agent_training.py의 validate_case, eligibility_reasons.

현재 전문가·안전 정책 검토를 요구하는 조건은 “risk_tags가 있거나 primary_action이 SAFETY_SUPPORT인가”다. 그러나 SUPPORT에도 safety_guidance 구성 요소를 넣을 수 있다.

재현 사례의 구조는 다음과 같다.

    {
      "decision": {
        "primary_action": "SUPPORT",
        "response_components": ["wording_example", "safety_guidance"],
        "safety_subjects": ["friend"],
        "question_id": null
      },
      "risk_tags": []
    }

검토 fixture는 일반 human 유형이며 qualification_ref와 safety_policy_version은 없다.

| 검사 | 예상 | 관측 |
| --- | --- | --- |
| 구조·학습 허용 검사 | 구성 불일치로 거절하거나 전문가·정책 검토 요구 | eligible_count=1, 제외 사유 없음 |
| export | 위 조건 미충족이면 거절 | train 1행 내보내기 성공 |
| 대조군: risk_tags에 acute_safety만 추가 | 전문가·정책 부족으로 제외 | eligible_count=0, risk_review_required와 reviewed_safety_policy_required |

**의미:** 안전 관련 구조가 명시돼 있어도 라벨 하나가 빠지면 검토 요구가 약해진다. 사람의 진짜 신원이나 권한을 위조한 문제가 아니라, 같은 코드 내부에서 안전 구성 요소와 승인 조건이 일치하지 않는 문제다.

**영향 제한:** 첨부된 실제 9개 예시가 이 경로로 승인됐다는 뜻은 아니다. 현재 예시들은 0개 허용 상태를 유지한다. 모든 무위험 SUPPORT 응답에 전문가 검토가 필요하다는 주장도 아니다.

**수정 방향:** 검토 요구 조건을 명시적 위험·안전 구조 전체에서 계산한다. SUPPORT와 safety_guidance의 공존을 허용한다면 필요한 전문 검토를 함께 요구한다. 정책상 허용하지 않는 조합이라면 구조 검사에서 거절한다. 단어 검색으로 위험 태그를 자동 확정하는 방식은 별개의 의미 판단 오류를 만들 수 있다.

**수정 후 통과 조건:** 같은 사례가 risk_tags 유무만으로 검토 요구를 바꾸지 않는다. 적합한 전문가·정책 기록이 없으면 제외되고, 실제 검토 기록이 충족된 경우에만 승인된다.

재현 결과 키: p01_safety_guidance_without_expert, p01_export, p01_control_risk_tag_present.

### F02. 알려진 실패가 다른 항목의 불확실성에 가려짐

**코드 위치:** counseling_pipeline/agent_evaluation.py의 _reviews.

현재 집계 순서는 “치명적 실패 → 어느 항목이든 불일치·uncertain → 어느 항목이든 fail → pass”다. 이 순서로 인해 한 항목에서 실패가 확정됐어도 다른 항목의 불확실성이 전체를 inconclusive로 바꾼다.

두 검토자가 다음처럼 판단한 합성 기록으로 재현했다.

| 평가 항목 | 검토자 A | 검토자 B |
| --- | --- | --- |
| 금지 조건 F1 | fail | fail |
| 요구 조건 R1 | pass | uncertain |
| 다른 조건 | pass | pass |

critical_failure는 false로 두었다. 이는 치명적 실패 플래그가 없는 일반 실패의 집계를 시험하기 위한 조건이다.

**관측:** outcome=inconclusive, failed_case_groups=0, inconclusive_case_groups=1. 한 검토자 안에서 F1=fail, R1=uncertain인 경우도 같은 결과였다.

프로토콜은 평가 기준을 모두 충족해야 통과하며 unanimous semantic failure를 실패로 정의한다. 동시에 불확실성·불일치를 inconclusive로 두므로 두 규칙이 겹칠 때의 우선순위도 분명히 정해야 한다. 이 검토에서는 F1의 확정 실패를 보존하고 R1의 불확실성을 함께 기록하는 집계가 적절하다고 판단한다.

**영향 제한:** 이 반례가 pass로 둔갑한 것은 아니다. 또한 critical_failure=true인 경로는 실패를 우선한다. 확인된 문제는 **이미 알려진 비치명적 실패가 실패 집계에서 누락되는 것**이다.

**수정 방향:** 조건별 합의를 먼저 계산한다. 어느 필수·금지 조건에서 실패가 확정되면 전체 실패를 유지하고, 다른 조건의 불확실성은 별도 메타데이터로 남긴다. 같은 조건에 대한 검토자 의견 자체가 갈리는 경우와, 서로 다른 조건에서 실패·불확실성이 공존하는 경우를 구분한다.

**수정 후 통과 조건:** 위 기록은 fail로 집계되며 실패 조건의 근거를 보존한다. 다른 조건의 불확실성도 별도로 확인할 수 있어야 한다.

재현 결과 키: unanimous_failure_plus_other_uncertainty, single_review_failure_plus_other_uncertainty.

### F03. 비어 있는 시험 집단을 실행·검토 없이 통과 처리

**코드 위치:** counseling_pipeline/agent_evaluation.py의 load_suite, evaluate.

load_suite는 전체 실행 단위 수와 ID 중복을 확인하지만 각 집단의 scenarios가 비어 있지 않은지는 확인하지 않는다. evaluate는 집단의 모든 실행 단위가 평가됐는지 all(...)로 확인하는데, 빈 목록에 대한 all(...)은 참이다.

**재현 조건:** 동봉 묶음의 사본에서 T30의 실행 단위를 T01 집단으로 옮겨 전체 실행 단위 수는 34개로 유지하고, T30.scenarios=[]로 만들었다. 이 변경된 사용자 지정 묶음은 load_suite를 통과했다. 실제 실행 기록이나 검토 기록 없이 기본 미실행 평가를 호출했다.

관측된 T30 결과:

    {
      "status": "evaluated",
      "outcome": "pass",
      "execution_units": 0
    }

전체 요약은 평가 집단 1개·통과 집단 1개가 됐고 response_candidate는 null이었다.

**영향 제한:** 현재 동봉된 정상 suite에는 빈 집단이 없다. 기본 묶음을 그대로 평가하면 30개 모두 미실행으로 올바르게 나온다. 문제는 suite를 편집·재생성하거나 --suite로 잘못된 자료를 받을 때의 검증 경계다.

**수정 방향:** 각 집단에 한 개 이상의 유효한 실행 단위를 요구하고, 선언된 집단별 구성과 실제 구성을 대조한다. 평가 함수에서도 빈 case_units를 통과로 처리하지 않도록 독립적으로 방어한다.

**수정 후 통과 조건:** 위 묶음은 로딩 단계에서 거절된다. 어떤 호출 경로에서도 실행 단위 0개인 집단이 evaluated/pass로 표시되지 않는다.

재현 결과 키: empty_group_default_not_run.

### F04. 동일 원천 상담을 검증셋에서 반복해도 분류 감사 통과

**코드 위치:** counseling_pipeline/release_audit.py의 _check_rows, audit_sources, audit_release.

_check_rows는 외부 행 ID의 중복을 확인한다. audit_sources는 각 행이 실제 원천 상담에 대응하는지 확인한다. 그러나 전체 상담 단위에서 같은 conversation_id가 새 행 ID를 달고 같은 split에 여러 번 들어오는 경우와 manifest의 선언 건수 불일치는 검사하지 않는다.

**합성 재현:** 원천 상담 8개인 작은 DB와 train 4행·validation 4행의 정상 분류 패키지를 만들었다. 이어 validation 상담 한 개의 행 ID만 바꿔 20회 추가하고, 실제 행에 맞게 특징·타깃·가중치·해시를 다시 생성했다. 원천 DB는 그대로 유지했다.

| 항목 | 정상 대조군 | 중복 반례 |
| --- | ---: | ---: |
| 원천 상담 수 | 8 | 8 |
| train 상담 행 | 4 | 4 |
| validation 상담 행 | 4 | 24 |
| manifest의 exported_conversations | 8 | 8 |
| 실제 감사의 conversations_checked | 8 | 28 |
| 독립 분류 감사 passed | true | true |
| source.passed | true | true |

잘못된 원천 split을 지정한 별도 대조군은 정상적으로 거절됐다.

이 반례는 낡은 해시를 통과시킨 공격이 아니다. **새 자료의 파일 해시는 모두 맞는데 자료 구성 자체가 잘못된 경우**다.

동일 검증 상담 한 건의 비중은 정상 대조군에서 1/4=25%, 중복 반례에서 21/24=87.5%가 된다. 이것은 실제 모델 정확도를 측정한 값이 아니라 평가 자료에서 해당 원천이 차지하는 비중을 계산한 것이다.

**영향 제한:** 실제 제출된 1,107개 상담에 중복이 있다는 결과가 아니다. 학습과 검증 사이의 누출을 재현한 것도 아니다. 같은 검증셋 안의 사례 반복과 선언 건수 불일치를 감사 코드가 놓치는 문제다.

**수정 방향:** 전체 상담 행은 conversation_id 기준으로 유일성을 확인한다. 의도적인 변형·반복 자료라면 별도의 자료 계약과 집계를 둔다. manifest의 전체·split·라벨별 선언 건수와 실제 자료를 비교한다. 현재 건수 1,107을 하드코딩해서는 안 된다.

**수정 후 통과 조건:** 정상 패키지는 통과하고, 동일 원천을 새 행 ID로 중복한 패키지는 거절된다. 유일성과 건수 검사는 각각 독립적으로 확인한다.

재현 결과: release_duplicate_probe_results.json의 duplicate_validation.

### F05. 질문은행 의존성이 과거 대화에 있으면 이용 근거 검사에서 빠짐

**코드 위치:** counseling_pipeline/agent_training.py의 eligibility_reasons, training_example.

현재 행동에 따른 질문은행 전용 근거 검사는 primary_action == ASK_CFI일 때 적용된다. 하지만 학습 입력에는 이전 assistant 발화도 포함된다.

**재현:** 질문은행 Q09와 동일한 문구를 과거 assistant 발화에 넣고, 현재 사용자는 그 질문에 답하기를 거절하며 다른 지원을 요청하게 구성했다. 현재 행동은 SUPPORT다. 사례의 합성 원천 근거 fixture는 충족했지만 question_bank 항목은 unverified, local_training_allowed=false로 유지했다.

**관측:** eligible_count=1, train 1행 export/load 성공. 질문은행 문구는 내보낸 입력에 그대로 남았다. 현재 행동을 ASK_CFI로 바꾼 대조군은 question_bank_use_unverified로 제외됐다.

**영향 제한:** 질문은행의 실제 사용권 위반을 입증한 결과가 아니다. 확인한 것은 “이용 근거를 검사한다”는 내부 조건이 현재 행동 코드에만 적용되는 범위 누락이다. 제공 자료는 질문은행을 사용자 제공 자료로 기록하고 있으나 실제 이용 범위 검토는 미확인 상태로 두고 있다.

이 반례는 질문은행을 별도 원천 의존성으로 기록하지 않은 경우다. source_root_ids에 질문은행을 명시한 사례는 기존 일반 원천 검사에서도 차단된다. 현재 행동이 ASK_CFI가 아닌 경우에도 실제 사용 자원을 빠짐없이 기록하게 하는 구조가 필요하다.

**수정 방향:** 원천 자료·대화 이력·목표 응답 작성에 사용한 자원 의존성을 기록하고 검사한다. 현재 행동으로 자료 사용 여부를 추정하지 않는다.

여기에는 두 종류의 연결이 필요하다.

| 연결 | 목적 | 예 |
| --- | --- | --- |
| 원천 사례 집단 | 학습·검증 사이의 자료 누출 방지 | 특정 상담과 그 파생 사례 |
| 사용 자원 의존성 | 사용 근거·버전 확인 | 질문은행, 공통 정책·템플릿 |

question_bank를 모든 source_root_ids에 무조건 추가하면 공통 자료를 사용하는 상담 전체가 같은 분할로 묶일 수 있다. **이용 의존성과 평가 독립성을 위한 원천 집단을 분리하는 편이 적절하다.**

**수정 후 통과 조건:** 현재 행동이 SUPPORT여도 알려진 질문은행 의존성이 있으면 근거를 검사한다. 해당 근거가 확인된 뒤에는 입력에 포함할 수 있으며, 공통 질문은행 때문에 무관한 상담의 분할이 합쳐져서는 안 된다.

재현 결과 키: p02_question_bank_history_export, p02_control_current_ask_cfi.

## 4. 추가 강화 항목 3개

### H01. 불완전한 주장·안전 주체 구조를 수락

validate_case에서 다음 두 가지를 재현했다.

- claim 객체에 subject·time·source_type·status·유효한 evidence가 있지만 claim과 slot이 없어도 구조 검사가 통과한다.
- SAFETY_SUPPORT의 safety_subjects를 문자열 "   "로 주어도 bool(...)이 참이므로 통과한다. 전문가·정책 fixture를 갖추면 학습 허용으로 이어진다.

claims=[]를 허용하는 것 자체와는 다르다. 주장 객체를 만들었다면 무엇을 주장하는지, 안전 주체를 기록했다면 누구인지 확인할 수 있어야 한다.

**수정:** 존재하는 주장에는 필요한 내용·슬롯을 검증하고, safety_subjects는 비어 있지 않은 문자열 목록으로 제한한다. 인물 ID를 사용하는 경우 알려진 인물 참조인지도 검사한다.

결과 키: p03_claim_without_claim_or_slot, p04_whitespace_safety_subject.

### H02. T30 불변성 검사에서 false와 0을 같은 값으로 취급

_execution은 T30 주석을 Python 객체의 ==로 비교한다. Python에서는 False == 0이므로 추가 주석 상태 값이 false에서 0으로 바뀌어도 같다고 판단할 수 있다.

합성 반례에서 두 주석의 정규화 JSON 해시는 다른데 structural_invariance=true, outcome=pass가 나왔다. 필수 preferred_action과 target_response를 바꾼 것이 아니라 추가 주석 값의 타입 차이를 시험한 결과다.

**수정:** 무엇의 불변성을 요구하는지 스키마로 정한 뒤, 타입을 보존하는 정규화 표현 또는 필요한 필드의 엄격한 타입 비교를 사용한다. 생성 문장의 단순한 표현 차이까지 미래 누출이라고 판정하는 별도의 오류와도 구분해야 한다.

결과 키: t30_json_type_difference.

### H03. 비표준 수치 자료 경로에서 잘못된 행 매핑 주소를 기록

evaluation_audit.build_evaluation_audit는 numeric_root를 인자로 받지만 _save_array는 row_mapping을 ../numeric/sentence_rows.jsonl로 고정한다.

수치 매핑 파일을 mappings_v2에 둔 합성 반례에서는 배열 자체는 올바르게 생성됐지만 산출물의 row_mapping이 존재하지 않는 numeric 경로를 가리켰다. 원천 DB는 변경되지 않았다.

**수정:** 실제 numeric_root를 기준으로 상대 경로를 계산하거나 경로 배치를 계약으로 제한하고 호출 시 검사한다.

**영향 제한:** 기본 폴더 배치에서는 나타나지 않는다. 경로를 바꿔 진단 산출물을 생성할 때의 메타데이터 결함이다.

결과 키: nonstandard_numeric_directory.

## 6. 실제 데이터에 대해 이번 자료로 말할 수 있는 범위

ZIP 안내는 원본 DB, 실제 학습·검증 텍스트 JSONL, NPZ/NPY 행렬을 제외했다고 명시한다. 따라서 다음은 이번 검토자가 실제 원본을 전수 재실행한 결과가 아니다.

- 상담 1,462개, 발화 406,316개, 문장 1,001,781개, 단어 등장 8,599,382개라는 원천 집계.
- 분류 자료 3,131행의 특징 재계산.
- 전체 분류 패키지의 94개 파일 검증.
- 실제 분류 모델 세 종류의 학습·예측 결과.

이번에는 해당 결과를 담은 보고서와 포함된 파일의 해시·내부 정합성을 확인했다. 실제 코드의 경로는 합성 자료와 기존 회귀 테스트로 재현했다.

### 추가로 확인한 내부 정합성

- release_audit.json이 기록한 감사 코드 해시와 제공 release_audit.py의 해시가 일치한다.
- 보고서가 기록한 해시 인덱스의 해시와 제공 FILES.sha256.json이 일치한다.
- 원래 94개 파일 목록 중 이 ZIP에도 포함된 16개는 모두 해시가 일치한다.
- 상담·문장 노출 명세는 원천 1,108개이며, 제공된 명세에서 train과 validation을 가로지르는 원천 ID는 0개다.

| 범주 | 원천 validation | 채택 validation | 보존율 |
| --- | ---: | ---: | ---: |
| 우울 | 51 | 24 | 47.06% |
| 중독 | 47 | 37 | 78.72% |
| 불안 | 41 | 36 | 87.80% |
| 기타 | 24 | 20 | 83.33% |

불완전 상담과 동일 본문 등을 제외했다는 설명이 있다. 이 제외 자체가 오류라는 결과는 아니다. 다만 원래 split을 유지해도 평가에 남는 사례 구성은 달라질 수 있다. 채택된 분류 자료에서의 성능을 원래 상담 전체나 보호자 응답의 품질로 확대 해석할 수는 없다.

## 8. 권고 수정 순서와 완료 조건

### 1단계: 승인·평가에서 잘못된 긍정 판정을 막는다

F01과 F03을 먼저 수정한다. 명시적인 안전 지원의 전문 검토를 빠뜨리지 않고, 실행 단위 0개인 집단은 통과할 수 없어야 한다. H01의 안전 주체 타입 검사도 이때 함께 적용할 수 있다.

### 2단계: 실패 집계와 자료 구성의 의미를 보존한다

F02와 F04를 수정한다. 하나의 확정된 실패가 다른 항목의 불확실성 때문에 사라지지 않아야 한다. 검증셋의 동일 원천 반복과 선언 건수 불일치는 거절하거나 명시적으로 모델링해야 한다.

### 3단계: 이용 자원의 의존성과 원천 계보를 분리한다

F05를 수정한다. 과거 대화·현재 목표 응답·각색에 사용된 자원의 근거를 확인하되, 공통 질문은행 사용을 원천 상담의 동일성으로 처리하지 않는다.

### 4단계: 자료·모델·운영 검증을 이어 간다

실제 목표 응답의 검토, 전체 원천 연결, 모델별 채팅 템플릿·토큰 마스크, 동일 조건 비교를 진행한다. 운영 안전·개인정보 처리와 실제 지역 자원은 별도 승인·검증이 필요하다.

기존 105개 테스트가 계속 통과하는지 확인하되, 이번 반례를 회귀 테스트에 포함해야 한다. 수정의 성공은 “테스트 개수가 늘었다”가 아니라, 정상 대조군은 통과하고 잘못된 반례는 정확한 이유로 거절되는지로 판단한다.

## 9. 재현 자료 사용법

별도 재현 ZIP에는 이 보고서, 세 분야의 합성 프로브 스크립트, 통합 실행기, 실제 실행 로그와 JSON 결과가 들어 있다. 원본 상담 데이터와 모델 가중치는 포함하지 않는다.

사용자가 제공한 원본 ZIP을 별도 폴더에 해제한 후 NumPy가 있는 기존 Python으로 실행한다.

    python3 reproduce_all.py \
      --source "/원본ZIP을해제한/말씨_적대적검증_자료모음_2026-10-09" \
      --output "/새로운/재현결과폴더"

--output은 원본 소스 바깥의 새 디렉터리여야 한다. 통합 실행기는 기존 테스트, 기본 미실행 평가, 미승인 export 차단, 추가 합성 프로브를 수행한다.

최종 배포할 통합 실행기를 Python 3.12.14·NumPy 2.3.5 환경에서 실행해 8개 절차가 모두 예상 종료 코드와 일치함을 확인했다. 기존 105개 테스트가 통과했고 미승인 내보내기 디렉터리는 생성되지 않았다. 실행 전후 원본 payload 77개 파일의 해시도 모두 같았다. 각 절차의 종료 코드만으로 제품의 통과를 판정하지 않으며, 세 분야의 상세 JSON에 각 반례와 대조군의 실제 관측을 기록했다.

**프로브의 종료 코드 0은 프로브가 실행됐다는 뜻이다. 제품이 통과했다는 뜻이 아니다.** 결과의 예상·관측과 이 보고서의 해석을 함께 읽어야 한다. 수정된 코드에서는 기존 반례가 거절되면서 프로브 일부가 조기에 종료할 수 있으므로 로그로 수정 효과와 실행 오류를 구분한다.

합성 “approved” 검토와 “verified” 허가 파일은 프로브 내부의 코드 조건을 시험하기 위한 자료다. 실제 학습 자료의 승인·허가로 재사용해서는 안 된다.
