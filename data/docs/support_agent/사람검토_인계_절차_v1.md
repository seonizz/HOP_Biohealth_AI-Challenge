# 사람 검토용 인계 묶음 v1

이 절차는 기존 합성 AI 초안과 검토 요청을 실제 사람이 검토할 수 있게 연결한다. 생성·검증 성공은 사람 승인·사용 권한·임상 타당성·학습 허가가 아니다. 기존 [검토 계약](결선_데이터_검토계약_2026-10-16.md)의 사람·전문가·출처 조건을 유지한다.

## 묶음의 단위와 상태

합성 20에피소드에서 다음 응답 24개를 각각 검토 단위로 만든다. `ASK_CFI` 2개와 `SAFETY_SUPPORT` 2개는 별도의 전문·권리 검토 대기 단위다. 기존 원천 큐 391개와 작성 요청 6개는 원본 manifest와 파일 해시로 연결한다. 이 수를 독립 학습 사례 수로 합산하지 않는다.

| 파일 | 용도 |
|---|---|
| `blind_inputs.jsonl` | 현재 응답·AI 판정·미래 발화를 가린 접두부. 이전 대화에 이미 있었던 응답은 보이는 맥락으로 유지 |
| `target_packets.jsonl` | 같은 단위에 연결된 응답·주석·원천 내용 해시. 접두부 판단을 기록한 뒤 열람 |
| `review_requests.jsonl` | 신원·역할·시각·독립 판단·최종 결정·근거·9개 검토 항목이 비어 있는 요청 |
| `legacy_references.json` | 기존 391개 큐와 6개 작성 요청의 원본 위치·해시·수량. 오프라인 주석 맥락은 미래 발화를 포함할 수 있어 다음 응답 입력으로 사용하지 않음 |
| `review_contract.md` | 인계 시점의 기존 검토 계약 사본 |
| `manifest.json` | 입력 파일·구현·계약·각 산출물의 해시와 미승인 상태 |

모든 새 요청은 `pending_human_review`, `review_only`, `human_approved:false`, `training_authorized:false`다. 원본 split은 출처 정보로 별도 보존한다. AI 검토 20개 기록과 실제 사람의 검토를 구분하며, 신원·판정·근거를 자동 채우지 않는다. 별도 4건의 원래 `development`, `training_allowed:false` 상태도 그대로 유지한다.

## 생성과 확인

저장 위치는 Git 제외 로컬 경로를 사용한다. 다음 명령은 저장된 파일만 읽으며 모델·DB·기존 후보를 변경하지 않는다. 출력에는 원문이나 사례 ID 없이 집계와 manifest 해시만 표시한다.

```sh
cd data
python -B -m counseling_pipeline.human_review_bundle \
  --release outputs/private/composition_v2_20261016/supporter/release \
  --pending-cases outputs/private/composition_v2_20261016/supporter/revision_2/human_expert_pending_cases.jsonl \
  --legacy-review outputs/private/finals_source_review_20261016 \
  --contract docs/support_agent/결선_데이터_검토계약_2026-10-16.md \
  --output outputs/private/human_review_v13_20261018_r1
```

검증할 때는 같은 인자에 `--verify`를 추가한다. 인계받은 별도 기록의 manifest SHA-256을 `--expected-manifest-sha256`으로 지정하면 묶음 자체의 교체도 탐지한다. 기존 출력은 덮어쓰지 않는다. 코드·원본·검토 계약이 바뀌면 새 버전 경로에 다시 생성하고 이전 묶음을 보존한다. 누락·추가·중복·내용 변경·원본 변경·승인 필드 위조는 실패하며 CLI 종료 코드는 2다.

현재 인계본은 **`human_review_v13_20261018_r1`**이다. 2026-10-18에 HR5의 입력 해시·소비 내용 불일치와 HR6의 Unicode JSONL 왕복 오류를 수정해 새 버전을 만들었다. manifest SHA-256은 `6da9d4115218d0794fdec7679bd40b0a2cd5f1c6c76735ed59645cd6a02e3899`다. 이전 `_r5`를 포함한 30파일은 보존했고 검토 내용 5파일은 `_r5`와 바이트가 같다. 기존 출력이 있으면 생성 명령에 `--verify --expected-manifest-sha256 <별도 기록한 실제 해시>`를 붙여 검증한다. 현재 구현으로 이전 버전 검증이 거절되는 것은 구현 결속의 결과이며 사람 판단 취소나 원본 손상을 뜻하지 않는다. [수정·검증 근거](../../../docs/competition/결선_v13_HR5_HR6_수정과_인계재검증_2026-10-18.md)

이 인계본의 범위는 기존 **합성 20대화·응답 24단위와 전문 보류 4단위**다. 이후 v9에서 추가한 주변인 응답 48개와 앱 단계 정답쌍 24개를 포함하는 전체 검토 묶음으로 확대했다고 해석하지 않는다. 사람 승인 0건이며 독립 test도 새로 확보하지 않았다.

manifest의 외부 pin 비교·엄격한 JSON 파싱·계획 비교·반환 해시는 한 번 캡처한 바이트에 결속한다. 파일을 읽는 동안과 산출물 검사 뒤에 내용·파일 식별자·크기·수정/변경 시각을 대조해 중간 변경을 거절한다. 공백 표현이 다른 JSON도 그 실제 바이트의 pin과 내용이 맞으면 검증할 수 있다. 성공은 검증한 스냅샷에 대한 판정이며, 파일 잠금이나 반환 이후의 불변을 보장하지 않는다.

모든 원본 입력도 안정성을 확인하며 한 번 캡처한다. 입력 SHA-256과 길이, 릴리스 검사·질문은행 탐지·사례 재검증·legacy 연결·계약 사본은 모두 그 바이트를 사용한다. 선언되지 않은 파일을 읽는 대체 경로는 없다. 생성 준비 끝·발행 직전과 별도 검증 완료 직전에 바이트와 파일 식별자·시각을 다시 비교한다. 잠깐 다른 내용으로 바뀌었다 복원되는 A→B→A 변경도 잘못된 내용으로 성공 발행하는 근거가 될 수 없다.

JSONL은 LF를 레코드 경계로 사용하며 CRLF도 지원한다. 문자열 내부의 U+2028·U+2029는 raw/escaped 표현 모두 보존한다. 빈 레코드는 기존처럼 건너뛰고 공백만 있는 레코드는 거절한다. 잘못된 문자열을 삭제하거나 파싱 오류를 무시하지 않는다.

입력 26파일에는 기존 코드 외에 중복 검사에 쓰는 `source_selection_audit.py`, 패키지 `__init__.py`, 실제 탐지에 읽는 질문은행을 포함한다. 현재 사례에 일치하는 질문이 없어도 해당 리소스 변경은 새 인계 버전을 요구한다. 질문은행의 버전·질문 목록·각 질문 객체·탐지 문자열 형태도 사용 전에 검사한다. 프로젝트 파일의 바이트 결속이며 실행 중 메모리·Python 표준 라이브러리·검토자 신원의 인증은 아니다.

JSON 문서가 객체가 아니거나 JSONL 행·접두부·판정 등의 컨테이너 타입이 잘못되면 일반 오류 JSON과 종료 코드 2를 반환한다. 릴리스 manifest의 파일별 메타데이터도 객체, 문자열 해시, 불리언을 제외한 비음수 정수 행 수여야 하고 실제 파일과 일치해야 한다. 잘못된 입력으로 새 묶음을 만들지 않으며, 기존 묶음 검증 실패도 그 묶음을 변경하지 않는다. 오류 출력에는 원문·입력 경로·traceback을 싣지 않는다.

**현재 인계의 경로 제약:** manifest는 해석된 절대 입력 경로와 구현 해시를 포함한다. 같은 파일 바이트를 다른 작업 루트로 옮기는 것만으로 기존 manifest를 검증할 수 있는 형식은 아니다. 기존 묶음의 검증에는 같은 해석된 입력 경로·바이트·구현이 필요하다. 다른 환경에서 새 묶음을 만들면 별도 버전과 manifest 해시로 기록하고 검토 단위의 내용 해시를 대조해야 한다. 이 절차는 사람의 판정·신원을 자동 이전하거나 승인하지 않는다. 논리 입력 ID와 로컬 경로를 분리하는 이식성 개선은 아직 구현하지 않았다.

## 실제 검토자가 할 일

1. 원문 접근·사용 범위가 허용된 로컬 환경에서 검증한다. 처음에는 `blind_inputs.jsonl`만 열고 단위 해시에 결합된 접두부 판단을 별도 기록한다.
2. `target_packets.jsonl`에서 동일 `review_unit_id`와 `review_unit_sha256`의 응답·주석을 연다. 근거·관점·행동·자율성·안전·개인정보·출처를 검토하고 실제 신원·역할·시간대가 있는 시각·판정 사유를 기록한다. AI 검토자와 사람이 같다고 기록하지 않는다.
3. 서명할 판단 기록은 별도의 접근 통제된 append-only 검토 기록으로 남긴다. 초기 pending 묶음을 승인 상태로 덮어쓰지 않는다. 불일치와 수정 이력은 보존하고 수정된 내용은 다시 검토한다.
4. 질문은행·안전 행동 4건은 전문가 자격, 정책/자료 버전·내용 해시, 사용 권한을 확인할 때까지 보류한다. 이 도구는 전문 판단이나 자료 사용 권한을 만들어 주지 않는다.
5. 학습 사례로 진행하려면 기존 `agent_training`의 사례 스키마·9개 검토 항목·허용 근거·분할·노출 게이트를 별도로 통과해야 한다. 인계 요청은 학습 사례나 승인 리뷰 형식이 아니므로 exporter에 직접 넣지 않는다. 합성 episode의 AI 승인을 사람 승인으로 이름만 바꾸는 변환은 제공하지 않는다.

검증기는 기록 연결과 pending 상태만 확인한다. 사람 신원·자격의 진위, 판단의 질, 누락된 출처나 과거 사용 이력의 완전성은 운영상 확인해야 한다. 묶음과 모든 원본·해시를 함께 다시 쓰는 행위를 로컬 해시만으로 인증할 수 없으므로 인계 manifest 해시는 별도로 보관한다.
