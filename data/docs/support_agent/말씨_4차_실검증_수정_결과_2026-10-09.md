# 말씨 4차 실검증·수정 결과

작성일: 2026-10-09. 대상은 사용자가 첨부한 「말씨 4차 적대적 검증 — 실데이터·토큰·GPU 검증 보고서 재검토」다. 첨부 문서는 검토 근거로 읽었으며, 그 안의 제안을 실행 권한으로 취급하지 않았다. 실제 데이터·코드·기존 기록을 대조하고 제한된 GPU 검증을 추가했다.

**판정: 원본 상담의 짧은 문맥 연구 후보라는 기존 한정은 타당하다. 이번에 출처 누락과 증거 절단을 재현·수정했고, 실제 토큰 배열과 생성 입력 연결을 추가 확인했다. 말씨 보호자/HOP 상담 모델을 바로 학습·출시할 준비가 끝났다는 판정은 여전히 불가하다.**

서버 전용 Python venv를 재사용하고 GPU 0 한 장을 UUID로 고정했다. Python 패키지·캐시·작업 경로 격리이며 VM/Docker 격리는 아니다. 옵티마이저 생성·step, 전체 학습, 모델 체크포인트 저장은 수행하지 않았다. GPU 검증의 LoRA 해시는 전후 동일했다.

## 2. 재현해 수정한 결함과 방어 공백

### A. 공유 문맥의 두 번째 출처가 사라짐 — 실제 구현 결함

`source_selection_audit.py`는 같은 문맥 해시의 출처를 split마다 하나만 보존했다. 같은 첫 8개 메시지를 공유하는 train 그룹 2개와 validation 그룹 1개를 구성하면, 실제로는 3개 그룹이 연결되는데 2개 그룹만 보류됐다. 나머지 train 그룹이 후보에 남는 반례를 원천 SQLite → SFT → 감사 → 보류 장부 경로에서 재현했다.

수정 후 각 공유 문맥은 모든 상담의 출처 목록을 갖는다. `source_admission.py`는 전체 그룹을 합집합으로 보류하고, 모든 출처와 실제 원본의 공유 해시 집합을 다시 비교한다. 구형 단일 대표 보고서도 원본 전수 대조로 출처가 완전함이 확인될 때만 허용한다.

### B. 공유 문맥 증거가 20개에서 잘림 — 감사·보류 연결 실패

공유 문맥 예시를 `[:20]`으로 자르던 처리를 제거했다. 21개 공유 문맥 반례에서 이전 admission은 개수 불일치로 중단했다. 이것은 조용한 재유입과 구분되는 증거 불완전 문제다. 수정 후 모든 공유 문맥을 증거에 남긴다.

### C. 과거 응답 일치의 누락 출처를 놓침 — 불완전 감사 입력 방어 공백

200자짜리 동일한 과거 상담사 응답을 가진 train 두 그룹과 일치 목표를 가진 validation을 구성했다. 감사 결과에서 두 번째 train 출처 하나를 제거하면, 이전 admission은 이를 받아들여 보류 5행 중 train 2행을 재허용했다.

최종 admission은 **모든 train 과거 assistant와 모든 validation 목표에서 공유 문구·train 출처·validation 행을 재구성**한다. 선언된 목록이 실제 목록과 정확히 같아야 진행하며, 문구 전체 삭제·출처 삭제·검증 행 삭제·중복 증거를 거부한다. producer의 정상 출력에 출처 누락이 있었다는 주장과, 불완전한 보고서를 consumer가 거절하지 못했다는 발견을 구분한다.

### D. 새 생성 검증기의 종료 분류 보강

생성 준비 함수는 마지막 정답을 제외한 native 생성 prefix를 독립 렌더링하고 정확한 token IDs를 확인한다. `prefix + max_new_tokens`가 선택한 총 예산을 넘으면 잘라내지 않고 거부한다. 본문에 역할·thought·제어 토큰이 있으면 거부하며 `<|tool_response>` 종료를 일반 답변 완료로 세지 않는다.

독립 리뷰에서 새 helper가 EOS 없이 짧게 끝난 출력을 `length_limit`로 분류할 수 있음을 발견해 수정했다. 이제 EOS가 없으면 예약 길이를 정확히 소진해야 한다. 이번 실제 GPU 출력은 EOS 2건·정확히 64토큰 소진 1건으로 이 추가 조건도 충족한다. helper 변경만을 위해 GPU를 다시 실행했다고 주장하지 않는다.

- 발화 근거가 연결된 감정 설명과 HOP 지원 행동 정답.
- 원본 이력 평가와 모델 자체 응답이 누적되는 다턴 평가.
- 충분한 전환·회복·종료 사례, 정책 고정 후 미사용 최종 test.

## 5. 캐시 없는 실제 토큰·라벨 대조 — R4-05

고정된 Transformers 5.17.0에서 전체 1,069개 상담을 방문했다. 각 상담의 첫·중간·마지막 행과 가능한 경계 공백 행을 선정하고 중복을 제거해 **3,155행**을 검사했다. 각 행마다 캐시 경로와 해당 행의 native 생성 prefix를 사용하는 비캐시 `encode_example` 경로를 비교했다.

`input_ids`, `labels`, `attention_mask`와 인코딩 결과의 모든 메타데이터가 정확히 같았다. 첫 assistant 사례 2,664행, 목표 경계 공백 36행, 메시지 경계 공백 101행, 현재 목표가 더 긴 행에서 과거 이력이 되는 사례 2,086행을 포함한다. 각 특징은 중복될 수 있다.

전체 원본 45,974행의 파일 해시·행 수·상담 범위는 확인했다. **비캐시 배열 비교 자체는 3,155행 표본이며, 45,974행 전부의 비캐시 배열 대조라고 확대하지 않는다.** 원본 줄의 바이트 보존과 native template의 경계 `.strip()`은 별도 계약이다. 원본 JSONL을 그대로 보존해도 모델 입력 문자열은 경계 공백 변환을 포함한다.

## 6. 실제 손실 비교: 초기 실패와 원인 분리 — R4-05

실제 원본의 길이 256/512 예시를 batch 2로 오른쪽 패딩했다. 전체 목표 87개, 각 행 첫 목표 1개씩, native 응답 끝 `<turn|>` 1개씩을 따로 감독했다. 첫 감독 위치는 221/460, 대응 logits 위치는 220/459다. 종료 label 위치는 254/510, 대응 logits 위치는 253/509다. 첫 행의 padding 256개는 손실에서 제외된다.

초기 GPU 실행에서 종료 토큰의 fused loss 0.2837460637과 반환 logits 수동 CE 0.2710328698이 사전 기준 `atol=0.002, rtol=0.002`를 벗어났다. 초기 실패 JSON·로그·실행 코드를 보존했다. 이를 통과시키려고 허용 오차를 넓히지 않았다.

추가 실행에서 실제 fused forward의 최종 hidden state를 캡처했다. 전체 FP32 head 참조에서도 종료 손실 0.2910676897 대 0.2864160538, 차이 0.0046516359가 남았다. 반환 logits 분기의 `no_grad` hidden state도 fused 분기와 최대 0.03125 차이가 있어, 단순 두 forward 비교만으로 label 버그라고 결론낼 수 없었다.

재실행의 반환 logits 비교는 첫 목표 토큰도 13.3874807358 대 13.4373388290, 차이 0.0498580933으로 기준을 넘었다. 같은 hidden state의 전체 FP32 참조에서는 첫 목표 비교가 통과했지만, 아래 정밀도 분리 진단은 종료 label 두 개에 한정했다. 첫 목표의 반환 logits 차이까지 동일한 원인으로 완전히 설명했다고 주장하지 않는다.

다음 진단에서는 **같은 hidden state와 같은 BF16 head 출력**을 사용해 softcap 정밀도만 분리했다. 실제 런타임은 CCE 비활성, Unsloth chunked compiled CE 활성 상태였다.

| 동일 중간값 진단 | 종료 label 두 개의 평균 CE |
|---|---:|
| 실제 모델 fused | 0.2910676897 |
| BF16 head → FP32 softcap → CE | 0.2910677195 |
| 직접 fused 함수, compile=True, 한 chunk | 0.2910677195 |
| BF16 head → eager BF16 softcap → CE | 0.2734025419 |
| 직접 fused 함수, compile=False, 한 chunk | 0.2734025419 |
| FP32 softcap 후 BF16으로 다시 반올림 | 0.3026933968 |

해당 배치에서는 compiled 경로와 FP32 softcap 기준이 약 **2.98×10⁻⁸** 차이로 맞고, 비컴파일 경로와 eager BF16 기준은 일치한다. 따라서 관측한 종료 손실 차이는 이 사례의 컴파일/중간 정밀도 차이로 재현된다. shift를 하지 않은 음성 대조의 CE는 2.4425868988로 달랐다. 이 증거로 현재의 label shift 오류를 확정할 근거는 찾지 못했다.

그러나 **초기 엄격한 비교 gate는 실패로 유지**한다. 모든 행·gradient·학습 품질·Trainer 동등성을 통과한 것으로 처리하지 않는다. 이번 결과는 같은 수학식이라도 연산 순서와 dtype에 따라 결과가 달라질 수 있다는 일반 원칙과 부합하지만, 판정의 직접 근거는 설치된 코드와 위 실행이다. [PyTorch 수치 정확성 문서](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html)는 일반 설명에만 사용했으며, 실제 실행 버전은 2.13.0이다.

## 7. 생성 입력·종료·예산 — R4-06

실제 `generate`의 첫 forward에 hook을 걸어 모델이 받은 token IDs를 확인했다. `token_healing=False`, greedy 생성, 고정 native 종료 ID 목록을 사용했다. 검증 prefix를 직접 전달했고 정답을 다시 붙이거나 template/BOS/assistant 헤더를 중복 적용하지 않았다.

| 예시 | Prefix | 새 토큰 예약 | 실제 새 토큰 | 종료 |
|---|---:|---:|---:|---|
| 합성 짧은 종료 요청 | 48 | 64 | 16 | `<turn|>` |
| 원본 길이 256 예시 | 221 | 128 | 52 | `<turn|>` |
| 원본 길이 4,096 예시 | 4,024 | 64 | 64 | 길이 소진, 문장 미완결 |

3건 모두 실제 prefill SHA가 검증 prefix SHA와 같다. 본문에 역할·thought 제어 토큰은 없었다. 긴 사례는 OOM이 아니라 길이 제한으로 중단됐다. 4,024+128은 4,096을 넘으므로 같은 프로파일에서는 허용하지 않는다. 이 3건으로 HOP 행동 품질이나 자연 종료의 성공률을 주장하지 않는다.

기존 후보 17,236행에 고정 생성 예약량을 적용하면 추가 보류가 필요하다.

| 새 토큰 예약 | Train 수용 / 추가 보류 | Validation 수용 / 추가 보류 |
|---|---:|---:|
| 64 | 15,466 / 46 | 1,720 / 4 |
| 128 | 15,303 / 209 | 1,698 / 26 |
| 256 | 14,897 / 615 | 1,652 / 72 |
| 512 | 14,022 / 1,490 | 1,545 / 179 |
| 1,024 | 12,259 / 3,253 | 1,335 / 389 |

계산은 `prefix_tokens + max_new_tokens ≤ 4096`이며 원문을 자르지 않았다. 이 표는 선택한 4,096 생성 프로파일의 예산 검사다. 다른 추론 한도가 불가능하다는 뜻은 아니며, 다른 한도는 별도 실측이 필요하다. Transformers의 `max_new_tokens`는 입력 길이를 제외한 생성 길이다. [Transformers 5.17 생성 API](https://huggingface.co/docs/transformers/v5.17.0/en/main_classes/text_generation)

## 9. 재현·증거 사용법

ZIP에는 최종 코드·테스트·이번 감사/보류 장부·실제 GPU 실행 당시 코드와 성공/실패 로그·기존 3차 토큰 장부·17,236행 후보·보고서·멤버 SHA manifest를 넣는다. 원본 45,974행 전체 파일, 12GB DB, 모델 weights, 기존 전체 문장·단어 자료는 중복 포함하지 않는다. 따라서 단위 반례는 ZIP만으로 재현할 수 있지만 실데이터 전수 재생성과 GPU 재실행은 해당 원본과 체크포인트가 별도로 필요하다.
