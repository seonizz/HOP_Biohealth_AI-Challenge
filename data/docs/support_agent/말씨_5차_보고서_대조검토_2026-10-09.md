## 3. 손실과 87개 감독 토큰 — R5-01

5차가 제시한 엄격 손실 실패 판단은 실제 코드의 `차이 ≤ 0.002 + 0.002 × |기준값|` 계산과 맞는다. 4차의 종료 토큰 정밀도 진단이 이를 전체 통과로 바꾸지 않는다는 해석도 맞다.

특히 보존된 비교 결과는 다음과 같다.

| 기준 경로 | 전체 목표 | 첫 목표만 | 종료 토큰만 |
|---|---|---|---|
| 같은 hidden state의 전체 FP32 head 참조 | 기준 내 | 기준 내 | 기준 초과 |
| 별도 forward의 반환 logits 참조 | 기준 내 | 기준 초과 | 기준 초과 |

같은 BF16 head 출력에서 softcap 정밀도를 분리한 후속 진단은 종료 label 두 개의 평균만 다뤘다. `n_chunks=1` 직접 호출과 평균 CE가 기록돼 있으며, token별 CE·gradient 비교 결과는 저장돼 있지 않다. 따라서 5차가 제안한 첫 목표·본문·token별 손실·불균등한 유효 label 수의 chunk 집계 확인은 **남은 검증 조건**이다. 실제 집계 버그가 발견됐다는 뜻은 아니다.

감독 수 87개는 보존 배열에서 직접 확인했다.

| 원본 입력 길이 | 최초 감독 위치 | 종료 토큰 | 종료 뒤 감독 토큰 | 감독 수 |
|---|---:|---|---|---:|
| 256 | 221 | 위치 254: ID 106 | 위치 255: ID 107 | 35 |
| 512 | 460 | 위치 510: ID 106 | 위치 511: ID 107 | 52 |

종료 ID 106까지만 세면 85개이며, 그 뒤 ID 107 두 개도 label에 포함되어 87개가 된다. 오른쪽 패딩 256개는 모두 `-100`이다. 종료 직렬화 계약 `<turn|>\n`과 일치한다. 이번에는 저장 배열을 확인했으며 ID 107을 실제 vocabulary로 다시 decode하지는 않았다. 따라서 ‘85개인데 87개로 잘못 계산했다’는 의심은 해소되지만 손실 수치 동등성까지 입증한 것은 아니다. ## 5. 생성 예산별 평가 대상 — R5-03

다섯 조건의 교집합은 train 12,259행, validation 1,335행이다. [공통 ID 목록](../../outputs/private/malssi_round5_review_20261009/common_profile_ids.json)을 저장했다. 이는 공정한 조건 비교를 위한 기존 후보 목록이며, 미사용 최종 test나 의미 품질 승인 정답이 아니다.

| 예약 | Validation 수용 | 원문 앞 1/3 | 중간 1/3 | 앞 1/3 비중 | 상위 5개 그룹 비중 |

## 6. EOS와 생성 설정 — R5-04

현재 helper는 예약 마지막 위치의 EOS도 `termination=eos`로 표시한다. 동일한 token IDs가 자연 생성인지 강제 EOS processor가 넣은 것인지 알려주는 입력은 없다. 따라서 이 필드를 ‘모델이 스스로 완결했다’는 의미로 쓰려면 실행 설정의 근거가 더 필요하다. Transformers 5.17의 `forced_eos_token_id`는 길이 한계에서 EOS를 넣을 수 있다. [공식 생성 API](https://huggingface.co/docs/transformers/v5.17.0/en/main_classes/text_generation)

다만 실제 저장 결과는 조기 EOS 16/64·52/128과 EOS 없는 길이 소진 64/64다. 실제 2건이 마지막 강제 EOS로 잘못 분류됐다고 볼 근거는 없다.

남는 증거 공백은 최종 상속된 generation config와 raw 생성 suffix IDs가 저장되지 않았다는 점이다. 다음 실행에서는 유효 `forced_eos_token_id`·종료 IDs·stop 문자열·추가 stopping criteria와 생성 suffix를 함께 남기면 원인 재판정이 가능해진다. 상담 답변의 의미적 완결성은 별도로 평가해야 한다.

로컬 합성 검사는 종료 경계 7개와 예산 4,095/4,096 허용·4,097 거부 3개를 확인했다. 같은 10개가 일반·`-O` 모드에서 모두 통과했다. 실제 모델 생성 10건을 실행한 것으로 계산하지 않는다. [합성 검사 기록](../../outputs/private/malssi_round5_review_20261009/generation_lane/findings.json)

## 7. 현재 마무리된 것과 다음 단계

이번 검토로 A–C 수정의 해당 반례, CLI 반환 연결, 87개 감독 수, 생성 예약별 실제 ID 포함 관계를 확인했다. 기존 295개 전체 회귀와 GPU 실험을 무조건 반복하지 않고 필요한 경계만 검사했다. 이번 검사 수는 **기존 회귀 26개, 별도 프로세스 6건, 합성 경계 10개**로 단위가 달라 하나의 총 테스트 수로 합치지 않는다.

다음에는 아래 목적에 맞춰 필요한 검증을 선택하면 된다.

1. 손실 경로: 비교 기준을 먼저 고정하고 첫 목표·본문·종료의 token별 CE, 유효 label 수가 다른 chunk, 필요한 gradient 범위를 확인.
2. 자동 실행: 저장 보고서의 필수 항목·상태를 검증하고 종료 설정·원시 생성 IDs를 보존.
3. 실제 학습: 업데이트를 진행할 단계에서 Trainer·옵티마이저·저장/재개·실제 자원 사용 확인.
4. 말씨 목표: 보호자 관점, 근거 있는 감정 설명, HOP 지원 행동과 다턴 회복·종료 평가.

현재 `model_training_authorized=false`, `optimizer_fit=unknown`, `hop_readiness=false`는 그대로다. 5차 보고서는 기존 검증을 무효화한 것이 아니라, 이미 확인한 범위와 다음 판단에 필요한 근거를 더 구체화한 것으로 평가한다.
