# 대화 보유와 삭제 운영 계약

작성일: 2026-10-16. v7의 O1(쿠키·세션 상실 뒤 삭제 수단 부재)을 보완하는 구현 계약이다. 이 변경을 확인하기 위해 사용한 것은 합성 데이터와 격리된 PostgreSQL 테스트 스키마다. 운영 DB에 마이그레이션이나 청소를 실행했다는 기록이 아니다.

## 개발 기본 정책과 집행

- `DATA_RETENTION_DAYS=30`은 **개발·시연 기본값**이다. 정수 1~90일만 허용하며 잘못된 값은 서버 시작을 거절한다. 운영 적용 기간·책임자가 확정됐다는 뜻은 아니다. 직접 실행의 `.env`, 생성 설정, Compose 환경 전달을 지원한다.
- 기산점은 `browsers.last_active_at`이다. 유효한 세션 쿠키로 API에 접근하면 DB 시각으로 갱신한다. 목록 조회·진행 조회도 접근에 포함되므로 열린 화면의 API 사용은 비활동 기간을 갱신할 수 있다. 쿠키의 고정 `SESSION_TTL_DAYS`는 연장하지 않는다. 잘못된/만료된 쿠키 및 삭제 키 사용은 이 시계를 갱신하지 않는다.
- `last_active_at <= 현재 DB 시각 - 보유기간`이면 접근을 허용하지 않는다. 시작 시 청소가 성공해야 서버를 열고, 실행 중에는 1시간마다 청소한다. 실패는 상담 내용 없는 `retention_cleanup_failed` 이벤트와 `/health`의 HTTP 503·`retention_cleanup_ok:false`로 드러내며 다음 주기에 재시도한다. 원래 로그에 요청 본문·세션 토큰·삭제 키를 기록하지 않는다.
- 정상 실행 중 SQL 삭제 시점은 만료 후 다음 청소까지 최대 1시간 늦을 수 있다. 서버가 정지해 있으면 재시작 때 삭제한다. 청소 실패·DB 장애 동안 정해진 시간 내 물리 삭제를 보증하지 않는다. 유효기간 조회 경계는 청소가 지연되어도 만료된 소유자를 재활성화하지 않는다.
- 자동 청소는 소유자 행 및 FK 연쇄로 `intakes`, `records`, `patient_states`, `patient_state_revisions`, `column_states`를 함께 제거한다. 세션 자격증명·삭제 키 해시도 제거한다. 질문 카탈로그는 대상이 아니다.

기존 DB에는 과거 접근 시각이 없으므로 `006_data_retention.sql` 적용 시점을 기존 소유자의 기산점으로 설정한다. 그 시점부터 설정 기간의 유예를 주며, 과거 이용일을 추정하거나 기존 내용을 즉시 삭제하지 않는다. 이전 소유자에게 삭제 키가 자동 생기지는 않는다. 유효 세션이 있는 이용자는 발급할 수 있고, 세션을 잃은 기존 이용자는 유예 후 자동 삭제 대상이다.

## 이용자의 삭제 경로

1. **현재 세션:** 내 기록에서 완료·미완료 대화를 개별 또는 전체 삭제한다. 연결된 원문·결과·상태·이력을 트랜잭션으로 삭제하며 칼럼의 읽음·담음은 남긴다.
2. **별도 보관한 삭제 키:** 접근이 가능한 동안 내 기록에서 발급한다. 서버는 무작위 32바이트(256비트), base64url 43자 키를 한 번 반환하고 SHA-256 해시만 저장한다. 새 키 발급은 이전 키를 무효화한다. 화면은 교체를 확인하고 키를 별도 보관하도록 안내한다. 키를 브라우저 영구 저장소에 자동 저장하지 않는다.
3. **쿠키 분실·세션 만료 후:** 새 세션이거나 쿠키가 없어도 내 기록에서 보관한 키를 입력해 해당 소유자의 모든 대화를 삭제할 수 있다. 두 단계로 범위를 확인하며 키가 다른 소유자의 것이면 현재 화면의 기록은 지우지 않는다. 쿠키만 지우고 화면을 새로고침하지 않은 경우에도 현재 세션의 목록을 다시 읽고, 세션이 바뀌었으면 이전 활성 대화를 지운다. 삭제 성공 뒤 목록 재조회에 실패하면 삭제 처리와 화면 갱신 실패를 구분해 알린다. 키를 가진 사람은 삭제할 수 있으므로 별도 보관이 필요하다. 이 키는 대화 조회·복구·새 세션 발급을 허용하지 않는다.
4. **키도 없는 경우:** 사람 이름이나 상담 문장으로 소유자를 추정하는 우회 경로는 없다. 마지막 유효 접근 시각 기준 보유기간 삭제가 적용된다. 아직 발급하지 않은 키를 잃어버린 세션에 소급 발급할 수 없다.

키 제출은 JSON 본문의 `POST /api/conversations/delete-with-key`로만 처리한다. URL 쿼리로 받지 않는다. 명시적인 허용 Origin, 기존 IP 속도 제한, 본문 크기 제한을 적용한다. 키를 보내는 데 세션/CSRF가 필요하지 않고, 발급에는 모두 필요하다. 잘못된 키·교체된 키·자동 삭제 후 키는 같은 `404 DELETION_KEY_INVALID`를 반환한다. 성공 응답은 삭제 여부와 현재 쿠키의 대상 일치 여부만 알리며 상담 내용을 반환하지 않는다. 삭제 후에도 키를 유지해 응답 손실 재시도를 허용한다. 자동 보유기간 삭제나 새 키 발급 이후에는 이전 키를 사용할 수 없다.

## 동시 요청과 검증

전체 삭제·키 삭제·새 상담 생성·답변 저장·결과 저장은 같은 소유자 행을 먼저 잠근다. 키 삭제는 `conversation_epoch`를 증가시켜 삭제 전에 제출됐지만 아직 저장하지 않은 새 대화를 거절한다. 삭제된 상담의 늦은 답변/결과 저장도 실패하며 새 행을 만들지 않는다. 자동 청소와 접근 갱신은 소유자 행 잠금으로 직렬화되고, 만료 후 새 데이터 쓰기는 청소 전에도 차단한다.

`tests/retention.test.js`는 설정값, 만료 쿠키, 쿠키 분실, 다른 소유자, 잘못된 키·키 교체·재시도, 키의 조회 권한 부재, Origin·CSRF·본문·속도 제한, 보유기간 경계, 지연 생성/저장, 시작·주기 청소, 청소 실패/회복, 기존 DB 유예를 합성 DB로 확인한다. `tests/ui.test.js`는 발급 확인, 키 대상 확인, 성공 전 캐시 보존, 다른 소유자 기록 보존, 실패와 입력 변경을 검사한다. DB는 `TEST_DATABASE_URL`의 무작위 스키마만 사용한다.

```sh
node --test tests/store.test.js tests/retention.test.js tests/ui.test.js
npm run check
```

위 DB 검사를 실행할 때는 운영 DB가 아닌 전용 합성 테스트 DB의 `TEST_DATABASE_URL`을 설정한다. DB가 없어서 건너뛴 결과는 삭제 검증 완료로 세지 않는다.

## 운영에서 아직 확정하지 않은 범위

| 항목 | 현재 확인 상태 | 운영 적용의 남은 조건 |
|---|---|---|
| 보유기간과 운영 책임자 | 개발 기본 30일과 실행 코드는 구현, 운영 승인·실명 담당자 미확정 | 실제 운영 주체가 기간·담당자·장애 대응을 기록 |
| 서비스 DB 삭제 | 트랜잭션 후 조회되는 행과 연결 상태의 제거를 테스트 | 운영 배포 시점·기산점 고지, 청소 상태 감시와 실패 대응 확인 |
| DB 파일·WAL·복제본·백업 | 이 구현은 SQL 논리 삭제이며 저장매체의 즉시 덮어쓰기를 증명하지 않음 | 백업 위치·보유기간·만료 삭제·복원 시 삭제 재적용 절차와 책임자 확인 |
| 모델 제공자·내보낸 파일 | 앱 DB 밖의 보관본을 이 API로 삭제하지 않음 | 외부 제공자 정책, 검증 내보내기·수동 사본 보유·삭제 범위 확인 |
| 운영 DB 적용 | 이 수정의 검증에서 미실행 | 운영자가 적용 계획·설정·기존 데이터 유예를 검토한 뒤 배포 |

운영 책임자와 백업 실제 삭제가 확인되지 않은 동안 “모든 저장 위치에서 완전 삭제 완료”나 “현장 운영 준비 완료”로 표현하지 않는다.

## 운영 증거의 로컬 사전 점검

`scripts/check-operations.js`는 위 미확인 항목을 빠뜨리지 않도록 **제출된 선언과 로컬 근거 파일의 해시**를 검사한다. 운영자를 인증하거나 문서 내용의 사실성을 판정하지 않으며, `.env`를 읽거나 DB·네트워크에 연결하거나 배포·복원·삭제를 실행하지 않는다. 실제 사람의 승인, 운영 배포와 매체 삭제는 별도 확인 사항이다.

```sh
# 인자를 생략하면 빈 실제 증거 템플릿을 검사한다. 현재 결과는 pending / 종료코드 1이다.
node app/scripts/check-operations.js

# 운영 담당자가 별도 로컬 폴더에 준비한 증거 목록을 읽는다.
node app/scripts/check-operations.js runtime/operations/operations.json
```

[빈 템플릿](operations-evidence.template.json)은 완료 예제가 아니다. 실제 증거 목록은 Git 제외 로컬 폴더에 복사해 작성하고, 원문·세션/삭제 키·접속 문자열을 근거 문서에 넣지 않는다. 파일 경로는 목록 파일의 폴더를 기준으로 한 상대 경로이고 SHA-256은 실제 파일 바이트의 해시다. URL·상위 경로·심볼릭 링크·알려진 키/환경 파일은 읽지 않는다. 출력은 고정된 필드 경로와 오류 코드만 포함하며 입력한 사람 이름·파일 내용·실제 근거 경로를 출력하지 않는다.

확인 순서는 다음과 같다.

1. **정책 승인:** `actual`과 `synthetic`을 구분하고 서비스 식별자·검토 시각을 기록한다. 실제 비활동 기간 1~90일, `last_valid_api_access` 기산점, 승인자·승인 시각과 승인 근거 파일을 제출한다. 개발 기본 30일을 운영 승인으로 대신하지 않는다.
2. **배포 검증:** 운영 배포 식별자·검증자·시각, 승인 기간과 같은 실제 설정, 현재 앱 소스 fingerprint, `006_data_retention.sql` 적용과 청소 상태의 검증 근거를 제출한다. 이 도구가 실행 중인 서버를 조회한 것으로 표현하지 않는다.
3. **저장 위치:** `database`, `wal`, `replicas`, `backups`, `exports`, `external_copies` 6영역을 각각 한 번 기록한다. 영역별 책임자·인벤토리 근거와 모든 위치의 식별자·보유일·만료 규칙·만료 검증 근거가 필요하다. 미사용 영역도 `not_used` 선언, 이유, 책임자와 이를 뒷받침하는 인벤토리 근거가 있어야 한다. 서비스 DB를 미사용으로 처리할 수 없다. 외부 보유본에는 사용 중인 제공자·수동 내보내기·사본의 범위를 실제로 확인해 적는다.
4. **복원과 장애:** 복원 이후 이미 삭제한 데이터의 삭제 재적용 및 만료 접근 차단을 검증한 담당자·시각·근거, 청소 실패 감시와 대응 책임·절차를 제출한다. 비활동 만료 청소만으로 보유기간 안에 수동 삭제한 데이터의 백업 복원까지 해결됐다고 추정하지 않는다.

저장 위치의 `locations` 항목은 `id`, `retention_days`, `expiry_rule`, `expiration_verified`, `expiration_evidence`를 사용한다. 서비스 DB 기간은 승인된 정수 1~90일과 같아야 한다. 그 밖의 위치는 실제 정책에 따라 시간 단위의 소수 일수나 즉시 만료의 0을 기록할 수 있으며, 구체적인 기산점·만료 동작은 `expiry_rule`과 근거 문서에 기록한다. `expiration_evidence`와 나머지 근거 참조는 `{ "path": "evidence/문서.json", "sha256": "실제 64자리 해시" }` 형식이다. 이 설명의 예시 문자열은 근거로 사용할 수 없다. 완료 시각은 미래가 아닌 UTC ISO 형식이며 승인→배포 검증→복원 검증→최종 검토 순서를 따라야 한다.

누락·대기·placeholder·해시 불일치·읽을 수 없는 파일·중복 영역·중복 JSON 키·미적용 배포는 `pending`과 종료코드 1로 차단한다. 정상 목록도 **해당 문서에 선언한 범위의 로컬 점검**일 뿐이다. `evidence_complete`와 종료코드 0은 입력의 증거 형식·해시가 충족됐다는 뜻이며 `production_ready`, `human_approval_authenticated`, `physical_deletion_verified`는 항상 `false`다. 자동 배포 승인 조건으로 사용하지 않는다.

증거 파일은 UTF-8(선택적 BOM)의 **`.json`, `.jsonl`, `.ndjson`, `.txt`, `.md`**만 지원하며 확장자 대소문자는 구분하지 않는다. JSONL·NDJSON은 빈 행을 제외한 모든 행이 JSON 객체·배열이어야 하며, 각 객체의 중복 키와 중첩된 `synthetic:true`를 검사한다. 서로 다른 행·객체에서 같은 키를 사용하는 것은 허용한다. 손상 JSON·잘못된 UTF-8·NUL 등 텍스트 제어 문자는 거절하며, JSON 구조로 시작하는 TXT/Markdown도 JSON 파싱 실패를 일반 텍스트 성공으로 바꾸지 않는다.

일반 TXT/Markdown은 읽을 수 있고 비어 있지 않은지 확인하는 범위다. 문장 의미·승인 사실·자유 서술 속 합성 여부를 인증하지 않는다. PDF·이미지·압축·기타 형식은 `EVIDENCE_FORMAT_UNSUPPORTED`로 거절해 해시만 맞는 파일을 검증 완료로 세지 않는다. 원본 형식을 보관해야 하면 별도 로컬 원본과 대조 가능한 지원 형식의 기록을 준비하고, 실제 운영 담당자가 원본과 내용의 일치를 확인해야 한다. 파싱·형식 오류로 거절된 파일은 `evidence_files_checked`에 포함하지 않는다.

합성 검증은 `synthetic_checks_passed`로만 표시하고 `operational_evidence_complete:false`를 유지한다. 빈 실제 템플릿의 실패와 합성 fixture의 통과는 서로 다른 결과다. 실제 승인·배포·사용자·기관 증거를 생성하거나 운영의 남은 감점을 해소한 것으로 계산하지 않는다.
