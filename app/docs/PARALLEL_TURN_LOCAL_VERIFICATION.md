# 질문·상태 병렬 처리 — 실제 로컬 모델 검증

2026-11-01(KST). Mac의 **Ollama 0.40.5 / `gemma4:12b`**로 합성 사례 4개와 실제 앱 API의 저장·재조회 사례 1개를 검증했다. 모두 통과했다. 모델 생성 POST는 총 **30회**였다.

## 실행 환경

- 모델: `http://127.0.0.1:11434/v1`. 해당 포트의 프로세스가 Mac의 `ollama`임을 확인했다.
- 작성·독립 검토 모델 모두 동일한 로컬 모델을 명시적으로 사용했다. `combined_blocks`, `json_schema`, `reasoning_effort=none`, 로컬 스트리밍·완성 JSON 처리와 토큰 한도 조회를 사용했다. 블록별 입력 축소도 활성화했다.
- 허용된 LAN Ollama `192.168.123.175:11434`는 `Host is down`으로 응답하지 않았다. 사용자에게 알린 뒤 확인된 Mac 모델로 검증했다.
- 모든 입력은 합성 사례다. 기존 상담 데이터·학습 데이터를 읽거나 모델에 보내지 않았다.
- 저장 검증은 이번 작업에서 생성한 일회용 PostgreSQL 컨테이너와 별도 스키마·임시 암호화 키를 사용했다. 기존 앱·DB·모델 설정은 변경하지 않았다.

## 실제 생성·검토 결과

| 합성 사례 | 모델 POST | 확인 결과 |
| --- | ---: | --- |
| 일반 관계 답변 | 6회 | 원문·근거 보존, 상태·안전 검토 승인 |
| 이미 답한 질문 생략 | 7회 | `burden` 생략, 상태·질문·안전 검토 승인 |
| 현재 위험을 부정한 답변 | 6회 | 부정 원문 보존, 긴급 판정 false |
| 이름이 없는 입력 | 5회 | 이름 모델 호출 없음, `name_index=null`, 기존 검토 유지 |
| 합계 | **24회** | **4개 모두 통과** |

위 24회는 모두 HTTP 200이며 구조·의미 오류에 따른 추가 생성이나 operation 재시작 없이 완료됐다. 호출 수는 반복·실패가 없는 이번 합성 실행의 관측값이며 모든 입력에 대한 고정값은 아니다.

실제 시작·종료 시각으로 다음을 확인했다.

1. 네 사례 모두 환자 상태 작성이 끝나기 전에 질문 작성이 시작됐다.
2. 상태 블록 내부는 환자 상태 → 이름 → 관계 기억 순서를 유지했다. 고정 null 이름은 모델 요청을 생략했다.
3. 모든 작성이 끝난 뒤에만 독립 검토가 시작됐다. 실행 대상 검토들은 서로 완료를 기다리지 않고 시작됐다.
4. 저장용 단계 순서는 기존 상태 → 질문 → 검토 순서를 유지했다.
5. 실행 전후 `relationship-turn.js`의 SHA-256이 같았다.

이는 앱 요청의 중첩을 확인한 결과다. Ollama 내부의 물리 추론 병렬성이나 이전 버전 대비 속도 향상률을 측정한 것은 아니다. 최종 카드 O4 경로는 이번 실제 모델 검증에 포함하지 않았다.

## 실제 앱 API와 저장

로컬 `createApp()` 서버의 답변 제출 API에 합성 답변 1개를 보냈다. 실제 모델 **6회**를 거쳐 HTTP 200으로 완료됐으며 아래 **11개 항목**을 확인했다.

- 답변 응답 전 두 작성 분기의 실제 모델 요청이 시작됨
- 생성 중 원답변의 pending 저장 유지
- 승인 전 부분 모델 결과를 저장하지 않음
- 승인 후 revision 갱신
- 승인 후 pending 해제
- 독립 검토 완료 표시 저장
- 원답변 원문 보존
- 상태의 원문 근거 저장
- 관계 기억의 원문 근거 저장
- DB 저장 내용에 평문 원답변이 포함되지 않음
- 저장 결과 재조회 시 내용 동일, 추가 모델 호출 없음

실제 모델을 사용한 취소·재시도 오류 주입과 최종 카드 생성·기록 저장은 이번 라이브 사례의 범위 밖이다. 관련 취소·복구·최종 저장 계약은 아래 기존 회귀 검사로 확인했다.

## DB 포함 회귀 검사와 수정

이전에 DB 부재로 건너뛰었던 검사까지 일회용 로컬 DB에서 실행했다. 첫 실행의 실패 2개는 저장 테스트가 마이그레이션 수를 7개로 가정한 데서 발생했다. 실제 파일과 `Store.connect()`는 `008_record_access_keys.sql`까지 8개였다.

[store.test.js](../tests/store.test.js)의 기대값 두 곳만 **7→8**로 수정했다. 암호화·재시작·키 변경 거절·체크섬 변조 거절·epoch·기록 보존 검증은 유지했으며 운영 코드 변경은 없었다.

| 검사 | 결과 |
| --- | --- |
| 수정 후 저장 검사 | 16개 통과, 실패·건너뜀 0개 |
| 일회용 DB 포함 전체 앱 검사 | **2,032개 통과, 실패·건너뜀 0개** |
| 수정 테스트 구문·공백 검사 | 통과 |
