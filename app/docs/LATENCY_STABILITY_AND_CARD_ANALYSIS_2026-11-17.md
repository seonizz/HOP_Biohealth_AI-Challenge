## 확인한 원인

1. 이전 검증용 전송 계층은 앱 스트림의 취소를 출력 무시로만 처리했다. GPU 생성은 계속되어 다음 요청이 같은 대기열에서 최대 900초까지 기다렸다.
2. 완료된 `request_timeout`을 모두 치명적 오류로 분류했다. 작업기가 요청 예외를 처리하고 살아 있어도 재시도·사후 검토를 `transport_closed`로 막았다. 전역 `CANCEL`은 작업기 종료용이어서 일반 요청 취소에 재사용할 수 없다.
3. JSON 제약은 올바른 형식만 보장한다. 문자열 안의 같은 허락 질문 448회 반복은 허용 길이 안이었고, 기존 중복 발화 검사는 완성된 출력만 검사했다. 반복이 처음 발생한 모델·프롬프트·디코더 요인의 기여는 이 한 번의 실행으로 분리하지 못했다.
4. 질문 뒤쪽에서 생략 판단이 1개에서 4개로 증가했다. 출력 토큰 64–77개가 237–250개로 늘어 디코딩이 약 14–18초에서 61–66초로 길어졌다. 질문별 모델 계산 횟수/초는 약 2.94–3.04로 비슷했다. 대기열 3–9ms와 문법 컴파일 약 0.1초는 주요 원인이 아니다.
5. 독립 안전 검토를 마치면 최종 분석 스키마에서 `safety`를 제거한다. 기존 근거 ID 변환기는 이 유효한 스키마를 지원하지 않아 분석 근거를 긴 원문 객체로 다시 출력하게 했다.

## 수정한 동작

- 반복 발화는 생성 중 조기 차단한다. 일반 초안은 동일한 완결된 허락 질문 12회 반복 시 중단하며, 이미 직접 발화 검증을 적용하던 경로는 기존 1회 상한을 유지한다. 미완성 출력을 승인하거나 저장하지 않는다.
- 요청 UUID별 취소 표식을 사용한다. 모델이 해당 요청을 멈추고 캐시 정리·어댑터 동일성 검사를 마친 종료 응답을 받은 뒤에만 다음 요청을 시작한다. 다른 요청·작업기는 종료하지 않는다.
- 종료 요청 ID와 복구 증거가 모두 일치한 시간 초과·취소만 재사용한다. 종료 확인 누락·불일치·작업기 장애는 계속 실패로 처리한다. 정상 종료 직후 늦게 도착한 취소가 다음 요청을 취소하지 않도록 구분한다.
- 질문 생략 출력의 필드명·이유 코드 축약을 실험했으나 첫 실측 실패 후 제거했다. 근거 ID 압축은 유지하며 원래 질문 ID·설명·근거·판단을 기존 검증에 전달한다. 이전 생략을 무조건 캐시하지 않고 새 원문에 따라 재평가한다.
- 독립 안전 판단을 제외한 최종 분석에도 근거 ID 압축을 적용한다. 카드 상세 분석 근거도 같은 원문 ID 표를 사용한다. 문장 자르기·근거 삭제·새 토큰 상한은 도입하지 않았다.
- 토큰 수 외에 모델 계산 횟수, 강제/샘플 토큰, 호스트 디코딩·청크 전송 시간을 기록해 실제 병목을 구분한다.

## 카드 생성 시 대상자 내부 분석

`MODEL_DETAILED_CARD_ANALYSIS=true`에서 기존 최종 분석 호출에 `case_formulation`을 포함한다. 별도 모델 호출은 추가하지 않는다.

| 내부 정보 | 저장·검토 기준 |
|---|---|
| 상황·행동·감정·관계·변화 | 원문이 뒷받침하는 항목만 최대 8개로 구성 |
| 실제 주체 | 대상자·이용자·타인·불명확을 구분; 문항 보관 그룹만으로 정하지 않음 |
| 보고 방식 | 관찰 보고·발언 보고·이용자 해석·모델 가설을 구분 |
| 시점과 변화 | 현재·과거·변화·불명확; 전후 상태·빈도·강도를 만들어 넣지 않음 |
| 확실성과 근거 | 보고/가설 구분과 정확한 원문 인용; 가설을 확정 사실로 승격하지 않음 |
| 정보 부족 | 해당 영역을 `unknown`으로 남기며 생략·미응답을 답변으로 만들지 않음 |

모든 항목의 내용뿐 아니라 주체·보고 방식·시점을 기존 독립 분석 검토의 주장 목록에 포함한다. 검토 누락·근거 없는 주장·자기 승인은 거부한다. 통과한 내부 분석만 카드 작성에 전달하고 `record.provenance.agent.case_formulation`에 보존한다. 최종 카드와 관계 표시의 기존 형식은 유지한다. 긴급 안전 판단이 승인된 경우 추가 상세 분석으로 긴급 안내를 늦추지 않는다.

로컬 앱 전체 회귀는 **3,190/3,190 통과**, 실패·생략 0개다. 상세 카드의 합성 모델 생성→암호화 DB 저장→정확한 재조회→소유자 격리를 검증했고 임시 DB 삭제를 확인했다. JavaScript 문법·JSON 검사와 모델 설정 식별 검사 5개도 통과했다. 이 결과는 GPU 실모델의 생성·저장 성공과 구분한다.
