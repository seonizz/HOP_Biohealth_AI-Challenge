# 관계 에이전트 기술 계약

최종 카드를 개별 검토가 끝난 순서대로 표시하는 기존 경로와 개선 제안은 [최종 카드 반 스트리밍 상세 설계](../../최신/FINAL_CARD_PROGRESSIVE_DELIVERY.md)에 정리했습니다. 해당 문서는 2026-11-03 기준의 구현 전 설계이며, 현재 구현과 제안 계약을 구분합니다.

현재 코드의 프롬프트는 `relationship-v3.20-source-based-avoid-repair`이며 통합 턴 검토는 `combined-turn-v48`입니다. 하나의 모델이 답변별 상태 갱신과 최종 분석·검토·가이드 생성을 순서대로 수행합니다. 이 버전은 문항 단위 안전 근거 ID 선택·서버 원문 복원과 후속 답변의 출처 구분을 보존하면서 다단계 작성·주장 검토·카드별 수정·진행 조회를 통합한 버전이며, 이전 `relationship-v3.5-rag` 실험이나 `ai/local_api/backend_patch`의 실행 결과와 구분합니다. 실행 설정은 [앱 실행](../README.md), 확인된 검증과 남은 작업은 [현황과 할 일](../../docs/current/현황과_할일.md)을 기준으로 봅니다.

## 답변별 상태 갱신과 최종 생성

사용자 답변은 먼저 PostgreSQL의 대기 상태와 버전 이력에 저장합니다. 모델은 매 답변 뒤 누적된 현재 답변 원문 전체와 현재 원문으로 검증된 이전 상태·관계 메모리, 현재 대화에서 검색한 `retrieval.documents`를 읽습니다. 기본 답변·직접 입력·후속 답변과 `answered`/`unknown`/`refused`/`skipped` 상태를 구분하여 기존 `patient_state`, `name_index`와 별도 `relationship_memory`를 반환합니다. 관계 프로토콜에서는 사용자가 허용된 문항을 건너뛰어도 모델 갱신을 수행하지만, 건너뜀을 새 사실이나 동의로 해석하지 않습니다.

최신 pending 질문의 문항·사람 metadata를 현재 원문의 해당 항목과 연결하여 `latest_answer={subject,question_id,question,status,answers}`로 전달합니다. `MODEL_STATE_MODE=combined`는 상태·관계 기억·질문 계획의 통합 초안과 별도의 상태 검토를 요청합니다. 새 로컬 설치의 `combined_blocks`는 같은 초안을 상태·이름·관계 기억·질문 블록으로 나누어 생성한 뒤 전체 검증과 독립 상태 검토를 수행합니다. 질문 블록에는 검증 전 상태 초안 대신 원문·질문 후보·해당 retrieval을 제공합니다. 생략·추가 확인 제안이 있으면 별도 `question_review`를, 위험 제안이 있으면 별도 `safety_review`를 추가합니다. 검토가 지지한 질문 선택만 유지하며 생략 문항의 답변을 만들지 않습니다. 상태 거절 시 현재 원문으로 다시 작성하고 새 검토를 받으며, 이미 승인된 위험 제안은 상태 재작성에서 사라져도 전체 근거를 다시 안전 검토합니다. 호출 수는 선택한 생성 모드와 질문·위험 제안, 형식·전송·상태 수정 필요 여부에 따라 달라집니다.

`MODEL_STATE_MODE=staged`는 비교·복구를 위해 기존 `state_observations` → `relationship_memory` → `state_review` → `question_plan` 경로와 조건부 `question_review`·`safety_review`를 보존합니다. 모델·체크포인트를 바꾸는 설정이 아닙니다. STATE는 새 관찰·생활 변화·정정·이용자 부담·도움의 한계·지원 자원을 확인한 뒤 finding을 갱신합니다. 현재도 유효하고 중요한 이전 내용은 유지하되 더 구체적인 근거나 정정이 있으면 이전 해석을 수정·교체합니다. 초기 통합 비교 당시의 실행 기록은 `-combined-turn-v13`으로 구분합니다. 당시 비교의 범위·결과는 [호출 통합 비교 기록](TURN_CALL_COMPARISON.md)을 참고하세요.

사용자 지정에 따라 통합 대상은 답변 후 다음 질문으로 넘어가는 구간입니다. 최종 분석·전략·카드 작성·검토·후처리는 기존 경로를 유지합니다. 최종 요청에서 상태가 없거나 오래되어 재구성해야 할 때도 `MODEL_STATE_MODE`와 무관하게 기존 관찰 → 관계 기억 → 상태 검토의 3단계를 사용합니다.

`latest_answer`가 대상자 또는 이용자의 `answered` 원문이면 서버가 해당 문항의 전체 원문과 후속 답변을 `patient_state.facts`에 직접 보존합니다. 모델이 그 문항을 선택하지 않아도 누락을 이유로 다시 호출하지 않습니다. 모름·거절·건너뜀에는 적용하지 않으며 이용자 목적은 별도 목적 필드로 유지합니다. 원문이 인용 한도 10,000자를 넘으면 Unicode 문자를 자르지 않는 연속 구간으로 나눠 보존합니다. 의미적 중요성이나 가설 정확도를 인증하는 것은 아닙니다.

서버 검증이 성공하면 두 메모리를 암호화된 대화 상태와 이력에 저장하고 다음 질문으로 진행합니다. 실패한 답변은 보존하며 같은 질문에서 수정하거나 재시도할 수 있습니다. 같은 답변의 재시도는 대화 기록을 중복 추가하지 않습니다.

`relationship_memory`(통합 경로의 `turn_draft.state.relationship_memory` 및 이전 단일 STATE 호출 포함)가 원문에 없는 진단·성향명으로 거절되면(`agent_unreported_label`), 해당 호출의 남은 재시도는 `patient`/`supporter`의 원문 보고만 허용하고 `relationship=[]`로 요청합니다. 실패 응답을 삭제·변환해 수락하지 않고 새 응답을 축소 스키마와 기존 출처 검증으로 다시 확인합니다. 실패 trace·시도 상한·공통 deadline은 유지하며 다음 STATE와 최종 분석에는 원래 스키마를 사용합니다. 이 복구의 성공은 가설 생성의 성공을 뜻하지 않습니다.

### 별도 내부 관계 메모리

| 모델 출력과 저장 위치 | 내용 |
| --- | --- |
| `patient_state` → `agentMemory` | 기존 상태 요약·원문 사실·미확인 내용·이용자 목적을 유지합니다. |
| `relationship_memory` → `agentRelationshipMemory` | `patient`, `supporter`, `relationship`의 관찰·해석을 각각 0~2개와 별도 `unknowns`로 저장합니다. |
| `relationship_state` → `prior_relationship_memory` | 다음 모델 호출에서 현재 원문으로 다시 검증한 관계 메모리만 제공합니다. 근거가 오래되었거나 사람·문항이 맞지 않으면 이전 메모리를 승인하지 않습니다. |

STATE 모델은 `patient_state`의 `facts`와 `unknowns`만 생성합니다. 각 fact에는 `subject`, `question_id`, `quote`, `certainty`만 허용하고 자유로운 `summary`나 `interpretation`은 거절합니다. 서버가 사람과 보고·미확인 여부를 알리는 문구 및 정확한 인용으로 `interpretation`과 `summary`를 구성하고 이용자 목적을 원문에서 가져옵니다. 이전 상태의 근거가 현재 원문에 유효하더라도, 자유 요약·보고 해석은 모델에 다시 전달하기 전에 같은 계약으로 정규화합니다. 긴 원문이 표시 한도를 넘으면 근거를 보존했다는 고정 문구를 쓰며 원문 `quote`는 줄이지 않습니다.

저장된 관계 메모리의 각 finding은 `interpretation`, 정확한 원문 `evidence`, `certainty`를 가집니다. 모델 생성 단계에서 `patient`와 `supporter`의 `reported` finding은 `evidence`, `certainty`만 허용하며 서버가 출처를 밝힌 원문 보고 문구를 만듭니다. 원인·동기·마음이나 여러 답변 사이의 인과관계를 추론하는 `tentative` finding만 모델이 해석을 작성합니다. `relationship`의 모든 finding도 스키마에서 `certainty=tentative`로 제한합니다. `patient` finding은 대상자 문항의 근거만, `supporter` finding은 이용자 문항의 근거만 사용합니다. 모름·거절·건너뜀은 확정 근거로 쓰지 않으며 확인되지 않은 정보는 `unknowns`에 남깁니다. `tentative`의 의미적 타당성은 별도 검토·평가가 필요합니다.

통합 v12는 모델 작성 한도와 서버 저장 한도를 구분합니다. 모델 초안은 그룹당 2개 finding·각 3개 근거를 유지하며, 모델이 직접 근거 4개를 작성하면 거절합니다. 서버가 검증된 최신 인용을 추가하거나 관측된 reported 2행+tentative 1행 표현을 손실 없이 정규화한 경우에만 patient/supporter의 reported 근거를 최대 6개로 저장합니다. 각 원본 행의 형식·출처·사람을 먼저 검증하고 모든 인용과 가설을 보존하며, 저장할 전체 주장을 새 독립 검토에 전달합니다. tentative·relationship의 3개 근거 한도는 유지합니다. 저장된 reported 근거가 4~6개이면 해석은 서버의 정확한 원문 보고 문구여야 하며, 다음 문맥·검색·최종 분석에서도 같은 근거를 검증해 전달합니다. 최종 생성의 프롬프트·스키마·단계는 유지하지만 입력 기억이 달라질 수 있으므로 실제 최종 품질 비교는 별도로 필요합니다.

통합 v13은 patient/supporter memory의 인용이 원문에 정확히 존재하지만 enum의 완전 문장보다 짧은 절인 경우를 처리합니다. 원래 ref의 형식·사람·문항·원문·literal 검색 범위를 먼저 검증하고, 같은 사람·문항의 기존 enum에 있는 유일한 완전 문장 또는 전체 답변으로만 확장합니다. 서로 경쟁하는 문장, 문맥이 다른 중첩 인용, 1000자 길이 조각은 자동 선택하지 않습니다. 해석과 certainty는 변경하지 않으며, 확장 후 전체 초안 검증과 새 독립 검토를 거칩니다. 이는 인용 문맥을 늘리는 정책이며 자동 의미 승인이 아닙니다. 내부 진단에는 요청·단계·위치·길이·해시만 남기고 원문은 기록하지 않습니다. facts·relationship 그룹·질문·안전 판단·staged·최종 생성에는 이 확장을 적용하지 않습니다.

매 턴 상태 출력 스키마는 각 사람의 실제 `answered` 원문을 확인합니다. 이름을 제외한 근거가 없으면 해당 `patient` 또는 `supporter` 배열의 `maxItems`를 `0`으로 지정합니다. 이용자 목적의 답변을 다른 사람의 원문으로 옮겨 넣을 수 없도록 근거의 `subject`도 해당 사람으로 제한합니다. 이름만을 근거로 한 finding은 서버 검증에서도 거절합니다.

`agentRelationshipMemory`는 기존 대화 상태의 AES-256-GCM 암호화·버전 저장 구조에 포함하며 별도 평문 파일이나 새 DB 테이블에 저장하지 않습니다. 뒤로가기·정정은 이후 `agentMemory`, `agentRelationshipMemory`, 모델 결과·최종 기록을 무효화합니다. 새 답변과 이전 근거가 맞지 않으면 현재 원문을 기준으로 다시 생성합니다.

최종 `relationship_memory`는 검토를 통과한 `relationship_analysis`에서 다시 구성합니다. 승인된 강점·한계 중 해당 사람의 근거만 가진 항목을 `patient`와 `supporter`에, 승인된 관계 특징을 `relationship`의 `tentative` 항목에 반영하고 미확인 내용도 승인된 분석에서 가져옵니다. 이전 메모리의 거절된 해석을 최종 상태에 다시 저장하지 않습니다.

최종 결과는 다음 순서로 준비합니다.

| 단계 | 역할과 검증 |
| --- | --- |
| 상태 확인 | 기존 상태와 관계 메모리가 모두 현재 원문에 유효한지 확인합니다. 어느 하나라도 없거나 부적합하면 최종 문맥에서 두 메모리를 다시 생성하고 검증합니다. |
| `relationship_analysis` | 대상자·이용자별 `observations`에 정확한 원문 인용을 최대 2개 선택하고 관계 특징·강점·한계를 분석합니다. 서버가 관찰 요약을 인용 그대로 구성하며 각 해석의 근거를 실제 답변과 대조합니다. |
| `analysis_review` | 가이드를 만들기 전에 분석 자체의 중대한 오류를 현재 원문과 대조합니다. |
| 필요 시 `analysis_repair` → `analysis_review_after_repair` | 분석을 한 번 수정하고 다시 검토합니다. 다시 거절되면 전략·가이드 생성으로 넘어가지 않고 실패합니다. |
| `communication_plan` | 실제 관찰 장면과 이용자의 목적을 바탕으로 말투·첫마디 근거·상대의 선택·이용자 자기돌봄을 설계합니다. |
| `plan_review` | 말하기 전략의 목적·관찰·선택권을 검토하며 필요하면 한 번 수정·재검토합니다. |
| `guide_write` | 기존 카드에 들어갈 첫마디·행동·피할 표현·다음 단계·자기돌봄을 작성합니다. |
| `card_care`, `card_doList`, `card_avoid`, `card_next` | 자기돌봄·행동·피할 표현·다음 단계를 각각 전담 작성하고 즉시 검증합니다. 긴급 행동은 기존 고정 계약을 유지합니다. |
| `guide_quality` | 실제 장면·이용자 목적·대화 허락·상대의 선택·행동 대안·자기돌봄을 살펴보고 문장 개선점을 최대 3개 제안합니다. |
| 필요 시 `guide_refine` | 품질 개선 제안을 한 번 적용합니다. 없는 사실을 보충하지 않고 이후 중대한 오류 검토를 받습니다. |
| `speech_opening`, `speech_listening`, `speech_offer` → `speech_write` | 첫마디·듣기·제안을 별도로 작성한 뒤 실제로 건넬 전체 발화로 통합합니다. |
| `speech_review`, `support_review` | 발화·행동의 근거와 이용자 부담·자기돌봄을 별도로 검토합니다. |
| `guide_review` | 원문과 분석·최종 안내를 대조하여 사람 혼동, 없는 사실·성별·동의 확정, 강압, 진단·치료 지시, 현재 위험 누락 등을 검토합니다. |
| 최종 검토에서 분석 오류 발견 시 | 분석 수정 예산이 남아 있으면 `analysis_repair_after_guide_review` → `analysis_review_after_guide_review_repair`를 실행합니다. 승인된 새 분석으로 전략·가이드·품질 검토·필요 시 다듬기·최종 오류 검토를 다시 수행하며 이 단계들은 `_after_analysis_repair` 접미사를 사용합니다. 분석 수정 예산이 없거나 재검토도 거절되면 실패합니다. |
| 필요 시 `guide_repair` → `guide_review_after_repair`, 전체 최대 두 차례 | 지적된 카드만 반환하도록 제한하고 즉시 검증한 뒤 기존의 다른 카드와 합쳐 다시 검토합니다. 두 번째 수정에는 `_2`가 붙습니다. 분석 수정 후 가이드를 다시 작성해도 이미 사용한 가이드 수정 횟수를 초기화하지 않습니다. 마지막 검토도 거절되면 최종 결과를 저장하지 않습니다. |

위 작성·검토 단계는 순차 실행합니다. 마지막으로 검토가 끝난 발화를 `speech_detail`로 나누고 각 조각의 이유·원문 근거를 `speech_detail_review`로 검토합니다. 조각을 합친 문장이 최종 발화와 일치해야 하며 제한된 수정에도 검증되지 않으면 저장하지 않습니다. 각 단계는 완전한 JSON Schema 출력과 서버 검증을 통과해야 다음 단계로 넘어갑니다. 품질 검토는 문장의 구체성·사용성을 개선하는 단계이고, 분석·최종 오류 검토는 중대한 오류의 승인 여부를 판단하는 단계입니다. 제한된 수정 후에도 분석·최종 오류 검토에 부적합하면 실패로 처리합니다.

최종 결과에는 `relationship_analysis`, 선택적 `conversation_detail`과 `provenance.agent`의 `prompt_version`, 실행 `stages`, `reviewed:true`, `quality_reviewed:true`, `retrieval`을 저장합니다. `retrieval`에는 검색 방식과 단계별 색인 원문 수·선택한 `source_ids`가 있습니다. 원문 내용은 이 추적 metadata에 넣지 않습니다. `reviewed:true`는 최종 중대한 오류 검토를 통과했다는 뜻이고 `quality_reviewed:true`는 문장 품질 검토를 수행했다는 뜻입니다. 사람의 검토나 임상 타당성 확인을 뜻하지 않으며 `clinically_validated:false`를 유지합니다.

상태 갱신 한 번과 최종 에이전트 실행 한 번은 각각 설정된 `MODEL_TIMEOUT_MS`의 공통 제한 시간을 사용합니다. 최종 생성의 모든 분석·검토·재시도·수정은 같은 마감 시간 안에서 실행하며 단계마다 제한 시간이 새로 부여되지는 않습니다. 일시적 연결 오류나 형식·근거 검증 실패에 따른 재요청은 단계별 최대 3회입니다. 분석 수정·재검토는 초기와 최종 검토 후를 합쳐 전체 1회, 중대한 가이드 오류 수정·재검토는 재작성 전후를 합쳐 전체 2회입니다. 품질 개선은 각 작성 흐름에서 필요할 때 한 번 수행합니다. 이들 제한과 공통 마감 시간 안에서 검토를 통과하지 못하면 최종 결과를 저장하지 않습니다.

### 추가 출력 제한

같은 해석을 여러 분석 그룹에 복제하는 출력은 거절합니다. 이용자가 명시적으로 선택한 상담·진료 목표는 긴급 안전 상황을 제외하고 `script`에도 남도록 검사합니다. 품질 수정 지침은 180자로 제한하며 장면·목표를 삭제하지 않도록 요청합니다. 내부 finding과 관계 요약에서 인용에 없는 완벽주의·강박·수면장애 명칭을 붙이는 출력도 거절합니다. 발화문의 `(줄바꿈)` 편집 표시는 저장·검토 전에 실제 문단 구분으로 변환합니다. 이런 형식·표현 검사는 해석의 모든 세부 주장이 인용으로 뒷받침된다는 인증은 아닙니다.

## 원문 관찰과 관계 해석 분리

모델 분석·분석 수정 출력은 `observations`, `relationship`, `unknowns`, `safety`만 허용합니다. `observations.patient`와 `observations.supporter`는 해당 사람의 현재 `answered` 원문에서 고른 근거 객체를 각각 최대 2개 갖습니다. 이름만을 근거로 한 관찰과 다른 사람의 인용은 거절하며, 근거가 없으면 빈 배열로 남깁니다.

서버가 `patient_summary`와 `supporter_summary`를 원문 인용과 출처를 알리는 고정 문구로 구성합니다. 이 요약에 모델이 원인이나 성향을 새로 서술할 수 없으며 저장 전에도 관찰 인용과 정확히 일치하는지 검사합니다. 대상자 문항 역시 앱 이용자의 관찰·전언이라는 점을 표시합니다. 각 요약은 최대 2개의 1,000자 인용을 보존하도록 2,400자로 제한합니다. `observations`는 최종 저장 결과에도 유지합니다. 기존 `observations` 없는 기록은 이전 계약으로 검증하지만 새 모델 생성 경로에서는 자유 요약 필드를 허용하지 않습니다.

관계 해석은 별도 `relationship`에 근거와 함께 남기며, 원문 인용이 일치하더라도 해석의 모든 의미가 맞는다는 보장은 없습니다. 이 부분은 분석 검토·최종 검토와 사례 평가로 계속 확인합니다.

## 현재 즉각적 위험의 행동 계약

원문 근거와 분석 검토에서 `safety.urgent=true`가 유지되면 `script`, `doList`, `avoid`, `next`, `care.tips`의 긴급 행동은 검토된 문구로 제한합니다. `urgentGuideActions`가 검증된 이름만 선택적으로 넣고, 생성 스키마의 문자열·배열 enum과 서버의 정확한 일치 검사로 같은 문구를 요구합니다. 현재 위험에 동의 대기나 나중 대화를 권한 초기 실패 출력을 조용히 덮어쓰지 않고 거절하여 다시 생성합니다. 모든 재시도가 실패하면 결과를 저장하지 않습니다.

긴급 시 `review_scope`를 전달하여 품질 검토의 수정 대상을 `care.feel`로 제한합니다. 최종 오류 검토는 관계 분석과 위험 판정, `care.feel`, 안내 분류 `top`을 계속 검토합니다. 고정 행동 필드를 변경하라는 검토 출력은 스키마 검증에서 거절하며, 품질 수정에서는 `top`도 유지합니다. `care` 필드로 들어온 수정 제안이 있더라도 작성 결과의 `care.tips`는 정확한 일치 검사를 다시 통과해야 합니다. 이후 위험 판정이 정정되면 현재 판정에 맞게 검토 범위도 다시 계산합니다.

분석을 나중에 수정해 긴급 여부가 바뀌면 작성·품질 수정·오류 수정마다 현재 분석으로 스키마를 새로 만듭니다. 긴급 행동 계약은 `agent.safety_guidance_version=immediate-help-v1`로 추적합니다. 일반적인 대화에는 이 고정 행동을 적용하지 않습니다. 긴급 도움 원칙의 참고 근거는 [NIMH 자살 FAQ](https://www.nimh.nih.gov/health/publications/suicide-faq)와 [Manchester NHS의 친구 지원 안내](https://mft.nhs.uk/camhs/supporting-a-friend/)입니다. 원문 관찰·관계 해석은 계속 현재 대화의 RAG 근거를 사용하고, 긴급 시 `care.feel`에는 이용자가 보고한 감정만 반영하도록 요청하고 최종 검토합니다. 위험 판정이나 자유로운 해석의 의미 전체가 자동으로 검증된다는 뜻은 아닙니다.

## 대화 원문 기반 RAG

`sourceDocuments`는 호출 시점의 현재 대화 문맥에서 `answered`인 대상자·이용자·이용자 목적 답변만 문서로 만듭니다. 각 문서는 사람, 문항, 질문, 선택/직접 입력/후속 답변의 정확한 원문과 원문 내용에서 만든 `source_id`를 가집니다. 매 호출 새로 색인하므로 정정 전 원문, 생성한 메모리·가이드, 다른 세션을 검색 자료로 사용하지 않습니다. 모름·거절·건너뜀은 검색 근거에서 제외하고 응답 상태로 따로 전달합니다. 질문 진행 판단만 예외적으로 `unknown` 원문을 명시적 상태와 함께 별도 추가할 수 있습니다. 이는 `not_needed`의 문맥상 불필요성 판단에만 사용하며, 상태·최종 생성의 사실 검색이나 답변 완료 근거로 승격하지 않습니다.

검색 방식 `conversation_lexical_v1`은 NFKC 정규화·소문자 변환 후 단어와 문자 bigram을 추출합니다. query와 원문 문서에 겹치는 항목의 역문서빈도 가중치를 합하고 문서 항목 수로 정규화하여 순위를 매깁니다. BM25나 임베딩·vector 검색을 구현한 것은 아닙니다. 대상자 상태, 이용자 부담, 관계 상호작용, 지지 자원의 역할별 query와 이용자 목적을 사용하며 최종 단계에서는 분석 요약·검토 의견도 query에 보탭니다.

검색 상위 개수는 같은 답변의 원문·직접 입력 변형 수가 아닌 서로 다른 문항 수로 계산합니다. 고정 선택하는 이름·관계·목적은 순위 슬롯을 소비하지 않습니다.

최신 답변, 이름·관계·이용자 목적, 위험 표현을 포함한 원문은 순위와 관계없이 선택합니다. 상태 호출의 검증된 이전 메모리와 최종 단계 payload에서 이미 인용한 문항의 원문도 유지합니다. 짧은 대화는 전체 답변을 선택합니다. 검색된 문항은 선택 보기·직접 입력·후속 답변이 함께 들어가도록 묶고 원문 전체를 제공합니다. 위험 표현이 포함되었다는 이유로 긴급 상태를 확정하지 않으며 부정·화자·시점도 원문과 함께 읽습니다.

매 상태 갱신과 최종 생성의 모든 단계에 `retrieval` payload를 전달합니다. 전체 현재 `answers`도 원문 대조 자료로 유지합니다. 근거 객체 enum은 해당 호출에서 선택한 원문으로 제한하고, 생성 후에도 인용의 사람·문항·quote가 검색 원문에 실제 포함되는지 검사합니다. 검색 밖의 인용은 `agent_retrieval_evidence`로 거절하며 기존 현재 원문 검증도 함께 수행합니다. 이는 인용 출처의 범위를 확인하는 장치이며 해석의 타당성이나 의미 검색의 완전성을 인증하지 않습니다.

최종 `agent.retrieval`은 `method`와 단계별 `stage`, `indexed_sources`, `source_ids`를 남깁니다. 운영 진단 로그에 원문이나 생성 내용을 기록하지 않습니다. 검색 자료는 서버 내부 모델 입력에 쓰며 별도 벡터 DB나 외부 검색 서비스로 보내지 않습니다.

## 전체 원문과 문맥 한계

현재 관계 프로토콜은 누적된 원문을 읽으며 입력을 조용히 삭제하거나 축약하는 복구를 수행하지 않습니다. Ollama **0.40.0 MLX**에서 OpenAI 호환 채팅은 `ChatHandler`로 연결되고 MLX 분기에서 `truncate=false`를 사용합니다. 근거는 고정 커밋의 [채팅 입력 처리](https://github.com/ollama/ollama/blob/0d0720e51fb2fd9aa58781c3d720c06d720c2e7b/server/routes.go#L3183-L3188)입니다.

MLX runner는 토큰화한 입력을 모델 문맥 한계와 비교하여 한계에 도달한 입력을 오류로 처리합니다. 모델이 HTTP 400과 `input length (N tokens) exceeds the model's maximum context length (M tokens)` 메시지를 반환하면 앱은 `MODEL_CONTEXT_TOO_LONG`으로 명시 실패합니다. 현재 관계 프로토콜에서는 이 오류를 원문 축약으로 재시도하지 않고 입력 답변·대기 상태를 보존합니다. [MLX runner의 입력 한계 검사](https://github.com/ollama/ollama/blob/0d0720e51fb2fd9aa58781c3d720c06d720c2e7b/mlxrunner/pipeline.go#L73-L82).

`/api/ps`에서 관측한 `context_length:32768`은 그 응답의 표시값입니다. 이 숫자만으로 실제 모델·runner의 최대 입력 하드 한계를 확정하지 않습니다. 실제 거절 여부와 한계는 해당 버전의 입력 검사 및 오류 응답과 함께 확인합니다.

## 원문과 사람 구분

`patient`는 도움받을 대상자, `supporter`는 앱 이용자, `user_goal`은 이용자가 전하려는 말과 바라는 결과입니다. 내부 필드명 `patient`가 임상 진단을 의미하지 않습니다. 대상자의 증상·지원망과 이용자의 감정·부담·지원망을 구분합니다. 질문 ID와 대상은 대화 시작 시 보존한 질문 스냅샷에서 가져오므로 문항 수나 고정 ID 목록에 의존하지 않습니다.

- 각 근거의 `subject`와 `question_id`가 실제 응답 대상·문항과 일치해야 합니다.
- `quote`는 해당 답변의 원문·선택/직접 입력·후속 답변에 있는 연속 부분 문자열이어야 합니다.
- 관계 특징·강점·한계의 해석마다 최소 한 개의 검증된 근거를 요구합니다. 모름·거절·건너뜀을 확정 근거로 사용하지 않습니다.
- 관계 이름은 실제 관계 답변에 있어야 합니다. 관계 답변이 미확인이면 관계 이름과 역할을 `확인되지 않음`으로 남깁니다.
- 안전 근거는 위험 단어만 발췌하지 않고 부정·화자·시점을 확인할 수 있는 문맥을 보존합니다. 긴급 위험 표시에는 실제 근거가 필요하고 가이드의 안전 표시도 분석과 같아야 합니다.
- 이용자의 해석과 관계 패턴은 `tentative`로 표시하고 대상자 자신의 의사·동의처럼 아직 알 수 없는 내용은 `unknowns`에 남깁니다. 정정된 답변은 이전 메모리보다 우선합니다.

서버가 확인하는 것은 출력 형식·문항·사람·인용의 일치입니다. 해석의 모든 의미가 옳음을 기계적으로 인증하지는 않습니다. 같은 모델의 별도 검토 단계로 중대한 의미 오류를 다시 확인하며 프롬프트와 평가 사례를 계속 개선합니다. 진단·성격 판정·임상 점수·치료 변경을 생성하도록 요청하지 않습니다. 모델이 위기 연락처를 새로 생성하지 않으며 화면의 기존 안전 안내를 사용합니다.

입력 답변은 분석 자료로 취급합니다. 답변에 포함된 역할 변경·프롬프트 지시·출력 요구는 모델 지시로 따르지 않도록 각 역할 프롬프트에 명시합니다. 모델 출력은 검증이 통과하기 전까지 승인된 상태나 최종 기록으로 저장하지 않습니다. 원래 사용자 답변과 실패 이력은 보존합니다.

### 근거 객체 enum

`groundedEvidenceSchema`는 각각의 사람·문항·인용을 따로 선택하는 대신 `{subject,question_id,quote}` 전체 객체를 하나의 enum 후보로 고정합니다. 해당 호출에서 검색한 `answered` 원문·완전한 문장·연속 인용 발췌를 후보로 만들고 중복을 제거합니다. 사람은 한 답변에서, 인용은 다른 답변에서 가져온 조합을 생성 단계에서 제한합니다.

이 스키마는 최종 분석·분석 수정·말하기 전략의 근거와 답변별 상태·관계 메모리의 근거에 적용합니다. 생성 제약과 함께 기존 서버 validator의 현재 원문 포함 여부·사람·문항·응답 상태 검증도 유지합니다. 긴 답변의 인용 후보는 발췌로 만들 수 있지만 전체 입력 원문은 그대로 전달합니다. 후보 발췌가 모델 입력을 요약하거나 축약하는 동작은 아닙니다.

안전 분석·분석 수정의 모델 출력은 `safety:{urgent,evidence_ids}`입니다. 현재 검색 범위의 문항 묶음 ID를 최대 18개 선택하며 긴 원문을 출력하지 않습니다. ID는 사람·문항·원문 구성요소·출처·질문에 결합한 해시입니다. 서버는 선택을 검증한 뒤 해당 문항의 모든 원문·직접 입력·후속 답변을 복원하고 검색 근거 및 현재 원문 검증을 다시 수행합니다. 존재하지 않는 ID, 정정 전 ID, 검색 밖 ID, 중복 ID, 기존 quote 출력 형식은 새 생성 경로에서 거절합니다. 초기 분석·일반 분석 수정·가이드 검토 후 분석 수정에 동일한 계약을 적용합니다.

모델 입력의 `answers`와 검색 문서는 `{origin,fields,question,text}`로 출처를 구분합니다. `answer_snapshot`의 `rawText`는 최초 원문, `text/custom`은 후속 답변이 병합된 현재 표현일 수 있습니다. `follow_up`은 후속 질문과 답변을 별도로 보존하며, 동일하거나 포함된 문자열이어도 이 출처를 지우지 않습니다. 같은 snapshot 내부의 완전히 같은 문자열만 필드 이름을 합칩니다. 모델이 짧은 후속 답변을 무조건 안전 확인으로 해석하도록 강제하지는 않습니다.

‘잘 모르겠어요’ 선택만 있으면 `unknown`으로 남아 검색·안전·관계 인용 근거에서 제외합니다. 같은 다중 선택 답변에 내용 있는 직접 입력이 있으면 `answered`로 두고 선택의 불확실성은 `selection_status:unknown`으로 모델 입력에도 전달합니다. 전체 답변과 직접 입력을 함께 검색하며, 안전 출처를 선택하면 모름 문구·전언·부인·시간 표현을 포함한 원문 구성요소 전체를 복원합니다. 이전 저장 문맥과 기록도 읽을 때 이 계약으로 정규화하되 암호화 저장본·이력·기존 생성 결과를 변경하지 않습니다. 일반 `unknown`의 비어 있지 않은 `rawText`만으로 상태를 바꾸지는 않습니다.

저장 분석은 기존 `safety:{urgent,evidence}` 형식을 유지합니다. 복원한 인용에는 길이 제한을 적용하지 않고 완전히 같은 인용 문자열만 합치며, 포함 문자열인 후속 정정은 남깁니다. 선택 ID는 `agent.safety_source_ids`, 계약 버전은 `agent.safety_evidence_version=question-bundle-v1`에 남기고, 기록의 `context`로 출처별 묶음을 재현할 수 있습니다. 최대 18문항 × 6개 원문 구성요소를 허용합니다. 후보가 없으면 빈 enum을 만들지 않고 선택 배열을 비웁니다.

분석을 포함한 모든 단계에서 웹의 고정 출력 토큰 예산을 제거하고 모델 서버가 공개한 출력 상한 또는 서버의 생성 기본값을 사용합니다. 긴 안전 원문을 재출력해야 하는 요구도 없으며, 출력 필드별 스키마 검증은 유지합니다. 전체 모델 전송·수신 정책은 [앱 실행 문서](../README.md#모델-전송수신-한도)를 따릅니다. 원문을 잘라 통과시키거나 서버가 `urgent`를 자동 변경하지 않습니다. 인용 출처가 정확해도 판단의 의미 정확성은 별도이며 실제 모델 검사 범위는 [수정 v4](../../docs/competition/결선_재평가_지적_수정_v4.md)에 기록합니다.

## 질문과 화면

현재 관계 에이전트의 질문 계획은 미응답 후보 중 이미 답한 질문(`already_covered`)과 답변 맥락상 불필요한 선택 질문(`not_needed`)을 구분해 생략합니다(2026-10-23 사용자 재확인). `already_covered`는 같은 사람의 해당 질문을 충족하는 원문을 요구합니다. `not_needed`는 직접 답변이 없어도 실제 맥락이 불필요하다는 판단을 지지하면 허용하며, 기존 최소 답변 수·필수 및 분기 후보 제한을 유지합니다. 검토도 두 사유를 구분하고, 단순 미응답만으로 `not_needed`를 거부하지 않습니다. 생략·확인 질문 결정은 별도 검토하며 근거가 부족하면 원래 질문을 유지합니다. 생략한 문항은 `auto_skipped`로 남기며 실제 답변이나 최종 사실 근거를 만들어 채우지 않습니다. 기본 문항 뒤에는 서버에 정의된 도움 의향·이전 반응·이용자 경계의 선택적 확인 질문 중 아직 답하지 않은 것을 고를 수 있습니다. 모름·거절·건너뜀도 소비된 질문으로 보며 임의 질문은 생성하지 않습니다. 즉각적 위험의 조기 종료는 문항 단위 안전 ID에서 전체 원문을 복원한 뒤 현재 신체 위험인지 별도로 검토해야 합니다. 기존 필수 입력·조건부 분기·되돌리기는 유지하고 정정은 두 메모리와 결과를 무효화합니다.

결과 화면은 기존 안내 5개(자기돌봄, 첫마디, 해볼 행동, 피할 표현, 다음 단계)를 유지합니다. **함께 살펴본 관계** 카드는 접힌 상태로 추가하며 펼치면 그분의 상황·이용자의 마음·관계 특징·강점·서로의 한계·미확인 내용을 표시합니다. 원문 근거도 별도 접힌 영역에서 확인할 수 있습니다. 추정은 확인이 필요하다고 표시하고 생성 문장과 인용은 HTML 이스케이프합니다. 칼럼용 분류는 화면에서 `경향` 대신 `안내`로 표시합니다.

기록 화면에도 같은 분석을 보여 주며 `relationship_analysis`가 없는 이전 기록은 기존 안내와 대화 기록을 그대로 표시합니다. 기존 위기 안내 카드와 하단 연락처는 유지합니다. 최종 생성은 하나의 서버 요청으로 처리하며 소유자만 접근하는 `/api/intakes/:id/progress`에서 공개 단계명·시도 번호·완료 목록을 조회합니다. 기존 칸 없는 연속 진행바와 점 세 개 대기 표시를 유지하고, 결과 저장 전에 완료로 표시하지 않습니다. 삭제·정정·화면 전환 뒤 늦게 도착한 조회 응답은 반영하지 않습니다. 카드 표시는 사용자 지정 `85fe360` 기준을 유지합니다. 첫마디는 크림색 점선 카드에 전체 발화와 오른쪽 위 복사 버튼을 표시하고, 행동·피할 표현 카드는 넓은 화면에서 나란히 배치합니다. 검증용 단계·이유·근거는 저장 계약에만 남기며 화면에 추가하지 않습니다. 대화 기록은 기본 접힘이며 상세 발화가 없는 이전 기록도 표시합니다. 오류가 나면 저장된 답변으로 재시도할 수 있습니다.

### 입력·화면·칼럼 동작

브라우저별 익명 세션을 사용하며 이메일·회원 가입을 요구하지 않습니다. 시작·서비스 소개·대화·결과·내 기록·칼럼의 6개 화면에서 단일/다중 선택, 직접 입력, 단독 보기, 필수 입력, 후속 질문, 되돌리기, 문장 복사와 기록 삭제를 제공합니다. 이름은 필수 입력이며 별도 이름 후속 질문은 사용하지 않습니다. 기존 상담의 질문 버전과 관리자가 수정한 문항은 보존합니다. 대처와 받아 본 도움은 한 문항으로 합치고 이용자의 힘들었던 순간을 묻습니다. 질문 정의와 변경 방법은 [질문 관리](QUESTIONS.md)를 따릅니다.

전송한 글은 즉시 작성창에서 비우고 사용자 말풍선과 대기 표시를 그린 뒤 요청합니다. 재시도에는 캡처한 원문을 사용합니다. 실패한 원문은 대기 상태·버전 이력에 보존하며 화면은 연결·응답 검증·시간 초과를 구분합니다. 실패 답변 수정은 대기 답변을 교체하고 같은 입력 재시도는 중복 추가하지 않습니다. 최종 결과 생성 실패도 기존 대화에서 재시도할 수 있습니다.

공통 내비게이션, 대화 종료·새로고침 나가기 확인, 응원 문구, 결과 생성 로딩·카드 등장 효과, 두 번 눌러 기록 삭제를 유지합니다. 칼럼은 분류·안 읽음·담음 필터, 읽기 완료, 글자 크기와 이전/다음 읽기를 제공합니다. 수록 자료는 목록·요약·원문 링크 10편과 본문 9편이며 본문 없는 1편은 요약을 표시합니다. 오늘의 글·다른 글 뽑기·말씨 정원은 현재 화면에서 사용하지 않습니다.

## 저장과 진단

| 테이블 | 저장 책임 |
| --- | --- |
| `questions` | 문구·보기·순서·대상·조건·후속 질문 |
| `browsers` | 익명 토큰 해시와 세션 정보 |
| `intakes` | 대화 진행·원문 답변·두 내부 메모리 |
| `patient_states` | 현재 대상자·이용자 문맥과 모델 내부 메모리 |
| `patient_state_revisions` | 답변·정정·모델 변경 버전 이력 |
| `records` | UI 카드·전체 대화·선택적 관계 분석·실행 출처 정보 |
| `column_states` | 읽음·담음 상태 |

상담·상태·이력·결과는 AES-256-GCM으로 암호화하고 PostgreSQL은 Docker 이름 있는 볼륨에 저장합니다. 브라우저에는 접근 쿠키만 두며 상담 내용은 저장하지 않습니다. 기본 30일 세션 만료 뒤에도 서버 기록은 남습니다. 기록을 명시적으로 삭제하면 연결된 대화와 상태 이력도 삭제합니다. 쿠키를 지우거나 다른 브라우저를 사용하면 기존 익명 기록에 접근할 수 없으며 브라우저 간 동기화는 하지 않습니다.

운영 로그에는 요청 ID·생성 호출 ID·실제 fetch별 시도 ID·오류 단계·상태 코드·처리 시간만 남기고 대화 본문·모델 출력·인증 키를 넣지 않습니다. 복호화 검증 자료를 비공개 `runtime/server-verification.json`으로 내보내는 명령은 [실행·검증](../../docs/current/실행과_검증.md)을 따릅니다. 이 파일은 Git과 웹 제공 대상에서 제외합니다.

기본 모델 호출은 `stream:false`, `reasoning_effort:none`, `temperature:0.2`와 단계별 JSON Schema를 사용합니다. `MODEL_AGENT_FORMAT`은 `json_schema`/`json_object`/`prompt`, `MODEL_REASONING_EFFORT`는 `omit`/`none`/`low`/`medium`/`high`를 지원하며 어느 전송 방식에서도 같은 서버 검증을 수행합니다. 실행기 문법에서는 문자열 `maxLength`만 제거하되 원래 스키마의 길이 제한은 서버에서 유지합니다. 답변은 이용자의 보고이며 임상적으로 확인된 사실이 아닙니다. 원문 요약·보고 문구는 서버가 구성하며 가설·미확인 내용·가이드는 모델이 생성합니다. 인용 검증은 임상 타당성 인증이 아닙니다. 임의 질환 점수는 계산하지 않으며 결과 분류는 칼럼 연결용입니다.

실행 코드는 [모델 게이트웨이](../src/model.js), [관계 에이전트](../src/relationship-agent.js), [대화 원문 검색](../src/relationship-retrieval.js), [역할 프롬프트](../src/relationship-prompts.js), [서버](../src/server.js)에 있습니다. 최근 수정·검증 이력은 [대응 v2](../../docs/competition/결선_적대적_평가_v2.md)와 [재평가 지적 수정 v3](../../docs/competition/결선_재평가_지적_수정_v3.md)에 보존합니다.

실제 요청은 `model_attempt`와 고유 `attempt_id`로 구분합니다. 재시도 대기의 종료·제한시간은 `model_retry_wait`와 `after_attempt_id`로 연결하며 요청 수에 더하지 않습니다. fetch 전 실패는 `model_request_failure`로 별도 기록합니다.

### 응답 오류 복구 보강 (2026-10-23)

통합 초안은 현재까지의 원문·직접 입력·후속 답변과 검색 범위에서 새로 작성합니다. 이전 모델의 요약·선택 목록·가설·미확인 문구를 `previous_reviewed_context`라는 입력 예시로 반복 제공하지 않습니다. 저장된 메모리와 정규 검증·검색의 과거 인용·문맥 지문은 유지하고, 현재 실패 초안과 독립 검토 의견의 짝도 수정 요청에 보존합니다. 분할 전송 형식을 개선한 현재 통합 턴 버전은 `combined-turn-v39`입니다.

통합 초안의 구조 오류가 반복돼 작은 블록으로 나누어 다시 생성할 때, 실패한 전체 초안인 `failed_combined_candidate`를 각 블록의 입력에 다시 넣지 않습니다. 전체 현재 원문·검색 범위·이미 생성한 블록·구조 오류 피드백은 보존합니다. 각 블록의 실패 응답은 해당 호출의 기존 수정 절차에서만 사용하고, 완성된 블록도 전체 근거 검증과 독립 검토를 통과해야 합니다.

일반 사실의 160자 이내 인용 후보는 긴 문장을 나눌 때 원문에 있는 쉼표·세미콜론 등의 절 경계를 우선하고, 그 경계가 없으면 단어 경계를 선택합니다. 임의 위치에서 단어가 잘려 검토기가 미완성 관찰로 읽는 문제를 줄이며, 인용 문자열은 계속 원문의 정확한 부분 문자열입니다. 전체 답변과 별도 안전 근거는 그대로 보존하고 부정·시점·화자·정정 검토에 사용합니다.

통합 상태 검토 입력은 `review_target`이고 출력은 `state`입니다. 검토 대상 초안에 검토 결과용 `audits`가 없다는 이유로 거절하는 혼동을 방지합니다. 검토기는 현재 원문·현재 초안·현재 주장·원문 역할표만 받으며, 수리 작성기는 기존 실패 초안과 검토 의견의 짝을 그대로 받습니다. `reported_excerpt`, `tentative_hypothesis`, `unresolved_information`을 구분해 선택 인용·가능한 가설·실제 미확인 범위를 각각 검토합니다. 모든 감사 ID·확실성 조건과 최신 중요 정정의 누락 검사도 유지합니다.

과거 판단을 말한 원문과 최신 정정이 함께 인용된 것은 대화 이력의 보존으로 구분합니다. 최신 정정이 해당 사람의 보고 기록에도 반영됐는지 계속 검토하며, 현재 가설이 과거 판단을 사실로 사용하거나 정정을 누락·왜곡하면 거절합니다. 질문 검토는 후보의 실제 문구와 같은 사람의 원문을 대조합니다. 추가 확인은 `clarification_need`라는 필요성 주장을 심사하며, 답변이 원문에 있다는 사실을 추가 질문 승인 근거로 뒤집지 않도록 구분합니다.

검토 출력 자체가 형식을 어겼으면 그 실패 검토를 다음 초안의 예시로 다시 넣지 않고 현재 감사 ID와 구조 피드백으로 검토를 다시 요청합니다. 이미 모든 감사 ID를 가진 검토기가 자신의 audits 누락을 초안의 결함으로 쓰는 경우는 검토 형식·범위 오류로 거절합니다. 이 처리는 반려를 승인으로 바꾸지 않으며, 실제 근거 오류나 최신 정정 누락에 대한 반려는 유지합니다.

두 unknowns 배열의 같은 미확인 범위는 허용됩니다. 모든 미확인 감사가 supported이고 실제 내용 오류 없이 두 배열 사이의 중복만 삭제하라는 좁은 형식의 검토 의견은 검토 범위 오류로 다시 심사합니다. 자동 승인하지 않으며, 이미 답한 범위·불필요한 한계·정정 누락·unsupported 감사가 섞인 반려는 기존대로 유지합니다. 이 재심사도 기존 호출의 최대 3회 안에서만 수행합니다.

별도 검토 모델은 `MODEL_REVIEW_REASONING_EFFORT`로 사고 옵션을 독립적으로 설정할 수 있습니다(`omit`, `none`, `low`, `medium`, `high`, 기본 `none`). 작성 모델의 옵션·서버 문맥 길이·출력 상한은 이 설정으로 바꾸지 않습니다. 같은 이름의 LAN GGUF와 Mac MLX 모델이라도 검토 동작이 다를 수 있으므로 실제 저장된 실패 입력과 원래 검증기로 확인합니다.

`agentComplete`의 기존 검증에서 `agent_schema`로 거절했지만 수정 정보가 없으면, 검증 전 복사본을 요청 스키마와 대조해 누락 키·자료형·문자열 길이·배열 개수의 경로와 제한값을 다음 요청에 전달합니다. 기존 검증의 승인·거절 결정과 명시적인 수정 정보는 유지합니다. 정상적으로 정규화할 수 있는 출력을 새로 거절하지 않으며, 근거·의미 검증 실패를 구조 오류로 바꾸지 않습니다. 수정 정보에는 모델 출력값·알 수 없는 키 이름·원문 enum 후보를 넣지 않습니다.

수정 후 발화·돌봄 검토가 이전 이력의 문구를 현재 오류로 지적해 `agent_review_stale`로 거절되면, 다음 검토 요청에서 `revision`과 그 거절 출력을 제외합니다. 현재 원문·답안·claim·계획·검색 근거는 그대로 전달하고, 서버 검증은 기존 이력을 계속 보유해 같은 오류의 반복을 거절합니다. 이후 구조 오류가 생기면 그 오류의 구체적인 수정 정보를 전달합니다. 이 복구 상태는 해당 호출에만 존재하며 다음 단계·요청에 공유하거나 저장하지 않습니다.

두 경로 모두 개별 요청의 최대 3회 시도와 독립 검토를 유지합니다. 지속되는 내용 오류를 자동 승인하거나 안내 전체를 무한 재생성하지 않습니다. UI 디자인·입력 저장·최종 저장 계약도 변경하지 않습니다. 관련 검사는 `model-schema-feedback.test.js`, `model-review-current-recovery.test.js`, `combined-schema-feedback.test.js`, `relationship-agent.test.js`에 있습니다.

### 실행 환경과 스트림 복구 확인 (2026-10-24)

호스트 실행·Docker·별도 검토·기관 안내·연결 검사 도구가 같은 모델 설정 모듈을 사용합니다. 루트와 `/v1/chat/completions` 주소를 API 루트로 정규화하며, Docker에서는 loopback만 호스트 별칭으로 바꿉니다. 명시한 LAN·DNS 주소는 보존하고 임의 서버 탐색이나 장애 시 전송 대상 자동 변경은 하지 않습니다. 새 설정·기존 설정 보존·Node/Compose 환경 직렬화와 선택한 모델 옵션을 검사하며, 별도 API의 형식과 용량 조회 지원 여부도 명시적으로 설정할 수 있습니다. 실제 로컬 `.env`의 작성·검토 모델은 모두 Mac Ollama를 사용하며 LAN 연결을 필수 의존성으로 두지 않습니다.

실제 모델이 기존 스키마의 배열 상한을 넘거나 완성된 JSON 69개를 연결해 출력하는 실패를 확인했습니다. 다른 저장 실패 스트림은 바깥 객체를 닫기 전 구분자를 빠뜨린 채 새 문자열·객체를 출력했습니다. 유한 스키마의 스트림에서 이런 명백한 배열·단일 JSON·값 위치 오류가 생기면 해당 시도만 중단하고 기존 수정 절차로 전달합니다. 실제 저장 스트림 재생에서 각각 약 1,579자·2,002자에 잘못된 반복을 중단하고 reader 해제를 확인했습니다. 전체 응답의 시간·토큰·글자 수 예산을 새로 추가하지 않습니다. 불확실한 스키마는 조기 검사를 끄며, 전체 통합 초안의 기존 보고 정규화 예외와 저장 전 원문·독립 검토는 보존합니다. 부분 출력은 수정 예시나 승인 결과로 재사용하지 않습니다.

Mac에서도 이미 답한 선호의 추가 질문 방지와 두 사람의 지원 자원 구분 2개 사례가 모두 통과했으며 같은 9개 소스 해시가 유지됐습니다. 별도 비공개 실험에서 avoid 전용 판정 이름과 세 역할별 검토를 각각 시험했습니다. 둘 다 정상 안내를 통과시켰지만, 대안 부분만 무제한 지원 약속으로 바꾼 음성 대조군까지 모델이 승인했습니다. 이 결과는 모델 검토의 누락이며 전체 서비스의 승인과 구분합니다. 해당 문장은 기존 `knownSpeechIssues` 검사에서 반려되므로 실험의 모델 승인값만으로 서비스 결과를 승인하지 않습니다. 모든 원문·현재 문안·엄격한 스키마·기존 전체 검증기를 유지했으며 실험 결과를 사용자 기록으로 저장하지 않았습니다. 추가로 현재 검토 문구를 그대로 확인하게 한 역할별 실험은 정상/무제한 대안을 구분했지만, 이 더 복잡한 계약은 서비스에 도입하지 않았습니다. 단순한 전용 판정 형식도 기존 코드 검사에 걸리지 않는 허위 동의 대안을 독립적으로 반려하는 것을 확인했습니다. 이 대조군은 원문에 없는 동의를 만들어 넣었으며, 정상 원문과 다른 항목은 그대로 유지했습니다.

Compose의 기관 안내 모델 용량 조회 옵션도 명시값이 없으면 기본 모델 값을 상속하도록 맞췄습니다. 합성 요청 회귀, 실제 Compose 설정 해석 6조합, 이 시점의 전체 검사 1,675개가 통과했습니다. 이 검사는 실제 외부 API 인증이나 공급자별 지원 기능의 가동 증거를 대신하지 않습니다.

가족 합성 사례의 정상 API 흐름은 LAN 모델에서 27개 답변을 거쳐 최종 생성·저장·재열기까지 통과했습니다(완료 revision 54). 이전에 실패한 상세 생성과 독립 상세 검토가 수정 후 모두 통과했으며, 완료 요청에는 모델 호출 31개가 있었습니다. 기록을 두 번 읽은 해시 일치·기록 목록 포함·결과 요청의 중복 저장 방지·다른 세션의 404를 확인했습니다. 자동 생략 2개는 모두 `already_covered`였고, 해당 필드의 가상 답변과 최종 근거 20개 중 생략 문항 인용은 모두 0개였습니다. 관련 소스 6개의 해시도 실행 전후 같았습니다.

직장 동료의 새 합성 사례는 LAN 모델로 정상 API 답변 17개를 입력한 뒤 Mac 작성·검토 모델로 결과 생성·저장·재열기까지 완료했습니다. 여러 사실을 자연스러운 긴 답변 두 개로 묶은 `rich_followup` 변형이며, 질문 ID·생략 지시·기대 판정은 입력에 넣지 않았습니다. 최종 생성은 v3.19를 로드한 서버에서 30개 생성·검토 단계를 통과했습니다. 모델 시도 36회 중 형식 오류 6회가 있었고 기존 재시도와 두 차례 JSON 형식 복구로 해결됐습니다. 저장된 분석·안내는 검토한 최종 문안과 정확히 같았으며 별도 원문 대조에서도 앞서 발견한 성품 전제·지원 주체 오류가 남지 않았습니다. 기록 해시·목록·중복 저장 방지·다른 세션의 404가 통과했고, 자동 생략 12개의 가상 답변과 최종 근거 21개의 생략 문항 인용은 모두 0개였습니다. 이 새 입력에서는 상황 설명 문항이 자동 생략돼 전화 고장 정정은 전달되지 않았으므로, 해당 정정의 검증 사례로 세지 않습니다.

v3.20의 카드 수정 경로는 위 실제 재생과 서비스 경로 회귀 검사로 별도 검증했습니다. 전체 생성이 진행되던 v3.19 서버를 중간에 바꾸지 않았으며, 저장 완료 후 v3.20 서버로 재시작해 새 기록과 기존 가족·동료 기록이 같은 해시로 열리는 것을 확인했습니다. 이 재열기에는 새 모델 호출이 없었습니다. 기존 브라우저 기록도 새로고침 후 열렸고 카드 디자인은 유지됐습니다. 실제 검증 범위는 Mac·허용된 LAN Ollama의 생성, Docker의 설정·합성 모델 연결, 정상 API 저장·격리·재열기입니다. 다른 운영체제 전체 실행이나 별도 상용 API의 실제 가동 성공을 보증하지 않습니다.
