# 말씨 질문셋 v3.1 — 변경 내용과 검증

작성일: 2026-11-19 · 묶음 ID: `malssi-intake-3.1.0-rc1` · 이전 판본: `malssi-intake-3.0.0-rc1` (보존)

## 1. 무엇이 바뀌었나

**질문 개수·ID·보기·입력 형식·화면은 그대로이고, 문구만 바꿨다.** 기본 질문 9개 + 확인 질문 1개, 보기 값과 순서, 앱 행의 `sort_order`·`type`·`opts`는 3.0과 같다. 프론트엔드 파일은 변경하지 않았다.

도움말은 Q3-03(상대를 실명 대신 관계로 적기), Q3-05(앞으로 하려는 일은 적지 않아도 됨), Q3-07(메시지·전해 들은 말의 처리), Q3-08(방법을 고르고 시간·횟수를 함께 적기)만 바꿨다.

그 밖의 데이터 변경:

- `questions.json`: `default_priority`와 각 문항의 `order`를 목적 → 상황 → 관계 → … 로 기록했다. 앱이 이미 목적·상황을 먼저 묻는 것(`compact-question-flow.js`)과 맞춘 것이며, 앱 행의 `sort_order`는 3.0 그대로다. Q3-03의 `collects`에 `relationship`을 추가했다.
- `tasks.json`: 관계를 쓰는 과업의 `question_needs["Q3-03"]`에 `relationship`을 추가했다. 필수 정보(`required_facts`)와 허용 문항 집합은 3.0과 같다.
- `policy.json`: `question_progression.base_order`를 위 순서로 맞췄다.
- `codebook.json`: 묶음 ID만 바뀌었다.

## 2. 앱에 연결한 방식

- `seeds/questionnaire-v3.1/`을 **추가**했다. `seeds/questionnaire-v3/`(3.0)은 그대로 둔다.
- `seeds/questions.json`은 3.1 문구의 실행 행이고, 3.0 행은 `seeds/questions-v3.0.json`으로 보존했다.
- `src/v3-bundles.js`에 v3 계약을 따르는 묶음 ID 두 개를 등록했다. 3.0 스냅샷으로 저장된 대화는 자기 문구 그대로 이어진다.
- `migrations/015_questionnaire_v3_1.sql`은 기존 행을 `question_bank_archive`에 `before-malssi-intake-3.1.0-rc1`로 보관한 뒤 문구를 바꾼다. 대화·기록 테이블은 건드리지 않는다.
- `src/split-question-router.js`의 질문 선택 지시문에 두 줄을 더했다(별도 커밋). 시간 정보는 Q3-08이 남아 있으면 그 문항으로 묻고, 이미 한 일(Q3-05)을 앞으로 할 일(Q3-08)보다 먼저 묻고, 빠진 정보를 특정하지 않는 포괄 질문은 만들지 않는다.

### 진행 가드 (세 번째 커밋)

2026-11-18 사용 기록에서 "할 수 있는 도움(Q3-08)" 뒤에 시간·포괄 맞춤 질문 두 개가 나오고 다시 "이미 한 말이나 행동(Q3-05)"으로 되돌아간 문제를 서버에서 막는다. 규칙은 3.1 묶음의 `questions.json` `planning`에 선언하고 `src/question-flow-guards.js`가 적용한다. 이 선언이 없는 3.0 스냅샷 대화는 이전과 같다.

| 규칙 | 동작 | 선언 |
| --- | --- | --- |
| 되돌아가지 않기 | 뒤 순서 문항이 한 번 표시되면 그보다 앞 순서의 아직 묻지 않은 문항은 후보에서 빠진다. 순서는 목적 → 상황 → 관계 → 상대의 말·행동 → 나의 대응 → 나의 마음 → 상대의 바람 → 가능한 일 → 원하는 선택. 답변을 정정하면 그 전에 표시된 문항은 계산에서 빼고 다시 계획한다 | `planning.forward_only` |
| 맞춤 질문의 주제 제한 | 이미 표시된 등록 문항의 주제(가능한 일·시간, 관계, 마음, 원하는 선택, 말과 행동)는 모델이 쓴 맞춤 질문으로 다시 물을 수 없다. 출력 스키마에서 해당 주제를 빼고 검증에서도 거절한다 | `planning.custom_followup.focus_owner` |
| 포괄 질문 금지 | "더 있다면", "자유롭게", "덧붙이", "반영하고 싶은", "그 밖에"처럼 빠진 정보를 특정하지 않는 맞춤 질문을 거절한다 | `planning.custom_followup.reject_unspecific_questions` |

빠진 문항의 답은 만들지 않는다. 해당 정보는 `not_asked`로 남고 결과에서 미확인으로 다룬다. 문맥에 따른 질문 생략(`already_covered`, `not_needed`)은 그대로다.

앞 답과 거의 같은 답이 나올 질문을 별도 사유로 생략하는 기능(`would_repeat`)은 넣지 않았다. 기존 `already_covered`가 같은 역할을 하며, 새 사유는 모델 출력 형식을 바꿔야 해서 실모델 검증 없이 넣기에는 위험이 크다.

## 3. 실험

스크립트와 결과는 `docs/questionnaire-v3.1-experiments/`에 있다.

### 실험 1 — 문구 후보 비교 (`e1_wording.py`)

바꾼 6개 문항마다 후보 3개씩, 총 729개 조합을 비교했다. 기준은 질문끼리의 글자 2-gram 자카드 유사도(헷갈릴 가능성), 물음표 수(한 번에 두 가지를 묻는지), 시점 표지 유무, '도움' 전제어 유무, 길이다.

| 지표 | 3.0 | 3.1 |
| --- | --- | --- |
| 질문 쌍 유사도 평균 | 0.081 | 0.055 |
| 가장 비슷한 쌍 | Q3-04·Q3-05 0.357 | Q3-01·Q3-03 0.179 |
| Q3-05·Q3-08 유사도 | 0.138 | 0.035 |
| 본문 물음표 수 합계 | 11 | 10 |
| 본문 글자 수 합계 | 291 | 281 |

유사도만으로는 다른 조합이 최솟값이었으나(평균 0.041), 그 조합은 Q3-03에서 관계를 묻지 않아 실험 2의 질문 수 이점이 없다. 최종 선택은 두 실험 결과와 사람이 읽었을 때의 자연스러움을 함께 보고 정했다.

### 실험 2 — 진행 시뮬레이션 (`e2_flow.py`)

실제 모델 없이, `tasks.json`의 과업별 필요 정보와 묶음의 계획 규칙("아직 묻지 않은 문항 중 가장 앞 순서")으로 6개 과업 × 4,000회씩 가상 진행을 돌렸다. 이용자는 본문이 묻는 정보를 90%, 도움말에만 있는 정보를 30%, 묻지 않았지만 흔히 섞이는 정보를 35% 확률로 말한다고 가정했다.

| 조건 | 판본 | 평균 질문 수 | 필수 정보 확보율 | 정보가 늘지 않은 질문 수 | 추가 질문 필요 횟수 |
| --- | --- | --- | --- | --- | --- |
| 필수 정보만 묻기, 4개 한도 | 3.0 | 2.30 | 0.81 | 0.25 | 0.21 |
| | 3.1 | 2.30 | 0.89 | 0.13 | 0.11 |
| 필요 정보 전부 묻기, 4개 한도 | 3.0 | 3.56 | 0.76 | 0.29 | 0.12 |
| | 3.1 | 3.35 | 0.80 | 0.20 | 0.10 |
| 필요 정보 전부 묻기, 10개 한도 | 3.0 | 4.37 | 0.81 | 0.41 | 0.21 |
| | 3.1 | 3.95 | 0.90 | 0.25 | 0.11 |

- 차이가 가장 큰 과업은 시간 제안(T2)이다. 필수 정보만 묻는 조건에서 확보율이 0.26 → 0.75가 된다. 3.0은 시간이 도움말에만 있어 Q3-08을 묻고도 시간을 못 받는 경우가 많았다.
- 확률 가정을 27가지로 바꿔도 3.1의 평균 질문 수는 27가지 모두에서 3.0 이하였고, 필수 정보 확보율은 27가지 모두에서 3.0 이상이었다.
- 시드 5개로 반복했을 때 값의 흔들림은 ±0.005 이내였다.

**한계:** 이 수치는 가정한 확률과 규칙 기반 계획에서 나온 것이다. 실제 모델이 고르는 질문과 실제 이용자의 답으로 잰 값이 아니다. 실모델·실사용 기록으로 다시 확인해야 한다.

## 4. 회귀 검사

2026-11-19, Node 22.23.5, 격리 PostgreSQL 16(일회용 클러스터)에서 `node --test tests/*.test.js`를 실행했다. 저장소는 Node 24를 요구하므로 Node 24에서 한 번 더 돌려 확인해야 한다.

| 대상 | 실행 | 결과 |
| --- | --- | --- |
| 변경 전 `0b9c68c` | 1회 | 3,357개 중 3,356 통과, 실패 0, 건너뜀 1 |
| v3.1 문구만 적용 | 3회 연속 | 3회 모두 3,362개 중 3,361 통과, 실패 0, 건너뜀 1 |
| v3.1 문구 + 진행 가드 (최종) | 3회 연속 | 3회 모두 3,368개 중 3,367 통과, 실패 0, 건너뜀 1 |

건너뛴 1개는 이 실행 환경에 IPv6 루프백이 없어서 생긴 것으로 변경 전에도 같다. `npm run check`와 `git diff --check`도 통과했다.

새 검사 `tests/v31-flow-guards.test.js`(6개):

- 보고된 대화를 재현한다. Q3-08이 표시된 뒤에는 Q3-05를 포함한 앞 순서 문항이 후보에 없고, 모델이 골라도 거절된다.
- Q3-05를 먼저 물으면 Q3-08이 그 뒤에 정상적으로 나온다.
- Q3-08 표시 뒤 "가능한 시간을 넣을 수 있나요?"와 "반영하고 싶은 내용이 더 있다면…"이 두 모델 경로 모두에서 거절된다. 등록 문항이 다루지 않는 구체적인 질문은 허용된다.
- 목적을 정정하면 앞 순서 문항이 다시 후보가 된다.
- 3.0 스냅샷 대화에는 이 규칙이 적용되지 않는다.

기존 검사 2개(`tests/compact-question-flow.test.js`)는 뒤로 가는 선택 순서와 Q3-08 뒤의 시간 맞춤 질문을 전제로 해서 3.1 규칙에 맞게 고쳤다.

새 검사 `tests/v31-question-bank.test.js`(5개):

- 3.1이 활성 묶음이고, 질문 수·ID·보기·형식·`sort_order`가 3.0과 같으며 문구는 6개 문항만 다르다.
- Q3-05에 '지금까지', Q3-08에 '앞으로'와 '시간'이 있고 Q3-07에 '도움'이 없다. Q3-05를 뺀 모든 본문은 물음표가 하나다.
- 묶음 파일의 SHA-256·바이트 수가 `bundle.json`과 맞다.
- 3.0 스냅샷 대화는 3.0 문구를 유지하고 새 대화는 3.1로 시작한다.
- 과업의 필수 정보와 허용 문항 집합이 3.0과 같다.

기존 검사에서 고친 곳은 판본에 묶인 값뿐이다: 상황 질문 문구 정규식 1곳, 묶음 ID 2곳, 마이그레이션 개수 2곳, 마이그레이션 검사의 대상 파일.
