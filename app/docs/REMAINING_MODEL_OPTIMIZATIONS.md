# 미적용 모델 최적화 후속 반영

2026-11-01 후속: [검토 호출 묶음과 원문 일치 재사용](REVIEW_CALL_OPTIMIZATION.md)을 구현했다. 아래 2026-10-31의 보류 목록은 당시 기록이며, 제한된 이름·안전 재사용과 검토 묶음의 현재 적용 조건은 후속 문서를 따른다.

후속 사용자 요청의 답변 상태·질문·안전 검토 병렬화는 [별도 구현 기록](PARALLEL_TURN_REVIEWS.md)을 따른다. 로컬 반영만 수행했으며 아래 수치·검증은 병렬화 이전 작업의 기록이다.

다음 단계인 질문 작성·상태 블록 처리 병렬화는 [후속 구현 기록](PARALLEL_TURN_DRAFT_BLOCKS.md)에 정리했다.

2026-10-31. 기존 기획과 GitHub에 올린 `dc02c68`의 코드를 대조해 남은 로컬 구현·설정 연결을 반영했다. GPU 서버 접속·SSH·실제 모델 호출·운영 설정·실행 서비스 변경은 하지 않았다. 기존 검토, 상세 저장, 문맥에 따른 질문 생략과 카드 디자인을 유지한다.

## 적용한 항목

| 미적용 항목 | 반영 결과 | 확인한 효과 |
| --- | --- | --- |
| 검토마다 토큰 한도 재조회 | 부모 operation 안에서 생성·검토 Gateway별로 검증된 정책 재사용 | 정상 O4의 capability GET **15→2회**, 모델 POST **18회 유지** |
| 최종 검토 입력 중복 | 동일한 최상위 `script`만 전송에서 제외하고 단일 카드에 무관한 care/avoid 지시 제외 | 합성 O4 POST body **340,550→335,342 bytes**, **5,208 bytes·1.53% 감소** |
| 품질 개선의 전체 재출력 | 지적된 필드만 한 요청에서 생성한 뒤 나머지 값을 그대로 병합 | 수정 요청 1회와 품질 재검토 1회 유지. 미지적 카드·top·assessment 보존 |
| GPU overlay의 상태 모드 누락 | 명시적 상태 모드는 보존하고 미지정 시 `combined_blocks` 사용 | 블록 입력 축소 옵션만 켜고 실제로는 적용되지 않는 기본 구성 방지 |
| 적용 상태를 알 수 없는 설정 검사 | 실제 활성 옵션·비활성 옵션 표시, 설정 예시에 주석형 옵션 추가 | 네트워크 없는 검사로 옵션의 실효 적용 조건 확인 가능 |

GET 감소와 모델 호출 감소는 다른 지표다. 검토 14회를 포함한 정상 O4 18회는 유지한다. 바이트 수는 합성 fixture의 전체 POST body이며 토큰·GPU 시간·실제 생성 품질 감소율이 아니다. 품질 수정은 필요할 때 기존과 같이 총 +2회이며 필드 수만큼 호출을 늘리지 않는다.

## 토큰 정책 재사용 경계

- `MODEL_REUSE_TOKEN_POLICY=true`를 명시했을 때만 사용한다. 생성·검토 Gateway는 각각 자기 목적지·인증·모델·transport에 연결된 값을 사용한다. Gateway 사이에 정책을 공유하지 않는다.
- Python API는 서버 인스턴스마다 불투명한 `token_policy_revision`을 만들고 모델·한도 설정을 복사해 고정한다. `/healthz`에 revision을 제공하며, POST의 `X-Malssi-Token-Policy-Revision`이 다르면 추론 전에 `409 / token_policy_changed`로 거절한다.
- 앱은 이 계약을 제공하는 서버에서만 캐시한다. 서버 교체로 revision이 바뀌면 기존 요청 내용을 보존한 채 정책을 다시 조회하고 기존 요청 재시도 범위 안에서 재전송한다.
- 정책 조회 실패·인증 오류·지원하지 않는 metadata는 정상 정책으로 보관하지 않는다. revision 없는 구형 서버는 동시 검토에서도 각자 새로 조회한다. operation 재시작·새 사용자 요청은 새 캐시를 사용한다.
- 오류·전송 실패·입력 예산 거절 시 캐시를 무효화한다. 컨텍스트 거절 후 출력 예약을 줄이는 기존 동작과 전체 원문 보존을 유지한다.
- ready/busy/draining 상태, 취소 종료와 실제 추론 슬롯은 캐시하지 않는다. POST마다 서버의 기존 readiness·대기열·종료 확인을 거친다. 구형 클라이언트처럼 revision 헤더가 없는 요청도 기존 검증·준비 상태 경로를 유지한다.

## 검토·저장 보존

검토 입력 축소는 retrieval 계산 뒤 전송 payload에만 적용한다. 원문, claims, 스키마, 검증 함수와 전체 가이드 검토는 유지한다. `script`가 같지 않으면 어느 복사본도 삭제하지 않는다.

부분 품질 수정은 검토가 지적한 필드 집합을 중복 제거하고 정확한 키만 허용하는 스키마로 받는다. 누락·다른 카드·전체 guide·assessment 출력은 거절한다. 병합한 전체 결과에 기존 검증을 실행하고 미지적 필드의 동일성을 확인한다. 긴급 고정 행동과 care.tips도 그대로 유지한다. 이후 품질·발화·지원·교차 카드 검토와 `conversation_detail` 생성·검토를 계속 수행하며 반려·취소 시 완료 결과로 반환하지 않는다.

## 설정과 실제 적용

| 설정 | 기본값 | 적용 조건 |
| --- | --- | --- |
| `MODEL_COMPACT_REVIEW_INPUTS` | false | relationship_agent의 최종 검토 입력 |
| `MODEL_SCOPED_QUALITY_REFINEMENT` | false | relationship_agent, extras 유지, 품질 지적 발생 |
| `MODEL_REUSE_TOKEN_POLICY` | false | discovery 활성 + 서버 revision 계약. 생성·검토 각각 적용 |
| GPU overlay의 세 옵션 | true | 사용 승인을 받은 뒤 overlay를 실제 실행해야 적용 |
| GPU overlay의 `MODEL_STATE_MODE` | combined_blocks | 명시한 combined/staged 값은 덮어쓰지 않음 |

기존 `.env`, 실행 중인 별도 복사본과 프로세스는 변경하지 않았다. 위 옵션이 구현됐거나 overlay에 적혀 있다는 사실만으로 실행 서비스에 적용됐다고 판단하지 않는다. `node scripts/check-model.js`는 기본적으로 설정만 확인하며 네트워크를 사용하지 않는다. `--generate`는 실제 모델 요청이므로 GPU 실행 구성에서는 사전 승인이 필요하다. 캐시의 실제 지원 여부는 구성 검사에서 단정하지 않고 `tokenPolicyReuseRequested`로 구분한다.

## 구현 후 검토와 검증

구현을 마친 후 독립 검토를 수행했다. extras를 생략하는 구성에서 품질 수정이 활성으로 표시되는 오류를 고쳤다. 동시에 도착한 검토가 구형 서버의 첫 조회를 공유하는 경우도 각자 새로 조회하도록 보완했다. 재검토의 미해결 지적은 없다.

| 검사 | 결과 |
| --- | --- |
| 앱 전체 `env -u TEST_DATABASE_URL node --test tests/*.test.js` | **1,928 통과, 0 실패, 85 건너뜀**. 실제 DB 필요 검사는 제외 |
| Python API·대기열·worker·revision 검사 | **73 통과, 0 실패**, 합성 backend·localhost HTTP만 사용 |
| JavaScript 구문·JSON 검사 | 통과 |
| Compose | YAML 파싱·옵션 기본값·검토 보존 검사 통과. 컨테이너 미기동 |
| O4 GET/POST 비교 | 실제 Gateway와 mock HTTP에서 15 GET→2 GET, 18 POST·요청 본문·반환/저장 payload 동일 |
| 최종 입력·부분 수정 검사 | 원문·claims·retrieval 보존, O4/기존 경로, 잘못된 키, 긴급 고정 내용, 반려·취소 확인 |

별도 허용된 Ollama 검토 API는 `Host is down`으로 결과를 얻지 못했다. 완료 판단은 실제 로컬 검사와 독립 코드 검토에 근거한다. 첫 전체 검사의 로컬 포트 권한 제한은 localhost 테스트 실행 권한으로 해결했으며, 환경 예시의 기존 setup 기본값 계약도 주석형 옵션으로 보존했다.

## 남은 적용 경계

사용자는 구현·검증 결과 확인 후 **로컬 반영까지만 유지**하도록 선택했다. 이번 후속 수정은 로컬 작업 폴더에 보관하며 GPU 접속·배포·실행 서비스 변경과 추가 GitHub 푸시는 수행하지 않는다.

- 사용자 승인 후: 지정 GPU 서버 작업 폴더의 worker 패치·guarded bridge·앱 실행본/설정 적용, 같은 합성 사례의 실제 생성·검토·취소·저장 확인.
- 실제 모델 결과가 필요한 선택: `combined` 비교 후 상태 모드 채택, 단계별 출력 예산 조정. 이번 변경으로 통합 모드 채택이나 토큰 상한을 강제하지 않는다.
- 계속 보류: O5 검토 제거·승인 재사용, 턴 간 이름/분석 추론 재사용, 독립 GPU 용량이 필요한 병렬화. 기존 검토·저장 요구를 근거 없이 줄이지 않는다.
