# 답변별 모델 호출 통합과 비교 — 2026-10-17~18

사용자가 같은 모델로 답변별 4회 호출을 2회로 합치고, 기존 방식과 기능·정확도를 비교하도록 요청했다. 이후 사용자는 **최종 결론은 최대한 유지하고, 답변 후 다음 질문까지 느린 구간을 개선하는 것**이 목적이라고 명시했다. 호출 수만 줄고 대기시간이 늘면 성능 개선으로 판정하지 않는다. 이 개발 상세는 서비스 화면에 추가하지 않는다.

## 구현

- 기본 `MODEL_STATE_MODE=combined`: `turn_draft`에서 상태·관계 기억·질문 계획을 작성하고, `turn_review`가 원문에 대조하여 각각 검토한다. 초안의 자기 승인은 허용하지 않는다.
- `MODEL_STATE_MODE=staged`: 기존 관찰 → 관계 기억 → 상태 검토 → 질문 계획과 조건부 질문·안전 검토를 보존한다. 같은 모델 endpoint와 체크포인트로 비교한다.
- 정상 응답은 2회다. 잘못된 형식·전송 오류의 기존 재시도와, 상태 검토 거절 후 한 차례 재작성·재검토는 추가 호출이다. 항상 정확히 2회에 종료한다는 계약은 아니다.
- 상태와 질문의 검색 범위는 별도로 검증한다. 원문 인용·사람 구분·이름·질문 후보·입력 상태·전체 안전 근거의 기존 검증을 재사용한다. 입력을 절단하지 않는다.
- 최신 답변 전체 보존, 암호화·버전 관리, 실패 시 대기 답변 보존, 재시도 중복 방지, 뒤로가기·정정 경합은 기존 저장 경로를 사용한다.
- 상태 재작성 때문에 앞서 검토한 위험 판단이 없어지지 않도록, 승인된 위험의 전체 근거를 다음 검토에도 전달한다. 명시적인 안전 재검토 없이 위험을 취소하지 않는다. 최종 즉각적 위험 판단이면 질문 생략·추가 확인을 취소한다.
- `combined-turn-v3`부터 두 `unknowns` 배열의 각 항목도 독립 검토 대상으로 포함한다. 최신 원문에서 이미 답한 사람·시점·범위는 미확인으로 되돌리지 않는다. 항목별 검토가 빠지거나 미확인이라는 판단이 지지되지 않으면 승인하지 않는다. 한 항목은 한 가지 미확인 사항만 담으며, 검토 이유에서 초안의 범위를 임의로 좁혀 승인하지 않는다.
- `combined-turn-v4`는 상태·질문 입력에서 값이 완전히 같은 필드만 `shared_input`으로 한 번 제공한다. 서로 다른 검색 범위는 각 입력에 유지한다. 검토 요청의 결정적 요약·인용 재서술과 이미 `claims`에 있는 기억 복사본을 제거하지만 전체 원문·사실·이름·모든 관계 주장·미확인 주장은 남긴다. 출력은 한 줄 JSON과 짧은 검토 이유를 요청하며, 스키마·원문 검증·검토 항목 수·재작성 한도를 완화하지 않는다.
- `combined-turn-v5`는 일반적인 미응답 문항을 미확인 목록으로 복제하게 하던 상속 지침을 정리했다. 실제 모름·거절·상충과 현재 관찰·가설·도움 결정의 단정을 막는 구체적 한계는 계속 남긴다. 아직 묻지 않았어도 현재 판단에 필요한 동의·시간·부담의 한계는 제외하지 않는다. `questions`가 `state` 밖의 형제 키임을 명시하며, 검증 규칙을 완화하여 잘못된 JSON을 수락하지 않는다.
- `combined-turn-v6`는 최신 정정·부정·시점 변경이 관계 기록에서도 유지되도록 프롬프트를 보강했다. 원문 facts와 안전 판단이 맞아도 reported finding의 정정 누락을 거절하도록 요청했으나, 실제 긴 정정 사례에서는 여전히 빈 관계 기록이 승인됐다. 이 버전을 서비스 적용 기준으로 통과시키지 않는다.
- `combined-turn-v7`는 원출력 전체를 검증한 뒤 모델이 선택한 최신 `answered·reported` 인용을 같은 인물의 관계 기록에도 보존한다. 이름·관계명·연락 정보는 제외한다. 원문을 키워드로 해석하거나 새 결론을 만들지 않으며, 기존 reported 근거에 병합하거나 빈 자리에 추가한다. 기존 인용·가설을 삭제하지 않고 스키마의 2개 finding·각 3개 근거를 넘으면 재시도 대상으로 거절한다. 저장할 인용은 기존 스키마·출처·검색 범위를 모두 통과해야 하고, 서버가 보존한 기록도 두 번째 모델 호출의 독립 검토 대상이다. 모델이 필요한 정정 인용 자체를 선택하지 않은 경우까지 자동으로 해결하는 장치는 아니다.
- `combined-turn-v10`은 관측된 reported 2행+tentative 1행을 각 행 검증 후 손실 없이 묶는다. `v11`의 용량 재선택 안내만으로는 긴 실제 대화의 실패가 해결되지 않았다. `v12`는 모델 초안의 2개 finding·각 3개 근거를 유지하면서, 서버가 보존하는 patient/supporter의 reported 인용만 저장 단계에서 최대 6개로 구분한다. 기존 인용·가설을 삭제하지 않으며 전체 저장 주장을 새 독립 검토에 전달한다. 이는 저장 정책 변경이다. [실서비스 전체 흐름 검증](../../docs/archive/2026-10/실서비스_전체흐름_검증_2026-10-18.md)에 원래 실패·각 후보·실제 후속 결과를 보존하며, 아래의 짧은 v7 비교 수치를 v12 전체 대화의 개선율로 사용하지 않는다.
- 실제 후반 답변에서 v12도 원문 절과 허용 인용 문장의 enum 불일치로 3회 재시도 후 실패했다. v13은 검증된 동일 사람·문항의 절을 기존 허용 후보의 유일한 완전 문장으로 확장한 뒤 독립 검토한다. 초안 요청은 그대로이며, 최종 경로는 변경하지 않는다. 전체 앱 검사 607개 통과는 구조 검증 근거이고, 실제 전체 대화의 속도·최종 품질 통과를 뜻하지 않는다.
- 최종 안내 생성 단계는 변경하지 않는다. 최종 요청에 유효한 상태가 없어 상태를 재구성하는 경우에도 기존 `state_observations` → `relationship_memory` → `state_review`를 사용한다. `combined`는 질의응답에만 적용한다. 같은 상태를 입력했을 때 최종 요청 본문·프롬프트·스키마·토큰 예산·후처리가 기존과 동일함을 7개 회귀 검사로 검증한다. 질의응답에서 생성한 기억까지 확률적으로 같다고 보장하는 검사는 아니다.

## 비교 방법

[합성 사례 16개](../scripts/turn-comparison-cases.js)를 실제 추론 결과를 보기 전에 고정했다. 이름만 있는 경우, 사람별 지원 자원, 부정·시점, 이전 가설 정정, 충분히 답한 질문의 생략, 유사하지만 미응답인 질문, 추가 확인의 필요·불필요, 모름·거절, 현재·부정·과거 위험, 지시 주입, 3,003자 답변 말미의 정정을 포함한다. 원천 상담·학습 데이터나 기존 사용자 대화는 사용하지 않는다.

평가용 `expected`는 모델 입력에 포함하지 않는다. [비교 실행기](../scripts/compare-relationship-turns.js)는 같은 사례의 두 모드 실행 순서를 번갈아 배치하고, 같은 모델·생성 설정을 사용한다. 모델 생성문은 무시하지 않고 원문 출처·기억 선택·정정·질문 결정·안전 판단의 고정 검사로 평가한다. 서버가 자동으로 보존하는 최신 원문과 모델이 기억에 선택한 근거를 별도로 검사한다. 호출 횟수는 HTTP 요청 시도부터 기록하며 계측 실패가 모델 오류 분류·재시도를 바꾸지 않게 한다. 실행기 v2는 상태 갱신 전체 소요시간(검증·재시도 포함)과 입출력 토큰도 기록한다. 모델 로딩·최종 결론 생성·브라우저 렌더링 시간은 이 수치에 포함하지 않는다. 이는 사용자 요청에 따른 응답시간 개선 검증이며, 대회 평가의 속도 제외 원칙을 변경하지 않는다.

이 사례들은 유한한 합성 회귀 검사다. 일반적인 한국어 상담 정확도나 통계적 비열등성을 입증하는 평가가 아니다. 모델 실패는 성공한 사례의 분모에서 숨기지 않고 별도로 기록한다. 양쪽이 같은 오류를 내는 경우도 통과로 간주하지 않는다.

첫 실측의 독립 원문 검토에서, 이미 이야기를 들어 달라는 요청이 보고됐는데도 통합 경로가 대화 의향을 미확인으로 남긴 오류를 발견했다. 기존 161개 자동 검사는 이 모순을 잡지 못했다. 이를 수정하면서 해당 사례와 같은 의미를 가진 지시 주입 사례에 각각 검사 1개를 추가했다(총 163개). 추가 검사는 첫 결과를 본 뒤 만든 회귀 검사이며, 사전 고정 검증이나 별도 평가 데이터로 제시하지 않는다. 16개 모델 입력은 변경하지 않았다. 표현 기반 자동 검사만으로 모든 의미를 보장하지 않으므로 생성 결과의 별도 대조를 유지한다.

v4에서는 현재 의향이 아닌 **의향의 지속 여부**를 미확인으로 둔 문구를 위 표현 검사가 오탐했다. 독립 의미 검토 후 지속 여부·기간·가능성의 명시적 한정만 허용하고, 같은 항목에 현재 의향 번복이 함께 있으면 계속 탐지하도록 보완했다. 기존 오류 28조합과 새 경계 36조합을 포함한 평가기 검사 9개가 통과했다. 기존 v1/v2의 실제 의미 오류는 계속 실패하며, v4의 한정된 표현 1건만 재평가에서 통과로 바뀌었다. 원래 실패 기록과 수정된 평가기의 SHA-256·재평가 결과는 별도로 보존한다. 검사 수는 163개로 유지했다.

v5의 16개 출력은 당시 163개 검사를 통과했지만, 독립 의미 검토에서 관계 기록의 완결성 차이 3건을 추가 발견했다. 긴 답변 말미의 정정, 현재 위험의 부정, 과거 위험 이후·현재의 부정이 관계 기록에서 빠졌다. 전체 원문과 안전 판단은 정확했고 실제 위험 오판은 확인되지 않았다. 최종 결론에 전달할 요약 정보가 줄 수 있으므로 v6에서 보완하고 세 사례에 근거 선택 검사를 각각 추가했다. 최신 검사는 **166개**이며, 추가 3개도 결과를 본 뒤 만든 회귀 검사다. 기존 v5를 새 기준으로 읽으면 13/16이며, 원래 통과 기록은 그대로 보존한다. 16개 모델 입력은 변경하지 않았다.

## 기능 검사

- 변경 전 관련 모델·검색 검사: **146개 통과**.
- 통합 단위·전송 검사: **84개 통과**. 3가지 출력 형식, 설정 오류, 원문·사람·이름 근거 오류, 전 주장과 미확인 항목 검토, 재작성 한도, 질문 제안 취소, 안전 재검토, 원문 비절단을 포함한다. v4에서는 공통 입력을 합치면 기존 입력이 정확히 복원되고 세 검토 범위와 모든 주장이 보존되는지 추가 확인했다. v5에서는 상충하는 두 원문, 실제 모름·거절, 미질문인 동의·시간·부담의 개별 검토와 잘못 중첩한 질문 블록 거절을 확인했다. v7에서는 최신 선택 인용의 보존·중복·사람 구분·용량과 기존 오류를 덮지 않는 검증 순서를 확인했다. 평가기 12개·최종 경로 보존 7개와 합쳐 원문 전달 3개까지 관련 검사 106개가 통과했다.
- 같은 합성 초안·검토를 실제 `ModelGateway`의 두 모드에 넣은 7개 비교에서 반환 내용이 일치했다. 이는 호출·검증 계약 확인이며 실제 생성 정확도 비교를 대체하지 않는다.
- 실제 `createApp`·`ModelGateway`·HTTP·PostgreSQL을 연결한 추가 3개 검사에서 다음 질문·저장 결과 일치, 두 번째 요청 실패 후 대기 상태와 재시도, 뒤로가기 중 늦은 응답 차단을 확인했다.
- 별도 임시 PostgreSQL DB에서 앱 전체 **530개 통과, 실패·제외 0개**. 검사 DB는 종료 후 삭제하고 기존 서비스 DB를 보존했다.
- 독립 코드 검토에서 위험 판단 소실, 계측에 의한 오류·호출수 변화, 정리 예외 시 GPU 반환 누락을 발견하여 수정했다. 재검토에서 세 수정과 관련 회귀를 확인했다.
